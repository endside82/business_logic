목적과 정본

기능 PRD는 사용자가 어디에서 무엇을 하고 어떤 결과를 얻는지 설명한다. 2026-11-07 결정에 따라 제품 내용만 본문에 두고, 서버·앱 계약을 복사하지 않는다. 문서를 고치기 전에는 실제 소스를 읽는다.

판단할 내용우선 근거문서에 남길 것
제품이 제공하기로 한 정책승인된 제품 결정·정책정책과 결정 근거. 구현과 다르면 차이를 명시
현재 구현한 동작해당 버전의 서버·앱·관리자·실시간 소스진입·조작·권한·상태·결과·실패 복구
확인한 결과버전·환경·결과가 있는 실행 기록소스 확인, 로컬 시험, 실기기·외부 연동 확인을 구분
고객에게 공개한 범위현재 설정·배포 기록·출시 범위구현과 배포·공개를 구분

과거 조사 메모와 units/는 조사 당시의 참고 자료다. 최신 코드의 정본으로 취급하거나 이 자료로 현재 PRD 전체를 덮어쓰지 않는다. 날짜를 바꾸거나 코드 위치 검사만 통과했다고 내용 검수를 완료 처리하지 않는다.

작성 전 확인

  1. 구현 교차표와 해당 기능 명세에서 기능의 경계를 찾는다.
  2. 서버는 community_api/modules.txt의 모듈에서 실제 Controller, Service, DTO/VO, enum을 확인한다. 관리자 API는 같은 저장소의 admin-app 모듈이다.
  3. 앱은 실제 입구와 API → Repository → Provider → Screen/Widget의 연결을 확인한다. 관련 관리자 웹·실시간·MCP 동작이 있으면 함께 확인한다.
  4. 요청·응답 필드, 상태 값, 권한, 오류 처리의 일치 여부를 대조한다. 기술 계약을 본문에 중복 작성하지 않고 불일치가 제품에 미치는 결과를 적는다.
  5. 시험은 실제로 확인하는 조건을 읽는다. 시험 파일이 있다는 사실과 해당 버전에서 통과한 결과를 구별한다.

변경 없는 근거는 재사용한다. 새로운 의문이나 변경 없이 전체 로그·같은 소스·같은 이미지를 반복 확인하지 않는다.

기능 PRD 구성

결론

현재 제공하는 범위, 사용자가 만나는 제약, 아직 확인하지 못한 범위를 짧게 쓴다. 구현·검증·공개 상태를 하나의 ‘완료’로 합치지 않는다.

코드 위치

구현을 찾아갈 서버·앱 파일이나 심볼을 짧게 적는다. 서버 창구의 자동 관리 블록은 verification/sync_source_reference_docs.mjs가 갱신한다. 이 검사는 함수·주소의 존재를 검증하며 제품 설명 전체를 검증하지 않는다.

전체 동작 흐름

  1. 실제 메뉴·목록·알림·공유 링크에서 진입한다.
  2. 사용자가 내용을 확인하고 행동을 선택한다.
  3. 권한·현재 상태에 따라 허용하거나 이유를 안내한다.
  4. 성공 결과와 바뀐 상태를 보여준다.
  5. 원래 화면으로 돌아왔을 때 목록·배지·선택 상태가 어떻게 반영되는지 적는다.
  6. 취소·연결 실패·결과를 모르는 요청·권한 상실에서 복구하는 방법을 적는다.

제품 규칙과 상태·권한 표

누가 어떤 상태에서 무엇을 할 수 있는지, 제한·금액·기한·부수 효과를 적는다. 한 행동이 여러 메뉴에 중복 노출되는지 실제 입구끼리 대조한다. 제품 상태와 운영자 숨김 등 별도 표시를 혼동하지 않는다.

사용자·상태가능한 행동차단·실패 때 안내성공·복귀 결과

남은 차이와 위험

판정항목확인 근거사용자 영향남은 조치·완료 조건
  • Gap: 확인한 구현 불일치 또는 아직 구현하지 않은 요구사항.
  • Risk: 현재 구현에서 확인한 제한이나 회귀 위험.
  • Decision Needed: 정책·운영 등 명시적 결정이 필요한 사항.
  • 미검증: 요구한 실행 확인을 하지 못한 상태. 제품 결함으로 세지 않는다.
  • 미판정: 소스 대조 자체가 끝나지 않은 후보. 무엇을 확인해야 판정되는지 적는다.
  • 해소됨: 현재 근거로 해결을 확인했다. 본문의 과거 결함 설명도 함께 고친다.

현재 실행할 후속 작업은 앞으로 할 일의 해당 항목과 연결한다. 공개 사이트의 현황 사본은 그 정본을 따른다. 기능 문서마다 별도 작업 번호나 독립적인 미완료 총계를 만들지 않는다.

수용 기준과 검증 근거

시작 조건 → 구체적인 조작 → 관찰할 결과로 쓴다. 성공뿐 아니라 해당 기능의 권한·중복 요청·취소·실패·복귀 조건을 포함한다. ‘안전하게 처리’, ‘일관성 유지’, ‘해당 흐름 실행’만으로 결과를 대신하지 않는다.

시나리오 등록 수, 시험 파일 수, 시험 통과 수, 실제 앱·외부 연동 확인 수를 구분한다. 화면 이미지·탐색 맵·문서 HTML은 실제 앱 업무 성공의 증거가 아니다. 시각 질문이 있는 변경만 대표 화면을 확인한다.

완료 판정

  • 실제 입구에서 결과와 복귀까지 설명이 이어지고, 상태·권한별 차이가 명확하다.
  • 현재 본문과 위험 표가 서로 모순되지 않는다. 해소된 옛 결함을 현재 결함으로 남기지 않는다.
  • 정책과 구현이 어긋나면 승인 없이 정책을 바꾸지 않고 차이를 표시했다.
  • 근거의 저장소 버전과 확인 범위를 추적할 수 있다. 검증하지 않은 항목을 완료라고 쓰지 않는다.
  • 기능 HTML·도메인 요약·공통 정책·QA에서 같은 사실을 설명하는 부분도 갱신했다.
  • 내부 문서는 독자가 이해할 수 있는 전체 제목으로 실제 위치에 연결했다.

자동 생성기는 자료 수집과 형식 변환에만 쓴다. 개별 문서의 수동 교정·제품 결정을 덮어쓰지 않는다. 과거 문서 제거는 완료 문서 정리 원칙에 따라 현재 참조가 끝났는지 확인한 뒤 한다.
