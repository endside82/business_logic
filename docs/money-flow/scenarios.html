1. 지갑 충전

1.1 사용자가 직접 충전하는 경우

사용자 관점:

  • 사용자는 충전 금액을 선택한다.
  • PG 결제가 성공하면 지갑 유료 잔액이 증가한다.
  • 충전 내역은 거래 내역에 남는다.

비즈니스 규칙:

  • 충전 금액에는 최소·최대 한도가 있다.
  • 지갑 전체 잔액에도 상한이 있다.
  • 충전으로 들어온 금액은 유료 포인트다.
  • 유료 포인트 lot은 나중에 결제, 환불, 출금 가능성 판단의 근거가 된다.

예외 상황:

상황 사용자/운영 의미
PG 승인 실패 충전 실패로 종료된다. 지갑 잔액은 변하지 않는다.
PG는 성공했지만 DB 저장 실패 PG 취소를 시도한다. 취소도 실패하면 운영 보상 대상으로 남는다.
중복 confirm 이미 완료된 충전은 중복 지급되지 않아야 한다.

1.2 자동충전이 발생하는 경우

사용자 관점:

  • 사용자가 이벤트 선결제 등에서 잔액이 부족하고 자동충전이 설정되어 있으면, 부족분 충전을 먼저 시도한다.
  • 자동충전 성공 후 원래 결제가 이어진다.
  • 자동충전이 실패하면 원래 결제도 잔액 부족으로 실패한다.

비즈니스 규칙:

  • 자동충전도 일반 충전과 같은 유료 포인트다.
  • 월 한도, 지갑 상한, 결제수단 유효성 검사를 통과해야 한다.
  • 자동충전은 “사용자가 실제로 지불 가능한 결제 수단을 사전에 등록했다”는 전제에서만 의미가 있다.

기획 주의:

  • 결제 실패 UX에서 “잔액 부족”과 “자동충전 실패”를 구분하면 CS가 쉬워진다.
  • 자동충전이 켜져 있어도 한도나 PG 실패 때문에 결제가 실패할 수 있다.

2. 지갑 소비 공통

2.1 유료 우선 결제

많은 상품은 유료 포인트를 먼저 쓰고, 부족하면 무료 포인트를 이어서 쓴다.

해당 흐름:

  • 이벤트 참가비
  • 마켓 아이템
  • 마켓 번들
  • 플랜 구매
  • 클럽 기부
  • 클럽 가입비
  • 개인 구독
  • 클럽 운영 구독 중 지갑 결제분

비즈니스 의미:

  • 사용자 입장에서는 총 잔액으로 결제된다.
  • 정산·환불에서는 유료분과 무료분이 끝까지 분리된다.
  • 무료분은 출금 가능한 현금성 수익이 아니다.

2.2 유료만 가능한 결제

현금성 채무나 외부 출금에 가까운 흐름은 유료 포인트만 허용한다.

해당 흐름:

  • 모임 선입금
  • 모임 정산 분담금
  • 모임 정산 송금
  • 사용자 외부 출금 예약
  • 정산 보정 회수
  • 정산 후 환불에 따른 호스트 회수
  • 호스팅 티켓 구매

비즈니스 의미:

  • 무료 포인트를 현금성 권리로 바꾸는 것을 막는다.
  • 사용자에게 “무료 포인트 사용 불가” 사유를 명확히 보여줘야 한다.

2.3 무료 포인트만 복원되는 경우

무료 포인트로 낸 금액을 환불하면 무료 포인트로 돌아온다.

사용자에게 중요한 메시지:

  • 환불 금액의 일부가 무료 포인트로 돌아올 수 있다.
  • 이는 결제 당시 무료 포인트를 사용했기 때문이다.
  • 무료 포인트 환불분은 외부 출금할 수 없다.

3. 이벤트 참가비와 호스트 정산

3.1 지갑 선결제로 참가하는 경우

시나리오:

  1. 사용자가 이벤트 신청 승인을 받는다.
  2. 이벤트가 선결제를 요구하면 사용자가 지갑으로 결제한다.
  3. 잔액이 부족하고 자동충전이 가능하면 자동충전을 먼저 시도한다.
  4. 결제가 성공하면 참가 상태가 확정된다.
  5. 정원 초과, 제재, 상태 오류가 있으면 결제와 참가 확정이 함께 취소된다.

사용자에게 보이는 결과:

  • 결제 성공: 참가 확정
  • 잔액 부족: 결제 실패
  • 정원 마감: 참가 확정 실패, 지갑 차감 없음
  • 중복 결제: 거부

호스트에게 보이는 결과:

  • 결제 직후 바로 지갑에 돈이 들어오지 않는다.
  • 이벤트 종료 후 정산 대상이 된다.

3.2 은행 이체 선결제로 참가하는 경우

시나리오:

  1. 사용자가 은행 이체를 선언한다.
  2. 호스트 또는 운영 확인자가 입금 여부를 확인한다.
  3. 확인되면 결제가 PAID 상태가 되고 참가가 확정된다.

비즈니스 의미:

  • 은행 이체는 지갑 포인트가 즉시 움직이지 않는 off-ledger 구간이다.
  • 입금 확인 전에는 결제 확정으로 보면 안 된다.
  • 환불도 지갑 자동 환불이 아니라 별도 확인/처리 흐름이 필요할 수 있다.

3.3 이벤트 종료 후 정산되는 경우

시나리오:

  1. 이벤트가 종료되고 CLOSED 상태가 된다.
  2. 주간 배치가 정산 대상 이벤트를 찾는다.
  3. 이벤트 생애 전체의 순 결제액을 유료분과 무료분으로 나눈다.
  4. 유료분에 플랫폼 수수료와 원천징수세를 적용한다.
  5. 정산 레코드가 PENDING으로 생성된다.
  6. 운영 승인 후 지급이 실행된다.
  7. 호스트 지갑에 유료 순지급액과 무료 포인트 지급분이 들어온다.

정산 예시:

항목 예시
총 유료 결제 100,000원
총 무료 포인트 사용분 10,000P
플랫폼 수수료 10,000원
원천징수세 2,970원
호스트 유료 지급 87,030원
호스트 무료 지급 10,000P

기획 주의:

  • 무료 지급분은 호스트의 무료 포인트 잔액으로 들어간다.
  • 무료 지급분은 외부 출금 대상이 아니다.
  • 유료 정산액이 조정으로 0 이하가 되면 자동 거절될 수 있다.
  • 환불 유보액이 남아 있으면 정산 지급이 보류될 수 있다.

3.4 이벤트 결제 환불이 발생하는 경우

정산 전 환불:

  • 참가자에게 지갑 환불이 이뤄진다.
  • 호스트에게 아직 지급되지 않은 정산 예정 금액에서 빠진다.
  • 유료/무료 환불 구성이 원결제 구성을 넘지 않는다.

정산 후 환불:

  • 참가자에게 먼저 환불된다.
  • 이미 호스트가 받은 유료 순지급분은 미수금으로 잡힌다.
  • 이후 호스트의 다음 정산에서 우선 상계된다.

기획 주의:

  • 정산 후 환불은 호스트에게 “이미 받은 돈 중 일부가 다음 정산에서 차감된다”는 의미다.
  • 호스트 정산 화면에는 “미수금 상계” 또는 “환불 회수” 표현이 필요하다.

4. 마켓 아이템·번들·플랜 구매

4.1 단일 아이템 구매

시나리오:

  1. 사용자가 아이템을 구매한다.
  2. 지갑에서 금액이 차감된다.
  3. 구매 기록과 컬렉션이 생성된다.
  4. 크리에이터 수익은 PENDING으로 쌓인다.
  5. 환불 가능 기간이 지난 뒤 월간 정산 대상이 된다.

크리에이터 관점:

  • 구매 직후 정산 가능 금액이 생기지만 즉시 입금되지는 않는다.
  • 정산 전 환불되면 해당 수익은 지급되지 않는다.

4.2 번들 구매

시나리오:

  1. 사용자가 번들을 구매한다.
  2. 번들에 포함된 각 아이템의 원작자에게 매출이 배분된다.
  3. 배분은 아이템 정가 비율을 기준으로 하며, 반올림 잔액은 마지막 항목에서 맞춘다.
  4. 각 크리에이터별 수익이 PENDING으로 기록된다.

기획 주의:

  • 번들 하나를 샀더라도 정산 대상 크리에이터는 여러 명일 수 있다.
  • 부분 환불은 선택된 번들 아이템의 earning만 대상으로 한다.
  • 번들 보너스는 무료 포인트만 허용된다.

4.3 플랜 구매

시나리오:

  1. 사용자가 유료 플랜을 구매한다.
  2. 본인 플랜은 구매할 수 없다.
  3. 이미 구매한 플랜은 중복 구매할 수 없다.
  4. 구매 금액은 마켓과 같은 크리에이터 정산 흐름으로 들어간다.

기획 주의:

  • 플랜 직접 구매도 크리에이터 정산 대상이다.
  • 무료 플랜은 매출 earning을 만들지 않는다.
  • 플랜은 마켓 정산과 같은 월간 정산·환불 경계를 공유한다.

4.4 마켓·플랜 환불

정산 전 환불:

  1. 구매자 지갑으로 환불된다.
  2. 크리에이터 미지급금에서 차감된다.
  3. 크리에이터에게 회수할 돈은 없다.

정산 후 환불:

  1. 구매자 지갑으로 환불된다.
  2. 이미 지급된 크리에이터 금액은 미수금으로 기록된다.
  3. 다음 월간 정산에서 미수금을 먼저 상계한다.
  4. 전액 회수되면 해당 earning은 회수 완료 상태로 정리된다.

환불 상태 이해:

상태 비즈니스 의미
REQUESTED 구매자가 환불을 요청했다.
AWAITING_BUYER 판매자가 추가 자료를 요청했다.
ESCALATED 운영자 판단이 필요하다.
REFUNDED 환불이 완료됐다.
REJECTED 판매자 또는 운영자가 환불을 거절했다.
DISPUTED 거절 후 분쟁으로 넘어갔다.

5. 모임 선입금과 모임 정산

5.1 모임 선입금

시나리오:

  1. 참가자가 모임 선입금을 낸다.
  2. 포인트 결제는 유료 포인트만 사용할 수 있다.
  3. 선입금은 즉시 호스트에게 지급되지 않고 clearing 상태로 잡힌다.
  4. 이벤트가 정상 종료되면 호스트에게 release된다.
  5. 은행 이체 선입금은 호스트가 외부에서 이미 받은 돈으로 보고 상태만 종결한다.

환불:

  • 참가자가 환불 가능 기간 안에 취소하면 정책에 따라 일부 또는 전액 환불된다.
  • 포인트 선입금 환불은 원래 결제자의 지갑으로 돌아간다.
  • 시작 후 환불률이 0%일 수 있다.

기획 주의:

  • 선입금은 이벤트 참가비 정산과 다르게 “종료 시 release”되는 별도 흐름이다.
  • 정책 문구에는 “선입금은 종료 후 호스트에게 지급”이라는 설명이 필요하다.

5.2 모임 정산 분담금

시나리오:

  1. 호스트 또는 정산 생성자가 정산 항목을 만든다.
  2. 참가자는 자신의 분담금을 납부한다.
  3. 포인트 납부는 유료 포인트만 가능하다.
  4. 납부 즉시 수취자 지갑으로 금액이 들어간다.
  5. 모든 share/transfer가 완료되면 정산이 COMPLETED가 된다.

기획 주의:

  • 모임 정산은 플랫폼 수수료 정산이 아니라 사용자 간 채무 청산이다.
  • 무료 포인트는 사용할 수 없다.
  • 완료된 납부는 취소 시 역분개가 필요하다.

5.3 모임 정산 취소

취소 시 처리:

  • 완료된 포인트 송금은 되돌린다.
  • 은행 이체 완료 건은 수동 환불 필요 상태가 된다.
  • 혼합 결제는 포인트 부분만 자동 회수하고, 은행 부분은 수동 확인이 필요할 수 있다.
  • 역분개가 실패하면 재시도 대상이 되고, 반복 실패 시 운영자 경보가 발생한다.

사용자 안내:

  • “정산이 취소되어 받은 금액을 환불해야 합니다.”
  • “포인트 환불은 자동 처리되었고, 은행 이체분은 수동 환불 확인이 필요합니다.”

운영 주의:

  • REVERSAL_FAILED, PENDING_MANUAL_REFUND 상태는 CS·운영자가 확인해야 한다.
  • 실패한 역분개는 자동 재시도되지만, 3회 실패 후에는 운영 개입이 필요하다.

6. 클럽 기금

6.1 클럽 기부

첫 출시: 무료 포인트만 사용할 수 있다. 유료 잔액은 건드리지 않으며 무료 잔액이 부족하면 전체 기부를 거절한다.

시나리오:

  1. FREE 클럽의 멤버가 기부한다.
  2. 사용자 지갑에서 차감된다.
  3. 클럽 기금에 적립된다.
  4. 유료분과 무료분은 클럽 기금 안에서도 분리된다.

기획 주의:

  • 무료 포인트로 기부한 금액은 클럽 기금의 무료분으로 들어간다.
  • 클럽이 현금성 인출을 할 때 무료분은 제외된다.

6.2 클럽 가입비

첫 출시: BUSINESS 클럽 가입비도 무료 포인트만 차감한다. 받은 금액은 클럽 기금의 무료분이 되어 운영비에는 쓰지만 현금으로 인출할 수 없다.

시나리오:

  1. BUSINESS 클럽 가입 시 가입비가 있다면 지갑에서 결제된다.
  2. 클럽 기금에 적립된다.
  3. 멤버 기록에 납부 금액과 거래가 남는다.

환불:

  • 자발적 탈퇴는 일정 기간 안에서만 환불될 수 있다.
  • 강퇴, 차단, 클럽 폐쇄는 환불 대상이 될 수 있다.
  • 클럽 기금이 부족하면 플랫폼 선지급 미수금이 생길 수 있다.

기획 주의:

  • 가입비 환불은 “클럽 기금에서 나가는 환불”이다.
  • 기금이 부족할 때 플랫폼이 대신 지급한 금액은 클럽의 미수금으로 남는다.

6.3 클럽 운영 구독

첫 출시: 클럽 기금으로 전액 충당될 때만 성공한다. 기금이 모자라 오너 지갑 부족분이 생기면 실결제 스위치가 거절하고 앞선 기금 차감도 함께 되돌아간다.

시나리오:

  1. 클럽 운영 구독료를 결제한다.
  2. 먼저 클럽 기금에서 가능한 만큼 차감한다.
  3. 부족분은 오너 지갑에서 결제한다.
  4. 구독은 ACTIVE 상태가 되고 만료일이 설정된다.

기획 주의:

  • “클럽 기금 결제분”과 “오너 지갑 결제분”을 구분해야 한다.
  • 기금·지갑의 유료분은 플랫폼 구독 매출, 기금의 무료분은 프로모션 비용으로 기록한다.

6.4 클럽 기금 인출

시나리오:

  1. 클럽 오너가 인출을 신청한다.
  2. 클럽의 환불 예비금, 진행 중 인출, 미수금 등을 제외한 가용 잔액을 계산한다.
  3. 월 1회 제한을 확인한다.
  4. 수수료와 원천징수세를 계산한다.
  5. 승인 시 paid 기금만 예약 또는 차감된다.
  6. 지급 성공 시 은행 출금 또는 오너 지갑 지급으로 확정된다.

비즈니스 규칙:

  • 무료 기금은 현금 인출할 수 없다.
  • paid 기금만 인출 가능하다.
  • 기금에 미수금이 있으면 순지급액에서 먼저 상계된다.
  • 인출 처리 관리자 ID가 남는다.

운영 주의:

  • linked external withdrawal 경로는 승인 시 reserve로 묶고 outbox 지급 성공 시 확정한다.
  • direct wallet payout 경로는 오너 지갑으로 바로 지급한다.
  • 실제 은행 지급 provider는 별도 실연동 검증 대상이다.

7. 개인 구독과 개최권

7.1 개인 구독

시나리오:

  1. 사용자가 PREMIUM 구독을 신청한다.
  2. 지갑에서 결제된다.
  3. 구독은 ACTIVE가 되고 자동갱신이 켜진다.
  4. 자동갱신일이 오면 배치가 각 구독을 독립 처리한다.

비즈니스 규칙:

  • BASIC은 레거시 성격이며 신규 구독 대상이 아니다.
  • 개인 구독은 플랫폼 매출이다.
  • 무료 포인트 사용분은 프로모션 비용 성격이다.

사용자 안내:

  • 자동갱신 취소는 남은 기간을 즉시 없애는 것이 아니라 다음 갱신을 막는 행위다.
  • 재활성화는 새 결제를 동반한다.

7.2 프라이빗 모임 개최권·호스팅 티켓

시나리오:

  1. 사용자가 개최권 또는 호스팅 티켓을 구매한다.
  2. 프라이빗 모임 개최 비용은 무료 전용 또는 유료 전용 경로로 나뉠 수 있다.
  3. 호스팅 티켓 구매는 유료 포인트로 결제하고, 구매 후 티켓 수량과 만료일이 기록된다.
  4. 티켓으로 개최하면 지갑 결제 없이 티켓이 차감되고, 취소·복원 시 티켓 수량이 복구될 수 있다.

비즈니스 규칙:

  • 플랫폼이 판매자인 흐름이다.
  • 호스트나 크리에이터 정산으로 넘어가지 않는다.

8. 사용자 외부 출금

8.1 출금 신청

시나리오:

  1. 사용자가 외부 출금을 신청한다.
  2. 출금 가능 권리가 있는지 확인한다.
  3. 일·월 한도와 요청 빈도를 확인한다.
  4. 요청은 PENDING 상태로 생성된다.

출금 가능성 판단:

  • 단순 총 지갑 잔액만 보지 않는다.
  • 정산성 수취 권리와 이미 진행 중인 출금 요청을 함께 본다.
  • 무료 포인트는 출금 권리에 포함되지 않는다.

8.2 출금 승인

시나리오:

  1. 운영자가 출금을 승인한다.
  2. 사용자 유료 지갑 잔액이 예약 차감된다.
  3. 예약 분개가 만들어진다.
  4. outbox에 지급 작업이 들어간다.

사용자에게 보이는 의미:

  • “출금 진행 중”이다.
  • 아직 은행 지급 완료는 아니다.

8.3 지급 성공, 실패, 복구

지급 성공:

  • outbox 워커가 지급 provider를 호출한다.
  • 지급 성공이면 출금 요청은 PAID가 된다.
  • 예약 계정이 소거되고 은행 출금으로 확정된다.

지급 실패:

  • 재시도 대상이 된다.
  • 일정 횟수 초과 시 DEAD_LETTER가 된다.
  • 운영자는 재시도하거나, 실제 지급이 나가지 않았음을 확인한 뒤 예약을 복원할 수 있다.

운영 주의:

  • 현재 Noop 지급 provider는 실제 송금을 수행하지 않는다.
  • 운영 환경에서 Noop provider가 활성화되면 안 된다.

9. 마일리지

2026-09-03 현재: 아래 핵심 흐름은 코드·운영 화면과 실계정 화면 왕복을 마쳤지만 아직 운영 설정으로 닫혀 있다. 실제 기기 알림과 화면 이동을 확인한 뒤 개통한다. 시즌·사진 승인 적립·고급 검토 기능은 이 흐름과 별도로 미완성 상태다.

9.1 적립

시나리오:

  1. 클럽 활동, 체크인, 리뷰, 수동 지급 등의 조건으로 마일리지가 적립된다.
  2. 회원 잔액과 원장에 같은 결과가 반영된다.
  3. 등급 산정 대상이면 등급 재계산에 반영된다.

비즈니스 의미:

  • 마일리지는 클럽 참여도와 리워드 목적이다.
  • 지갑 유료·무료 포인트와 무관하다.

9.2 사용

시나리오:

  1. 회원이 마일리지를 사용한다.
  2. 잔액이 충분한지 확인한다.
  3. 만료가 빠른 적립분부터 소비한다.
  4. 소비 이력이 남는다.

기획 주의:

  • 사용 단위는 클럽 정책에 맞춰 정의해야 한다.
  • 마일리지 사용은 현금 결제가 아니므로 지갑 거래 내역과 혼동하지 않는다.

9.3 회수와 만료

회수:

  • 적립 또는 사용 기록만 회수 대상이다.
  • 이미 만료된 기록이나 회수 기록 자체를 다시 회수하는 것은 막는다.
  • 사용 회수 시 원래 소비했던 적립분 잔여가 복원된다.

만료:

  • 만료일이 지난 적립분의 남은 수량을 차감한다.
  • 마일리지 점검이 회원 잔액과 원장 합계가 같은지 확인하고, 어긋나면 플랫폼 운영자의 이상 사건 목록에 남긴다.

10. 운영자 작업

10.1 정산 승인·완료

운영자는 정산을 승인하거나 완료할 수 있다.

현재 원칙:

  • admin이 직접 지갑을 지급하지 않는다.
  • 정산 완료는 API internal 경로로 위임한다.
  • API는 중복 지급, 환불 유보, 미수금 상계, 조정 후 0 이하 자동거절을 처리한다.

운영 문구:

  • APPROVED: 지급 가능 상태
  • PAYING: 지급 처리 중
  • PAID: 지갑 지급 완료
  • FAILED: 자동 재시도 대상
  • REJECTED: 지급하지 않음

10.2 운영자 환불·보상

운영자는 특정 원거래를 기준으로 환불하거나, 무료 포인트 보상성 지급을 할 수 있다.

실제 운영 경로: 관리자 웹 /free-point-grants에서 대상 사용자·금액·필수 지급 사유를 입력하고 금액을 한 번 더 입력해 확정한다. MANAGE_PAYMENT 쓰기 권한과 Idempotency-Key가 필요하고 한 번에 10,000,000P를 넘길 수 없다. 지급은 기존 지갑의 무료 lot·거래·원장에 함께 기록되며 이 화면에서 되돌릴 수 없다.

주의:

  • 일반 환불은 원거래 한도와 유료/무료 구성을 따른다.
  • 원거래가 없는 보상은 일반 환불이 아니라 운영 보상으로 취급해야 한다.
  • 실패 보상은 FailedRefund 운영 큐와 연결된다.
  • 현금을 돌려줘야 하는 건은 무료 포인트 지급 화면이 아니라 원거래 환불·FailedRefund 경로를 사용한다.

10.3 차지백

차지백은 사용자의 지갑을 직접 움직이는 흐름이 아니다.

비즈니스 의미:

  • PG나 카드사에서 이미 발생한 손실을 플랫폼 회계에 인식한다.
  • 지갑 환불이나 정산과 다른 운영 회계 사건이다.
  • CS 문구에서는 “환불”과 “차지백”을 구분해야 한다.

10.4 원천징수세 납부

정산 시 원천징수세가 예수금으로 쌓이고, 운영자가 납부하면 예수금이 줄어든다.

비즈니스 의미:

  • 호스트·크리에이터에게 지급하기 전 세금을 원천징수한 것으로 본다.
  • 납부는 사용자 지갑 사건이 아니라 플랫폼 회계 사건이다.

12. CS 답변 기준 예시

12.1 “왜 환불금 일부가 무료 포인트로 들어왔나요?”

결제 당시 무료 포인트가 함께 사용된 경우, 환불도 같은 구성으로 복원됩니다. 유료로 낸 금액은 유료 잔액으로, 무료 포인트로 낸 금액은 무료 포인트로 돌아옵니다.

12.2 “이벤트 결제했는데 호스트에게 바로 입금되나요?”

아닙니다. 이벤트 참가비는 이벤트 종료 후 정산 대상이 되고, 정산 생성·승인·지급 과정을 거친 뒤 호스트 지갑에 지급됩니다.

12.3 “마켓 판매금이 왜 바로 안 들어오나요?”

마켓·플랜 판매금은 환불 가능 기간이 지난 뒤 월간 정산으로 지급됩니다. 환불 가능 기간 안의 판매금은 정산 대기 상태입니다.

12.4 “정산 후 환불이 승인되면 판매자는 어떻게 되나요?”

구매자에게 먼저 환불되고, 이미 판매자에게 지급된 금액은 다음 정산에서 우선 차감됩니다.

12.5 “클럽 기금은 전부 인출할 수 있나요?”

아닙니다. 무료 포인트로 들어온 기금, 환불 예비금, 진행 중 인출, 미수금 등을 제외한 paid 가용분만 인출할 수 있습니다.

12.6 “출금 신청했는데 왜 아직 입금이 안 됐나요?”

출금은 신청 후 승인, 예약, 지급 처리 단계를 거칩니다. 승인 상태는 지급 진행 중이라는 뜻이고, PAID 상태가 되어야 외부 지급이 완료된 것으로 봅니다.
