1. 현재 제품의 돈은 세 종류로 나뉜다

1.1 유료 포인트

사용자가 실제 결제 수단으로 충전했거나, 정산·환불·수취를 통해 받은 현금성 잔액이다.

유료 포인트는 다음 성격을 가진다.

  • 결제에 사용할 수 있다.
  • 정산 수취분 등 조건을 만족하면 외부 출금 대상이 될 수 있다.
  • 환불될 때도 유료 포인트로 복원된다.
  • 무료 포인트와 섞여 보일 수 있지만, 내부적으로는 항상 별도 잔액과 사용 이력을 가진다.

1.2 무료 포인트

프로모션, 보너스, 무료분 정산 등으로 지급되는 비현금성 잔액이다.

무료 포인트는 다음 성격을 가진다.

  • 허용된 상품 결제에는 사용할 수 있다.
  • 외부 현금 출금에는 사용할 수 없다.
  • 수수료와 원천징수세 계산 대상이 아니다.
  • 환불될 때도 무료 포인트로만 복원된다.

1.3 클럽 마일리지

클럽 활동, 등급, 리워드 목적의 별도 점수 경제다. 지갑 포인트와 다르다.

마일리지는 다음 성격을 가진다.

  • 지갑 잔액으로 전환되지 않는다.
  • 현금성 결제나 정산, 출금에 쓰이지 않는다.
  • 클럽 단위로 적립, 사용, 회수, 만료된다.
  • 등급과 시즌 기록에 영향을 준다.

2. 제품 전체에 공통으로 적용되는 원칙

2.1 지갑 차감과 비즈니스 처리의 역할이 다르다

지갑에서 돈을 빼는 행위와, 그 돈이 누구에게 귀속되는지는 별개다.

예를 들어 이벤트 참가자가 선결제를 하면 먼저 참가자 지갑에서 금액이 차감된다. 그 다음 이벤트 도메인이 “이 금액은 호스트에게 정산될 참가비”라고 기록한다. 모임 정산, 마켓 구매, 클럽 기부도 같은 방식이다.

기획 관점에서는 다음처럼 이해하면 된다.

  • 지갑 차감: 사용자가 돈을 썼다는 사실
  • 도메인 처리: 그 돈이 이벤트, 마켓, 클럽, 정산 중 어디로 귀속되는지
  • 회계 원장: 위 두 결과가 플랫폼 장부에서 맞는지 확인하는 거울

2.2 무료 포인트는 현금화되지 않는다

무료 포인트는 결제 경험을 보조할 수 있지만, 플랫폼 밖으로 나가는 돈이 될 수 없다.

따라서 무료 포인트가 포함된 결제는 다음과 같이 처리된다.

  • 호스트나 크리에이터에게 무료분이 지급되어야 하는 상품이면 무료 포인트로 정산된다.
  • 플랫폼 매출 상품이면 무료분은 프로모션 비용으로 처리된다.
  • 외부 출금, 모임 정산, 선입금처럼 현금성 권리만 인정되는 흐름에서는 무료 포인트를 쓸 수 없다.

2.3 환불은 원래 결제 구성을 넘을 수 없다

환불은 원거래를 기준으로만 이뤄진다.

기획적으로 중요한 규칙은 세 가지다.

  • 이미 환불한 금액을 합산해 원결제 금액을 넘을 수 없다.
  • 유료로 낸 금액은 유료로, 무료로 낸 금액은 무료로만 복원된다.
  • 부분 환불도 이 원칙을 지킨다.

이 규칙 때문에 무료 포인트를 유료 포인트로 바꾸는 환불, 같은 결제에 대한 중복 환불, 원결제보다 큰 보상성 환불은 일반 환불 경로에서 허용되지 않는다. 보상성 지급은 운영자 보상 경로로 분리해야 한다.

2.4 수수료와 원천징수세는 유료 매출에만 붙는다

이벤트 정산, 마켓·플랜 정산, 클럽 인출은 수수료와 원천징수세를 계산한다.

공통 계산 기준은 다음과 같다.

  1. 유료 매출을 기준으로 플랫폼 수수료를 계산한다.
  2. 수수료를 뺀 금액을 기준으로 원천징수세를 계산한다.
  3. 남은 금액을 수취자에게 지급한다.
  4. 무료 포인트 매출은 별도 무료 포인트로 지급되며 수수료와 세금 계산에 포함하지 않는다.

현재 기본값은 플랫폼 수수료 10%, 원천징수세 3.3%다. 단, 일부 경로는 정책 테이블이나 도메인별 설정값을 적용한다.

2.5 정산은 “즉시 수익”이 아니라 “확정 후 지급”이다

사용자가 돈을 냈다고 바로 호스트나 크리에이터가 출금 가능한 돈을 받는 것은 아니다.

도메인별 확정 시점은 다르다.

영역 돈을 내는 시점 수취자에게 확정되는 시점
이벤트 참가 선결제 시 이벤트 종료 후 주간 정산 생성 및 승인 완료 후
마켓 아이템·번들 구매 시 환불 가능 기간이 지난 뒤 월간 정산 완료 후
플랜 구매 구매 시 마켓과 동일하게 월간 정산 완료 후
모임 선입금 선입금 시 이벤트 정상 종료 시 호스트에게 release
모임 정산 분담금 납부 시 납부 즉시 수취자 지갑으로 이동
클럽 기부·가입비 결제 시 클럽 기금으로 즉시 적립
개인 구독·개최권 결제 시 플랫폼 매출로 즉시 처리

2.6 admin은 돈을 직접 움직이지 않는 것이 원칙이다

운영자가 정산 완료, 환불, 보상, 강제 환불 같은 작업을 수행할 수는 있다. 다만 실제 지갑 이동과 정산 완료는 public API 서버의 보호장치를 거친다.

이 원칙이 중요한 이유는 다음과 같다.

  • 환불 중인 정산을 잘못 지급하지 않기 위해
  • 이미 지급된 정산을 중복 지급하지 않기 위해
  • 정산 후 환불로 발생한 미수금을 다음 정산에서 회수하기 위해
  • 사용자 지갑, 도메인 상태, 회계 원장이 동시에 맞도록 하기 위해

admin이 직접 공유 DB를 기록하는 예외는 운영 회계성 작업에 한정된다. 예: 차지백 손실 인식, 원천징수세 납부.

3. 비즈니스 유형별 분류

3.1 Flow-through: 사용자 돈이 수취자에게 넘어가는 흐름

사용자가 결제하고, 이후 호스트·크리에이터·클럽·다른 사용자가 수취자가 되는 흐름이다.

대표 예시는 다음과 같다.

  • 이벤트 참가비
  • 마켓 아이템·번들 구매
  • 플랜 구매
  • 클럽 기부
  • 클럽 가입비
  • 프라이빗 모임 참가비

무료 포인트가 허용되면 무료분도 수취자에게 전달될 수 있다. 다만 무료분은 현금 출금 대상이 아니라 무료 포인트로만 남는다.

3.2 Platform revenue: 플랫폼이 판매자인 흐름

사용자가 결제하고 플랫폼이 매출을 인식하는 흐름이다.

대표 예시는 다음과 같다.

  • 개인 구독
  • 클럽 운영 구독 중 지갑 결제분
  • 프라이빗 모임 개최권
  • 호스팅 티켓

무료 포인트가 사용되면 수취자에게 넘겨줄 대상이 없으므로 프로모션 비용 성격으로 처리된다.

3.3 Paid-only clearing: 현금성 채무를 맞추는 흐름

사용자 간 정산, 외부 출금, 선입금처럼 현금성 권리를 맞추는 흐름이다.

대표 예시는 다음과 같다.

  • 모임 선입금
  • 모임 정산 분담금
  • 모임 정산 송금
  • 사용자 외부 출금
  • 정산 보정 회수
  • 이벤트 정산 후 환불에 따른 호스트 회수

이 흐름에서는 무료 포인트를 사용할 수 없다.

4. 상황별 빠른 판단표

질문 현재 기준 답
무료 포인트로 이벤트 참가비를 낼 수 있나? 가능하다. 단 수취자는 무료분을 무료 포인트로 받는다.
무료 포인트로 외부 출금할 수 있나? 불가하다. 외부 출금은 유료 잔액과 정산성 수취 권리를 기준으로 한다.
무료 포인트로 모임 정산 분담금을 낼 수 있나? 불가하다. 모임 정산은 paid-only다.
이벤트 결제 직후 호스트가 돈을 받나? 아니다. 이벤트 종료 후 정산 생성, 승인, 지급 완료가 필요하다.
마켓 구매 직후 크리에이터가 돈을 받나? 아니다. 환불 가능 기간이 지난 뒤 월간 정산으로 받는다.
정산 후 환불이 발생하면 어떻게 하나? 구매자에게 환불하고, 이미 받은 크리에이터·호스트 금액은 미수금으로 잡아 다음 정산에서 회수한다.
클럽 기금 인출에 무료 포인트가 포함될 수 있나? 무료 기금은 인출 불가다. paid 기금만 인출 가능하다.
출금 신청 후 바로 은행 송금되나? 아니다. 승인 시 예약되고, outbox 워커가 지급을 확정한다. 현재 실제 지급 provider는 외부 연동 게이트가 남아 있다.
운영자가 정산금을 직접 지급할 수 있나? 직접 DB 지갑 이동은 봉인되어 있고, API internal 경로로 위임해야 한다.
마일리지를 포인트로 바꿀 수 있나? 현재 흐름상 불가하다. 마일리지는 별도 클럽 경제다.

5. 기획에서 특히 주의해야 할 경계

5.1 “잔액”이라는 단어는 하나가 아니다

사용자 화면에서 보이는 잔액은 단순해 보일 수 있지만, 기획 문서에서는 최소한 다음을 구분해야 한다.

  • 총 지갑 잔액
  • 유료 잔액
  • 무료 잔액
  • 출금 가능 잔액
  • 정산 예정 금액
  • 이미 지급된 정산 금액
  • 회수 예정 미수금
  • 클럽 기금 잔액
  • 클럽 기금 중 paid 인출 가능 잔액
  • 클럽 마일리지 잔액

특히 “정산 예정”과 “지갑 입금 완료”를 같은 것으로 쓰면 운영·CS 문구가 틀어진다.

5.2 환불 시점은 정산 전과 정산 후로 나눠야 한다

같은 환불이라도 정산 전과 정산 후의 비즈니스 의미가 다르다.

정산 전 환불:

  • 구매자에게 지갑 환불
  • 수취자에게 아직 지급되지 않은 미지급금에서 차감
  • 크리에이터·호스트에게 회수할 돈은 없다

정산 후 환불:

  • 구매자에게 지갑 환불
  • 이미 지급된 수취자 금액은 미수금으로 잡힘
  • 다음 정산에서 우선 상계

따라서 환불 정책 화면, 정산 화면, 판매자 알림, CS 답변은 “정산 전 환불”과 “정산 후 환불”을 구분해야 한다.

5.3 은행 이체는 off-ledger 구간이 있다

일부 은행 이체 확인형 흐름은 플랫폼 지갑 원장 밖에서 일어난다.

대표 예시는 다음과 같다.

  • 이벤트 BANK 선결제
  • 모임 정산 BANK_TRANSFER
  • 가상계좌 입금 webhook
  • 실제 외부 출금 provider

이런 흐름은 사용자 상태와 운영 확인 절차가 중요하다. 지갑 포인트가 움직이지 않았다고 해서 돈 흐름이 없는 것은 아니다.

5.4 현재 실연동 게이트가 남아 있는 영역

현재 소스 기준으로 다음은 내부 상태머신과 보호장치는 있으나 실운영 provider 검증이 별도 필요하다.

  • 외부 지급 provider
  • 가상계좌 webhook
  • PG 대사
  • dormant PG 환불 큐 활성화
  • FailedRefund 운영 복구 자동화
  • internal token의 운영 보안 강화

6. 문서 사용법

실제 기능 기획 시에는 아래 순서로 확인한다.

  1. 이 개요 문서에서 돈의 성격을 정한다.
  2. 도식·종착점에서 해당 상황의 전체 흐름과 마지막 상태를 먼저 확인한다.
  3. 상황별 시나리오에서 해당 상황의 사용자·수취자·운영자 관점을 확인한다.
  4. 정책 수치나 예외 상황은 이 문서의 빠른 판단표와 각 하위 문서의 종착점 설명을 기준으로 맞춘다.
