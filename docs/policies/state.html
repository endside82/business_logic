상태 정책

모집·참석·돈·반환·분쟁·개인정보 처리의 서로 다른 상태와 후속 결과를 구분합니다. 2026-11-22 소스 대조이며 새 실행 검증 결과와 구분합니다.

상태를 읽는 기준

상태는 어떤 기록의 상태인지부터 구분한다. 모임 공개 상태, 신청, 실제 참석, 납부, 송금, 반환, 분쟁, 알림 전달은 서로 다른 기록이다. 같은 이름의 PENDING·COMPLETED라도 같은 사건을 뜻하지 않는다. enum에 전이가 있다는 사실만으로 모든 API·역할에서 그 전이가 허용되지는 않는다.

확인 순서문서에 남길 내용
대상과 현재 사실계정·대상·원천 기록, 저장 상태와 계산한 화면 단계
실행 자격현재 역할·소속·상태·기한·보류·공개 설정·필요한 동의
실행 결과저장된 전이, 아직 진행 중인 돈·알림·정리 작업
실패·복귀확정 거절·결과 불명·부분 처리·만료를 나누고 현재 결과를 다시 조회

권한의 공통 기준은 권한 정책, 금전 후속 처리는 결제·환불·정산 정책을 따른다. 화면 문구만으로 저장 상태나 외부 실행 완료를 판정하지 않는다.

이벤트 공개 상태와 실제 종료

EventStatus는 DRAFT·OPEN·CLOSED·CANCELED 네 값이다. 기본 전이는 DRAFT에서 OPEN 또는 CANCELED, OPEN에서 CLOSED 또는 CANCELED다. 일반 이벤트 enum에서 CLOSED·CANCELED는 다음 전이가 없다. 숨김은 이 enum의 다섯 번째 상태가 아니다. 노출 설정·운영 제한·시간 경계는 별도로 읽는다.

공개 모임의 편집 가능 범위와 일정 변경 제안은 상태 전이와 다른 계약이다. CLOSED 표시를 모든 모임의 실제 만남 종료로 번역하지 않는다. 특히 비공개 모임은 상대 선정 때 모집을 닫아도 만남과 완료 확인이 남는다. 정기모임 코스의 CLOSED 재공개는 별도 상태 기계다.

이벤트 생성·공개·마감·취소, 정기모임 코스 공개·마감·재개·취소를 따른다. 정기모임 코스의 재개는 VARIABLE에 허용되며 일반 이벤트의 CLOSED를 다시 OPEN으로 바꾸는 공통 규칙이 아니다.

신청·참석·선입금의 서로 다른 상태

기록현재 상태값혼동하면 안 되는 사실
ApplicationStatusPENDING, APPROVED, APPROVED_PENDING_PAYMENT, PAYMENT_EXPIRED, REJECTED, CANCELED, CANCEL_PENDING_REFUND승인과 참석 행 생성·납부 완료를 합치지 않음
AttendanceStatusATTENDING, WAITING, CANCELLED신청의 CANCELED와 철자가 다름. 회원·게스트 행과 정원을 별도 판단
EventPaymentStatusPENDING, PAID, REFUND_REQUESTED, REFUNDED, CANCELED결제 행과 송금·입금 신고 상태는 별개

신청 PENDING은 승인·결제 대기 승인·거절·취소로 이동할 수 있다. APPROVED_PENDING_PAYMENT에서는 납부 완료에 따른 APPROVED, 기한 만료 PAYMENT_EXPIRED 또는 취소를 구분한다. 이미 승인된 신청의 취소는 곧바로 CANCELED가 되거나 반환 대기 CANCEL_PENDING_REFUND가 남을 수 있다. 만료·거절·취소 후의 재신청·재승인 전이는 해당 명령의 현재 조건을 다시 검사한다.

선입금 대기 동안 참석 행 없이 논리적으로 자리를 예약하는 경우가 있다. 한 신청의 회원·게스트가 실제 참석과 대기로 나뉠 수도 있으므로 신청 한 행만으로 전체 인원의 참석을 세지 않는다. 유료 모임인데 선입금이 꺼진 설정을 무료 승인 흐름으로 우회시키는 과거 설명은 현재 거절 조건과 맞지 않는다.

납부 만료 처리는 기한이 엄격하게 지난 대상을 다룬다. 호스트의 은행 입금 확인을 기다리는 신고는 일반 만료 대상과 구분한다. 현재 은행 신고·확인 앱 경로가 있으며 신고 버튼 성공이 실제 송금·입금 확인·참석 확정을 모두 뜻하지 않는다. POINT는 지갑, CASH·현재 MIXED 앱 경로는 은행 안내를 사용하며 MIXED를 항상 사용자 결제수단 선택 화면으로 설명하지 않는다.

EventPaymentStatus의 PENDING은 PAID·REFUND_REQUESTED·CANCELED로, PAID는 REFUND_REQUESTED·REFUNDED로, REFUND_REQUESTED는 REFUNDED·CANCELED로 전이할 수 있다. 이 허용 목록은 모든 취소가 즉시 환불된다는 보장이 아니다.

이벤트 신청·참석·취소, 정원과 대기자, 선입금과 입금 확인을 함께 따른다.

비공개 만남의 계산된 단계

PrivateMeetingPhase는 EventStatus와 matchedAt·completedAt으로 계산한다. 독립된 단계 열을 저장하고 순서대로 증가시키는 모델로 설명하지 않는다.

조건계산 단계해석
DRAFTWAITING_PAYMENT초안의 표시 단계. 이 이름만으로 실제 미납 채무 존재를 단정하지 않음
OPENRECRUITING상대 모집
CANCELEDCANCELLED취소. 반환의 실제 완료와 별도
CLOSED + completedAt 있음COMPLETED완료 사실 저장
CLOSED + matchedAt 있음, completedAt 없음MATCHED상대 선정 뒤 실제 만남·완료 확인이 남음
위 조건에 해당하지 않음WAITING_PAYMENT현재 계산 함수의 기본값

선정은 선택 신청을 승인하고 실제 참석을 연결하며 다른 대기 신청을 정리한 뒤 모임을 PRIVATE_MATCH 사유로 닫고 matchedAt을 남긴다. 동일 선정의 재요청에서 참석 연결을 보완하는 경로도 있다.

완료 확인은 매칭된 모임의 호스트 또는 선정 상대가 예정 종료 시각 이후에 한다. 각자 확인 시각과 최종 completedAt은 다르다. 양쪽이 확인했더라도 보관금 보류 등 반환·지급 조건을 해결하지 못하면 곧바로 완료로 저장되지 않는다. 이미 완료된 확인의 재요청과 새로운 완료 전이를 구분한다. 이 정책의 직접 대조 범위는 선정·완료 확인이며 비공개 만남의 모든 결제·취소 실행을 새로 검증했다는 뜻은 아니다.

모임 정산과 송금·반환

기록현재 상태값완료의 경계
MeetingSettlementStatusDRAFT, ACTIVE, COMPLETED, CANCELLED초안 확정·분담 수집·종결·취소이며 개별 돈 이동과 다름
TransferStatusPENDING, BANK_AWAITING_CONFIRM, COMPLETED, CANCELLED, EXPIRED, SUPERSEDED, REVERSAL_FAILED, PENDING_MANUAL_REFUND, BANK_WAIVED납부·은행 확인·대체·반환 실패·수동 반환·은행 면제 상태를 보존
호스트 SettlementStatusPENDING, APPROVED, PAYING, PAID, FAILED, REJECTED호스트 정산금의 별도 지급 절차. 모임 정산이나 회원 송금과 합치지 않음

초안 정산을 확정하면 유효성 검사 뒤 ACTIVE가 되거나 남은 의무가 없는 경우 같은 요청에서 COMPLETED가 될 수 있다. 확정은 그 자체로 돈을 보내는 행동이 아니다. DRAFT·ACTIVE 취소가 CANCELLED로 저장돼도 지갑 반환·외부 은행 반환·수동 수습은 남을 수 있다.

EXPIRED가 TransferStatus.isOpen()에서 false인 것과 해당 정산의 완료 판정은 다르다. 완료 판정에서는 COMPLETED·CANCELLED·SUPERSEDED·BANK_WAIVED를 제외한 송금 의무를 따로 검사하므로 ‘기한 만료=채무 소멸’로 안내하지 않는다. BANK_AWAITING_CONFIRM은 수취 확인 전 상태이며 앱 신고 성공을 수취 완료로 바꾸지 않는다.

호스트 정산금의 FAILED·REJECTED에 임의로 자동 재지급·회원 재심 화살표를 붙이지 않는다. 각 재처리 명령·보류·외부 결과 확인 조건이 필요하다. 외부 지급 시작 전의 대기와 이미 요청한 뒤 결과를 모르는 UNKNOWN·조회 대기를 나누고, 응답을 잃었다는 이유로 새 지급을 보내지 않는다.

모임 정산 도메인, 금액 검토·정산 요청·취소와 반환, 결제·환불·정산 정책을 따른다.

이동 지원·차량 배정·조정 요청

이동 지원, 실제 차량, 현재 참가자의 이동 의사, 차량 배정, 물리 좌석과 조정 요청을 한 상태열로 합치지 않는다. 조율을 끄는 설정 변경도 기존 배정 기록의 삭제를 뜻하지 않는다.

대상상태·행동의 경계
차량 지원PENDING·APPROVED·REJECTED·WITHDRAWN·PARTICIPATION_ENDED. 지원·수정·철회·거절은 기존 배정을 유지하며 승인 시점에 운전자 배정으로 전환
배정 필요·개별 이동NEEDS_ASSIGNMENT·INDIVIDUAL과 개인 승차 장소. 공동 차량에 이미 배정된 사람의 의사 변경은 조정 절차 적용
이동 조율 종료LEFT. 모임 참가 취소와 다름. 현재 자리·대기 지원·요청을 정리하며 살아 있는 본인 차량은 먼저 취소
운행 취소차량 CANCELLED. 모임에 남는 전 운전자·승객을 다시 배정 대상으로 남김. 자동 SELF 차량이나 개별 이동을 생성하지 않음
조정 요청PENDING·RESOLVED·DECLINED·WITHDRAWN·PARTICIPATION_ENDED·EVENT_ENDED. 모임 종료에 따른 닫힘을 해결 성공으로 읽지 않음
모임 종료 뒤 미해결남은 배정 과제를 미해결 기록으로 보존. 화면에서 요청이 닫혔다고 모두 배정됐다고 표시하지 않음

차량 배정과 물리 좌석은 별개다. 지원 승인이 실제 좌석 선택 완료를 뜻하지 않으며 운전자는 동승 정원에서 제외한다. 상세 조건은 이동수단 공통 설정, 카풀 지원·개별 이동, 대절 버스와 자리 배정을 따른다.

일정 변경 응답·노쇼·분쟁

대상현재 상태값별도로 읽을 사실
일정 변경 개별 응답PENDING, ACCEPTED, DECLINED, AUTO_ACCEPTED, WITHDRAWN응답·기한 자동 동의·변경 묶음의 실제 확정은 다름
NoShowStatusCONFIRMED, APPEALED, OVERTURNED서버 판정과 앱의 OPEN·REJECTED·DEADLINE_PASSED 등 표시 분류는 다름
UnifiedDisputeStatusOPEN, IN_REVIEW, RESOLVED, CLOSED, ESCALATED, CLOSED_WITH_MANUAL_RECOVERY수동 수습을 남긴 닫힘과 모든 보상 완료를 합치지 않음
DisputeAppealStatusPENDING, DECIDED, COMPENSATION_APPLIED, UPHELD, RECOVERY_REQUIRED, REJECTED, CLOSED결정·보상 적용·인용·수습·기각·철회 닫힘을 보존

노쇼의 소명은 본인과 확정 시각부터 7일 기한을 검사하며 기각 뒤 재소명을 자동 허용하지 않는다. CONFIRMED·APPEALED에서 OVERTURNED로 뒤집은 결과는 별도 최종 판정이다. canonical 사건 ID가 있다는 사실을 통합 분쟁 등록부가 이미 만들어졌다는 뜻으로 사용하지 않는다.

통합 이의의 isClosed()는 PENDING 이외에서 true지만, 사건 종결 차단 판정은 PENDING·DECIDED·COMPENSATION_APPLIED를 별도로 다룬다. PENDING 본인 철회는 CLOSED로 바뀌며 재요청 성공 재생이나 재접수 권리를 자동 보장하지 않는다. 원천 동기화·보류 해제·알림·보상은 각각의 후속 결과를 확인한다. 기본 비활성인 플랫폼 판단 경로도 있으므로 상태 enum의 존재와 운영 접수 가능을 구분한다.

일정 변경 제안과 참가자 합의, 노쇼 확정·소명, 통합 이의 접수·철회을 따른다.

플랜 공개·구매 권리·차단 해제

PlanStatus는 DRAFT·PUBLISHED·HIDDEN·DELETED다. 플랜 본문 공개, 마켓 판매, 구매 거래, 보유 권리는 별개다. 무료 본문 열람이 구매 완료·모임 생성 권리를 뜻하지 않으며 숨김 이후 기존 유효 구매자의 접근도 별도로 판정한다. 플랜 상세와 열람 권리를 따른다.

DateBlockStatus는 BLOCKED·UNBLOCKED다. 해제는 이전 매칭·채팅방 복원을 뜻하지 않고 상대방이 설정한 차단까지 해제하지 않는다. 프라이빗 데이트 차단의 현재 관계·소프트 기록 정책을 따른다.

데이터 내보내기·삭제 예약·탈퇴

대상상태사용자에게 설명할 경계
데이터 내보내기PROCESSING, COMPLETED, FAILED, EXPIRED상태 조회 실패를 요청 없음으로 해석하지 않음. 완료 URL 열기는 실제 파일 수신 확인과 다름
데이터 삭제 요청PENDING, APPROVED, COMPLETED, CANCELLEDNONE은 저장 enum이 아니라 활성 요청이 없는 화면 표현
삭제 요청 취소본인 PENDING만 가능APPROVED 이후에도 취소 가능하다는 이전 설명은 현재 계약과 맞지 않음
예약 시각 도래PENDING의 30일 뒤 처리 대상제재·금전 의무·동의·실패 등의 실행 조건 재검사. 시각 도래만으로 COMPLETED 아님

활성 삭제 조회가 PENDING·APPROVED만 반환하므로 완료·취소 뒤 요청이 없다는 화면과 감사 기록 삭제를 혼동하지 않는다. 예약 시 공개 해제한 자료와 실행 전 일부 정리 결과는 취소·후속 실패 때 자동 복구되지 않을 수 있다.

즉시 탈퇴의 계정 비활성·신원 정리·세션 해제, 예약 삭제, 보존 기한에 따른 물리 제거는 서로 다른 처리다. 탈퇴가 이미 끝난 모임의 참가·출석 사실을 취소로 바꿔서는 안 되며 미결 책임과 후속 정리는 별도다. 데이터 내보내기, 데이터 삭제 예약, 즉시 탈퇴와 남은 참여 정리를 따른다.

위치 동의·좌표·만료와 보존

공유 동의, OS 위치 권한, 좌표 갱신, 공유 만료 시각, 실제 조회 권한과 조회 기록은 별개다. 동의 저장만으로 좌표를 취득하거나 타인이 본 것은 아니다. 주기적 좌표 갱신이 원래 공유 만료를 자동 연장한다고 설명하지 않는다. 공유 중지는 새로운 공개와 저장된 기록의 보존·삭제를 같은 결과로 만들지 않는다.

증빙 참조 해제와 저장소의 실제 파일 제거도 별도 단계다. 분쟁의 화면상 종결일 하나로 모든 원천의 보존 기한을 계산하지 않는다. 개인정보·안전 정책의 현재 소유권·목적·동의·보류·원천별 기한을 따른다.

알림 의도·알림함·발송·실수신

업무 상태 변경 → 알림 의도 → 알림함 기록·채널 작업 → 공급자 발송 → 실제 기기 표시를 하나의 완료로 합치지 않는다. 채널·기능별 구현이 다르며 모든 메일에 영속 큐의 자동 재시도가 있다고 일반화하지 않는다.

카테고리 끄기는 새 푸시와 알림함 기록을 함께 제한하며 이미 받은 기록을 삭제하지 않는다. 방해금지는 일반 푸시를 건너뛰는 조건이고 알림함 기록을 취소하지 않는다. 이를 무조건 다음 시간까지 보류·예약 발송하는 상태로 설명하지 않는다. 예외 종류·수신자 자격·발송 시점의 도메인 상태를 따로 검사한다.

처리 소유권·임대·다음 시도·만료·최대 시도는 발송 작업의 상태다. 알림함 읽음은 업무 완료가 아니며 공급자의 SENT·수락도 사용자의 수신 증거가 아니다. 알림 정책을 따른다.

계정 전환·오류 뒤 화면 복귀의 확인 기준

상태를 바꾸는 기능은 시작 계정·대상과 완료 시점 계정·대상을 맞춰야 한다. 조회 실패를 비어 있음이나 권한 없음으로 바꿔 쓰지 않고 현재 결과를 확인할 수 있게 한다. 낙관적 변경 실패는 해당 변경의 복구, 저장 후 조회 실패는 저장 결과 확인으로 나눈다.

이 기준을 모든 화면에서 새로 실행 검증했다는 뜻으로 읽지 않는다. 초안 보존, 업로드 중 이탈, 페이지 추가 조회, 권한 갱신, 계정 전환 응답 폐기는 각 기능 정본에 확인된 연결과 제한을 적는다. 검수 범위는 기획 QA 정책을 따른다.

결과 불명 명령과 재요청 키

앱의 시간 제한형 IdempotencyKeyHolder는 같은 입력의 키를 만든 시각부터 23시간 미만, 시계가 뒤로 가지 않은 경우 재사용한다. 시간창을 벗어난 기존 키는 해제하고 동일 입력의 즉시 재생성을 잠시 막으며 현재 결과 확인을 안내한다. 입력이 달라진 새 명령과 동일 명령의 재시도는 구분한다.

이 보관함의 untimed 모드는 위 시간창을 쓰지 않는다. 회원 금전 명령에는 별도의 계정별 영속 의도 저장소를 사용하므로 화면 메모리 보관함의 23시간 정책을 그대로 적용하지 않는다. 서버의 모든 API가 같은 기간 응답을 재생한다는 보장도 아니다.

확정 거절, 실행 성공, 결과 불명, 입력 수정은 각 명령의 키 해제·보존 규칙을 따른다. 응답이 없다는 이유로 돈·역할 변경을 새 키로 반복하지 않는다. 영속 기록이 필요한 명령에서 저장 실패는 실행을 막는 조건이며 UI 재시도 문구가 서버 중복 방지 계약을 대신하지 않는다.

상태 정책의 수용 기준과 검증 근거

  • 대상 분리: 신청·참석·결제·송금·반환·분쟁·알림을 같은 상태로 합치지 않는다.
  • 종료 경계: 모집 마감·실제 만남 종료·양쪽 확인·보관금 해제·완료 사실을 구분한다.
  • 후속 작업: 취소·기한 만료·삭제 예약·분쟁 닫힘을 돈 반환·물리 삭제·보상 완료로 확대하지 않는다.
  • 복구: 결과 불명에서는 해당 키·의도 기록과 현재 결과를 확인하고 기능별 확정 거절 조건을 따른다.
  • 증거: 직접 읽은 상태 enum·비공개 선정/완료·앱 키 보관과 동일 SHA의 기능 정본을 근거로 한다. 이번 제품 시험·실제 기기·운영 설정·외부 송금·푸시는 실행하지 않았다.

이동 조율·카풀·버스 상태

대상현재 상태 계약출시 전 확인할 경계
모임 이동 설정첫 배정은 차량의 자리 채우기 방식을 따른다(호스트 전담은 주최자만, 자기 점유는 참가자가 직접). 왕복은 나누지 않으며 앉은 참가자의 옮기기는 주최자가 허용한 동안 자기 점유 차량으로만 가능하다.웹 확인 완료. 휴대전화 화면과 실제 푸시는 미확인이다.
지원 대기차량 지원을 수정·철회하거나 승인받지 못해도 확정 전에는 기존 승객 배정을 유지한다. 확정 때만 운전자로 바뀐다.확인한 지원 경로는 중간에 반복하지 않는다.
배정 필요와 개별 이동배정 해제는 배정 필요다. 이미 배정된 사람의 개별 이동 희망은 주최자가 처리한 뒤에만 반영한다. 자동 자차 차량을 만들지 않는다.추가 웹 검사에서 두 상태를 구분해 확인했다.
운행 취소와 참가 취소운행만 취소하면 모임에 남는 전 운전자·승객을 다시 배정한다. 운전자가 모임 참가도 취소하면 남은 승객만 재배정 대상으로 남는다.두 경로를 각각 확인했다. 이전 자동 자차 복귀 규칙은 사용하지 않는다.
재배정 묶음과 모임 종료남은 대상이 0명이면 묶음을 자동 종료한다. 모임이 먼저 끝나면 미해결 그대로 보관하고 미처리 의견은 모임 종료로 닫는다. 성공 처리로 바꾸지 않는다.앱·관리자·서버의 미해결 두 명과 의견 상태가 일치했다.
차량 배정과 실제 좌석차량별 인원 배정이 기본이다. 다른 도면으로 바꿀 때 명단·배정 식별자는 유지하며 세부 좌석은 미지정으로 둘 수 있다. 변경 사유와 전환 전후 기록을 남긴다.합성 도면 변경과 사유 보존 확인. 사용할 실차 도면과 휴대전화 좌석표 조작은 별도로 확인한다.
