정산은 어디까지 확인됐나요?

기준일 구분: 아래 실제 웹 결과와 소개 사진은 2026년 9월 24일 확인입니다. 9월 26일의 초안 취소·저장 결과 유실 복구와 직접 송금 미납 알림 수정은 기본 브랜치와 자동 검사 기록을 확인했습니다. 아래 사진을 그 두 수정의 실제 화면·푸시 검증으로 사용하지 않습니다.

첫 비용 작성·금액 검토·입금 관리·개인 내역 검색의 실제 웹 시나리오 네 가지를 통과했습니다. 화면에서 발견한 수취인의 진입 누락과 잘못된 결제액 표시를 수정한 뒤, 변경 시나리오 묶음을 한 번 더 확인했습니다. 새 원본 11장과 이전 직접 송금 근거를 볼 수 있습니다.

확인한 행동실제 결과
첫 비용 → 검토 → 요청주최자가 아닌 수아를 결제자로 선택했습니다. 검토에 수아 결제 30,000원·다른 두 사람 결제 0원·각자 부담 10,000원이 표시되고 요청 후 정산이 시작됐습니다.
항목별 입금 → 완료수아가 모임 현황에서 본인 항목으로 들어갔습니다. 본인 몫에는 확인 버튼이 없으며, 나머지 입금을 확인하자 남은 2건 → 1건 → 0건, 모임 정산 완료가 반영됐습니다.
내 정산·월·기간 검색보낼 10,000원과 받을 9,000원을 따로 봅니다. 8월의 보낸 40,000원, 9월 1~10일의 받은 7,000원을 조회했고 목록과 합계가 일치했습니다.
취소 원본과 목록 복귀새 정산이 생겨도 취소된 6,000원의 원래 내역을 열었습니다. 돌아오면 선택 기간이 유지됐고 환불 확인이 남은 돈을 정상 완료 합계에 넣지 않았습니다.
직접 송금 확인 후 갱신‘내가 주고받는 돈’이 먼저 열립니다. 수취인이 9,000원을 확인하자 모임이 완료되고 개인 받을 돈도 9,000원 → 0원으로 갱신됐습니다.

자동 검사: 서버 정산·탈퇴 연결 345건, 규칙 74건, 앱 정산 228건의 기존 근거에 이번 화면 결함 방지 검사를 추가했습니다. 실제 MySQL의 동시 마지막 확인과 1,010건 목록 경계도 확인했습니다. 최종 전체 검사의 잔여와 다음 행동은 별도로 관리합니다.

확인하지 않은 것: 서명한 휴대전화 앱, 실제 은행 송금·외부 송금 앱 실행·푸시 전달입니다. 사진은 가상 회원과 금액을 쓴 웹 화면이며 월별 과거 기록은 조회용 준비 자료입니다. 포인트·혼합 납부 제한은 바꾸지 않았습니다.

기존 비용 편집의 입력 보존, 날짜·권한·실패 복구 조합과 이전 직접 송금 전체 여정은 같은 소스의 근거를 재사용했습니다. 영수증·재안내·기한 연장·이의·일괄 확인·환불 전체를 반복 검사하지 않았습니다.
