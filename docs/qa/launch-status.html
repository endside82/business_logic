첫 출시 판단 — 지금 공개할 수 있는가

이 페이지는 사업·기획자가 바로 판단할 수 있도록 첫 출시 범위, 지금까지 끝난 검증, 공개 전에 남은 일과 실행 순서를 한곳에 모은다. 기능 설명 문서에 적힌 “이렇게 동작한다”는 약속과 오늘 실제로 확인된 상태를 구분해서 보여 준다.

현재 결론

내부 시연은 가능하지만 외부 고객 공개는 아직 불가능하다. 로컬 환경의 신규 계정으로 첫 출시 흐름은 끝까지 통과했고, 첫 출시 범위를 직접 막는 코드·화면 결함은 현재 확인되지 않았다. 그러나 실제 메일·Google 로그인·모바일 푸시·서명 앱·운영 복구는 아직 확인하지 않았다. 외부 연동 10개 영역 중 9개는 연동 어댑터 코드가 완료됐다. 이것이 실환경 검증까지 끝났다는 뜻은 아니다. 본인확인(NICE)은 고객 앱·서버 연결과 관리자 웹의 결과·실패 이력 조회까지 끝났지만, 정상 API 장애 때 쓸 안전한 관리자 수동 승인과 계약·실신원·실기기 왕복이 남았다. 계좌 1원 인증은 공급자마다 계약별 API가 달라 계약을 확정한 뒤 실제 어댑터를 작성한다.

제공자 배정·정산은 코드 완료·출시 전이다. 직접·카탈로그·정기모임 배정부터 계약금, 참가자 분담, 수행 기록, 정산, 환불, 주간 지급까지 고객 앱과 서버에 연결됐다. 플랫폼 운영자도 자격 심사, 상품 정지·해제, 분쟁, 지급 원장 조회와 실패 재시도를 화면에서 처리할 수 있다. 봉인 중에는 새 거래만 막고 이미 성립한 계약의 종결과 환불·지급은 유지한다. 2026-09-04 기준 사용자용 API f94f09a0, 앱 a6a88a05, 관리자 API e7475312, 관리자 웹 acb8e59c는 모두 원격 기본 브랜치와 일치한다. 네 저장소 전체 회귀와 두 API의 제공자 초기 정의 대조, Codex 코드 검수를 통과했다. 이번 재검 결과는 사용자용 API 7,999건, 앱 3,033건, 관리자 API 1,185건, 관리자 웹 E2E 188건으로 모두 실패 0이다. 관리자 웹은 로컬 Node 22에서 재검했으므로 저장소가 요구하는 Node 24.14 이상에서 최종 실행을 한 번 더 한다. 남은 것은 플랫폼 결제 기반 출시, 지급 대행 실연동, 법무·세무 승인, 서명 앱 실계정 왕복이다. 모두 끝난 뒤 배포 설정의 출시 범위 목록에 PROVIDER를 추가하면 열린다.

클럽 마일리지 핵심 기능은 출시 상태다. 네 저장소의 코드·운영 화면·초기 정의 대조·서버 실계정·앱 화면 왕복을 마쳤고, 2026-09-04 운영 기본 출시 목록에 MILEAGE를 반영했다. 실제 기기의 알림 수신과 화면 이동은 출시를 막는 조건에서 출시 후 운영 확인으로 옮겼다. 시즌·사진 승인 적립·고급 검토 여섯 종·이벤트별 규칙·클럽별 후기 작성 기간은 핵심 기능과 다른 후속 기능이므로 계속 닫혀 있다. 다음 출시 승인 증거에는 현재 두 최초 설치 SQL의 빈 데이터베이스 설치 비교, 저장소가 요구하는 Node 24.14 이상 관리자 웹 재실행, 서명 앱·외부 서비스 왕복을 함께 묶는다.

코드 완성도와 출시 준비도는 같은 숫자가 아니다

코드가 존재하는 비율과 실제 고객에게 공개할 수 있는지는 별개의 질문이다. 현재 소스를 기능 계약, 고객 화면, 운영 화면, 복구 경로와 자동 검증으로 나눠 다시 본 결과는 다음과 같다.

  6. 클럽 마일리지 핵심 기능은 출시했다. 운영 기본 출시 목록에 MILEAGE를 반영했으며, 실기기 알림·화면 이동은 출시 후 운영 확인으로 남겼다. 시즌, 사진 승인 적립, 고급 검토 여섯 종, 이벤트별 규칙, 클럽별 후기 작성 기간은 별도 후속 기능이며 각각 제품 범위 확정·구현·운영 화면·검증을 마친 뒤 따로 출시한다.
  7. 현재 승인된 제공자 배정·정산의 첫 출시 범위에도 코드 작업이 남지 않았다. 플랫폼 결제 기반, 지급 대행 실연동, 법무·세무 승인, 서명 앱 역할별 왕복을 끝내고 운영 출시 범위 목록에 PROVIDER를 추가한다. 법무·세무 승인에서 현재 정책이나 데이터 항목의 변경을 요구하면 그 변경은 별도 코드 작업으로 다시 연다. 일정 중복 자동 검사와 역할명 표준화 등 알려진 한계는 기능 고장이 아니라 별도 후속 개선으로 관리한다.
  8. 관리자 돈 조치의 응답 유실 재시도 안전 보완. 무료 포인트 지급, 실패 환불 보상, 마일리지 사건 정정 세 화면은 같은 작업을 다시 실행할 때 같은 중복 방지 키를 쓰도록 닫혔지만, 출금 승인·거절·복구, 가상계좌 회수, 충전 취소·확정, 에스크로, 입금 확인·거절·환불, 결제 사건 복구 등 돈이 움직이는 호출부 22곳은 아직 실행할 때마다 새 키를 만든다(제공자 지급 재시도는 서버가 재시도 사슬 유일키로 중복을 막는다). 현금성 기능을 열기 전에 전부 같은 규칙으로 바꾸고, 첫 응답을 잃은 뒤 다시 눌러도 한 번만 처리되는 화면 검증을 추가해야 한다.

현금성 조치의 재시도 보완이 첫 출시 코드 차단 0건과 충돌하지 않는 이유는 현재 첫 출시가 무료 포인트 전용이고, 남은 호출부가 속한 현금성 결제·환불·출금 기능은 서버 설정으로 닫혀 있기 때문이다. 이 기능을 하나라도 열려면 해당 호출부의 보완이 먼저 끝나야 한다.

위 퍼센트는 테스트 커버리지가 아니라 현재 소스의 구현 범위를 비교한 근사치다. 제품 기능 175개 중 자동 테스트 파일을 문서에서 직접 가리키는 기능이 59개, 통합·사용자 여정 파일을 직접 가리키는 기능이 56개라는 수치는 문서와 검증 근거의 연결 정도이며 코드 구현률과 바꿔 읽으면 안 된다.

현재 소스 통합검증과 외부 계정·실기기·운영·법무·스토어 준비를 각각 구분해 표시한다. 정기모임 환불 완료 이력, 제재 계정 문의 관측, 제공자 배정·정산과 지급 복구를 포함한 제품 코드의 검증 기준은 마련됐다. 제공자 관련 네 저장소의 현재 커밋은 원격 기본 브랜치와 일치하므로 “먼저 푸시해야 한다”는 과거 조건은 해소됐다. 이제 같은 조합으로 두 최초 설치 SQL의 빈 데이터베이스 기능 스키마 차이 0과 요구 Node 버전의 관리자 웹을 확인하고, 서명 앱과 실제 외부 서비스를 연결한 실행 기록을 출시 승인 증거에 포함해야 한다.

미해결 항목 — 앞으로 할 일의 성격부터 구분한다

아래 항목은 모두 아직 닫히지 않았다. 각 행의 첫 라벨에서 구현 중, 정책이 확정된 구현 대기, 서버 선행, 미착수와 문서 작업을 구분한다. 완료된 항목은 목록에서 제거했다. 첫 출시 코드·화면 작업과 출시 후 보완을 섞지 않고, 현재 소스 통합검증은 별도 출시 조건으로 관리한다.

화면 연결만 남은 빠른 작업

서버 API와 앱 데이터 계층이 이미 준비됐고 화면 연결만 빠진 항목이다. 새 제품을 설계하는 일이 아니므로 대형 후속 작업보다 먼저 닫는다. 화면을 연결하고 표적 화면 테스트를 통과해야 완료이며, “서버가 있다”만으로는 완료가 아니다.

담당·구분현재 문제와 이미 있는 기반 다음 행동과 완료 기준관련 기능

출시 승인 전에 처리 방식을 결정할 항목

코드를 무조건 더 만드는 목록이 아니다. 제품·운영·개인정보 책임자가 선택지를 승인한 뒤 선택한 결과를 정책, 화면, 서버 또는 운영 절차와 테스트에 반영해야 닫힌다. 결정을 미룬 상태는 완료가 아니며 출시 승인 회의에서 명시적으로 처리해야 한다.

현재 봉인된 기능과 봉인 해제 계획

봉인은 “구현하지 않겠다”는 뜻이 아니다. 기능을 다시 여는 것이 목표이며, 지금은 확인된 위험 때문에 정해진 출시 조건으로 신규 사용만 잠시 막은 상태다. 고객 화면만 만들어져 있어도 완료가 아니다. 운영자가 상태와 실패를 보고 처리·복구·감사할 화면까지 있어야 실제로 봉인을 풀 준비가 됐다고 판단한다. 코드 구현과 운영 화면은 서로 다른 상태로 표시하며, 고객·서버 코드가 끝났더라도 운영 화면이 부족하면 “코드 완료·운영 화면 부분”으로 남긴다.

사적 모임은 개설부터 참가비 보관·완료 확인·분쟁·운영자 복구까지가 한 줄기로 이어져 있고, 닫힌 자리는 지갑을 쓰는 두 지점뿐이다. 전 과정과 자리별 해제 조건은 사적 모임 전 과정에서 본다.

봉인으로 인정하는 최소 조건

① 현재 코드 상태, ② 운영 화면의 조회·처리·복구·감사 범위, ③ 실제로 막는 설정이나 서버 차단 조건, ④ 막은 사유, ⑤ 승인자·결정일·결정서, ⑥ 해제 순서와 완료 근거가 모두 적혀 있어야 한다. 하나라도 없으면 임시 봉인이 아니라 미완성 또는 폐기 설계다. 사유는 셋 중 하나다. 범위 결정은 제품이 첫 출시 범위에서 뺀 것이고, 기능 미완성은 범위와 별개로 아직 만들지 않은 코드나 운영 화면이 남은 것이며, 미해결 결함은 확인된 결함 때문에 막은 것이다. 둘 다 해당하면 범위 결정을 적고, 남은 코드나 운영 화면은 왼쪽 칸의 상태로 읽는다. 현재 목록에 미해결 결함은 없다. 승인자·결정일·결정서가 기록 없음이면 결정 자체가 문서로 남지 않았다는 뜻이며, 범위 관문을 통과하려면 이 칸부터 채워야 한다. 현재 해제 순서는 1차 버스·카풀/유료 모임 직접 송금 → 2차 소셜 제공자별 출시 → 3차 데이트 → 4차 실결제 기반 → 5차 지갑 의존·구독·마켓·제공자 거래다.

기능·해제 순서 코드와 운영 화면 막은 사유·승인 기록과 실제 차단 조건 봉인 해제 절차와 완료 기준 관련 기능
놓치기 쉬운 연쇄

일반적인 지갑 차감을 닫았기 때문에, 현금성 포인트나 외부 지급이 필요한 기능은 함께 닫힌다. 클럽 기금 인출, 클럽 구독의 클럽 소유자 지갑 부족분, 모임 정산의 지갑 납부, 수익 출금이 여기에 해당한다. 다만 클럽 가입비·기부는 무료 포인트만 쓰는 명시적 예외로 열렸고, 클럽 구독도 기금으로 전액 충당되면 열린다. 각 기능 문서만 읽으면 이 경계가 보이지 않으므로 이 표를 함께 본다. 현금성 결제 코드는 준비됐지만 실제 계약·키·소액 실거래 확인 전에는 실행 경로를 열지 않는다. 닫힌 기능의 버튼은 유지하되, 기능별 제한 사유·남은 준비· 출시 조건을 설명하는 안내 화면으로 연결하는 일을 공개 출시 전 필수 정리로 올렸다. 환불·회수·탈퇴 잔액 정리는 고객에게 돌아가야 할 돈을 묶지 않기 위해 계속 열어 둔다.

봉인이 아니라 폐기·신규 기획인 기능

아래 항목은 설정을 바꿔 다시 여는 기능이 아니다. 기존 설계를 제거했기 때문에 다시 추진하려면 제품 가치·개인정보 권한·운영 책임부터 승인하고 새로운 구현 계획을 세워야 한다. 봉인 해제 일정이나 완료율에 포함하지 않는다.

이 문서 모음을 읽을 때의 한계

기능 문서는 대부분 현재형 단정으로 쓰여 있다. 그 문장은 “이렇게 동작하기로 했다”는 뜻이며, 오늘 그렇게 동작한다는 보증이 아니다. 다음 세 가지를 함께 기억한다.

  • 기능 문서 본문만으로는 현재 출시 상태를 알 수 없다. 그래서 각 기능 문서 맨 위에 이 페이지의 두 판단 기준을 요약해 표시했다. 요약과 본문이 어긋나면 요약을 최신 상태로 본다.
  • 문서 상태표는 구현 완료표가 아니다. PRD 문서 상태가 재는 것은 문서를 얼마나 소스와 대조해 썼는지이지 제품이 되었는지가 아니다.
  • 시나리오 커버리지는 시험 문서의 개수다. 시나리오 커버리지의 “빈틈 0”은 시험 항목을 다 적었다는 뜻이지 실제 환경에서 통과했다는 뜻이 아니다.

이 페이지의 출처와 갱신 규칙

  • 출시 판정·관문·외부 증거는 제품 저장소의 사업·기획자용 출시 현황, 출시 가능성 증명 현황, 실제 계정 실행 기록, 과거 통합검증 기록과 현재 저장소 상태를 함께 대조한다.
  • 문서 판정과 현재 소스가 어긋나면 한쪽을 임의로 우선하지 않는다. 실제 고객 동작과 출시 승인 기준을 다시 확인하고, 차이를 이 페이지의 필수 정리 항목으로 남긴 뒤 기준 문서도 같은 날 맞춘다.
  • 노출 여부는 운영 배포 설정에서 기계적으로 읽는다. 설정이 바뀌면 이 페이지도 같은 날 바꾼다.
  • 미해결 항목은 기능 문서의 서술을 후보로 삼되 현재 소스의 화면·라우트·서버 계약과 다시 대조한 것만 남긴다. 화면 연결, 출시 전 결정, 출시 후 개선, 문서 작업을 분리하고 다음 행동과 완료 기준을 함께 기록한다. 소스에서 이미 해소된 항목은 기능 문서가 늦게 바뀌었더라도 이 페이지에서 즉시 제거한다.
  • 봉인 항목은 코드·운영 화면·실제 차단 조건·봉인 사유·승인 기록·해제 절차·완료 기준을 함께 갱신한다. 코드와 운영 화면은 따로 판정하며, 운영 화면이나 해제 기준이 비어 있으면 “봉인 해제 준비 완료”로 표시하지 않는다.
  • 기준일이 오늘과 멀어졌다면 값이 아니라 기준일을 먼저 의심한다.
