판정할 결과부터 정하기

수용 기준은 기능이 제공해야 할 결과다. 문서 작성, 소스 대조, 시험 파일 존재, 시험 실행, 실제 외부 결과, 출시 승인은 서로 다른 증거다. 기능에 관련된 조건을 고르고 적용하지 않는 조건은 이유를 남긴다. 모든 기능에 동일한 개수의 시험·이미지·기기 조합을 요구하지 않는다.

기획 QA 정책의 실제 입구 → 업무 → 결과 → 복귀를 따른다. 공통 결과는 확인한 근거를 재사용하고 입구마다 다른 권한·대상·상태만 추가 검토한다. 햄버거 메뉴·상단 버튼·더보기·하단에 같은 행동이 중복되는지 실제 경로에서 확인한다. 탐색 맵이나 문서 HTML은 실제 앱 화면 검수의 증거가 아니다.

결과와 출시 판단 기록

판정마다 대상 버전·계정/역할·입구·시작 조건·행동·예상 결과·관측 결과·후속 미완료·증거 위치를 남긴다. 결과는 확인 완료, 실패, 미실행, 환경 미확인, 적용하지 않음과 사유로 구분한다. ‘O’ 한 칸으로 계획과 통과를 함께 표현하지 않는다.

금전 오집행·권한 우회·민감정보 노출·실제 핵심 업무 단절은 해당 기능의 출시 판단에 반영한다. 모든 기능의 모든 조합을 새로 실행해야만 문서를 고칠 수 있다는 절차로 확대하지 않는다. 구현·자동 검사·실제 사용 흐름·외부 환경·공개 승인은 출시 완료 기준의 별도 단계로 남긴다. 이번 문서 최신화는 출시 승인 또는 기능 공개 변경이 아니다.

기능별 범위와 연결 문서

전체 수용 기준 매트릭스는 175개 기능의 정본·등록 확인 항목·상세 시나리오를 연결한다. 시나리오 커버리지는 도메인별 수와 빠뜨리기 쉬운 범주를 구분한다. 정해진 ‘최소 5개’보다 기능의 실제 분기·실패·복구를 기준으로 작성한다.

Notion으로 옮겨도 기능 ID·정본 링크·동기화 기준·증거 범위는 유지한다. 아직 별도 카드를 만들지 않았다는 사실을 기능 PRD나 서버 계약이 없다는 뜻으로 쓰지 않는다. 기능별 현재 제한은 각 PRD가 우선한다.
