외부 서비스 가입·계약과 출시 준비

운영자가 가입·계약부터 키 발급, 설정 전달, 실제 이용 확인까지 진행하는 체크리스트다. 첫 출시 필수 서비스와 기능을 추가 공개할 때 필요한 서비스를 구분한다.

소스·공식 안내 확인: 2026-10-07. 실제 공급자 콘솔의 계정·계약·키 상태와 운영 환경은 별도 확인 대기다.

진행 순서와 완료 상태첫 출시 필수 서비스 iOS 로그인 구성과 심사 준비후속 기능의 외부 계약 스토어 제출 자료와 공개 확인운영자가 남길 완료 기록

진행 순서와 완료 상태

기능 범위와 공개 판단은 첫 출시 범위와 공개 전에 할 일을 함께 따른다. 문서 작성이나 키 발급만으로 출시 완료가 되지는 않는다.

  1. 계정 소유자·배포 방식: 서비스 명의, 콘솔 소유 계정, 복구 수단, 비용 결제 주체를 확인한다. Apple 가입과 Google Play 계정별 테스트 요건을 먼저 확인하고 iOS 로그인 구성을 결정한다.
  2. 도메인·운영 환경: 공개 주소, 검사 서버, 메일 발신 도메인, 파일 저장소, 관리자 허용망을 준비한다.
  3. 프로젝트·키·권한: Google·Firebase·지도·메일 자격 증명을 발급하거나 기존 보관 위치를 확인한다. 개발·시험·운영 환경을 구분해 빌드와 서버에 전달한다.
  4. 같은 출시후보로 확인: Android와 iPhone에 서명 앱을 설치하고 가입·알림·지도·파일·채팅·직접 송금 확인을 수행한다. 실패·취소·중복 요청·권한 회수도 같은 이용 흐름에서 확인한다.
  5. 운영·공개 확인: 경보 수신·백업 복구·이전 버전 복귀를 확인하고 스토어 자료와 검사한 앱을 대조한다.
상태완료로 기록할 근거
가입·계약 확인운영자에게 콘솔 접근 권한과 해당 서비스의 이용 권한이 있다. 기존 계약이 있다면 새로 가입하지 않는다.
발급·설정 확인사용 환경·앱 식별자·허용 권한이 맞고 키가 실행 환경에 전달됐다. 키 본문 대신 보관 위치·식별자·만료일을 기록한다.
실제 연동 확인서명 앱·실제 공급자·역할별 시험 계정의 성공과 실패 결과가 있다. 모사 응답이나 공급자의 접수 성공만으로 완료 처리하지 않는다.
운영 준비 확인한도·비용·만료·실패 경보를 받을 수 있고 재처리·복구 절차를 수행했다.

현재 상태: 이 문서는 실행할 준비를 정리한 것이다. 콘솔을 조회하지 않은 항목은 미확인이며, 계정이나 계약이 없다는 뜻이 아니다. 이전 자동 검사 결과와 이번 외부 검증 결과를 합쳐 완료로 표시하지 않는다.

첫 출시 필수 서비스

현재 앱은 이메일·Google 로그인, 모임·클럽·직접 송금·이동·투표와 알림·파일 기능을 제공하도록 설정되어 있다. iOS 공개 전 로그인 구성 판단은 별도 선행 조건이다. 이 문서를 추가해도 서버나 앱의 활성 기능은 바뀌지 않는다.

iOS 빌드·TestFlight 내부 테스트 절차

  1. 가입·앱 등록: Apple Developer Program 가입 안내에 따라 기존 회원 자격·권한을 확인한다. 조직 가입이면 D-U-N-S 등 조직 확인 조건을 준비한다. App Store Connect에 앱과 내부 테스트 사용자를 등록한다.
  2. 서명: Xcode 계정, Developer Team, Runner의 자동 서명, 배포 인증서·개인 키 또는 Xcode 관리 배포 서명을 준비한다. Push Notifications와 Associated Domains를 앱 Identifier 및 프로비저닝에 반영한다.
  3. 업로드 인증: App Store Connect의 Users and Access → Integrations에서 팀 API 키를 발급한다. Key ID·Issuer ID·다운로드한 .p8 파일을 보관하고 앱 업로드 권한을 확인한다. fastlane API 키 인증 안내를 따른다.
  4. 빌드·설치: 아래 설정 검사와 IPA 빌드 뒤 업로드를 실행한다. Apple 처리 완료 후 TestFlight 내부 그룹에 빌드를 연결해 iPhone에 설치한다. 수출 규정 질문은 앱의 실제 동작에 맞게 답한다.

현재 식별자: Bundle ID com.endside.community.communityApp, Team GSGHZ76QY5, Scheme Runner. 다른 팀으로 배포한다면 Xcode 프로젝트·fastlane Appfile·ExportOptions의 팀을 함께 맞춘다.

iOS 설정 위치와 실행 명령

원본 구현·상세 가이드는 저장소의 community_app/ios/fastlane/Fastfile과 community_app/docs/IOS_RELEASE.md다. 사이트에서도 실행할 수 있도록 필수 절차를 아래에 정리했다.

위치전달할 설정
community_app/ios/fastlane/.envAPP_STORE_CONNECT_API_KEY_KEY_ID, APP_STORE_CONNECT_API_KEY_ISSUER_ID, APP_STORE_CONNECT_API_KEY_KEY_FILEPATH. 마지막 값은 ios 기준 키 파일 경로다.
community_app/ios/Flutter/Secrets.xcconfigGOOGLE_MAPS_API_KEY, GOOGLE_IOS_CLIENT_ID, GOOGLE_IOS_REVERSED_CLIENT_ID, GOOGLE_SERVER_CLIENT_ID
community_app/dart_defines/prod.json운영 서버 주소, Google OAuth, Firebase iOS 설정. prod.example.json을 기준으로 작성한다.
# community_app/ios 에서 실행. macOS 시스템 Ruby 대신 Ruby 3.3 이상 사용
bundle config set --local path vendor/bundle
bundle install
cp -n fastlane/.env.example fastlane/.env
# 위 파일과 Secrets.xcconfig, dart_defines/prod.json에 실제 설정을 채운 뒤 실행
bundle exec fastlane ios validate_config
bundle exec fastlane ios validate_key
bundle exec fastlane ios build
# TestFlight 업로드가 필요한 시점에 실행
bundle exec fastlane ios deploy

build는 IPA 생성만, deploy는 TestFlight 전송까지 수행한다. 전송 완료는 Apple 처리·설치 완료와 다르다. 현재 레인은 외부 테스트·베타 심사·App Store 공개 심사를 제출하지 않는다. env:staging을 쓰면 대응 JSON과 native OAuth 설정도 staging으로 맞춘다.

버전은 pubspec.yaml의 version: 이름+빌드번호를 사용하며 업로드마다 빌드 번호를 올린다. 산출물은 community_app/build/ios/ipa/*.ipa다. 내보내기 실패 시 이전 IPA를 업로드하지 않도록 새 파일 생성을 검사한다.

키 구분: App Store Connect 업로드 키, APNs 푸시 키, 앱 배포 서명은 서로 다른 용도다. 파일 확장자가 .p8로 같아도 업로드 키를 Firebase APNs 칸에 넣지 않는다.

완료 조건: TestFlight에서 설치한 앱이 실제 서버에 연결되고 로그인·지도·푸시·딥링크가 동작한다. 10월 7일 fastlane 작업의 격리 검증 19개는 실제 Apple 호출·서명 빌드가 아니다. 당시 이 Mac의 배포 인증서·API 키·iOS 서비스 설정은 미준비였고, 다른 보관소의 가입·계약 상태는 확인하지 않았다.

Android 빌드·Google Play 테스트 절차

  1. Google Play Console의 개발자 계정·본인 또는 조직 확인·앱 등록 상태를 확인한다.
  2. 패키지명 com.endside.community.community_app을 기준으로 Play App Signing과 업로드 키를 준비한다. Google 로그인에는 스토어가 실제 앱에 사용하는 앱 서명 인증서 지문을 등록한다. 업로드 키 지문과 혼동하지 않는다.
  3. Google Play Android Developer API를 활성화하고 fastlane 서비스 계정에 해당 앱의 필요한 권한을 부여한다. 기존 앱이면 새 앱이나 새 서명 키를 만들지 않고 등록된 구성을 확인한다.
  4. 첫 AAB는 Console에 수동 등록하고, 이후 기존 fastlane 업로드 레인을 사용한다. 내부 테스트 링크로 설치·업데이트한 뒤 계정에 적용되는 프로덕션 접근 조건을 완료한다.
개인 개발자 계정의 비공개 테스트

2023년 11월 13일 이후 생성된 개인 개발자 계정은 프로덕션 접근 신청 전에 12명 이상이 14일 연속 참여하는 비공개 테스트가 필요하다. 내부 테스트 업로드와 별개이며, 기간을 채운 뒤 접근을 신청한다. 계정 유형·생성일과 Console의 현재 요구를 확인한다. 새로운 개인 개발자 계정의 앱 테스트 요구사항

iOS 로그인 구성과 심사 준비

현재 코드: 앱과 서버의 활성 제공자는 이메일·Google이며 Apple은 비활성이다. 이는 구현 설정의 설명이고, 그 조합으로 App Store 심사 요건을 충족했다는 뜻은 아니다.

공식 기준: Google 등 제삼자 로그인으로 주 계정을 만드는 앱은 예외에 해당하지 않는 한, 이름·이메일로 수집을 제한하고 이메일 비공개를 지원하며 동의 없는 광고 목적 이용 추적을 하지 않는 동등한 로그인 수단도 제공해야 한다. Apple 로그인 서비스 심사 기준을 따른다.

이 제품의 준비 방향: Google 로그인을 유지한다면 Sign in with Apple을 활성화하는 방안부터 검토한다. 일반 이메일 가입이 있다는 것만으로 위 요건을 충족했다고 판단하지 않는다. 다른 적합한 로그인 수단이나 예외를 적용하려면 실제 조건과 근거를 기록한다. 이는 심사 승인 보장이 아니다.

  1. Google 유지와 동등한 로그인 추가, 또는 iOS 로그인 범위 변경 중 출시 구성을 정한다. 문서에서 결정 대기를 완료로 바꾸거나 코드를 자동 활성화하지 않는다.
  2. Apple을 선택하면 App ID의 Sign in with Apple capability, 서버의 APPLE_CLIENT_ID audience, 필요한 웹 인증·토큰 철회용 Service ID·키 설정을 실제 인증 방식에 맞춘다.
  3. 앱과 서버의 제공자 목록·버튼·직접 호출 제한을 함께 변경·검증한다. 서버 설정 한 줄만 바꾸고 완료 처리하지 않는다.
  4. 실제 iPhone에서 첫 가입·재로그인·이메일 숨기기·연결 해제·계정 삭제·인증 철회를 확인한다. 숨긴 이메일로 메일을 보내면 Apple 비공개 이메일 릴레이 설정 안내에 따라 발신 도메인·주소 등록과 SPF·DKIM 인증도 준비한다.

완료 조건: 선택한 구성의 코드·설정·실계정 결과와 심사 설명이 일치한다. 카카오·네이버의 추가 공개는 계속 후속으로 두되, iOS 로그인 요건 판단 자체는 첫 공개 전에 끝낸다. 기능 설명은 현재 로그인 활성 상태와 iOS 공개 전 결정에서 연결한다.

Google 로그인 등록과 실제 계정 확인

  1. Google Cloud Console에서 사용할 프로젝트와 소유 권한을 확인한다. Google Auth Platform에 앱 이름·지원 이메일·운영 도메인·개인정보처리방침·동의 화면을 설정한다.
  2. Web·Android·iOS OAuth 클라이언트를 준비한다. Android에는 패키지명과 배포 서명 지문, iOS에는 com.endside.community.communityApp을 사용한다.
  3. 사용 대상·공개 상태·테스트 사용자를 점검하고 요청 scope에 필요한 검증을 확인한다. Calendar 접근 검증을 기본 로그인과 같은 작업으로 가정하지 않는다. Google OAuth 검증 요건

설정 위치: 서버의 GOOGLE_CLIENT_ID와 앱 JSON의 GOOGLE_SERVER_CLIENT_ID는 같은 Web 클라이언트다. 앱 JSON의 GOOGLE_IOS_CLIENT_ID는 iOS 클라이언트다. iOS native 파일에도 같은 두 값을 넣고 reversed ID를 맞춘다. 이 ID들은 비밀번호가 아니며, 서버용 비밀키를 앱에 넣는 작업과 구분한다.

완료 조건: 양 플랫폼의 서명 앱에서 신규·기존 계정 로그인, 취소, 연결·해제, 마지막 로그인 수단 보호를 확인한다. 잘못된 audience·만료 토큰이 거부되고 서버와 앱의 계정 결과가 일치해야 한다.

Firebase·APNs 푸시 연결

  1. Firebase Console에서 환경별 프로젝트와 Android·iOS 앱을 등록한다.
  2. 앱 설정의 프로젝트 ID·발신자 ID·플랫폼별 API 키·앱 ID를 확보하고 서버 발송용 서비스 계정 권한을 준비한다.
  3. Apple Developer에서 푸시용 APNs 키를 준비하고 Firebase의 iOS 앱에 Key ID·Team ID와 함께 연결한다. 앱의 Push Notifications와 Background Modes의 Remote notifications도 확인한다. Flutter FCM과 APNs 설정 안내

설정 위치: 앱은 dart_defines/prod.json의 FIREBASE_PROJECT_ID, FIREBASE_MESSAGING_SENDER_ID, FIREBASE_ANDROID_API_KEY, FIREBASE_ANDROID_APP_ID, FIREBASE_IOS_API_KEY, FIREBASE_IOS_APP_ID를 사용한다. iOS Bundle ID를 입력하면 실제 앱과 일치해야 한다. 현재 구현은 빌드 인자로 초기화하므로 콘솔에서 받은 JSON·plist 파일만 복사하는 것으로 끝나지 않는다. 서버는 FIREBASE_CREDENTIALS_PATH로 서비스 계정 파일을 읽는다.

완료 조건: Android·iPhone 각각 권한 허용·거부·재허용, 전경·백그라운드·종료 상태의 수신과 알림 클릭을 확인한다. 계정 전환·로그아웃·무효 토큰·재시도에서 다른 회원에게 알림이 가지 않고 중복 표시가 억제되어야 한다. 서버 발송 수락·실제 휴대전화 표시·화면 이동은 따로 기록한다.

Google Maps 앱 지도 설정

가입·발급: Google Cloud 프로젝트에 결제 계정을 연결하고 Maps SDK for Android와 Maps SDK for iOS를 활성화한다. 사용하는 플랫폼별 API 키를 만들고 Android 패키지·서명 지문 또는 iOS Bundle ID 및 API 사용 범위를 제한한다. Google Maps Flutter 프로젝트 설정

설정 위치: Android는 GOOGLE_MAPS_API_KEY 환경변수 또는 android/local.properties의 googleMapsApiKey, iOS는 ios/Flutter/Secrets.xcconfig의 GOOGLE_MAPS_API_KEY다. 서로 다른 제한이 필요한 두 플랫폼의 키를 무조건 공용으로 쓰지 않는다.

완료 조건: 스토어 서명 앱에서 지도·장소 마커·위치 공유가 표시되고 위치 권한을 거절해도 안내와 수동 선택 경로가 동작한다. 사용량·쿼터·비용 경보 수신처를 정하고 키 제한 오류와 한도 초과 시 안내를 확인한다.

Kakao Local 주소 변환 설정

가입·발급: Kakao Developers 앱과 카카오맵·Local API 이용 권한, REST API 키를 준비한다. 적용되는 무료 한도·추가 사용·과금 조건은 카카오맵 API 이용 안내에서 확인한다.

설정 위치: 서버 KAKAO_MAPS_API_KEY다. Google Maps는 앱 지도 표시, Kakao Local은 서버 주소↔좌표 변환을 담당한다. 카카오 로그인을 켜야만 주소 변환을 쓸 수 있는 구조는 아니다.

완료 조건: 실제 모임 주소와 현재 위치의 정방향·역방향 변환, 검색 결과 없음·시간 초과·한도 초과를 확인한다. 길찾기는 링크를 생성하는 현재 구현에 맞춰 Android·iPhone의 지도 앱 설치·미설치와 복귀를 확인한다. 별도 유료 경로 탐색 API 계약을 이미 사용 중인 것으로 적지 않는다.

메일 발송 계약·도메인 인증·실수신

  1. 운영 발송 공급자·발신 도메인·주소·지원 수신함을 정하고 발송 권한 및 SMTP 인증정보를 준비한다. 현재 반송·스팸 신고 수신 구현은 Amazon SES/SNS용이다. 다른 공급자를 선택하면 그 이벤트 연동의 호환 여부를 확인한다.
  2. DNS에 공급자 안내에 맞는 SPF·DKIM을 적용하고 DMARC 정책과 보고 수신처를 설정한다. 발신 도메인 인증과 운영 발송 허용을 별도로 확인한다.
  3. SES를 사용하면 사용할 리전에서 샌드박스 해제를 신청하고 발송 한도를 확인한다. Amazon SES 운영 발송 승인 절차
  4. SES configuration set의 배달·지연·반송·스팸 신고를 SNS와 서버의 POST /webhooks/email/ses/events에 연결하고 구독 확인·서명 검증을 확인한다.

설정 위치: 서버의 MAIL_HOST, MAIL_PORT, MAIL_USERNAME, MAIL_PASSWORD, MAIL_FROM, MAIL_FROM_NAME와 SES 사용 시 MAIL_SES_CONFIGURATION_SET다. 인증 링크용 AUTH_MAIL_CURRENT_KEY_ID·AUTH_MAIL_KEYS_*와 수신자 억제 해시용 MAIL_SUPPRESSION_HMAC_SECRET는 공급자 발급 키가 아닌 자체 운영 비밀이다. 후자는 전용 키 설정과 현재 대체 키 사용 여부를 확인해 보관·교체한다.

완료 조건: Gmail·네이버·다음 실제 수신함에서 가입 인증·비밀번호 복구 메일을 받고 링크를 처리한다. 재전송·오래된 링크·발송 지연·일시 실패·영구 반송·스팸 신고와 재발송 억제도 확인한다. 발송 API 성공만으로 수신 성공을 기록하지 않는다.

파일 저장소·검사·삭제 확인

  1. AWS Console에서 환경별 S3 버킷과 IAM 권한을 준비한다. IAM Role을 사용하면 장기 Access Key를 별도로 만들 필요가 없다. 호환 저장소를 선택하면 실제 지원 동작을 검증한다.
  2. 퍼블릭 접근 차단, 필요한 CORS, 암호화, 다운로드 URL 만료, 보존·삭제·백업 정책을 정한다. 버저닝과 보존 설정 때문에 개인정보 삭제 약속이 달라지지 않는지 확인한다.
  3. 업로드 검사 엔진을 준비한다. 현재 서버는 ClamAV의 clamd 연결을 지원하며 직접 운영할 수 있다. 별도 유료 검사 계약이 필수인 것으로 가정하지 않는다.

설정 위치: 서버 AWS_S3_BUCKET, AWS_S3_REGION, 필요 시 AWS_ACCESS_KEY·AWS_SECRET_KEY. 호환 저장소는 AWS_S3_ENDPOINT와 필요 시 AWS_S3_PUBLIC_BASE_URL을 지정한다. 모바일이 서명 URL로 접근하므로 기기에서 도달 가능해야 한다. 검사 공급자와 접속은 file.scan.provider=clamd, file.scan.clamd.host·port 등 서버 설정으로 전달한다.

완료 조건: 실제 사진·영수증의 업로드·조회·삭제, 서명 URL 만료, 타인 비공개 파일 접근 차단을 확인한다. 정상 파일·안전한 검사 시험 파일·검사 시간 초과, 계정 종료·파일 만료·삭제 실패 후 재시도 결과를 저장소에서 대조한다. 호환 저장소는 조건부 업로드와 기존 객체 덮어쓰기 차단까지 확인한다.

서버·도메인·경보·복구 준비

가입·설정: 선택한 호스팅과 도메인·DNS 계정, 서버·MySQL·Redis, HTTPS 인증서, 파일·실시간 채팅 주소, 운영 비밀 저장소와 백업 공간을 준비한다. 관리자 화면·API의 허용 네트워크와 로그인 권한도 정한다.

설정 위치: 앱 JSON의 API_BASE_URL, FILE_SERVER_URL, REALTIME_BASE_URL, SHARE_BASE_URL. 서버의 DB·Redis 연결, CORS·신뢰 프록시, 백업 설정과 OPERATOR_ALERT_WEBHOOK_URL을 해당 실행 환경에 전달한다. 관리자 위임·실시간 내부 토큰, JWT·AES·백업 암호화 키는 자체 생성·보관 대상이다.

완료 조건: 외부 통신망에서 가입 링크·공유 링크·파일·채팅이 열리고 두 기기의 채팅 재연결이 정상이어야 한다. 관리자 허용망 밖 접근 차단, 경보 실제 수신, 중복 없는 재처리, 격리 환경의 DB·파일 백업 복구와 이전 버전 복귀를 실행한다. 복구 시간·허용 데이터 손실·서비스 중단 기준을 기록한다.

후속 기능의 외부 계약

아래 서비스는 해당 기능을 공개하기로 결정했을 때 준비한다. 현재 주최자 계좌 직접 송금은 플랫폼 수납·자동 지급·계좌 인증과 다르다. 다만 직접 송금 자체의 계좌 안내·송금 신고·입금 확인·취소·환불은 서명 앱과 은행 내역으로 확인해야 한다.

공개할 기능가입·계약·키와 설정 위치실제 연동 완료 조건
플랫폼 결제·충전·저장 카드TossPayments 가맹 계약·심사와 결제수단·빌링 이용 범위를 확인한다. 서버 TOSS_SECRET_KEY·TOSS_CLIENT_KEY·TOSS_WEBHOOK_SECRET, 앱 TOSS_CLIENT_KEY, 빌링 공급자 PAYMENT_BILLING_AUTH_PROVIDER를 연결한다.소액 승인·취소·부분 환불·응답 유실·중복 요청·웹훅 재전송·장부 대조. 테스트 키 결과를 실결제로 세지 않는다.
출금·자동 지급지급대행 계약·이용 권한·수취인 등록을 확인한다. 서버 WITHDRAWAL_PAYOUT_PROVIDER, TOSS_PAYOUT_SECURITY_KEY와 PG 인증을 연결한다.실계좌 지급·실패·재시도·상태 조회·장부 대조. 키 발급만으로 남은 계좌 연결·출금 보완 개발이 완료되지는 않는다.
데이트 본인확인Toss 또는 NICE를 선택해 계약·상품 권한·복귀 주소를 준비한다. 서버 TOSS_CERT_CLIENT_ID·TOSS_CERT_CLIENT_SECRET 또는 NICE_CLIENT_ID·NICE_CLIENT_SECRET·NICE_PRODUCT_ID·NICE_RETURN_URL.실제 인증 성공·취소·실패·만료·변조 거부, 비공개 증빙 저장·관리자 확인·채팅·신고. 두 공급자를 모두 계약할 필요는 없다.
계좌 소액 인증공급자와 확인 범위를 결정한 뒤 계약·연결을 개발한다. 현재 BANK_ACCOUNT_VERIFICATION_PROVIDER 기본값은 FAKE다.실계좌 인증과 불일치·만료·중복 확인. 미인증 등록 계좌는 계속 인증 전으로 안내하며 첫 출시 직접 송금은 이 계약을 기다리지 않는다.
카카오·네이버 추가 로그인제공자 콘솔의 앱 등록·사용 설정·필요한 심사·클라이언트 키·native 설정을 준비한다. 카카오는 앱 KAKAO_NATIVE_KEY와 서버 KAKAO_APP_ID, 플랫폼 서명·복귀 경로를 맞춘다. 네이버는 SDK의 플랫폼별 Client ID·Client Secret·URL scheme 설정을 준비한다. 서버·앱 허용 목록도 함께 반영한다.신규·기존·연결·해제·실패 및 카카오 기존 계정 이전·복구. Apple은 iOS 로그인 구성과 심사 준비에서 먼저 판단한다.
Google Calendar 자동 동기화Calendar API, OAuth scope·필요한 검증·redirect를 준비한다. 서버 GOOGLE_CALENDAR_CLIENT_ID·GOOGLE_CALENDAR_CLIENT_SECRET·GOOGLE_CALENDAR_REDIRECT_URI, CALENDAR_SYNC_CLIENT.재연결·범위 변경의 남은 보완 후 실제 일정 생성·수정·삭제·토큰 갱신·동의 철회를 확인한다. 내부 일정과 파일 내보내기에 이 계약을 요구하지 않는다.
플랫폼 가상계좌 수납별도 제품 결정 후 가상계좌 이용 계약·발급·환불·웹훅 설정을 준비한다. 서버 VIRTUAL_ACCOUNT_PROVIDER와 해당 PG 설정.실제 발급·입금·기한 만료·환불·중복 통지·장부 대조. 현재 주최자 계좌 직접 송금과 함께 켜지 않는다.

계약·키의 공식 기준은 TossPayments API 키 안내와 TossPayments 지급대행 안내를 확인한다. 본인확인은 토스 인증 또는 NICE 아이디에서 적용 상품·계약 조건을 확인한다.

기존 SOS용 SMS 기능은 제품에서 제외되어 첫 출시 외부 계약 목록에 넣지 않는다. 후속 기능별 남은 구현은 후속 기능 준비와 함께 확인한다.

디지털 상품·구독의 결제 방식 결정

마켓 디지털 콘텐츠·앱 기능 구독·기간권은 판매할 상품과 국가별 배포 방식을 기준으로 스토어 결제 적용 여부를 먼저 결정한다. PG 계약만으로 모든 앱 내 디지털 판매가 가능한 것으로 가정하지 않는다. Apple 앱 내 구입 기준과 Google Play 결제 정책의 적용 범위·예외·별도 프로그램 조건을 확인한다.

스토어 결제를 선택하면 해당 유료 판매 계약·세금·정산 계좌·상품 등록을 준비하고 앱 결제와 서버 구매 검증·권한 지급·갱신·해지·환불 연결을 검사한다. 기존 Toss 구현이 스토어 구매 검증까지 제공한다고 표시하지 않는다. 완료 조건: 상품별 결제 경로의 근거, 필요한 구현, 실제 구매·복원·회수 결과가 일치한다. 오프라인 모임 비용의 주최자 직접 수납과 디지털 상품을 한 결제 유형으로 묶지 않는다.

  • 운영 도메인의 개인정보처리방침·이용약관·고객지원·탈퇴 안내를 준비하고 앱과 스토어의 링크를 실제로 연다.
  • 로그인·위치·사진·알림 등 실제 수집·이용·삭제 동작에 맞춰 개인정보 및 데이터 안전성 응답, 권한 설명, 연령 등급과 스크린샷을 작성한다.
  • 심사 계정과 필요한 역할·사용 방법을 제공하고 심사 중 서버에 접속할 수 있게 한다.
  • iOS 로그인 구성과 심사 준비, Android 빌드·Google Play 테스트 절차, 유료 기능이 있다면 디지털 상품·구독의 결제 방식 결정을 완료한다.
  • 검사한 설치 파일과 제출할 앱의 버전·빌드 번호를 맞추고 공개 대상·시점·중단 기준을 기록한다.

업로드 성공·TestFlight 설치·Google Play 내부 테스트·스토어 공개 승인은 각각 다른 상태다. 공개 승인 기준을 충족하고 실제 승인 결과가 있을 때만 공개 완료로 기록한다.

운영자가 남길 완료 기록

운영자 한 사람이 서비스별로 아래 양식을 채운다. 인증·DNS·권한·복구 같은 검증 결과와 비밀 보관 위치를 남기되, 비밀번호·키 본문·토큰·OTP·원문 계좌번호·신분증은 문서에 저장하지 않는다.
