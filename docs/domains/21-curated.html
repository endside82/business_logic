21. 서비스 제공자 배정·정산

호스트가 모임에 강사 등 서비스 제공자를 배정하고, 참가자가 서비스비를 공동 부담하며, 회차 종료 후 제공자에게 정산 지급하는 도메인. 카탈로그 계약은 5% 플랫폼 수수료와 원천징수를 적용하고, 기존 결제·원장 인프라 위에서 동작한다. 배정·결제·정산의 세 단계가 하나의 흐름으로 이어지고, 호스트는 일반 이벤트와 정기모임 어느 쪽에도 제공자를 붙일 수 있다.

기존 모임 도메인(이벤트·정기모임)을 변경하지 않고, 그 위에 제공자 배정·서비스비 분담·정산 흐름을 독립 레이어로 붙인다. 결제 인프라는 그대로 쓰되 서비스 제공자 전용 수익 추적과 분담 계산만 이 도메인이 담당한다. 호스트는 강사·통역사 등 서비스 제공자를 직접 지정해 참가자들이 각자 몫을 내도록 안내하거나, 일부 참가자의 서비스비를 호스트가 직접 대납할 수 있다.

2026-07-29 실제 소스 기준

공개 API는 curated 30개와 provider 19개, 총 49개 엔드포인트다. 데이터는 curated 7개와 provider 5개, 총 12개 엔티티/테이블로 구성된다. 관리자 API에는 심사 큐·상세·승인·거절· 추가자료요청·문서 URL·상품 정지/해제 8개 엔드포인트가 있고, Flutter에는 curated 5화면과 provider 7화면, 관련 라우트 13개가 있다.

현재 앱이 서버 계약을 모두 노출하거나 도달시키는 것은 아니다

과금 화면은 aggregate 금액만 보여 주며 X/D cap·chargeable을 충분히 설명하지 않는다. readiness 경고는 이름·금액 대신 raw userId를 표시하고 provider 지급내역 화면은 없다. 카탈로그 D>0 terms 수락 뒤에는 engagement가 먼저 생겨 계약금 버튼이 사라진다. 무료 제외에는 undo와 참가자 검증 공백이 있고, 정기모임 direct DRAFT 복제에는 재개 API가 없다.

제공자 센터와 카탈로그가 추가된 현재 구조

제공자 등록·검증

프로필과 증빙을 분리 관리한다

개인/사업자 프로필을 만들고 완료된 PROVIDER_DOC 파일을 제출한다. 상태는 NONE, PENDING, NEEDS_MORE_INFO, VERIFIED, REJECTED이며, 사업자번호는 암호화·유일 해시로 저장하고 응답에는 마스킹 값만 보낸다. 본인 숨김·관리자 정지·차단 관계는 공개 조회에서 404로 감춘다.

상품 카탈로그

상품을 고르고 서버 스냅샷으로 배정한다

VEHICLE, VENUE, LABOR, OTHER 상품을 지역·가격모델·가격 범위로 찾는다. ACTIVE 상품만 공개되며 차량/공간은 VERIFIED가 필수다. 배정 시 제공자·출처·상품 제목·카테고리·버전은 서버가 결정하므로 클라이언트가 바꿀 수 없다.

버전형 계약조건

총액 X와 계약금 D를 서로 수락한다

호스트 고정가 또는 제공자 견적을 불변 버전으로 누적한다. 상대방이 최신 버전을 수락해야 확정·과금·정산할 수 있다. 신규 수락은 FEE_V2_5PCT(5.00%)를 스냅샷하며, 기존 0% 계약은 재수락 전까지 그대로 유지된다.

이행·운영

이행 결과와 심사 권한을 따로 기록한다

terms-managed 배정은 FULFILLED 또는 PARTIALLY_FULFILLED여야 정산된다. 관리자는 검증 권한(NR)과 문서 열람 권한(NS)을 분리해 사용한다. 현재 관리자 프런트와 검증 결과 알림 연결, 상품 일정 충돌 검증은 남아 있다.

readiness는 사전 신호이고 실제 settle 게이트는 더 넓다

제공자 정산은 단순히 호스트가 "실행" 버튼을 누른다고 즉시 완료되지 않는다. 사전 readiness는 출석자 coverage 집합과 보장합계만 확인한다. 실제 settle은 여기에 회차 종료, CONFIRMED 상태, 최신 terms 수락, 이행 확인, earning 유효성, 계약금 적용을 더 검증한다. 현재 앱 경고는 미납자의 이름·금액이 아니라 #userId 목록만 보여 주며 전용 조치 CTA는 없다.

4가지 분담 방식

방식누가 내는가환불은 누구에게정산 완납 인정 여부
본인 결제 참가자 본인이 직접 납부 참가자 본인 인정
호스트 대납 호스트가 자기 지갑에서 대납 호스트에게 복원 인정
무료 초대 없음(금전 거래 없이 면제) 해당 없음 인정(면제된 것으로 처리)
노쇼 귀속 선납 참가자가 무단 불참 시 제공자 귀속 노쇼 전환 순간 환불 없음. 정산 전 전액환불은 가능 인정(제공자 수익으로 전환)

단, 호스트가 보장 총액을 설정한 direct 배정과 모든 offering/terms 배정에서는 무료 초대가 허용되지 않는다. 카탈로그 계약에서 무료로 초대하려면 돈이 실제 이동하는 호스트 대납을 사용한다.

운영자가 알아야 할 것

핵심 운영 원칙
  • 신규 카탈로그 계약은 5%다. 수락된 fee policy/rate를 계약에 고정하고, 각 charge/deposit의 gross에서 5%를 뺀 뒤 잔액에 3.3% 원천징수를 적용한다. direct/legacy와 기존 FEE_V1_PASSTHROUGH 계약은 0% 스냅샷을 유지한다.
  • 정산은 호스트가 직접 실행해야 한다. 회차가 종료돼도 호스트가 정산 버튼을 누르기 전까지 지급은 일어나지 않는다. 시스템은 완납 여부를 검증할 뿐이며, 자동 정산은 없다.
  • 미납이 한 명이라도 있으면 정산이 막힌다. 호스트가 그 참가자를 대납하거나, 허용되는 direct 수금액 모드에서만 무료 제외한 뒤 정산을 다시 실행한다. 카탈로그/보장 총액 모드의 무료 제외는 서버가 거부한다.
  • 정기모임 묶음 정산은 회차별로 결과가 개별 반환된다. 일부 회차가 통과되지 않아도 나머지 회차는 정상 처리된다. 통과 안 된 회차는 호스트가 별도 조치 후 재실행한다.
  • 계약금과 서비스비 설정은 동시에 쓸 수 없다. 호스트는 "총 서비스비 설정" 방식 또는 "계약금 선납" 방식 중 하나만 선택한다. 두 가지를 동시에 사용하면 시스템이 거부한다.
  • 제공자 본인은 본인이 배정된 모임의 참가자 서비스비를 낼 수 없다. 자기가 받는 서비스비를 자기가 납부하는 거래는 시스템이 차단한다.
  • path eventId와 assignment owner의 일치 검증은 endpoint마다 같지 않다. confirm/cancel은 서비스에서 assignment의 실제 event 권한을 검사해 권한 상승은 막지만, controller path의 eventId가 같은 event인지 별도로 검증하지 않는다.
  • 무료 제외·대납은 실제 참가자 여부를 서버가 확인하지 않고 되돌리기 endpoint도 없다. 입력 picker만으로 신원을 보장한다고 가정하면 안 된다.
