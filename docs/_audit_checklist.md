## 독자와 정본

제품·운영·기획 독자가 사용자의 행동, 권한과 상태, 실제 결과와 남은 책임을 이해할 수 있게 쓴다. 제품 본문에 서버·앱 계약을 복제하지 않는다. 정확한 기술 식별자가 판단·추적에 필요하면 필요한 만큼 인용하고 원천으로 연결한다. 검증 근거를 없애기 위해 모든 코드 위치·상태 값·수용 기준을 일괄 삭제하지 않는다.

현재 구현은 실제 소스, 제품 결정은 결정 정본, 실행 결과는 버전·환경·관측 결과가 있는 기록으로 판단한다. 과거 메모·사진·시험 수를 현재 계약이나 현재 통과로 쓰지 않는다. 문서 갱신일과 제품 실행일을 구분한다.

## 내용에서 확인할 것

| 관점 | 확인 질문 |
|---|---|
| 실제 입구와 복귀 | 어디서 열고, 누가 무엇을 할 수 있으며, 성공·실패·이탈 뒤 어디로 돌아오는가? |
| 권한과 관계 | 본인·주최자·운영진·참가자·구매자·차단·위임 조건이 실제 명령과 일치하는가? |
| 상태와 결과 | 초안·신청·승인·납부·확정·반환·종료를 섞지 않는가? 응답 유실과 확정 실패가 다른가? |
| 정보와 책임 | 실제 수취인·반환 주체·노출 범위·남은 처리·보존 의무를 읽을 수 있는가? |
| 제한과 공백 | 미판정·현재 결함·위험·실행 미검증·사용자 결정 대기를 구분했는가? |
| 관련 문서 | 이름과 링크가 실제 정본의 문단으로 이동하는가? 폐기된 기능을 현행 입구로 설명하지 않는가? |

도표·본문뿐 아니라 요약·카드·하단 관련 링크·데이터 파일·검색 결과도 같은 설명을 사용해야 한다. 본문을 고치고 옛 카드 설명을 남기지 않는다. 현재 내용과 과거 원문을 함께 보존할 때는 독자가 경계를 알아볼 수 있게 표시한다.

## 문장과 구조

- 실제 행동과 결과를 직접 쓴다. 비유·추상 명사·직역·불필요한 약어를 줄이고 같은 기능을 문서마다 다른 이름으로 부르지 않는다.
- 근거 없는 숫자·기간·성공 보장을 만들지 않는다. 필요한 수치는 기준 버전·상태·시간대·범위와 연결한다.
- 표는 조건 비교나 역할·결과 대응에 쓴다. 단순 입구를 설명하는 두 문장을 표·카드 여러 개로 부풀리지 않는다.
- 시나리오·다이어그램·메트릭·문단·경고의 개수를 정해 채우지 않는다. 복잡한 권한·금전·동시 처리에는 필요한 설명을 충분히 쓰고 단순한 기능은 간결하게 쓴다.
- 수용 기준은 확인 가능한 결과와 근거를 남긴다. 정해진 형식으로 평탄화하거나 기능마다 같은 정상/예외 비율을 강제하지 않는다.
- 상태 이름을 번역해 서로 다른 상태를 같은 말로 합치지 않는다. 독자가 구분해야 할 원형은 한국어 설명과 함께 필요한 위치에 둔다.

## 숫자와 완료 표현

기능 수·등록 확인 항목·상세 시나리오 제목·테스트 파일·실행 건수는 서로 다른 집계다. [시나리오 커버리지](../prd/04_qa_acceptance/scenario_coverage_matrix.md)와 [검증 근거 안내](../prd/04_qa_acceptance/scenario_completeness_audit_2026-08-30.md)를 따른다. 파일 존재·기능 번호·코드 위치 확인만으로 시나리오 통과나 출시 완료를 계산하지 않는다.

소스 병합·빌드·배포·스토어 업로드·설치·실기기 이용·외부 연동·정식 공개는 각각 기록한다. 현재 미해결 총계나 우선순위를 문서마다 따로 만들지 않는다. 같은 근거를 다른 수치로 반복해 진척을 부풀리지 않는다.

## 필요한 증거를 고르는 방법

1. 바뀐 내용과 아직 답하지 못한 질문을 정한다. 기존 소스·문서·검사·실행 기록의 버전과 범위를 확인한다.
2. 변경 없는 근거는 재사용한다. 새 변경·실패·의문이 없으면 같은 소스·전체 로그·이미지를 반복 열지 않는다.
3. 문서 변경은 내용·정본 관계·링크·앵커·생성 데이터 일치를 먼저 검사한다. 동적 표를 바꾸면 실제 행·필터·이동 대상의 문서 동작을 확인한다.
4. 요청 값·권한·저장 상태·횟수·돈 흐름은 해당 소스와 실행 근거로 판단한다. 배치·잘림·대비·이미지 표시처럼 시각 질문이 있을 때만 필요한 화면을 본다. 모든 항목에 큰 글자·다기기·스크린샷 검사를 일괄 추가하지 않는다.
5. 결과에는 확인한 범위·기준 버전·근거 위치·남은 질문을 적는다. 링크나 생성 검사의 통과를 내용 전체 검수로 대신하지 않는다.

## 작업 순서와 마무리

현재 작업 정본과 변경 영향을 따라 범위를 잡는다. 예전 페이지 수·고정된 무게 등급·도메인 순서를 작업량이나 잔여 기간으로 재사용하지 않는다. 독립된 작업을 나누더라도 같은 정본과 공개 사본을 동시에 덮어쓰지 않는다.

기능 정본의 의미를 먼저 대조하고 관련 도메인·정책·HTML·색인·집계를 동기화한다. 수동 교정과 과거 기록을 생성기로 덮어쓰지 않는다. 실제로 바뀐 범위의 검사를 통과한 뒤 새 변경이나 미해결 의문이 있을 때만 추가 확인한다.

마지막에는 원 요청의 문서·산출물·참조·공개 데이터가 모두 포함됐는지 대조한다. 남은 소스 변경·미검수 항목·미반영 사본을 숨기거나 작은 부분의 통과로 전체 완료를 선언하지 않는다. [예외와 경계 사례](../prd/00_prd_items/09_exceptions_edge_cases.md)의 적용 범위와 [릴리즈 증거 확인](../prd/04_qa_acceptance/release_readiness_checklist.md)의 단계 구분을 함께 사용한다.
