F03-02. 이벤트 상세

한 이벤트의 모든 정보를 모아 보여 주는 면이며, 신청 결정이 일어나는 마지막 화면이다. 같은 화면이 사용자 역할(호스트/공동호스트/참가자/비로그인)과 이벤트 상태(임시저장/모집/종료/취소/비공개)에 따라 완전히 다른 의미가 된다. 본 단위는 그 분기를 한 응답 안에서 처리하고, 사용자가 다음 동작 (신청·참석 취소·발행·종료·리뷰)으로 끊김 없이 이어 갈 수 있도록 자리한다.

이벤트 상세는 신청을 받는 면이자 호스트가 운영하는 면이고, 종료된 모임의 회고 자리다. 한 사용자에게는 "신청하기" 버튼이고, 호스트에게는 "수정·종료·취소" 버튼이며, 종료된 참석자에게는 "리뷰 작성·사진첩" 진입점이다. 취소된 모임은 현재 환불 정보를 보여 주는 상세이 아니라 본문 전체를 대체하는 차단 화면이다. 이 분기를 한 응답 안에서 처리하기 위해 서버는 사용자별 맥락(본인의 참석 상태, 신청 상태, 멤버십, 찜 여부)과 액션별 능력플래그를 응답에 함께 넣어 보낸다. 신청·출석·정원 등의 행과 라우트는 이 값을 소비하지만, lifecycle 액션바와 복제 메뉴는 아직 host/co-host identity와 이벤트 유형을 별도로 판정한다.

2026-07-29 소스 재실측 — 유료 승인제 결제 흐름 구현 확인

APPROVED_PENDING_PAYMENT 신청은 상세 응답에서 PENDING_PAYMENT로 변환되고, 결제 금액·기한·결제 필요 여부와 결제 대기 신청 건수가 함께 내려온다. 이 값은 좌석 수가 아니라 신청 row 수라 게스트 동반 신청의 party size를 반영하지 못한다. “결제하고 참석 확정”은 이벤트 선결제 전용 POST /api/v1/events/{eventId}/prepayment/wallet을 호출한다. 서버는 지갑 차감·회계 기록·신청 승인·참석 확정을 한 트랜잭션으로 처리하며, 확정 시 정원이 부족하면 전부 롤백한다.

같은 상세에는 인증 사용자용 GET /fit-preview도 배선돼 있다. 아는 사람과 비슷한 성향은 FEW/SEVERAL 버킷, 단골·초면은 k-익명성 기준을 통과한 10% 단위 비율, 성향 구성은 LOW/MID/HIGH 분포로만 표시한다. 최소 모수에 못 미치면 신호를 숨기고 원인원·원점수는 내려주지 않는다. 호스트 카드도 CLOSED 주최 3개 이상·증거 참석자 15명 이상·재방문율 30% 이상일 때만 “재방문 많은 호스트” 배지를 표시한다.

2026-07-29 상태·권한·lifecycle CTA 소스 재실측

CANCELED는 서버가 full EventVo를 반환한 뒤 Flutter가 역할과 무관하게 AppBlockedState로 조기 반환한다. 본문·더보기·하단바는 없다. CLOSED는 차단이나 흐릿한 overlay 없이 정상 본문에 “종료” badge만 붙고, 참석자에게 후기·피드백 같은 종료 후 행이 열린다.

삭제 상태는 현재 반대로 배선돼 있다. 서버는 host/co-host의 DRAFT만 삭제하지만 Flutter는 DRAFT에 “수정·발행”만 두고 CLOSED에 “삭제”를 둔다. 따라서 DRAFT는 앱에서 삭제할 수 없고 CLOSED 삭제는 400이 된다. 복제도 Flutter는 host-only·PRIVATE 숨김인데 서버는 co-host와 PRIVATE를 허용하고 CLUB_MEETING을 거부한다.

이 화면이 책임지는 4가지 결정

상세 화면 한 장이 동시에 결정해야 하는 것들.

결정 1

지금 사용자가 어떤 행동을 할 수 있는가

본인이 호스트인지, 이미 신청했는지, 정원에 여유가 있는지, 승인이 필요한지에 따라 하단 액션바의 버튼이 결정된다. "참석 신청" / "대기열 등록" / "신청서 작성" / "참석 취소" / "마감" / "수정·종료·취소"(호스트) — 같은 위치 다른 의미.

결정 2

어떤 정보를 가리고 어떤 정보를 보여 줄지

비공개 클럽 이벤트라면 비멤버에게는 본문·플랜·사진첩을 가린다. 임시저장 이벤트라면 호스트와 공동호스트만 화면에 들어올 수 있다. 정보 공개의 경계가 본 화면에서 정해진다.

결정 3

다음 단위로 어떻게 이어지는가

신청은 F03-05로, 호스트 액션은 F03-04로, 사진첩은 F03-09로, 플랜은 F03-10으로, 리뷰는 11 리뷰 도메인으로 분기된다. 본 화면은 각 단위의 진입점만 책임지고 실제 동작은 위임한다.

결정 4

외부 캘린더로 어떻게 내보낼지

더보기 메뉴의 "캘린더 추가"와 ".ics 다운로드"는 사용자가 직접 자기 캘린더 앱에 일정을 옮길 수 있게 한다. 일정 변경이 일어나면 푸시 알림이 가지만, 사용자가 한 번 외부로 내보낸 일정의 자동 동기화는 제공하지 않는다.

사용자 시나리오

기본 흐름

일반 사용자가 모집 중 이벤트 상세에 진입

탐색·홈에서 카드를 누르면 썸네일·일정·정원·가격·호스트 카드·설명·연결 플랜·유사 이벤트가 한 화면에 모인다. 하단 액션바에 "참석 신청"이 활성된다.

이 흐름이 남기는 것 — 신청 결정 직전 사용자가 가장 길게 머무르는 면. 상세에서의 이탈률이 추천 카드 품질의 직접적 신호.

호스트 진입

호스트가 자기 이벤트 상세에 들어옴

같은 화면이지만 DRAFT 액션바는 "수정·발행", OPEN은 "수정·종료·취소"로 교체되고 상단에 "주최자 화면입니다" 배너가 뜬다. CLOSED에는 현재 서버가 거부하는 "삭제"가 잘못 노출된다. 더보기에는 공지와, PRIVATE가 아닌 경우 "이 이벤트로 새로 만들기"가 추가된다. 신청서 관리·정원 설정·참석자·대기열·모임 정산 진입점도 capability에 따라 본문에 노출된다.

이 흐름이 남기는 것 — 호스트가 자기 이벤트를 운영하는 모든 진입로가 이 한 화면에 모인다. 호스트는 별도 관리 화면 없이 사용자 시점과 같은 면에서 운영.

가입 전

비로그인 사용자가 공유 링크로 진입

카카오 공유 등의 외부 링크를 누른 비로그인 사용자가 도착한다. 일반 정보는 모두 보이지만, "참석 신청"과 "찜"을 누르는 순간 로그인 화면으로 이동한다. 로그인 후 같은 이벤트로 자동 복귀한다.

이 흐름이 남기는 것 — 공유 링크의 가치가 가입 전환으로 이어지는 핵심 경로.

임시저장

일반 사용자가 임시저장 이벤트의 식별자로 진입

호스트와 공동호스트가 아니면 임시저장 이벤트는 "이벤트를 찾을 수 없습니다"로 처리된다. 모집 시작 전 이벤트의 존재 자체를 외부에 노출하지 않는다.

이 흐름이 남기는 것 — 호스트가 폼을 완성하기 전에 외부 노출되는 일을 막아 "초안인데 신청자가 들어왔다"는 사고를 방지.

종료 후

참석했던 모임이 종료됨

화면은 흐리거나 차단하지 않는다. 정상 본문에 "종료" badge가 붙고 신청 CTA만 마감 상태가 된다. 대신 "후기 작성", "함께한 사람 고르기", 사진첩이 살아난다 — 본인이 참석 확정 상태였던 사용자에 한해.

이 흐름이 남기는 것 — 모임이 끝난 뒤에도 사용자가 다시 들어오게 만드는 두 가지 가치(후기·사진첩)의 진입로.

취소 후

호스트가 취소한 이벤트

빨간 badge나 흐릿한 원문을 보여 주지 않는다. 응답 직후 "취소된 모임이에요"라는 AppBlockedState로 화면 전체를 교체해 hero·본문·환불 정책·더보기·하단바가 모두 사라진다. host/co-host도 같은 차단 화면을 본다.

이 흐름이 남기는 것 — 서버에는 full 상세가 내려오지만 사용자는 취소 사실만 확인한다. 환불/운영 정보를 이 화면에 둘지 정책 결정이 필요하다.

비공개 클럽

비멤버가 클럽 비공개 이벤트로 진입

제목·시간은 보이지만 본문·연결 플랜·사진첩은 가려진다. 그 자리에 "이 이벤트는 클럽 멤버만 볼 수 있습니다 + 클럽 가입" 안내가 뜬다.

이 흐름이 남기는 것 — 클럽 전용 콘텐츠의 가치를 보호하면서, 가입 전환의 여지(클럽 가입 CTA)를 같은 화면 안에 둔다.

캘린더 내보내기

참석 예정자가 .ics 파일을 내보냄

더보기 메뉴 → ".ics 다운로드"를 누르면 시스템 공유 시트가 뜨고, 사용자가 캘린더 앱이나 메일로 보낼 수 있다. 일정 변경 시 별도 알림이 가지만, 외부 캘린더의 자동 갱신은 제공 안 함 — 사용자가 직접 한 번 더 내보내야 한다.

화면에서 사용자가 인지하는 것

영역사용자가 보는 것그 자리에 둔 이유
썸네일 + 상태 배지 큰 이미지. 좌상단 뒤로가기, 우상단 더보기·찜 하트. 정상 본문에서는 모집/종료/임시저장 배지. CANCELED/HIDDEN은 이 영역 전에 차단. 이벤트의 현재 상태를 먼저 인지하지 못하면 사용자가 "신청 가능한 것"으로 오해한 채 액션바를 누른다.
일정·장소·정원·가격 시작/종료 시각, 주소(또는 온라인 URL), 정원(현재/전체), 가격. 신청 결정의 4대 단서. 카드 단계에서 본 정보를 상세에서 한 번 더 확인하게 해, 진입한 사용자가 즉시 다음 단계로 갈 수 있도록.
호스트 카드 호스트 닉네임 + 신뢰점수. 조건을 만족하면 “재방문 많은 호스트” 배지. 공동호스트가 있으면 함께 표시. 모임의 신뢰는 호스트의 신뢰. 누가 운영하는지 보이지 않으면 신청 결정의 마지막 한 걸음이 안 떨어진다.
설명 3줄 미리보기 + "더보기". 비공개 클럽 + 비멤버일 때는 가림. 모임의 결정적 단서는 호스트 본인이 쓴 텍스트인 경우가 많다. 너무 길면 사용자 결정이 지연되므로 우선 3줄.
환불 정책 안내 유료 + 사전결제 이벤트일 때만 노출. 환불 가능 기한과 환불율을 한 문단으로. 환불 조건을 신청 전에 사용자가 알지 못하면 취소 시점에 분쟁이 발생한다. 본 화면이 "사전 공지"의 책임 자리.
연결 플랜 가로 스크롤 카드. 호스트가 연결한 진행 자료. 활성 항목만 표시. "이 모임에서 무엇을 하는가"를 시각화. 결정 단서로 작동.
유사 이벤트 최대 5장 미리보기 + "더보기". 0건이면 빈 상태 안내만. 이 모임이 마음에 안 들어도 비슷한 다른 모임으로 사용자를 잡아 두는 자리.
하단 액션바 일반 사용자는 참석/대기/결제 CTA. host/co-host는 DRAFT "수정·발행", OPEN "수정·종료·취소", CLOSED "삭제"(현재 서버 계약과 불일치). 같은 화면 같은 위치에 한 가지 다음 동작만 보여 줘, 사용자가 결정을 미루지 않게 한다.
호스트 운영 메뉴 host/co-host와 club operator에게 capability별로 다르게 보임. 신청서는 host/co-host, 정원은 host/co-host/OWNER/ADMIN, 출석·모더레이션은 flag별. 역할명 하나가 아니라 서버가 실제로 허용하는 액션 단위로 운영 동선을 열기 위해.
"모임 정산" 진입 (2026-06-05 신설) 호스트와 참석 확정자에게 항상 보이는 메뉴. 정산이 아직 없으면 참가자는 "아직 정산이 없어요" 빈 화면, 호스트는 "정산 만들기" 버튼을 만난다. 그동안 참가자가 정산 화면으로 가는 길은 알림뿐이었다 — 이 입구가 정산 준비 과정을 스스로 찾아보는 공식 경로다 (F07-04).
자동 승급 강조 대기열에서 자동으로 참석 확정된 사용자에게 1회성 "참석 확정!" 강조. 자동 상태 전환은 사용자가 인지하기 어렵다. 한 번이라도 명확히 보여 줘야 "내가 뭘 했더라"의 혼란을 막는다.

운영자가 알아야 할 것

상세 화면이 만드는 비즈니스 결정점
  • 삭제 CTA는 현재 서버와 상태가 반대로 연결돼 있다. 서버는 host/co-host의 DRAFT만 삭제할 수 있지만, 앱은 DRAFT에 삭제가 없고 CLOSED에 삭제를 보여 준다. 유효 삭제 경로를 DRAFT에 옮기고 CLOSED에서는 제거해야 한다.
  • 다음 회차 gate도 역할·유형이 뒤집혀 있다. 서버는 host/co-host의 INDEPENDENT/PRIVATE를 허용하고 CLUB_MEETING을 거부한다. Flutter는 host-only이며 PRIVATE를 숨기는 대신 CLUB_MEETING에는 메뉴를 노출한다.
  • 역할·상태별 액션바 분기가 풀리면 신청·환불 분쟁이 즉시 발생한다. 본인 상태(참석/대기/심사/승인 후 결제 대기)와 이벤트 상태(모집/종료/취소)의 조합이 모두 분기되어 있는지가 본 화면의 안전 기준선.
  • 임시저장 이벤트는 호스트/공동호스트가 아닌 사용자에게 보이지 않는다. 초안 이벤트의 식별자가 외부로 새 나가도 비호스트는 "찾을 수 없습니다"로 처리된다.
  • 비공개 클럽 이벤트에서 비멤버에게 본문·플랜·사진첩을 가리는 가드가 본 화면의 책임. 가드가 풀리면 클럽 전용 콘텐츠가 노출되어 가입 가치가 사라진다.
  • 유료 승인제 이벤트의 액션바 라벨은 "심사 중 → 결제 필요 → 참석 확정"의 세 단계가 분명히 구분되어야 한다. 승인 즉시 결제로 넘어가는 회귀가 일어나면 환불 분쟁이 발생한다. (자세한 흐름은 F03-05·F03-06로 위임.)
  • 정원 설정은 서버 canManageCapacity가 단일 기준이다. 호스트·공동호스트·클럽 ADMIN/OWNER에게만 상세 진입 행과 라우트가 함께 열린다.
  • 결제 만료는 서버에서 fixedDelay 5분 스케줄러가 확정한다. Flutter는 기기 시계상 기한이 지나면 즉시 CTA를 막지만, 선결제 API 자체에는 기한 비교가 없어 정상 운용 시 약 다음 주기 내외의 soft grace가 있다. 실행 지연·실패가 가능해 5분은 하드 상한이 아니다. 하드 마감이 필요하면 서버 인라인 검증이 필요하다.
  • 결제 대기 수는 예약 좌석 수가 아니라 신청 건수다. 서버의 실제 정원 hold는 party size 합계이므로, 게스트 동반 신청이 있으면 앱의 만석 계산이 좌석을 과소 계상할 수 있다.
  • 외부 캘린더 내보내기는 자동 동기화하지 않는다. 일정 변경 시 푸시는 가지만, 사용자가 한 번 .ics를 내보낸 뒤의 자동 갱신은 제공 안 함 — 운영 측이 이 한계를 사용자 안내에 반영해야 한다.
  • "이 이벤트로 새로 만들기"는 빈 생성 폼 prefill이 아니라 서버 deep-copy다. 빈 body를 보내면 원본 시작시각 +7일과 같은 duration으로 새 DRAFT를 만들고 편집 화면으로 이동한다. 오래된 원본은 계산된 시작이 과거여서 실패할 수 있고, 참가자·결제·정산·후기·사진은 이관하지 않는다.

측정해야 하는 것

상세 화면이 정상이라고 부르려면
  • 상세 진입 → 신청 전환율 — 카드 품질이 아니라 상세의 정보 조합이 결정에 어떻게 작용하는지의 지표.
  • 비로그인 → 상세 진입 → 로그인 전환율 — 가입 전 사용자의 신청 의사가 본 화면에서 실제 가입으로 이어지는 비율.
  • 비공개 클럽 이벤트의 비멤버 진입 → 클럽 가입 전환율 — 본 화면의 클럽 가입 안내 카피가 실제 가입 의사를 만드는지 측정.
  • 호스트의 "이 이벤트로 새로 만들기" 사용 빈도 — 정기 호스트가 도구를 실제로 활용하는지의 신호. 낮으면 진입점 노출 위치 점검 필요.
  • 승인 후 결제 대기 상태에서 결제 미완료 비율 — 유료 승인제 이벤트의 가장 중요한 누수 지점. 결제 기한·결제 안내의 적합성을 직접 측정.
