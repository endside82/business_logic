F03-20. 이벤트 노쇼 관리

이벤트가 끝난 후, 참석 확정됐지만 나타나지 않은 사람을 기록하고 그 결정에 이의를 제기할 수 있게 한다. 호스트의 확정 → 참가자의 소명 → 결정 뒤집기로 이어지는 3단계 절차와, 노쇼 확정 후 사정이 생긴 경우 호스트가 부분 환불을 줄 수 있는 사후 조정 환불이 이 단위의 두 축이다.

설계 의도 — 호스트 기록이 최종이 아니다

이벤트 당일 연락 없이 불참했다는 사실은 호스트가 가장 잘 안다. 그래서 확정 권한은 호스트에게 있다. 그러나 호스트가 체크인을 놓쳤거나 참가자에게 예외적 사정이 있었을 수 있다. 때문에 확정된 노쇼에 대해 참가자가 소명할 수 있고, 호스트나 운영팀이 뒤집을 수 있다. 뒤집힌 노쇼는 제재 누적 카운트에서 제외된다. 회원은 정정 체크인도 생성되어 체크인 기반 공동참석 증거에 다시 포함되고, 원래 노쇼 기록은 감사 목적으로 남는다.

2026-07-29 current source 실측

서버 5개 노쇼 endpoint와 Flutter API 정의 5개가 대응한다. 참석자 목록의 NoShowManageSection은 일괄 확정·번복만 맡고, 단일 확정은 분쟁 상세의 호스트 액션 시트가 회원 targetUserId를 보내는 별도 경로다. 번복된 회원에게 기존 체크인이 없으면 서버가 method=NOSHOW_OVERTURN 정정 체크인을 한 번만 생성한다. 환불 확인 대기 제외는 일괄 확정에만 적용되고, 단일·일괄 모두 이벤트 종료시각을 서버에서 검사하지 않는다.

사용자 시나리오

기본 흐름 — 호스트

이벤트 후 체크인 안 한 참가자를 노쇼로 기록

참석자 목록의 노쇼 관리 섹션에서는 체크인하지 않은 인원을 일괄 확정하고, 이미 확정된 노쇼를 번복할 수 있다. 한 명을 사유·증빙과 함께 확정하는 current UI는 참석자 행이 아니라 분쟁 케이스 상세의 호스트 액션 시트에 있다. 이 호출부는 회원 userId만 보내므로 게스트 attendanceId 단일 확정 UI는 아직 없다.

이 흐름이 남기는 것 — 노쇼 기록은 이후 제재 카운트 근거로 남는다. 사유와 증거를 함께 남기면 소명 단계에서 판단 근거가 된다.

참가자 — 소명

불가피한 사정이 있었는데 노쇼로 기록됐다

회원 참가자는 노쇼 안내의 "소명할게요"를 눌러 canonical caseId가 포함된 통합 분쟁 이의제기 화면으로 이동한다. 소명 진행 중에는 제재 누적이 여전히 유지되지만, 운영팀 또는 호스트가 뒤집으면 누적에서 제외된다.

이 흐름이 남기는 것 — 노쇼로 기록되면 앱의 소명 CTA로 참가자가 직접 소명할 수 있다(2026-06-06 W14-S2 배선 완료). 서버는 EVENT_NO_SHOW:{noShowId} 형식을 강제한다. 게스트 노쇼는 서버상 예매 소유자가 소명할 수 있지만 현재 앱 CTA가 회원 row만 고르는 Gap이 남아 있다. 또한 CONFIRMED이면 7일이 지나도 CTA가 계속 보여, 제출할 때 서버가 기한 초과로 거절한다.

뒤집기

호스트가 체크인을 놓쳐서 잘못 기록됐다

호스트가 직접 또는 운영팀이 개입해 "노쇼 아님"으로 뒤집을 수 있다. 뒤집기 사유를 입력하면 해당 노쇼 기록은 제재 카운트에서 빠진다. 회원에게는 기존 체크인이 없을 때 NOSHOW_OVERTURN 정정 체크인이 함께 생겨 공동참석·핏·재방문 증거에도 복권된다. 게스트는 계정 기반 증거 주체가 아니어서 정정 체크인을 만들지 않는다. 기록 자체는 감사 목적으로 남아 있다.

사후 조정 환불

노쇼이지만 호스트가 부분 환불을 주기로 했다

서버 상한은 원 결제의 유료+무료 총액에서 이미 완료된 일반/선결제 환불을 뺀 잔액이다. 양수 환불은 원 결제의 유료·무료 비율대로 나뉘어 지갑에 복구되고 정산 claw-back 경로를 거친다. 0원도 허용되어 돈 이동 없이 감사 row만 남길 수 있다.

현재 제약 — 서비스는 대상 신청에 실제 노쇼 row가 있는지 검사하지 않는다. 화면의 유일한 caller도 원 결제액을 조회하지 않아 paidAmount=0으로 진입하고, 서버 상한만 최종 방어로 남는다.

제재 연계

같은 사람이 여러 번 노쇼가 됐다

노쇼 카운트는 일정 기간 내 누적으로 집계되고, 소유 게스트의 노쇼도 예매자에게 합산되며, 뒤집힌 건은 빠진다. 이 서비스는 정책 입력용 카운트만 제공한다. 자동 제재 기준과 실제 grant/enforcement는 이 서비스에 구현돼 있지 않다.

운영자가 알아야 할 것

운영 주의사항
  • 환불 확인 대기 중인 참가자는 노쇼 확정 대상에서 제외된다. 계좌이체 취소 후 호스트의 환불 확인을 기다리는 참가자는 일괄 확정 목록에 포함되지 않는다. 단, 단일 확정 API는 application 상태를 검사하지 않아 같은 보호가 적용되지 않는다.
  • 같은 참가자를 노쇼로 두 번 확정해도 한 건으로만 기록된다. 실수로 두 번 눌러도 기존 기록이 그대로 유지되며 중복 기록이 만들어지지 않는다.
  • 소명 기한은 노쇼 확정 후 7일이다. 7일이 지난 노쇼는 소명할 수 없다(요청 거부). 서버가 계산한 소명 가능 여부와 마감 시각을 앱이 받아, 기한이 지나면 소명 버튼 대신 만료 안내를 표시한다.
  • 사후 조정 환불은 paid+free 원결제 총액에서 기존 완료 환불을 뺀 잔액을 초과할 수 없다. 초과 금액 입력 시 서버가 거부한다. 환불금은 원결제의 유료·무료 비율대로 나뉘어 지갑에 각각 입금되므로 무료 포인트 몫이 유료로 바뀌지 않는다.
  • 같은 신청 건에 대해 환불을 두 번 제출할 수 없다. application row를 잠근 뒤 기존 기록을 확인해 동시 요청도 직렬화한다. 다만 no_show_refund.application_id 자체에는 DB UNIQUE가 없다.
  • 환불 성공이 참가자 알림 발송을 뜻하지 않는다. current source에는 notification/outbox 호출이 없고, 화면의 “참가자에게 안내됩니다” 문구만 남아 있다.

레드 플래그

자주 발생하는 케이스
  • 회원 참가자는 앱에서 직접 소명할 수 있다. 참석자 목록의 본인 상태 카드에서 통합 분쟁 이의제기 화면으로 이동한다. 호스트·권한 있는 공동호스트·클럽 운영진은 별도 노쇼 관리 섹션에서 일괄 확정과 뒤집기를 처리한다. 회원 CTA는 서버의 가능 여부·마감 시각과 일치하도록 보강됐다. 소유 게스트 row의 CTA와 게스트 소명 정책은 아직 결정되지 않았다.
  • 체크인 관리 권한이 없는 공동호스트는 노쇼를 확정할 수 없다(2026-06-06 수정 완료). — 체크인과 노쇼가 같은 권한 가드를 공유하도록 통합해, 체크인 관리를 맡기지 않은 공동호스트의 노쇼 확정·뒤집기가 차단된다. 그러나 사후 환불은 별개로, canHandleRefundIssue를 검사하지 않아 공동호스트 row만 있으면 실행할 수 있다.
  • 노쇼 환불을 이미 줬는지 앱에서 확인할 수 없다 — 제출 이력 조회 화면이 없어 호스트가 같은 참가자에게 중복으로 시도할 수 있다. 중복 제출 자체는 시스템이 차단하므로 돈이 두 번 나가지는 않는다.
  • 환불 GET은 객체 권한 검사가 없다. 전역 인증은 요구하지만 controller가 principal과 path eventId를 쓰지 않고 applicationId만 조회한다. 다른 신청 ID를 아는 인증 사용자가 타 이벤트 환불 정보를 읽을 수 있는 IDOR/BOLA 후보이므로 앱 조회 배선보다 서버 보완이 먼저다.
  • “노쇼 환불”이 실제 노쇼에 결박되지 않았다. 환불 서비스는 application과 event 일치만 확인하고 EventNoShow row의 존재·상태를 조회하지 않는다. 노쇼가 없는 신청도 처리될 수 있고, 확정·소명·뒤집힘 중 어떤 상태를 허용할지도 강제하지 않는다.
  • 환불 화면의 실제 진입 데이터가 불완전하다. 참석자 목록 long-press 진입은 없고, 유일한 분쟁 상세 caller는 ATTENDANCE/CHECK_IN sourceId도 applicationId로 그대로 사용한다. 원 결제 조회 없이 paidAmount=0으로 열려 금액 표시와 client 상한도 무력화된다.
  • 이벤트 종료 전에도 확정 요청이 통과할 수 있다. 단일·일괄 서비스와 관리자 버튼 모두 종료시각을 강제하지 않는다. 운영 문구는 "이벤트 종료 후"이지만 현재 서버 불변식은 아니다.
  • URL의 eventId와 noShow row의 이벤트가 같은지 검사하지 않는다. 소명·번복은 noShowId의 실제 이벤트/소유권으로 권한을 검사하므로 타 이벤트 권한 우회는 아니지만, 잘못된 path로도 처리가 가능해 자원 식별 의미가 어긋난다.
  • 환불 후 자동 알림·통합 케이스 생성은 구현돼 있지 않다. 서버는 HOST_ACTION_REVIEW-{UUID} 문자열만 환불 row에 저장하고, notification outbox나 조회 가능한 별도 dispute case row를 만들지 않는다.
