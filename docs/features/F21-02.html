F21-02. 참가자 서비스비 분담 결제

호스트가 총 서비스비를 설정하면 참가자 각자가 본인 몫을 직접 납부하는 흐름. 회차가 끝나기 전에는 각자 자유롭게 개별 납부하고, 회차 종료 후에는 시스템이 출석 인원으로 나눈 정확한 내 몫을 자동 계산해 표시한다. 서버는 같은 Idempotency-Key 재시도를 한 번만 처리하지만, 앱은 현재 액션 호출마다 새 키를 만든다.

설계 의도 — 내 몫은 클라이언트가 계산하지 않는다

"내 몫 납부"는 참가자가 직접 금액을 입력하는 것이 아니다. 회차가 종료되어 실제 출석 인원이 확정되면, 시스템이 총 서비스비를 출석 인원 수로 나눈 정확한 금액을 계산해 참가자에게 알려 준다. 참가자는 그 금액을 확인하고 납부 버튼을 누르기만 하면 된다. 회차 종료 전에도 개별 납부는 가능하지만, 이때는 자신이 납부하는 금액을 직접 입력한다 — 단, 전체 총액을 초과하는 납부는 거부된다.

2026-07-29 현재 소스 갱신 — 계약 총액·수수료

카탈로그 배정은 최신 계약조건이 수락돼야 과금할 수 있다. 서버 상태 응답은 계약 총액 X와 참가자 상한(X 또는 계약금이 있으면 X−D)을 분리하지만, 현재 Flutter 모델이 두 필드를 받지 않아 화면은 engagement에서 0인 serviceFeeGross를 총액으로 표시한다. 신규 카탈로그 계약은 각 charge/deposit마다 5.00% 플랫폼 수수료를 먼저 빼고, 잔액에 3.3% 원천징수를 적용한다. direct/기존 0% 스냅샷은 유지된다. 이벤트 상세의 진입 CTA는 CONFIRMED와 chargeable을 보지만, 결제 화면 자체는 직접 진입 시 이 값을 사용해 버튼을 닫지 않는다.

서비스비 납부가 이루어지는 두 방식

회차 종료 전 납부

각자 자유롭게 개별 납부

참가자가 원하는 금액을 직접 입력해 언제든 선납할 수 있다. 납부 금액의 합이 총 서비스비를 초과하면 거부된다. 이 방식은 확정된 내 몫이 산출되기 전이라 납부 금액을 본인이 결정해야 한다.

주의 — 회차 종료 후 실제 출석 인원이 확정될 때까지 정확한 "내 몫"은 알 수 없다. 선납 뒤의 부족분을 서버가 따로 산정해 주지는 않으며, 기존 first charge가 있으면 내 몫 API는 거부된다. 추가 납부는 사용자가 금액을 넣는 top-up 경로다.

회차 종료 후 내 몫 납부

시스템이 계산한 내 몫 그대로 납부

회차가 종료되면 실제 출석 인원(제공자 본인 제외)이 확정된다. 시스템이 참가자 상한(X 또는 X−D)을 그 인원수로 나눠 각 참가자의 몫을 산출하고, 아직 first charge가 없는 참가자는 그 금액을 그대로 납부한다. 금액 입력 없이 확인 후 납부 버튼만 누른다.

이 흐름이 남기는 것 — 모든 참가자가 동일 조건으로 정확한 몫을 내게 돼, "나는 얼마 내야 해?"라는 혼란 없이 납부가 마무리된다.

납부와 동시에 제공자 수익이 적립된다

참가자가 납부를 완료하는 순간, 그 금액이 제공자의 수익으로 즉시 기록된다. 정산이 완료된 뒤 일괄 기록하는 게 아니라, 납부 시점에 바로 제공자 미수금이 줄어든다. 이 덕분에 정산 시점에서의 수익 계산이 정확하다.

사용자 시나리오

기본 흐름

모임 참가자가 서비스비 납부 안내를 받음

피트니스 모임에 참가한 사용자가 이벤트 상세에서 "서비스비 납부" 버튼을 발견한다. 회차가 아직 진행 중이라 내 정확한 몫은 표시되지 않고, 납부하려면 금액을 직접 입력해야 한다. 모임이 끝난 뒤 사용자가 다시 상세에 들어오니 시스템이 계산한 "1인당 15,000원" 내 몫이 표시된다. 확인 후 납부 버튼을 누른다.

이 흐름이 남기는 것 — 참가자는 복잡한 계산 없이 시스템이 알려 주는 금액만 확인하면 된다.

내 납부 현황 조회

현재 화면은 합계만 보여 준다

참가자 화면은 myPaidAmount 합계와 서버 산정 분담액을 표시한다. 개별 납부 일시·행 목록과 남은 금액은 응답/화면에 없으며, 계약금 모드의 X·X−D 필드도 현재 Flutter 모델에서 유실된다.

현재 제약 — 여러 번 납부한 상세와 정확한 잔여액을 이 화면만으로 확인할 수 없다.

이중 납부 시도

납부 버튼을 실수로 두 번 눌렀을 때

네트워크 지연으로 같은 납부 요청이 두 번 전송되거나, 사용자가 실수로 버튼을 두 번 눌렀을 때 동일한 Idempotency-Key로 재시도되면 서버가 첫 결과를 재사용한다. 하지만 현재 앱 repository는 각 액션 호출에 새 UUID를 만들기 때문에, 서로 다른 탭 호출 전체를 같은 요청으로 묶는 상태는 유지하지 않는다.

현재 안전선 — 첫 과금은 beneficiary 중복 가드도 있지만 top-up 재시도는 동일 키 재사용을 클라이언트가 보장해야 한다.

총액 초과 납부 시도

참가자가 총 서비스비를 초과하는 금액을 납부하려 함

현재까지 모인 납부 합계와 지금 납부하려는 금액의 합이 총 서비스비를 넘으면 시스템이 거부한다. 공통 에러 안내가 표시된다. 현재 에러 응답에는 잔여액 payload가 없고 Flutter도 실제로 추가 납부 가능한 금액을 계산해 보여 주지 않는다.

제공자가 납부 시도

제공자 본인이 자기 몫을 납부하려 함

제공자가 같은 모임에 참가자로도 참여하고 있는 경우, 자기 배정과 연결된 서비스비를 자기가 납부하는 거래는 시스템이 차단한다. 서비스를 제공하면서 그 서비스비를 본인이 내는 구조는 허용되지 않는다.

화면에서 참가자가 인지하는 것

표시 항목사용자가 보는 것그 자리에 둔 이유
서비스비 납부 진입 이벤트 상세 화면에서 참석 확정자에게만, 그리고 실제로 납부할 서비스비가 있는 경우에만 버튼이 표시된다. 참석 확정 전이거나 납부 대상이 아닌 참가자에게 납부 버튼이 보이면 혼란을 준다.
회차 종료 전 serviceFeeGross와 내 aggregate 납부액. 금액 직접 입력 납부·top-up 버튼. 회차 종료 전에도 일찍 납부하고 싶은 참가자를 위한 기능. 내 확정 몫은 아직 표시 안 함.
회차 종료 후 "내 몫: 15,000원" 형태의 시스템 계산 금액과 my-share 납부 버튼. 기존 first charge가 있으면 서버가 거부. 계산을 시스템이 해 주므로 참가자가 직접 나눗셈할 필요 없음.
내 납부 합계 myPaidAmount aggregate만 표시. 개별 금액·일시 목록과 잔여액은 없음. 현재 응답/화면이 제공하는 정보의 경계. 이력·잔여액은 후속 대상.

운영자가 알아야 할 것

핵심 운영 원칙
  • 내 몫 계산은 회차 종료 후에만 확정된다. 다만 my-share는 전체 1인 몫의 첫 과금 경로다. 기존 선납의 부족분을 자동 산정·충전하지 않으며 그 경우 별도 top-up을 사용한다.
  • participant cap을 초과하는 납부는 시스템이 차단한다. cap은 direct X 또는 계약금 계약 X−D다. 현재 에러에는 잔여 납부 가능 금액이 포함되지 않는다.
  • 납부와 동시에 제공자 수익이 서버에 기록된다. 정산 완료 후 일괄이 아니라, 각 납부가 일어날 때마다 earning이 만들어진다. 다만 현재 제공자 앱 화면에는 예상 수익·지급 상태를 확인하는 UI가 없다.
  • 동일 Idempotency-Key 재시도만 서버가 한 번으로 묶는다. 현재 앱은 액션마다 새 키를 발급하므로 재시도 키를 화면 상태로 보존하는 보완이 필요하다.
  • 완료 알림은 현재 없다. 참가자 납부 진입은 이벤트 상세의 상태 조회에 의존하며, 모임 종료 후 별도 납부 요청 알림을 발행하는 curated 경로는 확인되지 않았다.
  • 직접 route는 실패할 CTA를 노출할 수 있다. 결제 화면이 chargeable·coverage·cap으로 자체 분기하지 않아 서버가 최종 방어선이다.
