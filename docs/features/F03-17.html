차량 좌석 배치도 운영

좌석표 편집·실물 확인 기록·별도 활성화·사용 후 원본 보호·복제/삭제와 합성 자료/제조사 후보/공개 도면을 구분한다. 2026-11-22 소스 대조이며 새 실행 결과와 구분합니다.

결론

운영자는 배치도를 만들거나 복제해 좌석표를 편집하고, 실제 이용할 차종·자료·확인 내용을 기록한 뒤 별도로 사용을 시작한다. 좌석표 편집기·확인 기록 저장·삭제 명령은 현재 구현돼 있다. 이미 사용된 원본은 수정·삭제하지 않고 복제본으로 새 구성을 준비한다.

합성 기본 자료 9종, 제조사 자료를 참고한 후보, 확인 완료·활성 도면은 다른 상태다. 기본 데이터가 존재한다는 이유만으로 실제 차량에 바로 쓸 수 있다고 판정하지 않는다. 좌석 지정 전환과 차량별 배정은 대절 버스 문서의 좌석 지정·해제·다른 배치도로 전환을 따른다.

입구와 읽기·쓰기 권한

관리자 메뉴 ‘차량 좌석 배치도’는 /vehicle-layouts로 연결된다. 로그인 상태와 MANAGE_EVENT 읽기 권한에서 목록을 조회하고, 쓰기 권한에서 생성·복제·편집·확인·활성화·삭제 버튼을 제공한다. 서버는 목록/상세에서 READ, 변경에서 WRITE를 검사한다. AdminPrincipal의 권한 제한을 사용하지 않는 관리자 분기는 그 내부 정책을 따르며, 화면의 버튼 제한만으로 서버 권한을 대신하지 않는다.

목록·상세에는 승객 정원, 활성 여부, 사용 이력 여부 inUse, 차량 종류·모델·출처·참고 내용, 확인 시각, 도면 개정, 최초 사용 시각이 있다. 목록의 등록 칸 수와 승객 정원을 혼동하지 않는다. 상세에는 좌석표가 함께 있다.

inUse는 현재 참조 차량의 존재뿐 아니라 firstUsedAt도 포함한다. 차량이 다른 도면으로 옮긴 뒤에도 이전 원본의 이름·좌석·확인 내용을 바꾸거나 삭제할 수 없다. 실제 좌석 전환은 새 도면과 이전 도면의 최초 사용을 기록하므로 과거 배정 근거가 남는다.

새 이름은 100자 이내의 비공백 값, 설명은 선택적으로 500자 이내다. 이름 중복은 사전 검사와 DB 유일 제약으로 거절한다. 복제에서 설명을 생략하면 원본 설명을 사용한다. 원본과 복제본은 서로 다른 사용·확인 이력을 갖는다.

좌석표 편집과 정원 계산

웹의 ‘좌석표 편집’은 비활성·미사용 도면에서 열린다. 표에서 자리 번호·줄·칸·종류·선택 가능 여부를 바꾸고 자리를 추가·삭제한다. 미리 보기는 차량 앞을 위로 두고 빠진 줄·칸을 빈 공간으로 유지한다. 사진 위에 좌석을 그리는 기능으로 설명하지 않는다.

서버 좌석표 입력은 1~300칸, 번호 1~10자, 앞뒤 공백 없음, 줄 0~29·칸 0~9다. 번호와 좌표가 중복되면 거절한다. 종류는 NORMAL·DRIVER·GUIDE·FOLDABLE·DISABLED·AISLE이며 빈 종류는 NORMAL로 정규화한다. DRIVER·AISLE·DISABLED는 승객이 선택할 수 없다. 승객 정원은 별도 요청 숫자가 아니라 유효한 선택 가능 칸에서 계산한다.

좌석표 초안 저장과 실물 확인의 기준은 다르다. 서버는 초안에서 운전석 하나·최종 차종별 정원을 모두 확정하지 않고, 확인·활성화 시 운전석 정확히 하나, 승객 1명 이상, CAR 최대 99·BUS 최대 100, 선언 정원과 계산 정원 일치를 검사한다. 앱의 실제 적용에서도 같은 핵심 구조를 재검사한다.

웹은 저장 전 중복·좌표·선택 불가 종류와 승객 0명을 미리 막으며 오류를 표시한다. 서버 최종 판정을 대체하지 않는다. 좌석 저장이 실패하면 편집 초안을 그대로 두고 오류를 표시하며 성공 후 상세·목록을 갱신한다.

실제 차량 확인 기록

확인 요청은 expectedDiagramRevision, CAR 또는 BUS, 정확한 차종·연식·인승 사양 vehicleModel(200자 이내), referenceUrl(1000자 이내), 확인한 쪽·사진 위치·좌석 구성 referenceNote(500자 이내)를 요구한다. 주소는 호스트가 있고 사용자 정보가 들어 있지 않은 HTTPS 형식이어야 한다. 서버가 자료 주소를 열어 내용의 진위를 자동 판정하는 기능은 아니다.

웹은 자료와 좌석 위치를 대조했다는 확인란을 체크한 뒤 제출하도록 한다. 서버는 현재 개정이 바뀌었으면 확인 저장을 거절한다. 입력한 차종·주소·확인 설명은 화면에 유지하고 오류를 표시한다. 관리자는 최신 도면을 확인해야 하며 같은 오래된 개정으로 확인이 성공했다고 표시하지 않는다.

확인 성공은 verifiedAt·verifiedBy 저장과 도면 개정 증가이며 활성화와 별개다. 이름·설명만 바꿔도 이전 확인을 해제한다. 생성·복제·수정·좌석표 저장·확인·활성 변경·삭제는 행위자·작업 종류·대상·설명을 관리 작업 기록에 남긴다. 기록 존재를 실물 대조 자체가 실제 수행됐다는 독립 증명으로 확대하지 않는다.

기본 데이터와 제조사 자료 후보

현재 기준 데이터 위치는 공개 API 저장소의 domain/src/main/resources/db/migration/R__seed_reference_data.sql이다. 옛 별도 관리자 API 저장소의 복제본을 함께 수정하는 흐름으로 안내하지 않는다.

기본 자료에는 25·28·41·45인승 버스와 7·9·11·12·15인승 승합차 이름의 합성 배치도 9종이 남아 있다. 이 초기 삽입에는 실물 확인 필드가 없고 현재 스키마 기본값도 미확인이다. 예전 is_active 값만으로 확인된 공개 목록에 들어가지 않는다.

별도 제조사 자료 후보의 정본은 api-app/src/main/resources/vehicle-layouts/manufacturer-layout-candidates.json이다. 현재 4개 후보는 K5 5인승, 카니발 7인승·9인승, 유니버스 FCEV 프라임 전문 전세 29인승이며, 저장된 승객 수는 운전자 제외 각각 4·6·8·28명이다. 이 수치는 저장소 후보 자료를 설명하는 것이며 실제 운행 차량의 사양을 이번에 확인한 결과가 아니다.

후보 정책은 INACTIVE_UNVERIFIED_CANDIDATES다. 좌표는 상대적인 좌석 위치이고 실제 길이·통로 폭의 축척이 아니다. 반복 시드는 후보를 비활성·미확인으로 넣으며, 관리자가 편집·확인·사용한 도면과 일부 남은 좌석표를 임의 복구하거나 덮어쓰지 않도록 조건을 둔다. 이 작업에서는 DB에 시드를 적용하거나 후보를 활성화하지 않았다.

확인 완료 도면이 없어도 차량별 배정 버스를 등록할 수 있다. 실제 좌석을 지정하려면 운영자가 사용할 차량 자료를 대조해 확인·활성화하고, 호스트도 실제 차량과 선택한 도면의 일치를 확인해야 한다.

공개 목록과 실제 적용의 경계

GET /api/v1/vehicle-layouts/verified?vehicleType=CAR 또는 BUS는 활성·verifiedAt 존재·차종 일치 자료를 이름순으로 반환한다. SELF 종류는 거절한다. GET /api/v1/vehicle-layouts/{id}/seats는 해당 번호의 좌석표를 반환하며, 이 조회 자체에 활성·확인 필터를 다시 넣는 구조는 아니다. 좌석표를 읽었다는 사실을 새 사용 허용으로 해석하지 않는다.

실제 적용인 TransportLayoutService는 활성·확인·차종·도면 개정과 좌석 구조를 다시 검사한다. 도면의 이름이나 화면 목록을 오래전에 읽었다는 이유로 적용을 허용하지 않는다. 기존 사용 이력 표시를 위해 남긴 비활성 도면과 새로 선택 가능한 도면도 구분한다.

관리자 API와 화면의 차이

관리자 기본 경로는 /admin/v1/manage/vehicle-layouts다. 목록 GET은 List<ManageVehicleLayoutVo>, 상세 GET /{id}는 ManageVehicleLayoutDetailVo다. 생성 POST와 복제 POST /{id}/clone은 HTTP 201·상세, 수정 PUT /{id}·좌석표 POST /{id}/seats·확인 POST /{id}/verify·활성 PATCH /{id}/active는 상세를 반환한다. DELETE /{id}는 HTTP 204·본문 없음이다.

웹 좌석표 편집·확인 폼은 비활성 상태를 요구한다. 서버의 미사용 원본 수정·좌석표 교체·확인 메서드는 활성 상태만으로 거절하지 않고 저장 때 비활성으로 바꾼다. 따라서 웹의 사전 조건과 직접 API의 조건을 동일하다고 적지 않는다. 쓰기 권한과 사용 이력 보호는 서버에서 다시 검사한다.

2026-09-02 문서의 ‘편집기·삭제는 후속’, ‘9종으로 바로 좌석 지정 운영 가능’은 현재 설명으로 재사용하지 않는다. 실제 기기·운행 차량·운영 데이터의 확인은 이동수단 공통 설정의 출시 상태와 기존 기록의 해석을 따른다.

수용 기준과 검증 근거

  • AC-01 권한과 입구: 차량 좌석 배치도 메뉴·경로를 사용하고 관리자 READ와 WRITE를 화면·서버에서 구분한다.
  • AC-02 초기 상태: 생성은 좌석 0·비활성·미확인이고 정원을 생성 요청 숫자로 임의 확정하지 않는다.
  • AC-03 복제: 원본·좌석을 한 번에 복사하되 확인·활성·최초 사용을 승계하지 않고 이름 중복을 거절한다.
  • AC-04 편집과 정원: 웹 좌석표에서 번호·좌표·종류·선택 여부를 편집하며 서버가 승객 정원을 계산한다. 빈 줄·칸을 압축하지 않는다.
  • AC-05 구조 검증: 중복·범위 밖 좌표·운전석/통로/이용 불가의 승객 선택을 거절하고, 확인/활성화에서 운전석 하나와 차종별 정원 일치를 검사한다.
  • AC-06 확인 계약: 현재 도면 개정·차종·HTTPS 자료·확인 내용을 검사하고 확인자/시각을 기록한다.
  • AC-07 별도 활성화: 확인 성공 후에도 비활성이며 사용 시작 명령에서 확인·좌석 정합성을 다시 검사한다.
  • AC-08 수정 시 해제: 미사용 원본의 이름·설명·좌석표를 수정하면 이전 확인과 활성 상태를 해제하고 개정을 증가시킨다.
  • AC-09 사용 이력 보호: 참조 차량이 없어져도 최초 사용 이력이 있으면 수정·재확인·삭제를 거절하고 복제본으로 작업한다.
