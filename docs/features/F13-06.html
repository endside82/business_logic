F13-06. 계정 삭제 요청 (30일 유예)

사용자가 개인정보 삭제·익명화를 예약하는 흐름. 신청 즉시 데이터가 사라지지는 않는다 — 30일 뒤 매일 새벽에 동작하는 서버 작업이 대상 개인정보를 익명화·삭제하고 법적 보존 기록은 남긴다. 사용자는 마이페이지 상단 배너로 상태를 인지하며, 공개 취소는 PENDING일 때만 가능하다. 이 흐름이 흔들리면 "지웠는데 안 지워졌다"거나 "안 지웠는데 지워졌다"는 사고가 발생해 서비스 신뢰가 즉시 무너진다.

2026-07-29 소스 재실측 — 게이트·삭제 범위

요청과 실행 직전 모두 미해결 금융 의무를 검사하고, 차단 항목이 있으면 DEACTIVATION_BLOCKED로 보류한다. 삭제 범위에는 관심태그·데이트 프로필/미팅/ 피드백·취향·이벤트 선택 피드백·trait 개인 세션이 포함되고 거래 5년 보존과 active legal hold 증거는 유지한다. 로그인 자체가 요청을 자동 취소하는 서버 계약은 없다.

현재 Gap은 Flutter가 차단 의무 상세를 일반 실패로 축약하는 점, 데이팅 사진 FileStorage 실물 삭제 호출이 없는 점, Entity의 unique=true와 canonical V1의 non-unique index가 서로 다른 점이다.

공개 취소는 PENDING만 CANCELLED로 바꾸지만 관리자 process는 현재 COMPLETED만 건너뛴다. 따라서 이미 CANCELLED인 요청도 내부 삭제 실행으로 이어질 수 있는 상태 가드 공백이 있다.

계정 삭제는 비가역적이라 사용자가 충동적으로 누른 결과가 실제 데이터 손실로 이어지면 안 된다. 그래서 본 단위는 "신청한 의사"와 "실제로 데이터를 지우는 동작"을 의도적으로 분리한다 — 신청은 사용자 화면에서 즉시 가능하지만, 실제 삭제는 30일 뒤 서버 작업이 수행한다. 요청이 PENDING인 동안 사용자가 다시 로그인해 "역시 안 지워야겠다"고 결정하면 명시적 취소로 원상 복귀할 수 있다. 동시에 30일은 사용자가 자기 데이터를 다른 곳으로 옮길(F13-05 데이터 내보내기) 충분한 시간이기도 하다. 즉시 비활성화(F13-07)와는 의도가 다르다 — F13-07은 "당장 비공개로 만들고 싶다", 본 단위는 "30일 뒤 개인정보 삭제·익명화를 예약하고 법적 보존 기록은 유지한다".

이 단위가 사용자 신뢰의 마지막 동선을 결정한다

계정 삭제 동선이 깔끔하지 않으면 "다시 가입"의 의사 자체가 사라진다
  • "내가 지운 게 정말 지워졌는가"의 확실성 — 사용자가 신청한 뒤 다시 들어와 봐도 자기 상태가 "삭제 진행 중"으로 분명히 보여야 한다. 배너가 사라지거나 정보가 어긋나면 "이거 진짜 신청된 게 맞나" 라는 의심이 남는다.
  • PENDING 취소의 즉시성 — 사용자가 "취소"를 누른 순간 배너가 사라지고 마이페이지가 원상 복귀해야 한다. 취소했는데 배너가 남아 있으면 사용자가 자기 통제권을 잃은 것처럼 느낀다.
  • 30일 후 실제 삭제의 정확성 — 매일 새벽 4시 작업이 동작하지 않으면 유예 기간이 무한 연장되어 "지웠다고 약속한 데이터가 아직 살아 있다"는 신뢰 무너짐이 생긴다. 반대로 작업이 잘못 동작해 유예 기간 전에 삭제가 시작되면 사용자가 회복 기회를 잃는다.

한 번의 삭제 신청이 통과하는 흐름

신청 즉시 데이터가 사라지지 않는다 — 30일 동안 살아 있다가 새벽 작업이 한 번에 정리한다.

사용자 시나리오

기본 신청

30일 뒤 개인정보 삭제·익명화를 예약

데이터 프라이버시 화면에서 "계정 삭제 요청"을 누른다. 확인 다이얼로그가 떠 한 번 더 의사를 묻는다. 사용자가 확인하면 요청이 저장되고 즉시 화면이 "삭제까지 30일 남음" 카드와 "삭제 취소" 버튼으로 바뀐다. 마이페이지 상단에도 같은 카운트의 배너가 따라붙는다.

이 흐름이 남기는 것 — 사용자가 "지금 결심한 결과"를 화면에서 즉시 확인할 수 있다. 결심과 화면 상태가 어긋나면 신뢰 자체가 무너지는 흐름.

유예 중 인지

며칠 뒤 마이페이지에 다시 들어옴

로그인해 마이페이지를 열면 상단 배너가 여전히 보인다. 남은 일수가 줄어 있다 — "삭제까지 22일 남음". 사용자가 "관리"를 누르면 데이터 프라이버시 화면으로 빠져 거기서 취소할 수도, 그대로 둘 수도 있다.

이 흐름이 남기는 것 — 사용자가 "내가 신청해 둔 일"을 잊지 않게 한다. 배너가 없으면 30일 뒤 갑자기 데이터가 사라진 걸 알게 된다.

PENDING 중 취소

다시 쓰기로 결심해 취소

"삭제 취소"를 누르면 요청 상태가 "취소됨"으로 바뀌고 마이페이지 배너는 즉시 사라진다. "계정 삭제가 취소되었습니다" 안내가 뜨고 사용자는 평소처럼 서비스를 이어 갈 수 있다.

이 흐름이 남기는 것 — 30일 유예 정책의 본질적 가치 — "결심이 바뀐 사용자를 돌려보낸다". 취소가 매끄럽지 않으면 다음에 사용자가 "신청은 가볍지만 취소는 어렵다" 라고 인지해 신청 자체를 망설이게 된다.

중복 차단

이미 신청한 상태에서 다시 누름

유예 중인 사용자가 어떤 경로로 다시 "계정 삭제 요청"을 누르면 서버가 "이미 진행 중인 요청이 있다"고 거절한다. 화면에는 "요청에 실패했습니다" 안내가 뜨고, 기존 요청은 그대로 살아 있다.

이 흐름이 남기는 것 — 같은 사용자에게 동시에 두 개의 삭제 요청이 살아 있는 상태가 운영·집계 양쪽에서 어떤 의미인지 정의되지 않게 만들지 않는다.

30일 만료

새벽 작업이 실제로 데이터를 정리한다

PENDING 상태로 만료 시각에 도달한 요청은 매일 새벽 4시 작업이 일괄 처리한다. 사용자·멤버 정보 익명화, 주소·태그·동의 기록·소셜 로그인·푸시 토큰·결제 자격증명·데이팅 프로필 등이 한 번에 정리되고 계정 상태가 EXIT로 바뀐다.

이 흐름이 남기는 것 — 거래 기록은 법적 보존 기간(현재 정책상 5년)에 따라 보존된다. 사용자에게 "거래 기록도 다 사라진다"고 안내하면 약속을 못 지키는 셈이 되므로 정책 안내 문구에 정확히 반영되어야 한다.

수동 취소

PENDING 요청만 사용자가 직접 취소한다

로그인은 삭제 요청 상태를 보여 줄 뿐 자동 취소하지 않는다. 사용자가 데이터 프라이버시 화면의 삭제 취소 CTA를 눌러 DELETE /api/v1/users/me/data-deletion을 실행해야 한다.

화면 구성 — 사람이 보는 것

영역보이는 것그 자리에 둔 이유
마이페이지 상단 배너 유예 중에만 노출. "계정 삭제 요청 진행 중" 제목, "삭제까지 N일 남음" 카운트, "관리" 텍스트 버튼. 사용자가 어느 화면에 있든 자기 계정 상태를 잊지 않게 한다 — 30일은 충분히 잊어버릴 수 있는 시간.
요청 전 안내 경고 박스 "30일 유예 기간 후 개인정보가 삭제·익명화되고, 법적 의무에 따라 일부 기록은 보존될 수 있습니다", 위험 색상의 "계정 삭제 요청" 버튼. 버튼 색상으로 결과의 비가역성을 분명히 한다. 다른 일반 버튼과 같은 색이면 사용자가 결과의 무게를 인지하지 못한다.
유예 중 카드 "삭제까지 N일 남음" 큰 글씨, 개인정보 삭제/법적 보존 안내, 외곽선 형태의 "삭제 취소" 버튼. 취소 버튼은 의도적으로 위험 색이 아니다 — "이 버튼을 누르면 위험한 일이 일어난다"가 아니라 "기존 신청을 되돌린다"는 의미.
요청 확인 다이얼로그 "정말 삭제하시겠습니까?" 본문 + 취소·삭제 두 버튼. 비가역적 결과의 동작에는 반드시 한 단계 의사 확인을 끼운다.

측정해야 하는 것

본 단위가 정상이라고 부르려면 이 다섯 가지가 추적되어야 한다
  • 삭제 요청 → PENDING 취소율 — 취소 가능 상태가 실제 회복으로 이어지는 비율. 너무 낮으면 유예 기간이 무의미하고, 너무 높으면 신청 단계가 너무 가벼운 신호.
  • 30일 만료 후 실제 삭제 작업 성공률 — 새벽 작업이 한 건이라도 실패해 만료된 요청이 누적되면 약속 위반.
  • 유예 중 사용자가 다른 기능을 계속 쓰는지 — 신청해 두고도 평소처럼 활동하는 사용자가 많다면 유예 정책의 가치가 잘 작동하는 신호.
  • 삭제 직후 같은 이메일·전화번호로 재가입하는 비율 — 너무 높으면 본 단위가 "계정 정리를 위한 도구"로 잘못 쓰이고 있다는 신호.
  • 마이페이지 배너 노출 후 "관리" 클릭률 — 사용자가 자기 상태를 능동적으로 확인하는지의 지표.

운영자가 알아야 할 것 — 비즈니스 리스크

본 단위에서 무너지면 사용자가 서비스 자체를 신뢰하지 못한다
  • 매일 새벽 4시 작업이 멈추면 정책 자체가 무너진다. 유예 만료된 요청이 누적되어 "지웠다고 한 데이터가 며칠씩 살아 있는" 상태가 된다 — 운영 모니터링의 최우선 알람 대상.
  • PENDING 취소가 즉시 화면에 반영되지 않으면 사용자가 "취소 안 됐나" 하고 또 누른다. 두 번째 취소는 "이미 취소된 요청"이라 거절되고, 사용자에게는 마치 자기 행동이 의미 없는 것처럼 느껴진다.
  • 마이페이지 배너의 남은 일수 계산이 어긋나면 사용자가 자기 상태를 잘못 인지한다. 특히 음수가 표시되거나 일정 안내 형식이 깨지는 회귀가 자주 나타난다.
  • 거래 기록(포인트·결제·정산)은 법적 보존에 따라 익명화·삭제에서 빠진다. 전량 삭제로 오해시키지 않도록 개인정보 삭제 범위와 법적 보존 범위를 함께 안내해야 한다.
  • 로그인 자동 취소는 서버 계약이 아니다. PENDING 취소 CTA의 204 성공과 provider 상태 초기화가 유일한 사용자 취소 흐름이다.
  • 현재 중복 차단은 PENDING만 검사하고 DB도 여러 이력 row를 허용한다. APPROVED writer가 생기면 APPROVED와 새 PENDING이 공존할 수 있다. 한 건 불변식이 필요하다면 허용 상태와 DB 제약을 함께 정의해야 한다.
  • 관리자 process는 CANCELLED도 실행할 수 있다. 사용자가 취소한 요청을 관리자 경로가 완료로 바꾸지 않도록 허용 상태 allowlist가 필요하다.
