F07-08 정산 이의제기·처리·변경 기록

이의 대상·참석 자격·입력/재시도·생성자와 운영팀 처리·조회 권한·기록 공개와 보관 범위를 구분한다. 2026-11-22 소스 대조이고 이의 중에 막히는 동작과 닫힌 까닭은 2026-11-26 다시 대조했으며 새 제품 실행과 구분합니다.

결론

이의 접수, 정산 생성자의 답변, 운영팀 판단, 정산 변경 기록 조회는 권한과 효과가 서로 다르다. 접수한 PENDING 이의는 해당 분담·항목 또는 송금의 의무를 끝내는 동작을 막는다. 회원의 결제·입금 확인·보냈어요와 그 취소·돌려줬어요·포인트로 환불하기, 생성자의 만료 송금 다시 요청·포기, 운영자의 은행 확인·손실 정리·돌려받을 돈의 포인트 보상·취소 뒤 입금 확인·가상계좌 늦은 입금 수락·초과 입금 반환이 여기에 든다. 이 막힘은 정산 생성자의 답변이나 운영팀 판단으로 이의가 PENDING을 벗어나면 풀린다. 이의를 받아들였다고 금액 변경이나 환불이 자동 실행되지는 않는다.

정산 생성자와 현재 모임 호스트를 같은 사람이라고 가정하지 않는다. 이의 전체 목록은 정산 생성자만 조회하며, 변경 기록은 본인이 관리하는 정산과 모임 수준 기록의 조회 범위를 별도로 판정한다. 과거 문서의 ‘참가자도 전체 감사 기록 조회’, ‘호스트 본인 분담은 무조건 이의 불가’, ‘모든 변경을 영구 보관’ 같은 해석은 현재 계약이 아니다.

현황 화면의 관리 입구는 현재 모임 호스트 기준인 반면 이의 관리 화면의 처리 버튼은 정산 creatorUserId를 기준으로 한다. 호스트가 바뀐 상황에서 입구 표시가 서버의 조회·처리 권한을 보장하지 않는다.

접수 요청과 대상별 자격

POST /api/v1/events/{eventId}/settlement/appeals는 Idempotency-Key를 필수로 받고 subjectType·subjectId·reason을 전달한다. 성공은 201 MeetingSettlementAppealVo다. 사유는 공백만 입력할 수 없고 서버 한도는 2,000자다. AuditSubjectType enum에는 SETTLEMENT·ITEM·SHARE·TRANSFER·PREPAYMENT가 있지만 이 접수는 ITEM·SHARE·TRANSFER만 허용한다. SETTLEMENT와 PREPAYMENT는 INVALID_INPUT이다.

대상동일 정산 소속 확인 후 허용하는 사람
ITEM항목 보유자 또는 해당 항목에 자기 분담이 있는 사람
SHARE해당 분담의 회원 또는 실제 낼 사람. 수입 항목의 지급 방향도 반영
TRANSFER해당 이체의 보내는 사람 또는 받는 사람

문 앞에서 모임 존재와 현재 호스트 또는 참석 자격을 먼저 검사한다. 일반 모임은 현재 참석 상태, 정기모임 회차는 실제 참석 정책을 사용한다. 과거 분담·송금 당사자라는 사실만으로 참석 취소 후에도 접수 자격이 유지되는 것은 아니다. 정산 생성자 본인이라는 이유만으로 모두 거절하는 별도 조건은 없으며 대상 당사자 조건을 그대로 적용한다.

서버는 정산을 잠가 최신 상태를 읽고 회원 상태도 잠가 확인한다. DRAFT는 MEETING_SETTLEMENT_NOT_ACTIVE로 거절하며 COMPLETED 접수는 허용하는 현재 정책이다. 취소된 정산은 현재 정산 조회에서 제외되므로 ‘DRAFT가 아니면 어떤 과거 정산이든 이 경로로 접수 가능’으로 확대하지 않는다. 대기 이의는 부모 정산 잠금 뒤 최신 커밋 기준으로 확인한다. 이미 대체된 SUPERSEDED 송금에는 새 이의 접수를 거절한다. 같은 대상에 PENDING 이의가 있으면 MEETING_APPEAL_ALREADY_PENDING, 닫힌 계정 또는 진행 중인 계정 삭제 요청도 각각 거절한다.

입력 보존과 요청 결과

분담금 이의 창은 공백 제거 후 필수 사유를 받고 앱에서 1,000자로 제한한다. 송금 이의 창은 2,000자다. 호스트 답변은 선택 입력이며 앱·서버 모두 2,000자까지다. 서로 다른 현재 한도를 하나의 값으로 쓰지 않는다.

접수 창은 요청 결과를 기다리고 중복 제출·작성 중 이탈을 제어한다. 열린 창에서 같은 사유를 재전송할 때 같은 명령 키를 사용하고 사유가 바뀌면 새 키를 만든다. 결과를 모르는 오류에서는 입력을 유지하고 재전송 안내를 한다. 이미 진행 중인 이의라는 응답은 현재 목록·행을 다시 읽고 접수되어 있음을 안내한 뒤 창을 닫는다. 창을 닫았다가 다시 열 때까지 키·입력을 영구 보관하는 구현은 아니다.

성공 뒤 이의 목록과 송금 목록을 다시 읽는다. 분담 접수는 호출한 내 분담 또는 항목별 납부 조회도 무효화하여 행의 행동 허용값을 갱신한다. 이의 목록 재조회 오류는 공급자의 오류 상태로 저장되며 접수 성공 자체를 되돌리지 않는다.

진행 중 이의의 영향

명령마다 보는 이의 대상이 다르다. 분담에 대한 명령은 그 SHARE뿐 아니라 부모 ITEM의 PENDING 이의도 보고, 송금에 대한 명령은 그 TRANSFER의 PENDING 이의를 본다. 명령은 정산과 대상 행을 잠근 뒤 대기 이의를 최신 커밋 기준으로 다시 읽는다. 이미 끝낸 같은 요청의 재시도는 이의 판정 앞에서 처음 결과를 돌려받는다.

운영자의 송금 처리 가운데 취소의 되돌림을 대신하는 둘(되돌림 실패의 포인트 보상, 되돌림 다시 시작)은 이의를 보지 않는다. 정산 취소와 취소가 시작한 자동 되돌림도 이의를 보지 않는다. 운영자의 의무를 끝내는 처리를 막는 까닭은 판정 전에 송금이 끝나 정산이 완료되면 완료된 정산은 취소할 수 없어 이의를 받아들여도 고칠 길이 닫히기 때문이다. 이의를 판정할 수 있는 사람이 같은 운영자이므로 운영자는 이의를 먼저 판정한 뒤 처리한다. 자세한 지급 방향·허용 상태는 분담·이체 납부와 신고, 이체 확인·만료·후속 처리를 따른다.

정산 생성자의 답변과 운영팀 판단은 모두 이의를 PENDING에서 벗어나게 하므로 위 막힘을 푼다. 이것은 막힘을 푸는 상태 변경이다. 이미 납부한 돈의 자동 환불, 항목 금액 수정, 취소된 정산의 자동 재개가 아니다. 또한 ITEM 이의가 모든 DIRECT 이체를 일괄 차단한다고 설명하지 않는다. 각 명령이 확인하는 대상 종류가 다르다.

이의로 닫힌 동작의 표시

서버는 막힌 동작을 응답에 「할 일이 있는데 이의로 닫힘」 으로 싣는다. 칸의 꼴은 허락, 또는 거절과 그 명령이 던질 오류 코드다. 이 칸을 채우려고 이의 조회가 늘지는 않는다(행이 이미 읽은 값을 쓰거나 쪽마다 한 번 읽는다). 잠금 없는 읽기이므로 명령의 판정이 정본이다.

응답칸뜻
정산 내역 상세actions.withdrawSent, actions.markReturned「보냈어요 취소」·「돌려줬어요」 의 판정이다. 할 일이 없으면(보낸 표시가 없음, 돌려받을 돈 표시가 없거나 이미 돌려줌, 송금 줄의 「돌려줬어요」) 칸을 싣지 않으므로, 거절 이유가 2000021이면 할 일이 있는데 이의로 닫힌 것이다. 옛 앱이 읽는 canWithdrawSent·canMarkReturned 는 이 칸에서 나온 참·거짓이다
송금 목록의 행보낸 사람 행 actions.reportSent·actions.withdrawSent, 받는 사람 행 actions.selfRefund그 동작의 당사자 행에만 싣는다. 싣지 않은 칸은 닫힘이다
관리자 송금 처리 목록, 송금 한 건 조회 GET /admin/v1/manage/meeting-settlements/transfers/{transferId}hasPendingAppeal, pendingAppealId, appealLockedMethods진행 중 이의가 있는가와 그 번호, 쓸 수 있는 처리 방법 가운데 이의 때문에 지금 받지 않는 것이다. 되돌림을 대신하는 둘은 들지 않는다

앱은 이의로 닫힌 「보냈어요 취소」·「돌려줬어요」·「포인트로 환불하기」 를 없애지 않고 잠긴 단추와 까닭(「이의가 처리된 뒤에 보냈어요를 취소할 수 있어요.」·「이의가 처리된 뒤에 돌려줬어요를 누를 수 있어요.」·「이의가 처리된 뒤에 포인트로 환불할 수 있어요.」)으로 보인다. 만료 송금의 다시 요청·포기는 「이의가 처리된 뒤에 다시 요청하거나 포기할 수 있어요.」 다. 화면을 연 뒤 이의가 걸려 서버가 거절하면 목록이나 상세를 다시 읽고 같은 글로 알린다. 새 앱이 actions.selfRefund 를 싣지 않는 옛 서버를 만나면 「포인트로 환불하기」 가 보이지 않으므로 서버를 먼저 올린다.

관리자 웹은 송금 처리 화면에 「이의 중」 과 그 이의의 판정 화면 연결을 보이고 잠긴 방법은 고를 수 없게 한다. 취소 뒤 입금 확인 화면은 송금 한 건 조회로 이의를 읽어, 이의 중이면 안내와 판정 화면 연결을 보이고 확인을 잠근다.

정산 생성자의 답변

PATCH /api/v1/events/{eventId}/settlement/appeals/{appealId}/resolve는 status와 선택 hostResponse를 받고 200 MeetingSettlementAppealVo를 반환한다. 이의 행을 잠가 PENDING인지 확인한 뒤, 경로의 모임과 해당 정산이 일치하는지 및 요청자가 정산 생성자인지 확인한다. 허용 상태는 APPROVED·REJECTED·RESOLVED다. PENDING으로 처리하거나 이미 처리한 행을 다시 처리하면 거절한다.

생성자의 답변은 hostResponse·resolvedByUserId·resolvedAt에 저장하고 이의 낸 회원에게 알림 발송 의도를 등록한다. 이 API는 현재 정산 상태를 ACTIVE로 한정하는 추가 조건이 없지만 이의의 기존 PENDING 여부·소속·생성자 권한은 요구한다.

앱은 생성자에게만 대기 카드의 거절·해결·받아들임을 표시한다. 답변 확인 창은 제출 전에 닫히며 이후 실패는 안내 메시지로 표시한다. 실패한 답변의 자동 복원이나 영구 명령 키 재생을 갖춘 접수 창과 동일한 흐름으로 설명하지 않는다.

운영팀 판단과 호스트 답변의 분리

운영팀 처리는 별도 서버 명령이다. 대기 이의를 APPROVED 또는 REJECTED로 판단할 때 판단 글은 필수이며, 이미 APPROVED인 이의를 RESOLVED로 닫을 수 있다. RESOLVED에서 글을 비우면 기존 운영팀 글을 유지한다. 명령 식별자에 최초 결과를 묶고 이의 행을 잠가 상태 전이를 다시 확인한다. 대기 이의를 판단하면 그 이의로 막힌 회원의 결제·확인과 운영자의 의무를 끝내는 처리가 풀린다. 생성자의 답변을 기다리지 않아도 된다.

운영팀은 operatorResponse·operatorResolvedAt과 내부 관리자 식별자를 기록하며 호스트 답변 칸을 덮어쓰지 않는다. 회원 응답에는 운영팀 판단 글·시각을 주되 관리자 번호는 주지 않는다. 앱은 기존 호스트 응답 아래에 운영팀 판단을 따로 표시하며, 글이 없어도 판단 시각이 있으면 표시한다.

운영팀 판단의 알림 대상은 정산 생성자와 이의 낸 회원을 중복 제거한 집합이다. 두 사람이 같으면 두 통을 등록하지 않는다. 접수·호스트 답변·운영팀 판단은 발송 의도 저장까지이며 실제 기기 수신을 보장한 검증은 아니다. 운영팀 판단 서비스 자체도 금액 변경·환불을 실행하지 않는다.

이의 목록과 표시의 한계

GET /api/v1/events/{eventId}/settlement/appeals는 생성자 권한 확인 후 현재 정산의 전체 이의를 생성 시각 내림차순 List로 반환한다. 페이지 응답이 아니다. 앱은 대상 종류·번호·사유·신청자 이름·접수 시각·상태와 별도 응답 상자를 표시한다. 로딩·오류와 재시도·빈 목록을 구분하고 목록 당겨서 새로고침을 제공한다.

송금 화면은 이 생성자 전용 목록을 구독하여 진행 중인 TRANSFER 번호를 계산한다. 조회 실패나 값이 없으면 빈 집합으로 대체한다. 따라서 일반 참가자 화면의 진행 중 표시와 이의·결제 행동 노출을 이 목록만으로 정확히 보장할 수 없다. 서버의 실제 명령 차단이 남아 있다는 사실과 화면이 올바르게 안내하는지는 별도다. 받는 사람의 「포인트로 환불하기」 와 정산 내역 상세의 「보냈어요 취소」·「돌려줬어요」 는 이 목록이 아니라 행의 서버 칸(이의로 닫힌 동작의 표시)으로 그린다.

변경 기록의 범위와 보관

GET /api/v1/events/{eventId}/settlement/audit-log는 page·size를 받아 Spring Page를 반환하며 기본 크기는 30이다. 같은 모임의 취소 전후 정산을 모두 조사하되 본인이 관리하는 정산 번호만 포함한다. 정산 번호가 없는 모임 수준 기록은 현재 모임 호스트일 때 포함한다. 어느 범위에도 권한이 없으면 FORBIDDEN, 정산 자체가 없으면 MEETING_SETTLEMENT_NOT_FOUND다.

보냈어요·취소의 SHARE/TRANSFER 기록은 해당 정산 생성자에게만 공개한다. 목록과 전체 건수는 같은 가시성 조건을 사용하며 생성 시각 내림차순·같은 시각이면 기록 번호 내림차순이다. 일반 참가자의 전체 정산 활동 기록으로 설명하지 않는다.

감사 발행기는 호출한 쓰기 트랜잭션 안에서 기록을 저장한다. 이의 접수·답변은 대상·행동·행위자·관련 정산 및 사유/처리 내용을 기록한다. 선택한 호출에서 기록되는 내용을 확인한 것이며 모든 코드 변경이 빠짐없이 기록되는지 전수 감사한 결과는 아니다. 현재 보관 작업은 매일 03:00에 90일보다 오래된 행을 삭제한다. 실제 운영 스케줄 실행 여부나 별도 법적 보관 적정성은 이번 소스 대조의 판정 범위가 아니다.

변경 기록의 공개와 앱 표시

행위자 역할은 USER·HOST·ADMIN·SYSTEM이다. 회원에게 제공할 때 ADMIN은 운영팀, SYSTEM은 시스템으로 표시하고 식별자를 비운다. 요청 추적 번호도 제거하며 beforeSnapshot·afterSnapshot·payload 안의 지정된 내부 관리자·인계 메모·작업·추적·서버 식별 키를 재귀적으로 제거한다. JSON 해석에 실패한 세부 내용은 숨긴다. 모든 종류의 개인정보를 자동 탐지하는 필터라고 설명하지 않는다.

앱은 30개씩 이어 읽고 추가 조회 실패는 목록 꼬리의 재시도로 처리한다. 줄에는 동작 이름·대상 종류와 번호·초까지의 시각·행위자를 표시한다. 모르는 종류나 동작은 알 수 없음이다. 반환 모델에 변경 전후·payload가 있어도 현재 화면에서 이를 펼쳐 읽거나 기록 줄을 눌러 상세로 이동하는 기능은 없다. 뒤로 돌아가면 이전 정산 화면으로 복귀한다.
