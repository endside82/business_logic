F03-19. 일정 변경 제안·참가자 합의 (RS-002)

호스트가 이벤트 일정을 바꿀 때, 변경 규모에 따라 즉시 반영(경미한 변경)과 48시간 합의(중대한 변경) 중 하나로 처리된다. 중대한 변경이면 참가자 한 명 한 명에게 제안이 발송되고, 참가자는 동의 또는 거절을 선택한다. 거절하면 무료 취소 + 100%·수수료 0 환불 정책으로 자동 취소를 시도한다. 실패는 거절 응답과 분리될 수 있다. PENDING이 소진되고 철회 row가 없으면 호스트가 최종 확정을 누른다.

일정 변경은 언뜻 호스트 권한처럼 보이지만, 1시간 이상 시간이 밀리거나 장소가 바뀌거나 가격이 오르면 참가자 입장에서는 "다른 이벤트"에 가까워진다. 이 경우 호스트가 일방적으로 바꿀 수 없도록 참가자에게 48시간 응답 기회를 준다. 거절하면 패널티 없이 나갈 수 있고, 48시간 내 무응답은 수락으로 간주한다. 경미한 변경(60분 미만·장소 그대로·가격 동결)은 즉시 반영해 운영 마찰을 줄인다.

2026-07-29 current source 실측

앱은 POST /api/v1/events/{eventId}/reschedule-proposals를 사용한다. 주소가 바뀐 오프라인 이벤트는 저장 전에 서버 geocoding으로 새 좌표를 구하고, newLatitude/newLongitude를 한 쌍으로 보낸다. 서버는 AUTO 변경이면 즉시 좌표를 반영하고, MAJOR 변경이면 before/after snapshot에 보존했다가 batch 확정 때 반영한다. 좌표 한쪽만 전달, 범위 밖, (0,0)은 거부된다. 앱에는 가격 변경 입력이 없어 newPrice를 보내지 않으므로 가격 변경 proposal은 현재 만들 수 없으며, 기존 가격이 합의 없이 바뀌는 것은 아니다. 호스트 현황은 최초 GET snapshot이고 polling/socket이 없으며, 참가자 화면의 기한도 남은 시간 countdown이 아니라 절대 시각이다.

사용자 시나리오

기본 흐름 — 중대한 변경

장소가 바뀌어서 참가 여부를 다시 결정해야 한다

호스트가 집결지를 A에서 B로 바꾼다. 공개 이벤트 편집 화면은 현재 입력과 무관하게 합의 기준 안내와 "1시간 이상·장소 변경·가격 인상" chip을 항상 표시하며, "장소 변경 포함 — 큰 변경입니다" 같은 동적 배너는 없다. 저장하면 계정 userId가 있는 ATTENDING/WAITING 참가자에게 "일정 변경 제안" 알림 생성을 시도한다. 참가자는 변경 전/후 장소를 나란히 보면서 동의 또는 거절을 선택한다.

이 흐름이 남기는 것 — 호스트가 변경을 강행하는 대신, 참가자에게 "이 변경으로도 참가할 건지" 선택권을 준다. 거절해도 패널티가 없다.

거절 → 환불

변경된 장소가 너무 멀어서 거절하고 나간다

참가자가 "거절"을 누르면 서버는 RESCHEDULE_DECLINED로 자동 취소를 시도한다. 성공하면 100%·수수료 0 정책이 적용되지만, 예외는 autoCancelFailed=true로 흡수되어 거절 row만 남고 참가 취소·환불이 지연될 수 있다. hosting ticket release도 best-effort다.

이 흐름이 남기는 것 — 변경을 원하지 않는 사람이 손해 없이 빠질 수 있어야 분쟁이 줄어든다.

48시간 무응답

알림을 놓쳐 응답 기한을 넘겼다

48시간이 지난 PENDING row는 기본 1시간 fixed-delay 스케줄러가 실행될 때 AUTO_ACCEPTED로 전이한다. 기한 직후 늦은 응답은 409를 받지만, 요청 안에서 시도한 AUTO_ACCEPTED 저장은 같은 트랜잭션의 예외로 rollback되므로 실제 영속 전이는 다음 scheduler 실행에 달려 있다.

이 흐름이 남기는 것 — 기한이 있어야 호스트가 무기한 대기 없이 변경을 확정할 수 있다.

호스트 — 현황 확인

누가 동의했고 누가 아직 안 답했는지 확인

호스트는 "일정 변경 제안 현황" 화면에서 동의/거절/미응답/자동수락 인원을 최초 GET snapshot으로 확인한다. 자동 polling·새로고침 gesture·socket은 없고, action 성공이나 오류 retry 때만 다시 읽는다. PENDING이 0이고 WITHDRAWN이 0이면 DECLINED가 있어도 "확정" 버튼이 활성화된다.

호스트 — 철회

변경 제안을 취소하고 원래 일정을 유지하기로 했다

호스트가 현황 화면에서 "철회"를 누르면 모든 제안이 취소되고 이벤트는 기존 일정을 유지한다. 이미 거절한 참가자의 자동 취소가 성공했다면 이를 되돌리지 않으며, 실패했다면 거절 row와 실제 참가 상태가 이미 어긋나 있을 수 있다.

경미한 변경

30분 일찍 시작하는 변경 — 참가자 동의 없이 즉시 반영

시간 변동이 60분 미만이면 "경미한 변경"으로 분류돼 즉시 반영된다. 참가자에게는 "일정이 변경됐습니다" 알림만 간다. 별도 동의 절차 없음.

참가자가 화면에서 보는 것

운영자가 알아야 할 것

운영 주의사항
  • PENDING이 있거나 WITHDRAWN이 있으면 호스트가 확정할 수 없다. DECLINED는 실제 자동 취소 결과와 무관하게 확정을 막지 않는다. 현재 화면 배너가 "거절 또는 대기 중이면 확정 불가"라고 써 서버 조건과 모순된다.
  • 가격 인상은 반드시 중대한 변경으로 처리된다. 가격을 올리면서 즉시 반영되는 경우는 없다. 단, 현재 앱에서 가격 인상이 포함된 변경을 호스트가 직접 요청하는 화면은 구현되지 않았다.
  • 거절 자동 취소가 성공하면 환불 정책은 100%·수수료 0이다. 취소 예외는 응답을 rollback하지 않고 autoCancelFailed로 반환되며 ticket release도 best-effort다. 이미 성공한 취소·환불은 호스트의 제안 철회로 되돌리지 않는다.
  • 변경 확정 알림은 별도로 발송된다. 변경이 최종 확정됐음을 참가자에게 알리는 알림이다. 현재 이 알림은 일반 이벤트 상세로만 연결되며 전용 화면은 없다.

레드 플래그

자주 발생하는 케이스
  • 앱에서 가격 변경 제안을 만들 수 없음 — 현재 이벤트 편집 화면에 가격 변경 입력 항목이 없고 newPrice도 전송하지 않는다. 서버 분류기는 값이 전달되면 가격 인상을 중대한 변경으로 정상 판정하지만, 앱에서는 가격 인상·인하 proposal 자체를 시작할 수 없다. null은 가격 변경 없음이므로 기존 가격이 합의 없이 바뀌지는 않는다.
  • 확정 후 이벤트 상세에 이전 일정이 표시되는 경우 — 확정 직후 앱이 화면 정보를 갱신하지 못해 기존 시간·장소가 남아 있을 수 있다. 화면을 나갔다 다시 들어오면 해소된다.
  • 대형 이벤트에서 1명 미응답으로 확정 지연 — 기본 fixed-delay는 1시간이지만 처리 시간·장애·설정 변경을 포함한 49시간 하드 상한은 아니다.
  • 게스트-only MAJOR 빈 batch — guest row는 userId가 없어 제안 대상에서 빠진다. 계정 대상이 0이면 서버는 batchId/count=0을 반환하지만 그 batch GET은 row가 없어 NOT_FOUND가 된다.
  • URL eventId와 batch 소속 미검증 — batch GET/apply/delete는 path eventId를 service에 전달하지 않는다. 실제 batch 이벤트의 소유권은 검사하지만 URL의 eventId와 일치하는지는 검사하지 않는다.
