F08-04. 블록 재정렬 · 계층 이동

이미 만들어진 블록의 순서를 한 번에 바꾸거나, 한 블록을 다른 블록의 자식으로 들여 넣는 화면이다. 블록 에디터(F08-03)와 별도 화면으로 두어 — 같은 화면에서 입력과 드래그를 동시에 하지 않도록 분리했다. 드래그·들여쓰기·내어쓰기는 모두 화면 안에서만 일어나고, "완료"를 누른 순간에 비로소 여러 서버 mutation을 순서대로 실행한다. 취소하면 처음 본 상태가 그대로다.

설계 의도 — 작성과 재정렬을 한 화면에 두지 않는다

블록 에디터에서 글을 쓰면서 동시에 드래그까지 받으면 사용자가 의도하지 않은 이동이 빈번하게 발생한다. 그래서 재정렬은 별도 화면에서, 사용자가 명시적으로 들어와서, "완료"를 눌러야 비로소 반영된다. 잘못 옮긴 블록이 그대로 서버에 저장되지 않게 하는 안전선이다.

이 화면이 다루는 두 가지

동작 1

형제 사이 순서 바꾸기

같은 부모 아래의 블록들을 길게 눌러 드래그해서 위·아래로 옮긴다. 부모는 그대로고 순서만 바뀐다 — 가장 흔한 정리 동작.

동작 2

들여쓰기 / 내어쓰기로 계층 바꾸기

각 카드의 우측 화살표로 한 칸 들여쓰면 직전 형제의 자식이 되고, 내어쓰면 한 단계 위로 올라간다. 루트 depth 0부터 depth 3까지 최대 네 레벨을 허용한다. 부모가 바뀐 블록은 좌측에 푸른 띠가 표시되어 사용자가 한눈에 알 수 있다.

"완료" 한 번이 일어나는 흐름

드래그·들여쓰기는 모두 로컬에만 머물러 있다가, 사용자가 완료를 누르는 순간 부모가 바뀐 블록 → 형제 그룹 순서 두 단계로 서버에 반영된다.

사용자 시나리오

기본 흐름

코스 순서를 다시 짠다

다섯 개의 코스 블록이 짜놓은 순서와 안 맞다. 재정렬 화면에서 세 번째 블록을 첫 번째 자리로 드래그하고 "완료"를 누른다. 에디터로 돌아오면 새 순서가 반영되어 있다.

이 흐름이 남기는 것 — 잘 작성된 본문을 처음부터 다시 쓰지 않고 손쉽게 다듬는 흐름. 작성에 대한 부담이 줄어든다.

계층 만들기

토글 아래로 두 블록을 끼워 넣는다

토글 블록 바로 아래에 평블록 두 개를 자식으로 두고 싶다. 그 두 블록의 들여쓰기 화살표를 한 번씩 누르면 각각 토글의 자식이 되고 좌측에 푸른 띠가 표시된다. "완료"를 누르면 부모 이동과 순서 갱신이 한 번에 일어난다.

취소

이리저리 옮겨 보다 그만둔다

이것저것 시도해 본 사용자가 마음에 안 들어 "취소"를 누른다. 로컬 변경이 모두 사라지고 에디터로 돌아간다. 서버에는 어떤 변경도 가지 않았다.

이 흐름이 남기는 것 — 작성자가 안심하고 실험할 수 있는 자리. 망쳐도 처음으로 돌아갈 수 있다.

계층 한도

이미 손자인 블록을 더 들여쓴다

깊이 3에 도달한 블록의 들여쓰기를 한 번 더 누른다. "완료"를 누르면 서버가 부모를 기준으로 이동 루트와 모든 자손의 깊이를 다시 계산하고, 하나라도 한도를 넘으면 그 move 전체를 롤백한다. 앱은 이후 요청을 멈추고 최신 서버 트리를 다시 불러온 뒤 "일부만 반영되었습니다. 최신 상태에서 다시 시도해주세요."를 표시한다.

동시 편집 위험

두 디바이스에서 동시에 편집했다

한쪽에서 재정렬을 시작한 동안 다른 쪽에서 새 블록을 추가했다. 첫 mutation의 revision이 맞지 않으면 서버가 409로 롤백하고, 앱은 최신 트리와 revision을 읽은 뒤 같은 요청을 한 번만 재시도한다. 오래된 화면이 새 블록을 빼고 형제 순서를 보내면 서버의 전체 형제 집합 검사가 이를 다시 거절한다.

운영 관찰 포인트 — 앱은 충돌을 기록·경고하고 최신 트리로 화면을 재설정한다. 다른 세션의 새 블록을 조용히 유실시키는 방식이 아니다.

빈 트리

블록이 한 개도 없는 플랜에 들어왔다

아직 본문이 비어 있는 플랜에서 재정렬을 누르면 "블록이 없습니다" 안내만 뜬다. 사용자는 취소하고 돌아가 에디터에서 블록을 먼저 만들어야 한다.

권한 가드

발행 중 플랜의 재정렬은 차단된다

발행 중 플랜의 편집 URL에 직접 들어와 재정렬을 시도하면 "완료" 단계에서 서버가 거절한다. 이미 산 사람들이 보는 본문이 작성자에 의해 무심코 바뀌는 사고를 막는 같은 가드가 여기에도 걸려 있다.

형제 집합 보호

누락·중복·외부 블록을 서버가 거절한다

부모별 reorder는 그 부모 아래 살아 있는 모든 형제 ID를 정확히 한 번씩 보내야 한다. 앱이 모르는 새 블록이나 읽기 전용 블록을 빼고 보내면 set-equality 검증을 통과하지 못한다.

계층 무결성

depth와 cycle은 서버 권위값이다

요청의 depth 값은 저장 기준으로 신뢰하지 않는다. 새 부모의 depth에서 다시 산출하고 자손까지 연쇄 계산한다. 자기 자신 또는 자신의 자손을 부모로 지정하는 cycle도 서버가 차단한다.

동시 편집

플랜 행 잠금 + revision 409 복구

같은 플랜의 mutation은 서버에서 직렬화되고, 기대 revision이 다르면 409다. Flutter mutation 큐는 최신 트리와 토큰을 reconcile한 뒤 한 번만 재시도하며, 충돌 버스트를 사용자에게 경고한다.

운영자가 알아야 할 것

잘 정돈된 본문이 재정렬에서 잘못 흔들리지 않게
  • "완료" 누르기 전까지는 어떤 변경도 서버에 가지 않는다. 사용자가 실험적으로 옮긴 자리가 그대로 마켓에 노출되지 않는 안전선.
  • 계층 깊이 3은 본문 가독성의 한계점이다. 더 깊어지면 들여쓰기로 인지하기 어렵고 마켓 미리보기에서도 잘려 보이지 않게 된다. 이 한도가 풀리면 "왜 내 블록이 안 보이지" 류 문의가 늘어난다.
  • 여러 HTTP 요청 사이의 부분 반영은 가능하다. 앞선 move가 성공하고 뒤 요청이 실패할 수 있다. 앱은 즉시 이후 요청을 멈추고 최신 트리를 다시 읽어, 오래된 로컬 결과를 성공처럼 남기지 않는다.
  • 다중 디바이스 충돌은 revision과 전체 형제 집합 검사가 잡는다. 409 시 최신 상태를 읽고 한 번 재시도하며, stale 화면이 새 블록을 누락한 reorder는 서버가 거절한다.
  • 들여쓰기로 자식 만드는 동작이 이 화면에만 있다. 에디터(F08-03)에는 자식 추가 동작이 없어서, 사용자가 "자식을 어떻게 만들지?"라고 막힐 때 재정렬 화면을 가리키는 안내가 필요할 수 있다.
