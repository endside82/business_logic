F08-15. 크리에이터 매출 귀속 보정

플랜 마켓의 세 가지 구매(개별 아이템·번들·플랜 직접)가 모두 크리에이터 매출 원장에 잡힌다. 유료 포인트로 결제한 금액에만 플랫폼 수수료·원천징수가 붙고, 무료 포인트 사용분은 수수료 없이 별도로 적립된다. 번들 매출은 큐레이터가 아니라 포함 아이템 원작자에게 정가 비례로 배분되어 원작자 권리를 보호한다. 환불은 이 매출 원장을 잠그거나 되돌리므로 두 기능은 같은 구매 기록을 기준으로 동작한다.

환불은 "이 구매가 만든 크리에이터 매출"을 정확히 찾아내 잠그거나(아직 정산 전), 회수하거나(이미 정산 완료) 해야 한다. 매출 원장이 구매 단위로 식별되지 않으면 환불 회계가 망가진다. 현재 매출 귀속과 환불은 모두 구매 ID를 기준으로 연결되어 있으며, 일부 환불도 선택한 구성품의 매출만 되돌린다.

사용자 시나리오

1. 개별 아이템 구매

"마켓에서 단품 데이트 플랜 구매"

구매자가 10,000원 결제. 그 아이템을 만든 크리에이터에게 매출 1건이 잡힌다. 플랫폼 수수료·원천징수 적용 후 다음 정산 주기에 크리에이터에게 지급.

이 흐름이 남기는 것 — 단순 구매에서 가장 직관적인 매출 흐름. 환불 발생 시 이 매출 행을 찾아 처리.

2. 플랜 직접 구매

"유료·무료 포인트를 섞어 플랜을 직접 구매"

플랜 작성자의 매출이 유료분과 무료분으로 나뉘어 기록된다. 수수료와 원천징수는 유료분에만 붙고, 두 금액의 합은 실제 구매 금액과 같아야 한다.

완료 판단 — 구매 원장과 크리에이터 매출 원장의 유료·무료 합계가 정확히 일치해야 한다.

3. 번들 구매 — 원작자 배분

"3개 아이템 묶음 30,000원 구매"

아이템 A(정가 10,000) + B(15,000) + C(8,000) 묶음. 결제 30,000원 → 각 아이템 정가 비율로 분배 → A 작가 9,090원, B 작가 13,640원, C 작가 7,270원에 매출 행이 따로 만들어진다.

완료 판단 — 큐레이터가 매출을 독식하지 않고, 원작자별 배분 합계가 실제 결제액과 같아야 한다.

4. 0원 정가와 반올림

"번들 구성품의 정가 합계가 0이거나 나눗셈이 딱 맞지 않는다"

정가 합계가 0이면 원작자 수로 균등 배분하고, 나눗셈 나머지는 마지막 매출 행이 흡수한다.

완료 판단 — 어느 원작자 금액도 음수가 되지 않고 모든 매출 행의 합이 실제 결제액과 정확히 같아야 한다.

5. 다중 원작자 혼합 결제

"여러 원작자의 번들을 유료 7,000·무료 3,000 포인트로 구매"

각 원작자의 배분액 안에서도 유료분과 무료분을 나눈다. 무료분에는 수수료와 세금을 붙이지 않으며 현금 인출 대상에도 넣지 않는다.

완료 판단 — 원작자별 유료·무료 합계와 전체 결제 합계가 모두 맞아야 한다.

6. 번들 구매 보너스

"구매 혜택으로 무료 포인트를 받는다"

무료 포인트만 지급하고 지갑 잔액, 무료 포인트 사용 순서, 사용자 거래 내역, 플랫폼 판촉 비용 원장을 함께 기록한다.

완료 판단 — 보너스가 현금성 유료 포인트로 바뀌지 않고, 사용자 지갑과 플랫폼 비용 장부가 같은 금액을 남겨야 한다.

7. 환불과 매출 보류·복구

"환불 신청 뒤 거절·일부 승인·전액 승인이 갈린다"

신청 중인 매출은 정산에서 빼고, 거절하면 다시 정산 가능 상태로 돌린다. 번들 일부 환불은 선택한 구성품의 매출만 되돌린다.

완료 판단 — 환불 결과와 무관한 원작자의 매출은 그대로 남고, 같은 매출을 두 번 되돌리지 않아야 한다.

8. 월간 정산 경계

"환불 가능 기간이 끝난 매출과 아직 남은 매출이 섞여 있다"

14일이 지난 대기 매출만 크리에이터별로 묶어 지급한다. 한 크리에이터의 계좌나 지급 실패가 다른 크리에이터의 정산을 막지 않는다.

완료 판단 — 정확한 14일 경계와 매출 상태를 지키고, 크리에이터별 지급 결과를 독립적으로 남겨야 한다.

9. 지급 후 환불금 회수

"이미 지급한 매출이 환불됐는데 다음 정산금이 부족하다"

다음 정산금에서 가능한 금액만 먼저 회수하고, 전액을 회수한 미수금만 종결한다. 부족한 금액은 다음 정산 주기로 넘긴다.

완료 판단 — 실제 회수액, 남은 미수금, 회계 분개가 일치하고 일부 회수를 전액 회수로 잘못 표시하지 않아야 한다.

현재 검증 수준

세 구매 경로의 매출 생성, 보너스 원장, 환불 보류, 정산 후 미수금 일부 회수는 코드와 서버 테스트에서 확인했다. 다만 정가 합계 0·반올림 잔액, 여러 원작자의 유료·무료 혼합 배분, 정확한 14일 정산 경계는 경계값을 직접 고정하는 테스트가 부족하다.

화면에서 창작자와 운영자가 확인하는 것

영역사용자가 보는 것그 자리에 둔 이유
매출 원장 라벨"개별 아이템·번들·플랜 직접" 출처별로 매출 카드 라벨이 구분.창작자가 자기 매출의 출처를 한눈에 인지하게.
유료/무료 분리"유료 매출 + 무료 포인트 적립" 두 항목이 별도 행으로 노출.창작자가 현금 지급 대상과 인출할 수 없는 무료 포인트를 구분하게.
번들 배분 안내번들 매출 카드에 "정가 비례로 배분됨" 작은 글자 안내.원작자가 "왜 매출이 더 적지?" 의문 갖지 않게.
매출 상태"대기·정산 완료·환불 보류·환불 완료·회수 대상" 상태가 카드에 노출.창작자가 자기 매출이 어느 단계인지 알 수 있게.
회수 안내정산 후 환불이 들어온 매출은 별도 알림과 남은 회수액을 표시.창작자가 다음 정산에서 차감되는 이유와 금액을 확인하게.

운영자가 알아야 할 것

정산·환불 영향
  • 매출 행은 구매 ID 기준으로 식별 — 환불 시 "이 구매가 만든 매출"을 정확히 찾을 수 있다.
  • 월간 정산은 "대기" 상태 매출만 — 환불 보류·환불 완료·역전 상태는 정산에서 제외.
  • 구매 경로별 유료·무료 분리 — 마켓 아이템·번들·플랜 직접 구매 모두 같은 분리 원칙을 사용한다.
  • 번들의 정가 합계가 0이면 균등 배분 — 안전망(예외 케이스 대비).
  • 번들 보너스 포인트 비용 — 플랫폼 판촉 비용 원장에 기록하며 원작자 매출에서 빼지 않는다.

레드 플래그

자주 발생하는 케이스
  • 지갑 환불의 유료/무료 분리 보존(2026-06-06 해소) — 환불이 결제했던 유료/무료 구성 그대로 복원되며, 장부와 실제 지갑이 같은 기준으로 기록된다.
  • 번들 큐레이터와 원작자 혼동 — 환불 권한자는 큐레이터, 매출 귀속은 원작자. 분쟁 발생 시 구분 안내 필요.
  • 배분 경계값 검증 부족 — 정가 합계 0, 반올림 잔액, 여러 원작자의 혼합 결제를 별도 테스트로 고정해야 한다.
  • 정산 후 환불은 미수금으로 관리 — 다음 정산금이 부족하면 일부만 회수하고 남은 금액을 다음 주기로 넘긴다. 창작자에게 차감 이유와 잔액을 보여 줘야 한다.
