F04-03. 클럽 생성·수정·삭제·소유권 이전

입력 복구·정원·권한 재확인, 폐쇄 금액 동의와 후속 반환, 재인증·책임 확인을 거친 소유권 이전과 실제 최종 결과를 구분한다. 2026-11-22 소스 대조이며 새 제품 실행과 구분합니다.

결론

클럽 생성은 소유자 회원·기금·기본 게시판·마일리지 설정을 함께 만들고, 정보 수정은 서버가 허용한 운영 권한으로 처리한다. 생성·수정 화면은 입력과 미확정 요청의 복구 상태를 확인한 뒤 전송한다.

클럽 삭제는 폐쇄 정리 금액을 확인한 후 INACTIVE로 바꾸는 처리다. 일부 가입비 반환은 후속 작업이므로 삭제 응답만으로 모든 회원의 환불 완료를 뜻하지 않는다. 소유권 이전은 제안·책임 확인·재인증·수락을 거쳐 EFFECTIVE가 되는 흐름이며, 제안 접수와 효력 발생을 구분한다.

실제 입구와 복귀

행동현재 입구성공 뒤
생성모임 탭 공통 메뉴의 클럽 만들기, 또는 필터 없는 빈 목록의 로그인 사용자용 첫 생성 입구보관 요청을 완료 처리하고 새 클럽 상세로 대체 이동
정보 수정모임 홈의 관리 → 모임 설정 구역의 정보·운영 설정상세 갱신 후 원래 화면으로 돌아감
폐쇄정보·운영 설정 아래의 삭제 행동. 서버 deleteClub 허용 조건 적용/clubs로 이동하고 관련 회원·이벤트·지갑 자료 갱신
소유권 제안같은 설정 화면의 클럽 넘기기. 서버 transferOwnership 허용 조건 적용생성된 넘겨받기 요청 상세로 대체 이동
넘겨받기 처리소유권 요청 목록과 /club-ownership-transfers/{transferId} 상세응답의 실제 최종 상태를 표시하고 관련 권한·기금·목록 갱신

클럽 목록의 생성 FAB, 상세의 설정 톱니, 멤버 길게 누르기를 현재 입구로 안내하지 않는다. 실제 목록 입구는 클럽 찾기와 모임 탭 탐색, 홈·정보·관리 구분은 클럽 상세와 가입·탈퇴를 따른다. 설정 라우트는 운영 권한 확인을 거치고 이전 제안 라우트는 이전 허용 행동을 확인한다. 화면에 남은 이전 콜백도 계정·세션·현재 경로·최신 권한을 다시 검사한다.

생성 계약과 입력

POST /api/v1/clubs는 ClubAddParam을 받고 201 ClubVo를 반환한다. 입력은 name·description·category·rules·joinType·thumbnailUrl·clubType·memberFee·maxMembers다. 서비스는 소유자 계정을 잠그고 상태, 이름 중복, ACTIVE 소유 클럽 수를 검사한다. 소유 한도 기본값은 5개이며 운영 설정값을 이번에 읽은 것은 아니다.

생성된 클럽은 ACTIVE, 회원 수 1이며 생성자를 OWNER로 등록한다. 기금과 공지사항·자유게시판·가입인사 게시판, 클럽 마일리지 프로그램 설정을 만든다. 설정 생성은 회원에게 마일리지를 실제 지급했다는 뜻이 아니다. clubType이 없으면 FREE이며 BUSINESS의 가입비만 저장한다. FREE에 양수 가입비를 보내면 거절한다.

앱은 이름 2~30자, 소개 10~500자, 카테고리 선택을 요구하고 이름·소개를 trim해 보낸다. 서버 생성 검증은 비어 있지 않은 이름과 최대 100자, 소개 최대 500자를 확인하므로 화면과 서버의 최소·최대 조건이 완전히 같지는 않다. 썸네일은 업로드 후 반환된 키를 사용한다. 서버는 파일의 존재·소유자·COMPLETED 상태·CLUB_THUMBNAIL 용도를 검사하며 표시용 외부 URL을 새 업로드 키처럼 승인하지 않는다.

수정 권한과 정원

PATCH /api/v1/clubs/{id}는 ClubModParam을 받아 200 ClubVo를 반환한다. 현재 클럽 소유자 또는 유효한 운영진 권한을 허용한다. 앱도 최신 editClub 허용 여부로 저장을 제어하며 업로드·복구 기록 준비 후 실제 전송 직전에 다시 검사한다. 단순 역할 문자열만으로 저장 권한을 확정하지 않는다.

수정 입력에는 이름·소개·카테고리·규칙·가입 방식·썸네일과 정원 설정이 있다. clubType·memberFee·ownerId를 이 수정 요청으로 변경하는 계약은 없다. null인 정원은 그대로 유지하며 clearMaxMembers로 명시 해제한다. 정원과 해제를 함께 보내거나 현재 회원 수보다 작은 정원은 거절한다.

선택 정원은 10·20·30·50·100 또는 미설정이다. 미설정이어도 서버 전체 상한은 적용되며 기본값은 1000명이다. 화면의 제한 없음이 서버의 무한 가입을 의미하지 않는다. 앱은 정원을 바꿨을 때만 값이나 해제 표시를 보낸다. 표시용 썸네일 URL을 그대로 보낸 수정은 기존 키를 보존하고 새 파일 키일 때 소유·완료·용도를 확인한다.

입력 보관과 미확정 요청

생성·수정 폼은 계정 세션의 초안을 열고, 이전 요청의 pending·completed·conflict 상태가 있으면 처리 결과를 먼저 확인하도록 전송을 막는다. 수정 초안은 서버 내용 변화도 대조한다. 같은 이미지 경로의 서명 쿼리만 바뀐 것은 별개 이미지 변경으로 보지 않으며, 실제 경로가 달라지면 충돌 판단 대상이다.

전송 전에 검증·필요한 썸네일 업로드·초안 준비를 마친다. 성공하면 클럽 번호를 보관 결과에 남기고 관련 클럽 자료를 갱신한다. 확정 거절은 재작성 가능한 상태로 돌리지만 반영됐을 가능성이 있는 오류는 미확정 상태를 유지하고 목록·상세를 다시 읽게 한다. 실패한 입력을 곧바로 비우거나 자동으로 같은 생성을 반복하는 흐름으로 안내하지 않는다.

이 생성·수정 API에는 가입·탈퇴와 같은 필수 명령 키 헤더가 없다. 초안 복구를 서버의 모든 중복 요청 방지와 동일한 보장이라고 쓰지 않는다. 계정 변경·권한 회수 뒤의 늦은 응답이나 저장 콜백이 새 계정에서 전송·이동을 계속하지 않도록 하는 앱 조건과 서버 원자성을 구분한다.

폐쇄 전 금액 확인

폐쇄는 DELETE /api/v1/clubs/{id}이며 ClubDeleteParam을 query/model attribute로 받고 성공 시 204다. 현재 소유자만 가능하다. 활성 회원 강퇴·차단 분쟁과 진행 중 인출이 있으면 거절한다. 이미 INACTIVE인 동일 소유자의 반복 요청은 다시 정리하지 않고 반환한다.

앱은 먼저 GET /api/v1/clubs/{id}/fund/debt로 폐쇄 의무를 조회한다. 조회 실패 시 삭제 확인으로 진행하지 않는다. 확인창에서 정리 금액을 보여 주고 클럽 이름을 정확히 입력하게 하며, 필요하면 무료 부족분을 낼 통화를 선택한다. 플랫폼 돈 기능이 닫혀 있으면 유료 납부 선택을 제공하지 않는다.

서버는 기금과 관련 구독을 잠근 상태에서 현재 폐쇄 계획을 다시 계산한다. 유료·무료별 구독 지갑 반환·구독 기금 반환·가입비 반환·기부 반환·기부 미반환·부족분 12개 금액이 요청 확인값과 같아야 한다. 소유자 부족분 납부가 있으면 expectedFundVersion도 맞아야 하며 무료 부족분에는 허용 납부 통화가 필요하다. 값이 달라지면 최신 의무를 포함한 거절로 재확인을 요구한다.

앱도 금액 충돌이면 새 의무를 읽고 확인창을 다시 연다. 이전 확인으로 바뀐 금액을 자동 승인하지 않는다. 이름 입력만 맞으면 금액과 무관하게 폐쇄되는 절차가 아니다.

폐쇄 결과와 후속 반환

서버는 OPEN·DRAFT 클럽 이벤트를 공통 취소 경로에 넘긴다. 종료된 이벤트까지 모두 삭제하거나 모든 참석·정산을 같은 순간 완료 처리한다는 뜻은 아니다. 이벤트 취소 뒤 반환 의무는 이벤트 수정·취소·마감·삭제의 실제 취소 흐름과 함께 본다.

정리 계획은 구독 잔여분의 지갑·기금 몫, 이전 소유자 구독의 기금 몫과 이전 납부 기록, 가입비 반환 의무, 기부 반환, 남은 기금의 미수금 상계, 소유자 부족분 납부, 잔여 기금 정리를 구분한다. 이전 소유자 구독을 현재 소유자의 새 현금 수입처럼 일괄 반환하지 않는다. 정리 뒤 기금과 미수금이 남으면 실패한다.

폐쇄 가입비 대상은 실제 납부액이 양수이며 납부 시각이 현재에서 7일 전보다 뒤인 회원이다. 원거래의 남은 유료·무료 반환 몫으로 의무를 계산하고, 회원 행을 지우기 전에 PENDING 반환 기록을 남긴다. 후속 반환 작업은 각 기록을 잠그고 돈 명령이 성공하면 DONE으로 표시한다. 회계 기간 종료는 보류, 재시도 가능한 실패는 재시도 일정, 거절 또는 재시도 한도 도달은 FAILED로 남는다.

매시 40분 복구 작업은 5분 유예를 적용한 기한이 된 PENDING 기록을 다시 처리한다. 코드상 실행 시간 제한 안에 끝나지 않으면 다음 주기로 이어간다. 이 스케줄 존재나 DELETE 204만으로 지갑 반환 완료를 판정하지 않는다.

폐쇄 본체는 진행 중 소유권 제안을 닫고 대기·회원 행을 정리해 회원 수 0, 클럽 INACTIVE로 저장한다. 채팅 접근 회수 신호와 신고 후속 이관, 반환 후속 작업을 연결하고 소유자를 제외한 기존 회원에게 클럽 폐쇄 알림을 요청한다. 실제 알림 수신·후속 처리 완료는 별도 증거가 필요하다.

소유권 제안과 요청 목록

POST /api/v1/clubs/{id}/transfer-ownership은 newOwnerId·선택 message·reauthentication을 받고 201 ClubOwnershipTransferVo를 반환한다. ACTIVE 클럽의 현재 소유자여야 하며 운영자 중지 조건도 검사한다. 대상은 다른 현재 회원·활성 계정이어야 하고 양쪽 차단 관계가 없어야 한다. 메시지 상한은 500자다.

소유자를 재인증하고 책임 요약을 저장한 PROPOSED 요청을 만들며 유효기간은 7일이다. 같은 소유자가 같은 대상으로 아직 유효한 제안을 다시 하면 기존 요청을 반환하고, 다른 대상의 진행 중 요청은 거절한다. 만료된 요청은 닫은 뒤 새 제안을 만들 수 있다. 제안은 역할을 바꾸지 않는다.

GET /api/v1/clubs/ownership-transfers/me는 보낸 사람 또는 받는 사람이 본인인 기록을 생성 시각·번호 내림차순 Page로 준다. 받은 요청만의 목록으로 설명하지 않는다. 단건은 제안 당사자만 읽을 수 있다. 앱 요청 목록은 50개 단위로 읽고 계정·클럽 변경 신호를 반영한다.

앱은 현재 회원 목록에서 대상을 고르고 본인 확인 후에도 대상·메시지·인증 수단·권한이 그대로인지 검사한다. 제안 성공은 요청 상세로 이동하며 실제 소유권 변경 성공 안내와 구분한다.

책임 확인과 수락

수락은 POST /api/v1/clubs/ownership-transfers/{transferId}/accept다. 받는 회원의 expectedVersion·responsibilityAccepted=true·expectedResponsibilityHash·billingChoice·필요한 planType·reauthentication을 요구한다. 서버가 다시 계산한 책임 내용의 해시와 확인값이 다르면 새 책임 확인이 필요하다.

책임 화면은 구독·갱신 가격, 유료/무료 기금과 상계, 미수금, 진행 인출, 미정산, 신고·분쟁·제재·예정 이벤트 수와 개인정보 책임을 다룬다. 진행 인출·미정산·같은 통화 기금으로 상계한 뒤 남는 미수금은 수락을 막는다. 신고·분쟁·제재·예정 이벤트는 책임 요약 항목이며 그 수가 양수라는 사실만으로 같은 보류 조건이 되지는 않는다.

서버는 현재 소유자·클럽 상태·대상 회원·활성 계정·차단·운영 중지·요청 버전과 만료를 다시 검사한다. 허용되면 기금으로 미수금을 상계하고 옛 OWNER를 ADMIN으로 바꾸며 위임 권한 비트를 지운다. 새 회원은 OWNER가 되고 클럽 ownerId가 바뀐다. 옛 소유자의 구독은 환불 없이 종료하고 자동 갱신을 끈다.

수동 갱신은 수락 중 새 청구 없이 넘겨받는다. 자동 갱신은 요금제 선택이 필요하며 기존 클럽 기간이 남아 있으면 그 만료를 이어 새 청구 없이 설정한다. 기간이 없으면 선택 요금제의 첫 구독 처리를 호출한다. 수락 내부의 ACCEPTED를 거쳐 같은 트랜잭션에서 EFFECTIVE를 저장하므로 일반 회원에게 별도 완료 버튼을 요구하지 않는다.

앱은 수동 갱신을 기본 선택으로 두고 현재 버전·책임 해시에 대한 확인을 저장한다. 재인증을 기다리는 동안 책임 내용·요금 선택·계정 등이 바뀌면 이전 확인으로 수락하지 않는다. 실패를 성공으로 닫지 않고 반환된 상태와 서버 행동 허용값을 사용한다.

거절·취소·만료와 결과 갱신

받는 회원의 decline과 보낸 소유자의 cancel은 expectedVersion과 선택 메시지를 받아 처리한다. 이미 PROPOSED가 아닌 요청은 현재 결과를 돌려준다. 따라서 취소를 눌렀더라도 서버가 EFFECTIVE를 반환하면 실제 이전 완료로 표시해야 한다. 만료 시각을 넘긴 결정은 EXPIRED로 닫고, 만료 작업도 잠금 후 현재 상태·시각을 재확인해 양쪽에 안내한다.

응답에는 status와 별개로 actionCode·canAccept·canDecline·canCancel·refreshRequired·cancelledBySystem이 있다. 아직 저장 상태가 PROPOSED여도 현재 클럽·소유자·대상·차단·만료 조건에 따라 행동할 수 없을 수 있다. EFFECTIVE의 refreshRequired에 따라 회원 권한·내 클럽·기금을 다시 읽고, 요청 목록·건수·메뉴 기록도 갱신한다. 수락 결과가 반영됐을 수 있는 오류에서도 관련 갱신을 요청한다.

운영자 비상 승계는 일반 회원의 제안·수락과 별도 명령이다. 운영 기록에 묶어 대상 자격과 보류 조건을 검사한 후 새 소유자 청구 없이 EFFECTIVE를 남기고 기존 제안을 닫는다. 운영자 화면·외부 재인증·실제 청구 실행을 이번 일반 앱 문서 대조에서 검증했다고 확대하지 않는다.
