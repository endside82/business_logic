사적 모임과 일반 모임의 차이

호스트의 개설 비용과 선정된 참가자의 참가비는 별도 거래다. 참가비가 있으면 선정 시 유료 지갑 잔액에서 차감해 보관하고, 완료·취소·분쟁·계정 상태에 따라 지급 또는 반환을 판정한다. 비공개 초대 모임이나 소개팅 프로필·매칭 전체와 같은 기능으로 묶지 않는다.

일반 이벤트의 발견·신청 권한과 사적 모임 전용 상세 권한도 다르다. 전용 상세는 호스트 또는 선정된 참가자만 조회한다. 신청했지만 선정되지 않은 회원에게 금액·채팅방만 가린 전용 상세를 제공한다는 옛 설명은 현재 계약과 다르다.

모임 단계와 돈의 상태

모임 단계판정과 의미
WAITING_PAYMENT초안(DRAFT). 개설 처리 전이며, 돈의 상태를 뜻하지 않는다.
RECRUITING모집 중(OPEN). 호스트가 신청자를 선정한다.
MATCHED모집이 닫혔고 선정 시각이 있으며 완료 시각은 없다.
COMPLETED닫힌 모임에 완료 시각이 있다. 지급·환불 결과는 보관금 상태를 따로 본다.
CANCELLED모임 상태 CANCELED. 취소와 참가비 반환 성공은 같은 판정이 아니다.

보관금 상태는 HELD(보관), RELEASED(호스트 지급), REFUNDED(참가자 반환), RECOVERY_REQUIRED(복구 필요), WRITTEN_OFF(회계상 상각), FORFEITED(탈퇴 수취인의 몰수 처리)로 구분한다. 상각·몰수는 지급이나 환불 완료가 아니다. 참가비가 없는 경우에는 보관금 상태가 없을 수 있다.

참가자가 지나는 길

발견과 상세 권한

일반 목록·검색·공유 링크의 노출은 이벤트 목록과 이벤트 상세의 현재 공개·차단·권한 조건을 따른다. 링크를 갖고 있다는 이유로 PRIVATE 전용 상세 권한을 얻지 않는다. 앱은 PRIVATE 상세 안에 전용 영역을 연결하지만, 서버가 전용 조회를 거절하면 그 영역의 오류 표시는 현재 비어 있다.

신청과 선정

신청은 참가 신청의 조건을 따른다. 호스트가 대기 신청 하나를 선정할 때 서버는 모임 소유자·PRIVATE 종류·모집 상태·신청 소속·상호 차단을 다시 확인한다. 참가비가 양수이면 선정된 회원의 유료 지갑에서 차감하고 보관금을 만든 뒤 승인·참석 기록·모집 종료를 처리한다. 잔액이나 현재 권한이 맞지 않으면 선정 완료로 표시하지 않는다.

선정된 신청에는 승인 알림을 outbox에 등록하고 나머지 대기 신청은 거절한다. 알림 등록은 실제 푸시 수신의 증거가 아니다. 같은 선정 요청의 재도착은 이미 선정된 신청을 확인해 현재 결과를 돌려주는 분기가 있다.

선정된 뒤의 채팅과 완료 확인

선정 시 전용 대화방을 연결한다. 앱의 채팅 버튼은 대화방 번호뿐 아니라 소개팅 공개 기능 조건과 취소 여부도 확인한다. 대화방 레코드 생성만으로 앱 입구가 공개되었다고 판정하지 않는다. 호스트와 선정된 참가자는 종료 시각이 지난 뒤 각자의 완료 확인을 남길 수 있다. 종료 시각이 없거나 아직 미래면 서버도 거절한다.

완료·자동 정산·취소의 결과

참가비가 없으면 양측 확인으로 완료된다. 보관 중인 참가비가 있으면 양측 확인 후 분쟁 보류 여부를 검사하고 호스트 지급을 처리한다. 분쟁 중에는 확인 시각이 남아도 지급과 완료를 확정하지 않는다. 양측 확인이 끝나지 않은 HELD도 모임 종료 후 24시간이 지난 후보가 되면 시간별 작업에서 다시 검사한다. 이는 정확히 24시간에 지급된다는 약속이 아니다. 취소·수취인 탈퇴·원거래 누락의 결과는 아래 돈의 상태를 따른다.

호스트가 지나는 길

생성과 다음 일정

서버 생성 입력의 hostingCostType은 PRIVATE 분기를 만들지만 공통 생성 폼에서 이 값을 사용자가 고르는 입구는 확인되지 않았다. 따라서 일반 생성 화면만으로 사적 모임을 처음부터 만들 수 있다고 안내하지 않는다. 이벤트 생성과 다음 일정·반복 일정의 현재 범위와 공백을 따른다.

상세의 “이 이벤트로 새로 만들기”는 권한과 원본 조건을 확인하는 서버 복제다. 서버는 독립 모임과 PRIVATE를 받으며 취소·숨김·정기모임 회차는 거절한다. 내용·위치·조건을 새 초안에 복제하고 참석·결제 실적은 옮기지 않는다. 새 시각 없이 요청하면 원본 시작 +7일을 사용하므로 오래된 원본은 복제 단계에서 거절될 수 있다.

개설 비용과 모집 마감

PRIVATE 전용 개설은 호스트 본인·초안·유형·현재 공개 가능 조건을 검사한다. 무료 포인트 전용, 유료 포인트 전용, 호스팅 티켓을 구분해 비용 또는 원본 티켓 사용을 기록한다. 개설 비용을 참가자의 보관금이나 호스트 수익으로 합산하지 않는다. 비용·티켓 반환 조건은 개인 구독, 프라이빗 호스팅 비용, 호스팅 티켓과 개설권 사용·반환을 따른다.

앱은 날짜와 시간을 고른 뒤 모집 마감 closedAt을 보낸다. 선택을 취소하면 개설하지 않는다. 돈을 쓰는 개설 입구는 현재 금전 기능 허용 상태를 확인하고, 티켓 경로는 이 클라이언트 검사에서 별도로 처리한다. 티켓이라고 모든 서버 조건을 우회하는 것은 아니다.

한 명 선정과 중복 조작

호스트는 전용 영역의 신청자 목록과 신청 관리 입구를 이용한다. 명령 진행 중에는 선정 버튼을 잠근다. 현재 선정 동작에는 별도 확인 대화상자가 없으며, 서버의 참가비 차감과 선정 결과를 확인해야 한다. 신청자 목록 실패 안내는 존재한다. 서버 전용 상세 응답에는 applicantCount가 없으므로 앱의 해당 값 표시 분기를 실제 제공되는 신청자 수 계약으로 쓰지 않는다.

완료 확인과 취소

완료 확인은 본인 확인 여부와 종료 시각을 검사한다. 취소는 확인 대화상자를 거친 뒤 세션과 진행 중 명령을 재확인한다. 서버는 호스트 본인·현재 상태·완료 여부와 보관금 분쟁 조건을 검사하므로 모든 단계에서 취소할 수 있는 것은 아니다. 완료된 만남이나 허용되지 않는 상태의 취소를 비용·티켓 반환 성공으로 안내하지 않는다.

개설·취소는 요청 키를 사용하는 명령이고, 선정·완료는 현재 API에서 그 헤더를 받지 않는다. 앱은 명령 실패를 토스트로 안내하고, 응답이 불명확하지만 저장됐을 가능성이 있으면 해당 상세·목록을 다시 조회한다. “실패 안내 없음” 또는 “버튼을 다시 누르면 언제나 안전”으로 단순화하지 않는다.

돈이 들어오고 나가는 자리

개설 비용과 참가비 보관

호스트 개설 비용은 선택한 통화·티켓 규칙을 따른다. 참가비 보관은 선정된 참가자의 유료 지갑 거래와 연결된다. 참가비가 0이면 차감·보관금 정산이 없는 모임이다. 결제·환불과 실제 외부 지급의 경계에 따라 임시 결제나 내부 지갑 기록을 실제 현금 이동으로 표현하지 않는다.

지급·환불·상각·몰수

결과현재 처리
RELEASED보관금을 호스트 지갑에 지급하고 원장에 기록한다. 외부 은행 송금 완료와 다르다.
REFUNDED취소된 모임의 참가자 원거래로 반환한다. 원거래나 선정 참가자 연결이 없으면 복구 필요로 남길 수 있다.
WRITTEN_OFF운영 수동 복구에서 원장상 상각한다. 호스트나 참가자에게 돈을 보낸 결과가 아니다.
FORFEITED수취인이 탈퇴한 경우 적용되는 별도 종결이다. 수동 처리에서는 유효한 몰수 동의도 검사한다.

호스트 취소의 개설 비용 환불과 티켓 반환은 참가비 반환과 별개다. 원본 거래와 티켓 상태를 검사하며, 만료된 티켓을 새로운 유효기간으로 되살리지 않는다. 모임 취소 응답만 보고 모든 거래가 반환됐다고 결론내리지 않는다.

일시 장애와 복구 필요의 구분

자동 정산 작업은 매시간 30분에 종료 후 24시간이 지난 HELD 후보를 검사한다. 분쟁 중이면 보관 상태를 유지한다. 일시적 데이터베이스·트랜잭션 장애는 HELD로 두고 다음 실행에서 다시 시도한다. 그 밖의 실패는 별도 기록으로 RECOVERY_REQUIRED 전환을 시도한다. 이 기록 자체가 실패한 경우까지 복구 등록 성공으로 단정하지 않는다.

복구 필요는 자동 지급·환불 성공과 다르다. 운영자는 현재 상태와 원거래를 대조한 뒤 자동 방향 재시도 또는 수동 복구 절차를 선택한다. 일반 HELD를 임의로 수동 처분하는 기능이 아니다.

분쟁과 보관금 보류

사적 모임 분쟁과 신고를 동반한 차단

사적 모임 원천에 걸린 활성 분쟁 보류와 당사자 사이의 증거 보존 중인 신고·차단 사건을 함께 검사한다. 신고를 동반한 차단만이 유일한 보류 경로라는 옛 설명은 현재와 다르다. 회원의 접수 입구는 분쟁 접수, 처리·증거·권한은 분쟁 해결을 따른다. 앱 접수 연결은 전용 상세 번호(privateMeetingId)와 모임 번호(eventId)를 구분한다.

지급·환불·수동 복구의 보류

활성 보류는 양측 완료 후 지급, 기한 경과 자동 지급, 운영자 재시도와 수동 복구 판정에 반영된다. 취소 역시 현재 보관금 조건을 검사한다. 단순 차단 여부·문의 등록·접수 화면 도달만으로 보관금 동결 성공을 추정하지 않는다.

사건 종결 뒤의 재판정

정산 판정 시 종결된 사건의 보류를 정리하고 남은 보류와 양방향 신고·차단 사건의 증거 보존 상태를 다시 검사한다. 사건 하나를 닫았다고 모든 보류가 없어지는 것은 아니다. 보류 해제는 그 순간 지급 완료를 뜻하지 않으며, 이후 해당 처리의 상태·기한·원거래 조건을 다시 만족해야 한다.

운영자의 재시도와 수동 복구

전용 화면과 권한

관리자에는 사적 모임 예치금 복구 목록과 모임별 수동 복구 화면이 있다. MANAGE_PAYMENT 읽기 권한으로 판정·이력을 조회하고 쓰기 권한으로 재시도·제안·승인·취소한다. 명령에는 요청 키가 필요하다. 서버가 계산한 retryable·manualRecoverable 및 차단 사유가 행동 가능 여부의 기준이다.

자동 방향 재시도

RECOVERY_REQUIRED의 모임이 CANCELED이면 원 결제와 선정 참가자를 찾아 환불 방향을, CLOSED이면 호스트 지급 방향을 산출한다. 운영자가 재시도 버튼에서 임의의 수취인이나 금액을 고르지 않는다. 호스트 지급 재시도는 종료 후 24시간 조건도 검사한다. 수취인 탈퇴, 분쟁 보류, 실패 환불 기록의 연결 상태를 확인한 뒤 거래·원장·연관 실패 기록을 함께 처리한다.

수동 제안·승인·취소의 경계

자동 방향을 산출할 수 없는 복구 필요 건은 서버가 수동 가능으로 판정할 때 대조 결과를 제안한다. 방향은 호스트 지급(PAYOUT_HOST), 참가자 환불(REFUND_PARTICIPANT), 상각(WRITE_OFF)이다. 보관액과 같은 양수 금액, 외부 대조 참조, 대조 설명과 필요한 수취인을 기록한다. 제안 단계에는 돈이 움직이지 않는다.

승인은 열린 제안 번호(expectedCaseId)와 판단 메모를 받아 현재 보류·모임·금액·수취인을 다시 검사하고 집행한다. 취소된 모임의 호스트 지급, 임의의 호스트 수취인, 원 참가자가 남아 있는데 다른 사람에게 환불하는 요청을 거절한다. 참가자 연결이 사라진 환불은 존재하는 회원과 대조 근거가 필요하다. 자동 방향을 산출할 수 있으면 수동 절차로 우회하지 않는다.

열린 제안 취소는 집행 없이 이력을 닫는다. 지급이나 환불 뒤 이를 되돌리는 취소가 아니다. 이미 종결됐거나 방향이 바뀐 제안은 승인하지 않고 취소로 정리한다. 제안자와 승인자 기록은 남지만 두 사람이 달라야 한다는 강제 조건을 현재 서비스의 계약으로 쓰지 않는다. 승인된 지급·환불은 수취인 알림을 등록하며 실제 전달은 별도 확인한다.

기능 공개 조건과 실제 출시 증거

서버 코드·앱 버튼·금전 허용 설정·소개팅 공개 설정·운영 배포는 서로 다른 근거다. 이 문서에서 모든 금전 기능이 OFF라고 고정하거나 외부 사업자 네 곳이 모두 연결돼야 기능 전체가 열린다고 단정하지 않는다. 현재 결제 정책과 릴리즈 증거 확인을 기준으로 해당 환경의 설정과 실거래 여부를 확인한다.

티켓 개설, 참가자 선정의 유료 지갑 차감, 대화방 생성, 앱 채팅 입구는 각각의 조건을 가진다. 한 조건의 성공이나 해제만으로 처음 생성부터 완료·환불까지 전체 이용 가능으로 발표하지 않는다.

운영 설정, 실제 생성 입구의 접근 가능성, 두 회원의 참가·선정·채팅·완료 왕복, 외부 실거래, 알림 수신, 관리자 실집행을 이번 문서 작업에서 실행하지 않았다. 소스 대조로 확인한 보호 조건과 남은 제품 공백을 실행 통과 수로 바꾸지 않는다.
