F03-15. 이벤트 카풀

서버에는 운전자 offer·탑승 선택·호스트 결정과 배정·안전신고 API가 있다. Flutter에는 운전자 신고 API·화면·route가 있으나 그 route로 이동시키는 인앱 caller가 없어 direct route/deep-link 수준이다. 전체 카풀 운영 화면은 완성되지 않았다.

카풀은 "누가 탈 수 있나"보다 "누가 누구 차에 배정됐나"가 중요하다. 운전자 지원, 호스트 확정, 참가자 배정, 배정 해제, 개별 이동 선택을 모두 분리해야 당일 혼선이 줄어든다.

현재 구현 경계

배정 로그 테이블은 있지만 서비스가 기록하지 않는다. 알림 77~80도 enum만 있고 발행·전송 코드가 없다. offer 목록은 Host/CoHost 또는 참석자만 보지만, 탑승자 목록의 일반 사용자는 별도 참석 검사 없이 자기 row만 본다. 자차 허용 토글도 SELF/DRIVER 선택을 실제로 막지 않는다.

사용자 시나리오

운전자

참가자가 운전자로 지원

좌석 수와 픽업 가능 인원을 입력해 차량 제공을 신청한다. 호스트가 확정하기 전까지는 배정 대상 차량이 아니다.

호스트

운전자 확정 후 참가자 배정

호스트가 운전자를 확정한 뒤 참가자를 해당 차량에 배정한다. 픽업 가능 인원 초과 배정은 차단된다.

참가자

개별 이동 선택

서버는 SELF 선택을 저장할 수 있지만 자차 허용 토글이나 실제 운전자 역할과 입력 enum을 대조하지 않는다. Flutter 선택 화면도 없다.

권한

참가자는 자기 정보만 본다

일반 참가자가 탑승자 목록을 조회하면 본인 항목만 보인다. 호스트는 전체 탑승자를 보며 운영한다.

방식 가드

카풀이 아닌 이벤트에서 진입

등록·결정·탑승·배정은 CARPOOL mode를 검사한다. 반면 offer 조회·탑승자 조회·신고에는 같은 mode 가드가 없어 완전히 닫히지는 않는다.

초안 단계 전환

카풀 설정 후 버스로 바꿈

초안에서 이동수단 방식을 버스로 바꾸면 더 이상 유효하지 않은 카풀 데이터가 삭제된다. 공개 전 변경이므로 사용자에게 알림은 필요 없다.

운영자가 알아야 할 것

당일 혼선을 줄이는 제약
  • 확정된 운전자만 배정 대상이다. 지원만 한 운전자의 차량에는 참가자를 배정하지 않는다.
  • 픽업 가능 인원을 넘길 수 없다. 좌석 수와 픽업 가능 인원은 다를 수 있다.
  • 배정 이력은 현재 남지 않는다. DDL의 assignment log를 서비스가 쓰지 않는다.
  • 알림은 미구현이다. 77~80 enum만 있고 생산 배선과 Flutter deep link가 없다.
  • Flutter는 신고만 제공한다. 운전자·탑승자·호스트 운영 화면은 없다.
  • terminal event mutation이 가능하다. offer 생성 외 decide/register/assign/report는 event status를 검사하지 않는다.
  • 재배정·등록 경쟁에 결함이 있다. full offer에 같은 passenger를 다시 지정하면 자기 count로 거부되고, register/assign 경쟁은 lost update될 수 있다.
