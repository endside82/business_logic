F01-07. 관심사 태그 관리

사용자가 본인 관심사를 표현하는 태그 묶음을 만들고 유지한다. 온보딩에서 처음 등록한 뒤 프로필에서는 추가·삭제할 수 있다. 서버 PUT은 이름·가중치 수정을 지원하지만 현재 앱 화면에는 편집 경로가 없다. 이 태그가 추천·검색의 직접 입력값이므로, 사용자가 본 단위를 다루는 빈도와 추천 품질이 정비례한다.

2026-07-29 소스 재실측

관심사 태그 CRUD는 유지되지만 현재 태그는 실제 추천 입력이다. PersonSheet는 공통 태그를 뷰어 weight 순 최대 5개만 보여 주고, 홈 사람 추천은 태그·선언 선호의 교집합을 COMMON_GROUND 신호로 쓴다. 데이팅 태그 Jaccard 성분(0.30)은 양쪽 communityDataOptIn=true일 때만 사용하며 미동의 시 남은 가중치를 재정규화한다. 추천·데이트 점수에는 저장 weight를 직접 곱하지 않는다.

같은 사람도 봄과 가을의 관심사가 다르다. 현재 앱은 서버 카탈로그에서 태그를 골라 추가하고 X로 삭제하는 방식으로 관심사 집합을 갱신한다. 서버에는 가중치와 PUT 계약이 있지만 앱의 Repository·Provider·화면에는 편집 호출이 없다. 따라서 현재 사용자가 조절할 수 있는 신호는 태그의 포함 여부이며, 가중치 자동 조정도 구현되어 있지 않다.

사용자 시나리오

최초 등록

온보딩에서 세 개 골라 등록

가입 직후 온보딩 관심사 화면에서 등산·카페탐방·영화 세 개를 고르고 "다음"을 누른다. 세 개가 차례로 등록되고 모두 성공하면 다음 단계로 이동한다. 세 개 모두 가중치는 같은 기본값이다.

이 흐름이 남기는 것 — 추천 시스템에 처음으로 사용자 신호가 들어오는 순간. 본 등록이 없으면 첫 홈 화면이 비어 보인다.

조회

프로필에서 내 태그 목록 확인

설정 화면의 관심사 항목에서 본인이 등록한 태그를 한눈에 본다. 관심도가 높은 태그가 위에 보인다 — 사용자가 본인이 어떤 흥미를 가진 사람인지 한 화면에서 확인할 수 있다.

서버 전용 계약

이름·가중치 편집은 현재 화면에 없음

PUT API를 직접 사용하면 본인 태그를 다른 카탈로그 라벨(예: 러닝 → 자전거)로 바꾸거나 가중치만 수정할 수 있다. 마라톤처럼 카탈로그 밖 라벨은 거절된다. 현재 앱에는 이 PUT을 호출하는 사용자 UI가 없다.

중복

이미 가진 태그를 또 추가하려 함

같은 이름의 태그를 다시 등록하면 서버가 거절한다. 프로필 화면은 이미 선택한 칩을 비활성화해 정상 흐름의 중복을 막지만, 동시 기기 등으로 서버 오류가 나면 현재 Provider는 실패를 false로 접고 화면도 await하지 않아 안내가 뜨지 않는다.

한도

21번째 태그 등록 시도

이미 20개를 등록한 사용자가 새 태그를 시도하면 "최대 20개까지 등록 가능합니다" 안내가 뜬다. 사용자는 덜 중요한 태그를 삭제하고 새 태그를 추가하거나 그대로 둘 수 있다.

삭제

흥미가 사라진 태그를 정리

더 이상 관심 없는 태그를 삭제한다 — 추천에서 즉시 제외된다. 사용자가 본인 관심사를 한 번씩 정리해 줘야 추천의 노이즈가 줄어든다는 사실이 본 단위의 가치.

운영자가 알아야 할 것

태그 정책과 결정점
  • 태그 카탈로그의 단일 출처는 서버다. 온보딩과 프로필 화면이 GET /api/v1/interests/catalog의 공유 Provider를 사용한다. 현재 허용 라벨은 25개이며 카탈로그 변경 때문에 클라이언트 앱을 다시 배포할 필요는 없다.
  • 사용자당 최대 20개 한도는 추천 알고리즘 성능에 맞춘 수치. 한도를 늘리면 알고리즘 입력 차원이 커져 추천 정확도가 떨어질 수 있다 — 한도 변경 시 추천 도메인과 함께 결정.
  • 다른 사용자의 태그를 수정·삭제할 수 없게 본인 소유 검증이 매번 일어난다. 본인이 아닌 태그 ID로 요청하면 "태그를 찾을 수 없습니다"로 응답해서 다른 사용자의 태그 존재 여부 자체를 알 수 없게 한다.
  • 가중치는 서버 모델에 있지만 현재 사용자가 조정할 수 없다. Retrofit PUT 선언만 있고 ProfileRepository·Provider·화면 호출자가 없다. 행동 기반 자동 조정도 현재 소스에는 없다.
  • 온보딩에서의 일괄 등록은 한 개씩 순차로 처리된다. 중간에 실패하면 일부만 저장되고 다음 시도에서 중복으로 거절될 수 있다 — 사용자가 답답하게 막힐 위험이 있는 알려진 한계점.
