F04-08. 게시판·게시글

게시판관리제공범위·글권한/상태·검색미적용·사진·초안/멱등재확인·예약실제결과·좋아요·프로필작성글범위를 구분한다. 2026-11-22 소스 대조이며 새 제품 실행과 구분합니다.

실제 접근 경로와 행동 입구

클럽 커뮤니티의 게시판 구역은 게시판 목록을 보여 준다. 회원 권한을 읽는 동안 로딩·재시도를 제공하고 비회원은 미리보기로 보낸다. 게시판 카드에서 /clubs/{clubId}/boards/{boardId}/posts로 들어가며, 커뮤니티 게시판 구역의 추가 버튼은 서버 createBoard 능력을 기준으로 게시판 만들기 창을 연다. 이전 문서의 목록 내부 “게시판 추가 TextButton” 설명과 구분한다.

게시글 목록 작성 버튼은 해당 게시판 행의 actions.write를 사용한다. 작성 경로는 /clubs/{clubId}/boards/{boardId}/posts/create, 상세는 /clubs/{clubId}/posts/{postId}?boardId={boardId}, 수정은 상세 경로의 /edit다. 상세·수정에서 유효한 boardId가 없으면 게시판에서 열라는 잘못된 접근 안내를 표시한다. 댓글 알림은 댓글과 대상 댓글 찾기의 경로로 연결된다.

상세 상단 더보기는 본인 수정, 서버 actions.pin 고정/해제, actions.delete 삭제, 타인 신고를 구분한다. 삭제는 확인 뒤 요청하고 성공 시 목록을 갱신해 복귀한다. 고정은 서버가 반환한 최종 상태로 안내하고 목록을 다시 읽는다. 타인 신고에는 COMMUNITY_POST, 게시글 ID와 클럽 ID를 전달한다. 댓글 행 메뉴는 별도 대상이며 게시글 메뉴와 혼동하지 않는다.

게시판 계약과 삭제 시 보존

기본 경로 /api/v1/clubs/{clubId}/boards에서 GET은 List<ClubBoardVo>, POST는 201 VO, PUT /{boardId}는 200 VO, DELETE /{boardId}는 204다. 생성은 name, 선택 description; 수정은 선택 name, description, sortOrder: Integer다. 응답은 ID·유형·이름·설명·순서·활성 게시글 수·최근 글 시각·최근 댓글 시각·actions.write다.

클럽 생성 시 NOTICE 공지사항, FREE 자유게시판, INTRODUCTION 가입인사를 순서 0·1·2로 만든다. 이는 공지 기능의 별도 공지 목록과 데이터가 다르다. 유효 운영진은 CUSTOM 게시판을 추가하고 수정·삭제할 수 있다. 이름은 생성 시 공백 불가·50자 이하, 설명은 200자 이하다. 같은 클럽의 동일 이름은 거절한다. 수정의 빈 이름은 이름 변경으로 적용하지 않고 null 설명은 기존 값을 유지한다. 수정 sortOrder에는 이 서비스의 별도 범위 검사가 없다.

기본 게시판 삭제는 BOARD_DEFAULT_NOT_DELETABLE이다. 사용자 게시판 삭제는 게시판·게시글을 잠그고 DELETED가 아닌 보존 대상이 있는지 검사한다. 예약 SCHEDULED와 숨김 HIDDEN도 이 검사에 포함한다. 보존 대상이 있는데 자유게시판이 없으면 삭제를 중단한다.

보존 대상이 하나라도 있으면 updateBoardId가 해당 게시판의 모든 글을 자유게시판으로 옮긴다. 이동 질의 자체에는 상태 필터가 없어 같은 게시판의 DELETED 글도 함께 옮겨질 수 있다. 전부 삭제 상태인 경우에는 이동을 생략하고 게시판 삭제와 남은 사진 참조 정리를 수행한다. “삭제 글은 항상 이동 제외”로 단정하지 않는다.

앱은 생성 창·전송 잠금·성공/실패를 제공한다. 수정·삭제 API와 Repository·Provider는 있으나 현재 앱 presentation의 호출 입구는 없다. 이를 앱에서 모두 사용할 수 있는 관리 기능으로 표기하지 않는다.

게시글 기본 경로는 /api/v1/clubs/{clubId}/boards/{boardId}/posts다.

목록은 현재 회원만 읽고 ACTIVE 글과 차단 관계가 아닌 작성자를 대상으로 한다. 고정 먼저·생성 시각 내림차순·ID 내림차순이며 앱은 20개씩 읽는다. 서버 검색 파라미터에는 페이지 외 검색어가 없다. 앱 검색창은 검색어를 기억하지만 setKeyword가 첫 페이지 재조회만 하고 실제 필터나 검색어 전송을 하지 않는다.

목록 VO는 ID·작성자·제목·고정·조회/댓글/좋아요 수·내 좋아요 여부·대표 사진 키/URL·생성 시각·투표 요약·장소 수다. 대표 사진은 정렬 순서 0의 한 장이다. 목록은 읽은 글들을 고정/일반으로 분리하고 새로고침·추가 페이지 오류 재시도를 제공한다. “최대 3장 썸네일”은 현재 목록 계약이 아니다.

상세는 게시판과 클럽 소속·활성 상태·현재 회원을 검사하고 차단 작성자는 NOT_FOUND로 가린다. 정상 상세 조회는 조회 수 증가 질의를 실행한다. 응답에는 본문·서식·사진 목록·수정 시각·상태·투표·장소·행 actions.pin/delete가 더해진다. 생성·수정·고정 응답과 생성 멱등 재생은 별도 경로이므로 모두 상세 조회 수 증가로 취급하지 않는다.

게시판 카드의 postCount는 모든 ACTIVE 글 수이고 최근 글·댓글 시각에는 차단 가림을 적용한다. 최근 댓글은 활성 글의 활성 댓글과 활성/삭제 부모 아래 답글을 포함한다. 카드 수와 차단 후 게시글 목록 총계가 항상 같다고 보장하지 않는다.

작성·수정·권한과 상태

생성 요청 ClubPostAddParam은 title, content, contentRich, imageKeys, scheduledAt, polls, places다. 수정 ClubPostModParam은 제목·본문·서식·사진키·장소를 받으며 예약 시각과 투표 정의 필드는 없다. 투표 변경은 별도 투표 명령이다. 장소·투표는 공개 범위 검사와 각 서비스 검증을 거친다.

서버는 제목·본문 공백을 거절하고 제목을 200자 이하로 제한한다. 앱 제목은 100자이며 본문은 RichContentEditor를 사용한다. 예전 단순 TextArea의 3000자 카운터를 현재 기준으로 두지 않는다. 서버는 평문과 contentRich의 일치·허용 서식을 검증한다. 앱 작성기에는 미리보기·사진 순서 변경·공개 범위가 열린 투표/장소 편집이 있다. 앱 작성기 한도는 사진 10장, 투표 5개, 장소 5개다. 세부 투표·장소 정책 전체를 이 문서에서 새로 검수한 것으로 간주하지 않는다.

일반 게시판 작성은 현재 회원, NOTICE 작성은 유효 운영진도 요구한다. 생성 기본값은 고정 false·조회/댓글 수 0이며 예약 시각이 있으면 SCHEDULED, 없으면 ACTIVE다. 수정은 현재 회원인 원작성자와 활성 글을 요구하며 운영진도 타인 글은 수정할 수 없다. 본인 삭제도 현재 회원을 요구하고, 타인 삭제는 유효 운영진만 가능하다. 이 게시글 삭제 API에는 댓글 조치와 같은 사유 본문이 없다. 삭제는 DELETED로 바꾸며 즉시 모든 첨부 파일의 물리 삭제를 보장하지 않는다.

서버 상태는 SCHEDULED, ACTIVE, DELETED, HIDDEN이다. 일반 목록·상세·수정·삭제·고정·좋아요는 활성 상태를 대상으로 한다. 앱 enum은 예약을 지원하며 모르는 상태는 unknown이다. 모델은 원문 상태 문자열을 보관하므로 현재 서버 HIDDEN이 자동으로 ACTIVE로 해석되는 계약은 아니다.

사진 첨부와 읽기

앱은 선택한 사진을 해당 계정·클럽·게시판·초안의 대기 파일로 보관하고 업로드할 때 초안 소유를 확인한다. ServerFilePurpose.clubPostImage로 업로드하며 실패한 대기 사진은 다시 올리거나 버릴 수 있다. 업로드 중이거나 대기 파일이 남으면 게시 요청을 막는다. 성공한 사진은 파일 키와 표시 경로로 초안에 저장한다.

서버는 최대 10장·중복 키·빈 키를 검사한다. 신규 첨부는 실제 파일이 존재하고 작성자 소유이며 COMPLETED, CLUB_POST_IMAGE와 호환되는 용도여야 한다. 다른 게시글 사진으로 이미 연결된 키도 거절한다. 수정 imageKeys는 최종 목록이며 null도 빈 목록으로 처리한다. 제외된 참조 해제·새 참조 연결·유지 사진의 순서를 동기화한다.

목록 대표 사진과 상세 사진은 작성자·용도를 지정한 다운로드 URL 발급 경로로 읽는다. 파일 키를 그대로 공개 URL로 만들지 않는다. 이전 CLUB_BOARD 표기나 “각 5MB·24시간 후 반드시 소실”을 이 게시글 코드의 현재 보장으로 유지하지 않는다. 파일 서비스의 업로드·보존 정책과 구분한다.

초안·불명확 결과·성공 후 정리

작성·수정 초안은 계정·클럽·게시판·선택 게시글 ID로 분리하고 세션/계정 세대를 확인한다. 제목·본문·서식·사진·대기 업로드·투표/장소 등의 입력을 500ms 뒤 저장하며 이탈 시 저장 후 나가기를 확인한다. 저장 실패를 감추고 이탈하지 않는다. 수정은 서버에서 읽은 글을 먼저 채운 후 해당 초안을 복원한다. 현재 수정 요청에는 기대 버전 필드가 없어 동시 수정 충돌 검출을 보장하지 않는다.

신규 작성은 요청 키와 전송 본문 전체를 PendingPostPublish로 저장한 후 전송한다. 저장 실패면 전송하지 않는다. 불명확한 결과에서는 편집을 잠그고 “게시 결과 확인”으로 동일 키·본문을 다시 보낸다. 예약 시각이 이미 지났더라도 미확정 요청의 결과 확인은 원래 본문으로 진행한다. 명확한 입력/처리 거절 또는 명령 영수증 안에서 확정된 권한/없음 거절만 pending을 해제한다.

서버의 키가 있는 작성은 계정·명령 종류·키로 결과 참조를 보관하고 같은 요청이면 게시글 ID로 현재 결과를 재구성한다. 같은 키에 다른 내용은 충돌이다. 재조회할 대상이 사라지거나 이동해 원래 게시판에서 읽을 수 없으면 결과 확인 불가 409이며 새 글을 다시 만들지 않는다. 키 없는 서버 호출은 기존 생성 경로이고 앱은 키를 보낸다.

성공 뒤에는 초안 정리를 끝내고 목록/상세를 갱신해 복귀한다. 정리 실패는 “서버 저장 성공·기기 정리 실패”로 분리하며 현재 화면에서 재발행하지 않고 정리만 재시도한다. 수정 때 공개 범위 때문에 보내지 못한 장소 초안은 저장된 서버 본문과 함께 남길 수 있다. 수정 API에는 신규 작성과 같은 멱등 키 계약이 없다.

일반 작성 초안의 캡처에는 예약 시각 필드가 없고 전송 준비가 끝난 pending 본문에만 scheduledAt이 포함된다. 따라서 전송 전 예약 선택까지 항상 재진입 복원된다고 설명하지 않는다.

예약 게시와 좋아요

앱은 서울 기준으로 지금보다 1분 뒤인 예약 시각을 요구하고 내 예약 목록 입구를 제공한다. 서버도 최소 1분·작성자 소유·SCHEDULED 상태와 동일 대상의 진행 중 예약 중복을 확인한다. 글과 예약 작업을 함께 생성하며 예약 글은 일반 목록·상세에서 제외한다. “앱에 예약 상태 enum과 관리 입구가 없다”는 과거 Gap은 더 이상 현재 설명이 아니다. 예약 작업 관리와 공개 글 수정은 다른 흐름이다.

예약 실행 때 글이 속한 현재 게시판과 현재 작성 권한을 다시 검사한다. 글이 이미 활성 상태이면 게시 완료 결과, 없거나 삭제되었으면 대상 소실, 권한을 잃었으면 권한 상실로 구분한다. 정상 실행은 ACTIVE로 전환하고 대기 투표를 연다. 공통 예약 처리에서 게시 완료는 EXECUTED, 대상 소실·권한 상실은 CANCELLED, 유효 실행 중 예외는 FAILED와 작성자 실패 알림으로 처리한다. 실행 차수를 잃은 요청은 이전 결과를 덮어쓰지 않는다. 이는 소스 계약이며 실제 시각에 실행됐다는 기록이 아니다.

고정은 유효 운영진이 ACTIVE 글을 잠근 뒤 현재 값을 반전하는 명령이다. 원하는 상태를 지정하는 멱등 명령과 다르며 이 서비스에 공지의 고정 3개 한도를 적용하지 않는다.

좋아요는 현재 회원·게시판 소속·ACTIVE 글을 잠그고 존재하지 않으면 추가한다. 취소는 존재하면 지운다. 각각 반복해도 중복 관계를 만들지 않으며 {postId, likeCount, likedByMe}를 반환한다. 앱 목록/상세는 요청 중 같은 글의 반복 탭을 억제하고 먼저 표시한 값을 서버 결과로 확정하거나 실패 시 되돌린다. 목록과 상세는 갱신 방식이 같지 않으므로 모든 화면의 즉시 일치를 보장하지 않는다.

프로필에서 내가 볼 수 있는 작성 글

GET /api/v1/users/{targetUserId}/club-posts는 Page<UserClubPostVo>다. 타인을 조회하면 계정 사용 가능·양방향 차단·프로필 상세 접근을 검사하고 클럽 비공개 설정이면 빈 페이지를 반환한다. 실제 목록은 대상 작성자의 ACTIVE 글 중 조회자가 현재 가입한 클럽만 포함하며 생성 시각·ID 내림차순이다. 대상 작성자가 현재도 그 클럽 회원이어야 한다는 추가 조건은 이 질의에 없다.

앱 프로필의 “내가 볼 수 있는 작성 글”을 펼칠 때 20개 단위로 조회한다. 보이는 총계·이전/다음 쪽을 제공하고 뒤쪽 페이지가 비면 첫 쪽으로 되돌린다. 카드에는 클럽·게시판·작성일을 표시하며 게시글 상세에 boardId를 함께 전달한다. 접힘·페이지·영역 크기 상태는 프로필 탐색 안에서 보관한다.

수용 기준과 검증 근거

  • AC-01 접근과 행동: 게시판·글 목록·작성·상세·수정·알림·프로필 입구가 필요한 club/board/post ID와 권한을 전달하는지 확인한다.
  • AC-02 게시판 생성: 기본 3종과 CUSTOM을 구분하고 유효 운영진·이름/설명 길이·중복 이름·전송 잠금을 확인한다.
  • AC-03 게시판 수정 제공 범위: 수정 API의 부분 적용과 앱 입구 부재를 구분하며 이름·설명·순서의 실제 조건을 확인한다.
  • AC-04 게시판 삭제 보존: 기본판 삭제 거절, 예약/숨김 보존 대상, 자유게시판 부재 시 중단, 보존 대상이 있으면 모든 글 이동을 확인한다.
  • AC-05 목록과 검색: 회원·ACTIVE·차단 필터·고정 우선·20개 페이지와 검색어 미적용을 구분한다.
  • AC-06 상세와 숫자: 클럽/게시판 소속·상태·차단·조회 수 증가 경로와 게시판 총계/최근 활동의 서로 다른 필터를 확인한다.
  • AC-07 작성 권한과 본문: 현재 회원·NOTICE 운영진·제목 서버200/앱100·본문/서식·예약 상태와 공개 범위 검사를 확인한다.
  • AC-08 수정과 삭제: 본인 현재 회원만 수정, 본인/유효 운영진 삭제, ACTIVE 조건과 게시글 삭제 사유 API 부재를 확인한다.
  • AC-09 사진 계약: 10장·중복/빈 키·파일 소유/완료/용도·기존 연결 검사와 최종 목록의 참조 해제/순서 반영을 확인한다.
  • AC-10 업로드와 초안: 계정/대상별 입력·대기 파일·이탈 저장·실패 재시도와 대기 업로드 중 게시 차단을 확인한다.
  • AC-11 작성 결과 재확인: 전송 전 키/본문 저장, 저장 실패 시 무전송, 불명확 결과 동일 요청 재생·충돌·결과 확인 불가를 확인한다.
  • AC-12 성공 후 정리: 서버 성공과 기기 정리 실패를 구분하고 정리 재시도가 재발행하지 않으며 보류 장소 초안을 보존하는지 확인한다.
  • AC-13 예약 생성과 실행: 최소 1분·소유/상태/중복·공개 목록 제외·실행 때 현재 권한·투표 활성·실제 작업 결과를 구분한다.
  • AC-14 고정과 좋아요: 고정 반전과 좋아요/취소 반복의 차이, 요청 중 중복 탭 억제·응답 확정·실패 되돌림을 확인한다.
  • AC-15 프로필 작성 글: 타인 접근/비공개·조회자 가입 클럽·ACTIVE 범위와 20개 페이지·ID를 포함한 상세 복귀를 확인한다.
  • AC-16 남은 경계: 검색·게시판 관리 입구·동시 수정·예약 초안·숨김 상태를 현재 구현된 기능과 분리해 기록한다.

ClubBoardServiceTest의 예약 글 이동·보존 대상 없음·자유게시판 부재 단언과 post_draft_lifecycle_test.dart의 응답 유실 후 같은 키·본문 복원 단언을 읽었다. 새 제품 시험을 실행한 결과가 아니며 보존한 과거 시나리오의 시드·주소·실행 기록을 현재 통과 수로 합산하지 않는다.
