F07-06 수취 확인·일괄 확인·만료·재요청·손실 정리

수취 확인과 신고·일괄 건별 처리·만료의 미완료 의무·재요청/포기·운영자 은행분 해소·전체 완료를 구분한다. 2026-11-22 소스 대조이며 새 제품 실행과 구분합니다.

결론

일반 계좌 송금은 받는 사람 또는 정산 생성자가 실제 입금 내역을 확인한 뒤 완료 처리한다. 생성자라도 본인이 보낸 송금을 스스로 확인할 수 없다. 혼합 결제의 은행분도 같은 당사자 원칙을 따르지만 가상계좌·수동 확인 허용 정책을 추가로 검사한다. ‘보냈어요’ 신고와 외부 송금 앱 열기는 입금 확정이 아니다.

일괄 확인은 건별 성공·실패를 반환한다. 만료 송금은 지급 의무가 끝난 것이 아니며, 재요청하거나 포기하는 후속 판단이 필요하다. 생성자의 만료 송금 포기와 운영자의 혼합 은행분 손실 정리는 서로 다른 처리다. 정산 전체 완료는 현재 남은 의무를 서버가 다시 판정한다.

실제 입구와 목록

정산 현황의 송금 내역에서 ‘모든 송금’과 ‘내가 주고받는 돈’을 본다. 초기 탭은 본인이 보내거나 받는 목록이며, 탭을 바꾸면 해당 범위를 다시 조회한다. 읽기 권한과 현재 정산 선택은 정산 현황·금액 요약·영수증 열람을 따른다.

이 화면의 관리 역할은 정산 생성자와 로그인 회원을 비교한다. 항목별 납부 방식의 정보성 송금 행은 목록에서 제외한다. 실제 항목별 입금은 항목별 납부 현황에서 다루며, 분담과 송금을 중복 확인하지 않는다. 지급 방향·계좌 조회·포인트 납부는 분담·송금 납부와 반환을 따른다.

일반 대기 송금의 확인 버튼은 수취자 또는 생성자에게 제공하고 송금자 자신은 제외한다. 대기 이의가 있으면 일반 확인을 막는다. 혼합 은행분 확인, 만료 송금의 포기·재요청, 일괄 확인과 다시 알림도 같은 목록에 연결되지만 각 행동의 서버 조건은 서로 다르다.

단건 수취 확인

대상서버가 확인하는 조건성공 결과
일반 송금요청 모임과 실제 정산 일치, 송금 PENDING, 정산 ACTIVE, 확인자가 송금자 아님, 수취자 또는 생성자, 대기 송금 이의 없음BANK_TRANSFER/COMPLETED, 완료 시각, 감사와 송금자 알림 등록, 전체 완료 재평가
혼합 은행분모임 일치, 송금 BANK_AWAITING_CONFIRM, 정산 ACTIVE, 송금자 아님, 수취자 또는 생성자, 대기 이의 없음, 수동 은행 확인 정책 허용포인트 거래는 유지하고 송금을 COMPLETED로 전환, 완료 시각·감사·송금자 알림 등록, 전체 완료 재평가
항목별 분담실제 낼 사람 자신 아님, 실제 받을 사람 또는 생성자, 진행 중·항목별 납부·미완료·자기 몫 아님, 분담/항목 대기 이의 없음, 모임 일치해당 분담 은행 납부 완료와 전체 의무 재평가

서버는 부모 정산·대상 행을 잠그고 조건을 확인한다. 잘못된 모임 번호나 다른 사람의 대상 번호를 넘기는 것으로 확인 권한을 얻지 못한다. 이전 설명의 ‘혼합 확인에서 모임 번호를 검증하지 않는다’는 현재 코드에 해당하지 않는다.

앱은 확인 전에 실제 입금 내역을 대조하라는 경고를 표시한다. 혼합 확인창의 송금 총액은 은행분과 다를 수 있음을 명시한다. 일반 송금 응답에는 별도 은행분 금액과 수동 확인 허용 상태가 없으므로, 버튼 노출만으로 서버의 수동 확인 허용을 보장하지 않는다. 정상 가상계좌의 자동 입금 처리와 사람이 확인하는 예외 경로도 구분한다.

일괄 확인과 부분 실패

앱은 현재 탭의 표시 대상 중 PENDING·확인 가능한 당사자·대기 이의 없음에 해당하는 송금 번호와 합계를 계산한다. 혼합 은행분 대기는 이 묶음에 넣지 않는다. 개별 체크박스로 임의 선택한 목록이 아니라 현재 계산된 확인 대상이다. 생성자에게 하단 일괄 확인을 제공하며 조회 실패·조회 중·처리 중·대상 없음이면 실행을 막는다.

서버 창구는 정산 생성자 본인인지 먼저 확인한다. 검사 함수 이름에 호스트가 들어가지만 현재 구현은 생성자 번호를 직접 비교한다. 이후 각 송금에는 수취자/생성자·본인 송금 금지·현재 상태·대기 이의·모임 소속 검사를 다시 적용한다. 현재 모임 호스트라는 이유만으로 일괄 확인 권한을 얻지 않는다. 목록은 비어 있거나 null 번호를 포함하면 거절한다.

각 건은 별도 확인 서비스의 트랜잭션으로 실행한다. 한 건이 실패해도 다음 건을 시도하며 성공 수·실패 수와 실패한 번호/이유를 응답한다. 이전 문서의 같은 서비스 내부 호출에 따른 건별 트랜잭션 누락 설명은 현재 구조에서 해소되었다.

앱은 성공·실패 건수를 나눠 표시한다. 현재 Provider는 서버의 개별 실패 상세를 화면용 결과에 넘기지 않으므로 어떤 건이 실패했는지 목록에서 즉시 설명하는 기능까지 있다고 쓰지 않는다. 성공이 있으면 관련 현황을 갱신하며 처리됐을 가능성이 있는 통신 실패에도 재조회한다. 같은 진행 중 일괄 요청은 다시 보내지 않고 계정이 바뀐 결과는 적용하지 않는다.

송금 신고와 다시 알림

‘보냈어요’는 실제 지급자가 등록하는 표시다. 신고 시각은 수취자·생성자에게, 본인 신고 여부는 송금자에게 공개한다. 다른 참석자에게 모든 신고 정보를 공개하지 않는다. 신고 철회도 은행 이체 취소나 입금 확인 취소가 아니다. 상세 조건은 분담·송금 납부와 반환을 따른다.

현재 ‘입금 확인 다시 알리기’는 PENDING과 BANK_AWAITING_CONFIRM을 확인한 뒤 안내 시트를 열고 실제 다시 알림 Provider를 호출한다. 서버 성공 응답 뒤에는 ‘다시 알림을 요청했습니다’라고 표시하며 실패는 오류로 표시한다. 이전 문서의 ‘서버 호출 없이 발송 성공 토스트만 표시’는 현재 구현과 다르다. 서버의 실제 수신 대상·간격·권한은 리마인드와 마감 연장의 조건을 따른다. 요청 성공은 기기 알림 수신 증명이 아니다.

만료와 해결 대기

서버 스케줄의 매일 05:00 실행은 생성 후 30일이 지난 PENDING 중 신고 표시가 없는 송금을 대상으로 한다. 실제 처리 직전 잠근 행에서 다시 상태와 신고 여부를 확인한다. 신고가 저장되어 있으면 만료시키지 않는다. 만료 시 송금자와 다른 사람인 정산 생성자에게 후속 판단 알림을 등록한다. 실행 시간은 서버 스케줄 설정 기준이며 이 문서에서 운영 타임존·실행 성공을 증명하지 않는다.

BANK_AWAITING_CONFIRM과 PENDING_MANUAL_REFUND는 시간이 지났다는 이유만으로 만료시키지 않는다. 매일 05:10 실행이 기본 3일 간격 설정으로 장기 대기를 확인한다. 은행 확인 대기는 수취자와 별도 생성자에게, 직접 반환 대기는 수취자에게 알림을 등록한다. 반복 횟수가 2 이상이면 운영 경보를 등록한다. 진행 중이 아닌 정산에 은행 확인 대기가 남으면 사용자에게 확인을 요구하는 대신 운영 경보를 남긴다.

30일을 넘긴 신고된 PENDING은 별도로 수취 확인 알림과 운영 경보 대상이 된다. 혼합 은행 확인의 최초 대기 기준은 별도 은행 대기 진입 시각이 아닌 생성 시각으로 계산될 수 있어, 결제를 늦게 시작하면 알림이 예상보다 빨라질 여지가 있다.

생성자의 재요청과 포기

행동조건결과
다시 요청모임 일치, 기존 송금 EXPIRED, 정산 ACTIVE, 생성자 본인, 재요청 횟수 2 미만, 송금 양쪽 계정 닫힘 아님같은 당사자·금액의 새 PENDING, 원본 연결과 횟수 증가, 원본은 SUPERSEDED, 감사·송금자 알림 등록
포기모임 일치, 송금 EXPIRED, 정산 ACTIVE, 생성자 본인, 선택 사유 500자 이하기존 송금 CANCELLED, 포기 시각·행위자·사유 저장, 감사와 전체 완료 재평가

재요청은 기존 행을 대기로 되돌리는 동작이 아니다. 앱은 최대 2회 안내와 한도 초과 비활성화를 제공한다. 포기는 선택 사유를 입력하는 확인창에서 실행한다. 상태가 이미 바뀌었다는 응답은 목록을 다시 읽어 안내한다. 포기 결과가 불확실하면 성공으로 닫지 않고 목록 확인 안내와 입력을 유지한다.

만료된 송금에 이의가 있으면 생성자의 행에도 ‘이의 제기 중’을 표시한다. 현재 재요청·포기 서버 함수에는 대기 이의를 별도로 차단하는 조건이 없으며, 새 송금 생성이 원본 이의를 자동으로 이전하는 처리도 이 경로에는 없다. 이의 표시와 각 행동의 실제 허용 조건을 혼동하지 않는다.

운영자의 손실 정리와 은행분

운영자의 해소 명령은 생성자의 만료 송금 포기와 별도다. 같은 작업 식별자에는 최초 결과를 재사용하고, 예상 버전·현재 상태·대상 계정·필요 잔액을 다시 판단한다. 은행 확인은 유효한 증빙 파일이 필요하다. 이번 대조는 서버 정책·실행 분기이며 관리자 화면 전체의 실제 이용 확인이 아니다.

혼합 은행 확인 대기의 손실 정리는 원래 포인트 거래의 남은 몫을 반환하고 은행분을 면제한다. ‘먼저 낸 포인트는 언제나 유지’라는 설명을 적용하지 않는다. 이후 은행분을 늦게 확인할 때는 이미 반환한 포인트를 회수해야 할 수 있으며 잔액 등 현재 조건을 검사한다.

포인트 보상도 항상 같은 결과가 아니다. 직접 반환 대기는 은행분 또는 해당 기록이 없는 총액을 무료 포인트로 보상한다. 되돌림 실패는 원 포인트 거래의 남은 금액을 반환하고, 은행분이 지갑에 적립되었는지 외부에서 받았는지에 따라 은행분 보상 후 종결하거나 직접 반환 대기를 남긴다. 이전 문서의 ‘가상계좌 적립 은행분은 재설정만 허용’은 현재 정책과 다르다.

수입과 취소 뒤 확인

지출과 수입은 실제 지급 방향이 반대이며 자기 몫에는 지급 의무가 없다. 정산 취소 뒤 외부 은행 송금이 뒤늦게 확인되어도 일반 진행 중 입금 확인을 그대로 실행하지 않는다. 운영자의 별도 취소 후 수취 확인은 취소 상태·현재 송금 상태·수동 수취 허용·사유·증빙을 검사하고 직접 반환 대기를 남긴다. 포인트 되돌림이 진행 중인 혼합 은행 확인은 바로 허용하지 않는다.

취소 이후 돈의 반환·역분개·실패 복구는 금액 검토·정산 요청·취소와 반환을, 수취인이 포인트로 돌려주는 행동은 분담·송금 납부와 반환을 따른다. 입금 확인, 신고 표시, 반환 의무 종료를 하나의 완료 표시로 합치지 않는다.

전체 정산의 완료

미완료 송금 의무에서 제외하는 상태는 COMPLETED, CANCELLED, SUPERSEDED, BANK_WAIVED다. EXPIRED는 남은 의무다. 은행 확인 대기·직접 반환 대기·되돌림 실패 역시 해결이 필요하다. 상태 이름이 취소·면제라는 사실과 실제 은행 수취 완료는 구분한다.

서버는 ACTIVE 정산에서 남은 송금 의무가 없는지 확인한다. 항목별 납부 방식이면 자기 몫을 제외한 분담도 모두 끝났는지 확인한다. 직접 송금 방식의 정보성 분담 행을 똑같이 실제 미납으로 세지 않는다. 조건을 모두 만족할 때 정산 완료·감사·생성자 알림을 기록한다. 단건 확인 성공이나 마지막으로 보이는 버튼 클릭만으로 전체 완료를 보장하지 않는다.

현재 제한과 확인 범위

분류확인 내용영향과 다음 확인
Gap목록의 ‘대기 금액’은 PENDING만 합산하며 혼합 은행 확인 대기는 제외한다.은행분 전체 미확인 금액으로 읽으면 부족하게 보일 수 있다. 별도 은행분 필드·표시 정의가 필요하다.
Gap일괄 확인 응답의 실패 번호·이유를 앱 결과가 건수로만 줄인다.실패한 개별 건과 이유를 화면에서 바로 설명하지 못한다.
Risk일부 혼합 확인·만료 행동·하단 행동은 정산 ACTIVE 여부나 수동 허용 여부를 화면에서 모두 걸러내지 않는다.완료·취소·가상계좌 상태에서 버튼이 보여도 서버가 거절할 수 있다. 화면 노출을 실행 권한의 증거로 쓰지 않는다.
Risk만료 이의 표시는 있지만 재요청·포기에 대기 이의 검사·새 송금으로 이의 이전이 없다.이의가 있는 만료 송금의 후속 처리 정책과 실제 동작을 함께 판단해야 한다.
Risk혼합 은행 대기의 첫 장기 대기 기준에 송금 생성 시각을 사용한다.늦은 혼합 결제의 첫 알림 시점을 별도 운영 확인한다.
미검증소스와 선택한 기존 단언을 대조했다.새 은행 거래·알림 수신·스케줄 실행·관리자 화면·기기·이미지 시험은 하지 않았다.

수용 기준과 검증 근거

  • AC-01 목록과 역할: 전체/본인 송금과 항목별 정보성 송금을 구분한다. 수취자·정산 생성자·현재 모임 호스트의 조회 및 실행 역할을 동일시하지 않는다.
  • AC-02 일반 확인: PENDING·ACTIVE·모임 일치·대기 이의 없음·수취자 또는 생성자를 확인하고 송금자 자신의 확인은 거절한다.
  • AC-03 혼합 확인: 은행 확인 대기와 실제 수취 당사자에 더해 수동 확인 정책을 검사한다. 총액을 은행분으로 단정하지 않는다.
  • AC-04 확인 결과: 송금 완료·완료 시각·감사·알림 의도를 기록하고 전체 완료를 다시 판단한다. 실제 은행 확인은 확인자의 책임이며 앱 경고를 유지한다.
  • AC-05 일괄 대상: 현재 표시 범위의 일반 대기·당사자·이의 조건으로 대상과 합계를 계산한다. 혼합 확인 대기는 포함하지 않으며 처리 중 중복 실행을 막는다.
  • AC-06 건별 실패: 별도 트랜잭션으로 각 송금을 확인하고 성공·실패를 구분한다. 실패 번호·이유 응답과 현재 앱의 건수 표시 제한을 명시한다.
  • AC-07 신고와 알림: 보냈다는 신고를 입금 확정으로 바꾸지 않는다. 다시 알림은 실제 서버 요청 결과를 표시하며 기기 수신 완료로 보장하지 않는다.
  • AC-08 만료 경합: 30일을 넘긴 미신고 PENDING을 선택하고 잠근 행의 상태·신고를 재검사한다. 신고가 확인되면 만료시키지 않는다.
  • AC-09 해결 대기: 혼합 은행 확인·직접 반환 대기는 자동 만료시키지 않는다. 장기 대기 알림·운영 경보와 신고된 장기 PENDING의 별도 경로를 구분한다.
  • AC-10 재요청: 진행 중 정산 생성자만 만료 행에서 최대 2회 새 송금을 만들며 닫힌 당사자 계정을 거절한다. 원본은 대체 상태와 연결 관계를 남긴다.
  • AC-11 포기: 진행 중 정산 생성자만 만료 행을 선택 사유 500자 이내로 취소 처리한다. 상태 변화·불확실 응답을 성공으로 꾸미지 않는다.
  • AC-12 이의 중 만료: 생성자 행에도 이의 표지를 보인다. 표지와 재요청·포기의 현재 허용 조건 및 이의 이전 부재를 구분한다.
  • AC-13 운영자 해소: 작업 식별자·예상 버전·현재 허용 방법·증빙·금액/계정 조건을 검사한다. 혼합 손실 정리는 남은 포인트 반환과 은행분 면제를 나눈다.
  • AC-14 취소 뒤 수취: 일반 확인과 별도 취소 후 수취 확인을 구분하고, 확인되었다는 이유로 반환 의무를 삭제하지 않는다.
  • AC-15 전체 완료: EXPIRED를 미완료 의무로 남긴다. ACTIVE와 방식별 실제 의무 충족 뒤에만 전체 정산을 완료한다.
  • AC-16 오류와 계정: 확인·재요청·포기·일괄 결과를 재조회하고 계정이 바뀐 결과는 적용하지 않는다. 화면의 남은 합계·권한 표시 제한을 숨기지 않는다.

근거는 현재 서버·앱 구현, MeetingSettlementExpirationWorkerTest의 잠금 후 신고 감지 시 만료하지 않는 단언, transfer_actions_provider_test.dart의 은행분 확인 성공/실패 후 상태 및 일괄 성공2·실패1 매핑 단언이다. 기존 시험 코드를 읽은 범위이며 새 실행 통과 기록이 아니다.
