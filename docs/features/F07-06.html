F07-06. 이체 확인 · 일괄 확인 · 상각

정산 생성자가 회수의 책임을 지는 단위. 참가자가 외부 송금 앱으로 보낸 돈은 우리 시스템이 자동 확인할 수 없어 사람이 입금 내역을 직접 확인해야 송금이 완료된다. 일반 계좌이체와 별개로, 혼합 결제의 은행분은 수취자 또는 정산 생성자가 "받았어요"를 눌러야 입금 확인 대기에서 완료로 넘어간다. 송금자는 정산 생성자이기도 해도 자기 송금을 스스로 확인할 수 없다. 5명에게서 받은 5건을 한 번에 처리하는 일괄 확인, 30일이 지나도록 보내지 않는 송금자를 위한 재요청, 그리고 끝까지 회수가 안 되는 송금의 상각(포기 처리)까지 — 호스트가 정산을 끝까지 마무리할 수 있도록 모든 회수 도구가 본 단위에 모여 있다.

계좌이체는 우리 시스템 밖에서 움직이는 돈이므로 입금 확인을 자동화할 수 없다. 그래서 본 단위는 외부 입금 내역을 확인한 결과를 시스템에 "선언"하게 하는 형태로 짜여 있다. 혼합 결제 은행분은 실제 수취자 또는 정산 생성자만 선언할 수 있고, 송금자 자신과 무관 사용자는 차단한다. 한 건씩 확인하면 5명이면 다섯 번의 동작이 필요하므로 일괄 확인을 따로 둔다 — 한 건 실패가 전체 응답 집계를 막지 않도록 부분 성공을 허용한다. 다만 현재 service 내부 호출은 실제 건별 Spring 트랜잭션 경계를 만들지 않는다는 구현 위험이 있다.

회수가 안 되는 송금에 대해서는 두 단계의 도구가 있다. 30일이 지난 만료 송금은 한 번 더 재요청해 볼 수 있고, 그래도 안 되는 송금은 상각으로 정산에서 제외시킨다. 회수 안 되는 한 건이 영원히 매달려 정산을 완료시키지 못하면 호스트의 부담만 누적된다.

다섯 가지 회수·확인 도구

도구 1 · 단건 확인

한 명의 입금을 직접 확인

호스트가 본인 계좌에서 입금 알림을 받고 community 앱에서 해당 송금 카드의 "이체 확인"을 누른다. 송금 상태가 완료로 바뀌고 송금자에게 "계좌이체가 확인되었습니다" 알림이 도착한다.

도구 2 · 일괄 확인

여러 명의 입금을 한 번에

모임 종료 직후 5명이 비슷한 시간에 송금하면 호스트가 일일이 누르기 번거롭다. 하단의 "이체 확인"으로 대기 중인 송금들을 한 번에 처리. 한 건이 이미 다른 디바이스에서 처리됐다면 그 한 건만 거절되고 나머지는 정상 진행된다.

도구 3 · 혼합 은행분 확인

수취자 또는 정산 생성자가 "받았어요"

POINT 부분은 이미 처리됐지만 은행분을 기다리는 카드에 표시된다. 보는 사람이 송금자가 아니면서 수취자 또는 정산 생성자일 때만 버튼이 나타난다. 실제 입금 내역을 직접 확인한 뒤 누르면 송금이 완료된다.

도구 4 · 재요청

만료된 송금을 다시 시도

30일이 지나도록 결제·이체 확인이 없는 송금은 시스템이 자동으로 만료 상태로 표시한다. 호스트가 카드의 "재요청"을 누르면 원본은 대체됨 상태가 되고 같은 금액의 새 송금이 만들어져 송금자에게 알림이 다시 간다. 한 송금당 최대 2회까지 재요청 가능.

도구 5 · 상각(포기)

회수 불가 송금을 정산에서 제외

송금자와 연락이 끊겼거나 더 이상 회수가 불가능한 송금은 사유를 입력하고 포기 처리한다. 해당 송금은 정산 완료 판정에서 빠져, 다른 송금이 모두 끝나면 정산이 완료된다.

버튼 노출과 서버 권한이 같은 식을 공유한다.

수기 확인 — 영수증이나 은행 응답을 검증하지 않는다

POST .../transfers/{transferId}/confirm-bank-portion은 body가 없는 endpoint다. 입금증·영수증·은행 조회 결과를 받지 않으며, 화면은 “실제 입금 여부는 시스템이 검증하지 않는다”고 경고한다. 확인자는 외부 입금 내역을 직접 보고, 되돌릴 수 없는 확인 다이얼로그에서 "받았어요"를 눌러야 한다.

현재 확인 금액은 은행분이 아니라 transfer 총액일 수 있다

서버 transfer 응답에는 POINT/은행 분할 금액이 없고 총액만 있다. Flutter 확인 다이얼로그가 이 총액을 “계좌이체 부분” 금액으로 표시하므로, 정확한 은행분 금액을 보여 주려면 서버 응답 계약을 보강해야 한다.

사용자 시나리오

기본 흐름 · 단건 확인

토스 알림으로 입금 확인 후 community 앱에서 확인 처리

호스트가 본인 토스 앱에 16,000원 입금 알림을 받는다. community 앱의 이체 내역 화면에서 해당 송금 카드의 "이체 확인"을 누르면 송금 상태가 완료로 바뀌고 송금자에게 "계좌이체가 확인되었습니다" 알림이 도착한다.

이 흐름이 남기는 것 — 호스트가 본인 계좌를 확인한 결과를 시스템에 명시적으로 선언하는 동작. 이 한 번의 누름이 송금자의 결제 상태를 "내가 보낸 줄 알았는데 호스트가 안 받았다 한다"에서 "호스트가 확인했다"로 바꾼다.

혼합 결제 · 은행분 확인

수취자가 외부 입금 내역을 보고 "받았어요"

POINT 10,000원은 이미 처리됐고 은행분 6,000원 확인을 기다리는 카드가 있다. 수취자 또는 송금자가 아닌 정산 생성자에게 "받았어요"가 보이며, 실제 입금 비검증 경고를 읽고 외부 계좌 내역을 확인한 뒤 누른다. transfer가 완료되고 완료 시각·감사로그가 기록되며 송금자에게 확인 알림이 간다.

수취자가 처리하기 어려우면 정산 생성자도 대신 확인할 수 있다. 단 그 정산 생성자가 해당 transfer의 송금자라면 self-confirm으로 차단된다.

차단 · 혼합 은행분 self-confirm

송금자 또는 무관 사용자가 "받았어요"를 우회 호출

화면에는 버튼이 없고, 직접 endpoint를 호출해도 송금자는 SELF_CONFIRM 403, 무관 사용자는 NOT_AUTHORIZED 403으로 거절된다. 이미 완료됐거나 다른 상태인 transfer는 NOT_AWAITING_CONFIRM 400이며 어떤 완료 부수효과도 남지 않는다.

기본 흐름 · 일괄 확인

모임 종료 직후 5명의 송금을 한 번에 처리

모임이 끝나고 5명이 비슷한 시간에 호스트에게 송금을 마쳤다. 호스트가 하단 "이체 확인"을 누르면 “이체 일괄 확인” 다이얼로그가 뜨고, "5건 (총 80,000원)의 외부 송금을 확인 처리합니다"와 실제 입금 비검증 경고가 표시된다. 확인하면 5건이 한꺼번에 완료 상태로 바뀌고, 마지막 한 건이 처리되는 순간 정산이 자동으로 완료된다.

이 흐름이 남기는 것 — 5번 누르는 동작을 1번으로 줄이지 않으면 호스트가 정산 마무리를 미루게 된다. 호스트의 부담을 줄이는 것이 정산의 끝맺음을 만든다.

일괄 확인 · 부분 실패

5건 중 2건이 이미 다른 디바이스에서 처리됨

호스트가 폰과 PC에서 동시에 일괄 확인을 시도하거나, 일부 송금이 이미 다른 경로로 완료된 상태에서 일괄 확인을 누른다. 5건 중 3건은 성공, 2건은 "이미 완료됨"으로 실패. 화면에는 "3건 성공, 2건 실패" 안내가 뜨고 새로고침 시 최신 상태가 반영된다.

이 흐름이 남기는 것 — 한 건의 실패가 다른 건의 처리를 막지 않는다. 호스트가 일괄 확인을 시도하다가 한 건 때문에 전체가 막히면 결국 한 건씩 누르는 노동으로 돌아간다.

만료 후 재요청

한 달이 지나도 송금하지 않은 사람에게 다시 알림

한 달 전 활성화된 정산에서 한 명이 송금을 잠수했다. 30일 경과 시점에 시스템이 그 송금을 만료 상태로 자동 표시했고 호스트에게 알림이 갔다. 호스트가 "재요청"을 누르면 "재요청 횟수: 0/2" 안내와 함께 확인 다이얼로그가 뜨고, 확인하면 원본은 대체됨 상태로 종결되고 같은 금액의 새 PENDING 송금이 만들어지면서 송금자에게 "30일 이내 처리해 주세요" 알림이 다시 간다.

재요청 한도

이미 두 번 재요청한 송금에 또 시도

같은 송금을 이미 2회 재요청한 상태에서 또 재요청을 시도하면 한도 초과로 거절된다. "이미 2회 재요청했습니다" 안내가 뜨며, 호스트가 선택할 수 있는 경로는 상각(포기)으로 좁아진다.

상각

연락이 끊긴 송금자를 정산에서 제외

송금자와 연락이 끊겨 더 이상 회수가 불가능한 상태. 호스트가 카드의 "송금 포기"를 누르면 사유 입력 다이얼로그가 뜬다. "송금자 연락 두절" 같은 사유를 입력하고 확정하면 송금 상태가 취소로 바뀌면서 사유가 기록된다. 이 송금은 정산 완료 판정에서 제외되므로 다른 송금이 모두 완료되면 정산이 자동으로 완료된다.

이 흐름이 남기는 것 — 회수가 안 되는 한 건이 영원히 매달려 정산을 미완료로 두면 호스트의 운영 부담만 누적된다. 사유를 남겨 두는 것이 향후 분쟁이나 운영 검토에서 근거가 된다.

차단 · 자기 분담 확인

참가자가 본인 분담을 본인이 확인하려 한다

UI에서는 본인 카드에 확인 버튼이 노출되지 않지만, 우회 호출이 들어오면 "본인이 본인의 분담을 확인할 수 없습니다"라는 이유로 거절된다. 참가자가 자기 분담을 본인이 완료 처리하는 사고를 막는 가드.

자동 완료 트리거

마지막 확인이 정산을 완료시킨다

5건 중 4건이 완료된 상태에서 호스트가 마지막 한 건을 확인한다. 본 단위가 확인을 처리하는 마지막에 "모든 송금이 완료(또는 취소·상각)됐는가"를 확인하고, 조건이 충족되면 정산 상태가 자동으로 완료로 바뀌고 호스트에게 완료 알림이 도착한다.

차단 · 이의제기 중

이의가 걸린 송금을 확인하려 한다

송금 한 건에 이의가 걸려 있는 상태에서 호스트가 확인을 시도하면 "이의제기가 진행 중입니다. 호스트 처리 후 다시 시도해주세요" 안내로 거절된다. 먼저 이의제기 화면에서 이의를 처리한 뒤 다시 확인 가능.

화면에서 사용자가 인지하는 것

화면 요소확인자가 보는 것그 자리에 둔 이유
이체 내역 리스트 송금 한 건당 카드 한 장. 송금자 이름·사진, 금액, 상태 배지(대기/입금 확인 대기/완료/만료/취소/대체됨/되돌리기 실패/수동 환불 대기). 회수 현황을 한 화면에서 훑어볼 수 있어야 호스트가 어떤 송금에 어떤 행동이 필요한지 판단할 수 있다.
"받았어요" 버튼 입금 확인 대기 카드에서 송금자가 아닌 수취자 또는 정산 생성자에게만 노출. 확인 전 실제 입금 비검증·되돌릴 수 없음 경고. 송금자의 일방 완료를 막으면서 실제 수취자와 정산 책임자에게 해소 수단을 준다.
하단 "이체 확인" 버튼 정산 생성자에게만 노출. 누르면 PENDING 송금 건수·합계와 실제 입금 비검증 경고가 있는 일괄 확인 다이얼로그가 열린다. 처리 가능한 송금이 몇 건인지 누르기 전에 보여 줘야 의식 없는 일괄 처리 사고를 막는다.
만료 송금 카드의 두 버튼 "재요청 (현재 0/2)" + "송금 포기". 재요청 한도가 차면 재요청 버튼은 숨김. 호스트가 선택할 수 있는 도구가 두 가지뿐임을 명확히 보여 줘 흐름이 멈추지 않게.
상각 사유 입력 경고 톤의 확인 다이얼로그. 사유 입력란이 있고, 입력 없이 확정해도 통과되지만 입력을 권장. 운영 검토에서 "왜 이 송금이 회수 안 됐는가"가 기록되어야 향후 정책 개선의 근거가 된다.
완료 후 하단 액션 현재 이체 화면은 정산 상태를 검사하지 않아 정산 생성자에게 "이체 확인"/"미납자 알림" 버튼이 남을 수 있다. 완료 상태에서는 액션을 숨기거나 비활성화하도록 상태식을 보강해야 한다.

운영자가 알아야 할 것

호스트의 회수 흐름이 막히면 정산은 영원히 미완료로 남는다
  • 외부 입금 내역을 사람이 확인하는 동작은 시스템이 자동화하지 않는다. 계좌이체는 우리 시스템 밖에서 움직이는 돈이라 확인 주체의 손이 한 번 들어가야 한다 — 이 동작을 줄이려고 자동 확인을 도입하려면 외부 결제 대행·은행 연동이 필요하다.
  • 혼합 은행분은 수취자 또는 정산 생성자만 확인한다. 송금자는 정산 생성자를 겸해도 self-confirm할 수 없고, 무관 사용자와 잘못된 상태의 호출도 서버에서 거절된다.
  • 수기 확인을 영수증 검증으로 오인하면 안 된다. endpoint에 증빙 body가 없고 앱도 실제 입금 비검증을 경고한다. 외부 입금 내역을 확인하지 않은 채 누르면 시스템이 거짓 입금을 판별할 방법이 없다.
  • 일괄 확인은 부분 성공을 허용한다. 한 건 실패로 전체가 멈추면 호스트가 한 건씩 다시 누르는 노동으로 돌아간다 — "성공 N건, 실패 M건" 형태의 응답이 호스트에게 명확히 전달돼야 한다. 단, bulk method가 같은 bean의 @Transactional method를 직접 호출해 Spring proxy를 거치지 않으므로, 주석과 달리 건별 service transaction은 만들어지지 않는다. 후반 side effect 실패 시 한 건 내부 원자성을 별도로 검증·보강해야 한다.
  • "미납자 알림"은 현재 실제 알림을 보내지 않는다. 화면은 PENDING 목록으로 문자열을 만들고 성공 토스트만 표시하며 서버/API를 호출하지 않는다. 성공 문구를 유지하려면 실제 remind 흐름에 연결해야 한다.
  • 표시 상태식에도 공백이 있다. “대기 금액”은 PENDING만 합산해 입금 확인 대기를 제외하고, 일반 BANK 단건 확인은 서버가 수취자도 허용하지만 화면 CTA는 정산 생성자에게만 보인다.
  • 송금 만료는 시스템 스케줄러가 자동으로 표시한다. 30일이 지나도 처리되지 않은 송금은 자동으로 만료 표시가 되며, 호스트에게 알림이 간다 — 호스트는 만료된 송금을 발견했을 때 재요청·상각 둘 중 하나를 선택해야 한다.
  • 재요청은 최대 2회까지만 허용한다. 무제한 재요청은 사용자 알림 도배가 된다 — 2회를 넘으면 상각으로 가도록 정책이 정해져 있다.
  • 상각은 회수의 마지막 수단이다. 상각된 송금은 완료 판정에서 빠지므로 다른 송금이 모두 완료되면 정산이 끝난다 — 상각이 너무 자주 발생하면 송금 수단이나 사용자 안내에 구조적 문제가 있을 가능성이 있어 운영 모니터링 필요.
  • 참가자가 본인 분담을 본인이 확인하지 못하게 한다. 자기 분담을 본인이 완료 처리하는 사고가 일어나면 청구가 우회된 셈이 된다.
  • 이의제기가 걸린 송금은 확인이 막힌다. 분쟁이 해결되기 전에 호스트가 확인을 눌러 두면 분쟁 해결이 어려워진다.
  • 완료 트리거가 본 단위 끝에 함께 묶여 있다. 마지막 송금과 모든 share의 완료 확인이 정산을 완료시키는 트리거다. 이 재평가가 누락되면 모든 납부가 끝나도 정산이 진행 중으로 남는다 — 호스트는 완료 알림을 받지 못한다.
  • 혼합결제의 계좌이체 부분을 기다리는 입금 확인 대기 송금과, 환불 되돌리기가 실패해 수동 환불을 기다리는 송금은 자동 만료되지 않는다. 실제 돈이 움직였을 수 있는 중간 상태라 시스템이 자동으로 만료시키지 않는다. 3일(기본값) 이상 방치되면 시스템이 관련자에게 재알림을 보내고, 2회 이상 풀리지 않으면 운영 알림이 올라간다.
  • 포인트 회수가 끝내 실패해 멈춘 돈도 이제 감시 대상이다 (2026-06-06). 환불에 딸린 포인트 회수가 정해진 횟수만큼 재시도해도 끝내 실패하면, 그 전까지는 아무 알림 없이 대기열에서 조용히 빠져 운영자가 손쓸 일이 있는지조차 몰랐다. 이제는 회수가 끝내 실패한 건도 운영자에게 경보가 올라가, "멈춘 돈을 아무도 모르는" 사각지대가 사라졌다. (계좌이체 환불 무응답·호스트 정산 지급 실패에도 같은 감시 장치가 세워졌다.)
