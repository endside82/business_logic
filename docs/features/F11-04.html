F11-04 신고 접수·관할 결정·본인 처리 내역

대상15종·전용 접수·관할과 맥락 검사·중복/우선 검토·본인 신고 상세와 문의 연결을 갱신한다. 2026-11-22 소스 대조이며 새 제품 실행과 구분합니다.

현재 범위와 입구

대상 화면에서 신고를 열고 사유·설명·증빙과 검토 범위를 선택해 접수한 뒤, 본인 신고 목록·상세에서 상태와 결과를 확인한다. 현재 기능은 POST 하나와 목록 GET만 있는 구조가 아니다. 일반 신고 입력, 대상별 전용 접수, 모임·클럽·플랫폼 관할 결정, 본인 상세 조회를 구분한다. 접수 성공은 담당자의 최종 처리 완료와 다르다.

일반 신고 라우터는 대상 종류·식별자·표시 제목과 선택적인 contextId, sourceClubId, sourceEventId를 화면에 전달한다. 앱 요청 모델에도 세 맥락 필드가 있으므로 과거 「앱 contextId 누락」을 현재 미해결로 남기지 않는다. 후기 카드의 이벤트별 신고 입구는 후기 식별자와 원래 이벤트 식별자를 전달한다.

접수 API와 현재 대상 종류

POST /api/v1/reports는 201 ReportVo를 반환한다. 요청은 필수 targetType, targetId, reason과 선택 description, evidenceFileIds, contextId, scope, sourceClubId, sourceEventId다. 대상·사유는 서버 Enum 이름을 사용한다.

서버 입력과 증빙 검사

일반 앱의 사유 선택은 괴롭힘·부적절한 콘텐츠·노쇼·사기·기타·지각·나쁜 매너 7종이다. 서버 Enum에는 여기에 운전자 미참석·위험 운전·부적절 행위·개인정보 유출·운전자 노쇼가 추가된 12종이 있다. 모든 서버 사유가 일반 앱 시트에 표시되는 것은 아니다.

설명은 서버에서 최대 500자, 증빙 원본 목록은 최대 5개다. 앱은 기타 사유에서 공백 제거 후 설명 10자 이상을 요구하고 업로드 중 제출을 막지만, 현재 서버 검증에는 기타의 10자 최소 조건이 없다. 증빙 검증은 양수 식별자를 중복 제거하고 파일 존재·본인 소유·업로드 완료·EVIDENCE 또는 REVIEW 용도를 검사한다. 성공 시 신고 증빙 참조를 연결한다.

자기 자신을 USER로 직접 신고하는 것뿐 아니라, 서버가 해당 대상의 당사자 식별자를 해석했을 때 신고자 본인인 경우도 거절한다. EVENT 대상은 현재 호스트 본인, CLUB 대상은 소유자 본인의 신고를 INVALID_INPUT으로 따로 거절한다. 대상 존재 검사가 먼저이며 출처·회원·중복 판정보다 앞에서 적용한다. 공동호스트나 클럽 운영진·일반 회원까지 같은 자기 대상 신고로 일괄 거절하는 조건은 아니다. sourceClubId, sourceEventId, contextId를 요청했다면 서버가 해석한 원래 맥락과 맞아야 한다. USER 신고에 모임·클럽 출처를 붙일 때는 신고자와 상대 모두 그 맥락의 관계 이력이 있어야 한다.

검토 범위와 처리 관할

검토 범위는 CLUB_INTERNAL, PLATFORM_POLICY, PRIVATE_INTEREST다. 원래 대상에서 클럽 소속을 찾고 클럽 기본 대상에 속하면 scope 생략 시 클럽 내부, 그 밖에는 플랫폼 정책으로 정한다. 앱은 지역 처리가 가능한 대상·맥락에 내부 범위를 제시하고 선택한 값을 명시적으로 보낸다. 클라이언트가 요청한 범위가 최종 담당자를 직접 결정하지는 않는다.

플랫폼 정책과 사적 이해관계 범위는 플랫폼으로 간다. 내부 범위라도 플랫폼 전용 대상, 지역 관할 없음, 처리 담당자가 신고 당사자인 경우는 플랫폼으로 넘긴다. 그 밖에는 이벤트 출처가 있으면 EVENT_HOST, 클럽만 있으면 CLUB_STAFF다. 내부 처리에서는 클럽 관계를 확인하며 앨범은 열람 범위 검사를 사용한다. 처리 당사자 충돌은 현재 이벤트 호스트·분쟁 처리 가능한 공동호스트 또는 클럽 OWNER/ADMIN을 기준으로 판단한다.

접수 상태는 PENDING으로 저장한다. 최초 관할 결정에서 플랫폼으로 넘어가 사유·시각이 생겼다고 해서 접수 응답의 상태도 곧바로 ESCALATED라고 바꾸어 설명하지 않는다. 앱 완료 안내는 실제 응답 관할과 선택 범위를 반영한다. 이후 검토·기각·경고·제재는 권한 있는 담당자의 별도 처리 흐름이다.

중복과 우선 검토

중복 기준은 신고자·대상 종류·대상 식별자이며, 서버가 확정한 context가 있으면 그 context도 포함한다. 이전 신고의 종결 여부와 관계없이 같은 기준의 기존 행이 있으면 REPORT_ALREADY_EXISTS다. 요청의 임의 context로 중복을 회피할 수 없다. 이 POST에는 멱등 키가 없으며 중복 거절을 기존 성공 응답의 재반환과 혼동하지 않는다.

주간 우선 검토는 새 행 저장 전에 최근 1주 기존 신고가 5건 이상인지 검사하므로 해당 창의 6번째 접수부터 조건을 충족한다. 대상 우선 검토는 최근 1개월의 다른 신고자와 이번 신고자를 합쳐 서로 다른 3명 이상인지 검사한다. 두 조건은 우선 검토 플래그를 켜며 건수만으로 자동 기각하거나 일반 계정 제재를 확정하지 않는다. 접수에는 감사 기록도 남긴다.

데이트 프로필 사진의 추가 효과

이 대상은 활동 가능한 본인 인증 신고자와 삭제되지 않은 APPROVED 사진을 요구하고 본인 사진 신고를 거절한다. 접수 후 PENDING·IN_REVIEW·ESCALATED·RESOLVED 신고의 서로 다른 유효 활동 계정이 5명 이상이면 사진을 UNDER_REPORT로 숨긴다. 승인 사진이 3장 미만이 되면 활성 데이트 프로필을 비활성으로 전환하고 사진 소유자 알림을 outbox에 등록한다. 일반 신고 우선 검토와 이 사진 임계 숨김은 서로 다른 정책이다.

앱 입력·복귀와 내 신고 조회

입력은 대상·context·출처 조합별 SubmissionDraft로 복원·제출 준비·완료를 연결한다. 접수 성공 시 내 신고 목록을 갱신하고 초안 완료 후 관할별 접수 안내를 보여 준 뒤 닫는다. 적용 여부가 불확실한 오류도 내 신고 목록을 다시 읽도록 표시한다. 확실한 거절만 초안 거절 처리로 연결한다.

GET /api/v1/reports/my는 본인의 신고 List<ReportVo>, GET /api/v1/reports/my/{reportId}는 본인 신고 한 건을 반환한다. 상세가 없으면 REPORT_NOT_FOUND, 다른 사람의 신고면 FORBIDDEN이다. 응답에는 원래 대상 표시명, 사유·설명·증빙, 상태·결과 메시지, 범위·관할·출처·이관 사유·접수/처리 시각이 포함된다. 페이지 응답으로 해석하지 않는다.

현재 앱에는 「내 신고 내역」 목록과 상세 화면이 연결돼 있다. 빈 상태·오류 재시도·목록 새로고침을 제공하고 상세에는 대상·설명·첨부 자료·처리 결과·시각을 표시한다. 「이 신고 문의하기」는 신고 식별자를 가진 문의 작성으로 이동한다. 목록 API만 있고 화면은 미연결이라는 과거 서술은 제거한다. 접수만으로 총점 감점이 적용된다고 하지 않고 신뢰점수의 실제 감점 범위를 따른다. 호스트 숨김의 자동 신고는 호스트 답변과 임시 숨김을 따른다.

수용 기준과 검증 근거

  • AC-01 대상과 전용 경로: 현재 15종을 구분하고 이동수단·이벤트 사진의 일반 접수 거절과 앨범 출시 범위 검사를 적용한다.
  • AC-02 본인과 출처 검사: 서버가 확정한 당사자·출처·context로 자기 신고와 허위 맥락을 거절하며 이벤트 호스트·클럽 소유자의 자기 대상 신고도 막는다. USER 출처는 양쪽 관계 이력을 확인한다.
  • AC-03 증빙과 설명: 설명 최대500자·원본 첨부 최대5개·본인 완료 파일의 허용 용도를 확인하고 기타 최소10자는 앱 한정으로 구분한다.
  • AC-04 관할 결정: 선택 범위와 실제 대상 맥락·담당자 충돌로 EVENT_HOST/CLUB_STAFF/PLATFORM을 정하고 접수 PENDING과 이관 메타데이터를 구분한다.
  • AC-05 중복: 확정 context를 포함한 대상 중복은 기존 신고 상태와 관계없이 거절하고 새 성공 응답처럼 처리하지 않는다.
  • AC-06 우선 검토: 기존 주간5건 이후 새 접수와 월간 서로 다른3명 조건을 구분해 우선 검토 플래그를 설정한다.
  • AC-07 사진 임계 처리: 유효 신고자5명에 사진을 숨기고 승인 사진3장 미만이면 활성 프로필을 비활성으로 바꾼다. 알림은 outbox 등록으로 구분한다.
  • AC-08 앱 접수 복귀: 대상별 초안을 사용하고 성공 안내·내 신고 목록 갱신·복귀를 연결하며 결과 불명과 확실한 거절을 구분한다.
  • AC-09 본인 이력과 문의: 본인 목록·상세만 반환하고 앱에서 결과·자료·시각과 신고 식별자를 가진 문의 입구를 제공한다.

근거는 현재 접수·관할·증빙·사진 임계 처리와 앱 입력·본인 목록/상세다. 과거 E2E 기록은 인용으로 보존하며 이번에 제품 시험을 새로 실행하지 않았다.

이 기능의 출시 완료 기준

현재 제한과 확인 범위를 함께 판정한다.

2026년 10월 13일 정리한 판정 조건입니다. 아래 목록 자체는 검사 통과 기록이 아닙니다. 현재 공개 범위와 실행 확인은 출시 상태와 근거를 따릅니다. 위의 날짜별 기존 분류는 현재 운영 설정이나 검사 통과를 대신하지 않습니다. 후속 기능은 첫 출시에서 신규 이용 제한을 확인하고, 기능을 열 때 아래 결과를 검증합니다.

  • 신고가 올바른 원문·대상·관할로 접수되고 신고자가 본인 처리 상태를 확인한다.
  • 중복 신고·삭제된 원문·증빙 소유권·권한 회수·허용되지 않는 신고 사유를 처리한다.

기능 본문에 남은 미구현·결함은 해결 증거 또는 명시적인 공개 범위 결정 없이 완료 처리하지 않습니다. 함께 적용하는 권한·실패·복구 확인과 버전·환경·결과·승인 기록을 갖춘 뒤 판정합니다. 리뷰 & 신고의 관련 완료 기준도 함께 확인합니다.
