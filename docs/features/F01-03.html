F01-03. 이메일 인증

가입 시 입력한 이메일이 실제로 사용자 본인의 것인지 확인한다. 가입이 끝나는 즉시 서비스가 인증 메일을 먼저 보내고, 메일 안의 링크를 한 번 누르면 인증이 완료된다. 2026-08-18부터 인증은 단순 안내가 아니라 권한의 경계다 — 인증 전에도 로그인은 되지만 그 상태에서 할 수 있는 일은 "인증을 끝내는 것"과 "계정을 정리하고 나가는 것"뿐이다.

설계 의도 — 가입은 막지 않되, 인증 전에는 좁은 문만 연다 (2026-08-18 결정)

이메일 인증을 가입 직후로 강제하면 가입 완료율이 떨어진다. 그래서 가입 자체는 그대로 통과시키고 로그인도 성공시킨다. 다만 인증이 끝나기 전까지 그 계정이 할 수 있는 일은 인증을 끝내는 길과 계정을 정리하고 나가는 길로 제한된다.

왜 바뀌었나 — 종전에는 인증 여부에 경계가 없어서, 메일을 한 번도 확인하지 않은 계정이 호스트 승인을 받고 모임을 운영하는 데까지 이르렀다(실제 계정으로 진행한 출시 전 점검에서 발견). "결제를 시작할 때만 안내한다"던 종전 방침은 이 결정으로 대체됐다.

왜 거부가 아니라 제한인가 — 로그인을 아예 거부하면 인증 메일을 다시 받을 수도 없다. 메일이 오지 않은 사용자에게 되돌릴 방법이 사라지므로, 문을 닫는 대신 좁힌다.

메일 링크 한 번 클릭이 일으키는 일

메일 안의 링크를 누르면 앱이 자동으로 열리고, 사용자가 별도 입력 없이 인증이 끝난다.

사용자 시나리오

기본 흐름

가입 직후 메일을 확인해 인증 완료

가입을 마친 사용자가 인증 화면을 본다. "이메일을 보냈습니다" 안내와 함께 "이메일 앱 열기" 버튼이 있다. 메일 앱에서 인증 메일을 찾아 링크를 누르면 앱이 자동으로 다시 열리고 짧은 진행 표시 후 "인증이 완료되었습니다" 화면이 뜬다.

이 흐름이 남기는 것 — 사용자가 직접 입력하지 않고도 인증이 끝난다. 4자리 인증 코드 입력 방식보다 사용자 실수가 적다.

메일 지연

메일이 안 와서 재발송

스팸함으로 분류되거나 메일 서버 지연으로 메일이 늦게 도착한다. 사용자는 화면의 "재발송" 링크를 누른다 — 60초 쿨다운이 시작되고 카운트다운이 보인다. 새 메일은 직전 토큰을 무효로 만들고 새 토큰으로 발송된다.

이 흐름이 남기는 것 — 사용자가 답답함을 토로하기 전에 스스로 해결할 동선을 제공. 운영 측 CS 부담을 줄인다.

만료 분기

하루 뒤에 메일을 열어봄

24시간이 지난 메일의 링크를 누르면 앱이 열리고 "인증에 실패했습니다" 화면이 나타난다. 화면에 곧장 "인증 메일 재전송" 버튼이 보여서 사용자는 한 번 누르면 새 메일을 받을 수 있다.

재사용 차단

이미 인증한 링크를 다시 누름

인증을 끝낸 후 같은 메일의 링크를 다시 눌러도 다시 인증되지 않는다. "이미 인증된 사용자입니다" 안내가 뜬다 — 한 번 사용된 토큰은 즉시 무효가 되어 노출되어도 재사용할 수 없다.

이 흐름이 남기는 것 — 인증 링크가 어디선가 노출되어도 한 번 이상은 쓰일 수 없다는 보안 약속.

미인증 진입 (2026-08-18 개정)

인증 안 한 사용자가 서비스를 쓰려고 함

가입은 했지만 메일 링크를 안 누른 사용자가 모임 신청이든 결제든 무엇을 하려 해도, 서비스가 그 자리에서 "이메일 인증이 먼저입니다"로 답하고 앱은 인증 화면으로 보낸다. 종전처럼 "결제 같은 결정 동작에서만 안내"하지 않는다 — 인증 화면 · 로그인 화면 · 내 정보와 탈퇴 화면을 빼면 갈 수 있는 곳이 없다.

중요 — 이때 사용자는 로그아웃되지 않는다. 로그인 상태는 그대로 유지되고 화면만 인증으로 안내된다. 이것은 로그인 실패가 아니라 "절차가 아직 안 끝났다"는 뜻이기 때문이다.

즉시 승격 (2026-08-18 개정)

인증을 마치자마자 곧바로 정상 사용

메일 링크를 누르면 그 다음 동작부터 바로 정상으로 풀린다. 다시 로그인할 필요가 없다. 서비스가 인증 여부를 매번 계정 상태에서 직접 확인하기 때문에, 인증과 해제 사이에 시차가 생기지 않는다.

이 흐름이 남기는 것 — "인증했는데 왜 아직 막히나"라는 문의 자체가 생기지 않는다.

오타 구제 (2026-08-18 신설)

주소를 잘못 적어 메일을 영영 못 받음

오타 난 주소로 가입하면 인증 메일이 어디에도 도착하지 않아 영원히 인증할 수 없다. 그래서 인증 전 상태에서도 탈퇴와 내 데이터 내보내기·삭제는 열어 둔다 — 계정을 정리하고 올바른 주소로 다시 가입하는 것이 이 상황의 정상 종료 경로다.

주의 — 정지·차단된 계정에는 이 길이 열리지 않는다. 탈퇴로 제재를 지울 수 없어야 하기 때문이다.

소셜 가입 (2026-08-18 신설)

카카오·네이버·구글·애플로 가입한 사람

소셜로 새로 가입한 계정은 처음부터 인증을 마친 것으로 태어난다. 이 계정에는 메일을 보낼 실제 주소 자체가 없어서(내부 식별용 주소만 있다) 인증 절차에 들어가면 빠져나올 수 없기 때문이며, 신원은 이미 소셜 제공자가 확인해 줬다.

예외 — 이미 이메일로 가입한 계정에 소셜을 연결하는 경우는 다르다. 그 계정의 주소는 사용자가 직접 적은 실제 주소이고 소셜 제공자가 그것을 확인해 준 적이 없으므로, 연결만으로 인증을 인정하지 않는다.

화면에서 사용자가 인지하는 것

화면 상태사용자가 보는 것그 자리에 둔 이유
발송 안내 "{사용자 이메일}로 인증 메일을 보냈습니다" 한 줄 + 이메일 앱 열기 버튼 + 재발송 링크(쿨다운 표시) + 로그인 복귀 링크 사용자가 자기 이메일을 한 번 더 확인하고, 메일 앱으로 한 번에 갈 수 있게.
인증 진행 짧은 진행 표시와 함께 "이메일 인증 중..." 한 줄 토큰 검증이 1~2초 걸리기 때문에 시각 피드백 없이는 "앱이 멈췄나" 오해가 생긴다.
인증 성공 큰 체크 아이콘 + "이메일 인증이 완료되었습니다" + "이제 모든 기능을 사용할 수 있습니다" + 로그인으로 이동 버튼 인증의 의미를 사용자가 분명히 인지하도록 — "메일 한 번 누른 게 무슨 의미였는지" 그 자리에서 보여준다.
인증 실패 큰 경고 아이콘 + 실패 안내 + "인증 메일 재전송" 버튼 + "로그인으로 돌아가기" 링크 실패에서 곧장 다음 행동(재전송)으로 이동할 수 있는 동선이 같은 화면에 있어야 사용자가 막히지 않는다.

운영자가 알아야 할 것

메일 발송 정책과 결정점
  • 메일 도착이 늦거나 안 오는 사례는 운영 측에서 모니터링한다. 사용자 측에는 안 보이는 문제(메일 발송 시스템 장애, 스팸 필터)이므로 발송 성공률과 인증 완료율을 별도로 추적해야 한다.
  • 재발송 60초 쿨다운은 메일 시스템에 부담을 주지 않기 위한 최소 간격이다. 악의적 반복 호출 차단 효과도 있다. 이 수치를 줄이면 외부 메일 서비스 차원의 발송 제한이 걸릴 위험.
  • 인증 메일의 보낸 사람 주소와 본문은 도메인 신뢰도에 직접 영향한다. 운영 측이 메일 본문·발신 도메인의 SPF/DKIM 설정을 일관되게 유지해야 사용자의 스팸 처리율이 낮아진다.
  • 인증은 가입의 조건은 아니지만, 사용의 조건이다 (2026-08-18 변경). 종전의 "결제·신청 같은 결정 동작에 한해 인증을 요구한다"는 정책은 폐기됐다. 이제 인증 전에는 열려 있는 네 가지(내 상태 확인 · 메일 다시 받기 · 인증하기 · 탈퇴와 데이터 정리)를 제외한 모든 동작이 막힌다. 허용 목록은 서비스 한 곳에서만 관리되므로 화면마다 정책이 갈리지 않는다 — 대신 목록을 넓히는 결정은 곧 경계를 무르게 하는 결정이므로 제품 차원에서 승인돼야 한다.
  • 가입 시 첫 메일 발송은 자동이지만, 실패해도 가입은 성립한다. 메일 시스템 장애로 첫 발송이 실패해도 사용자의 가입 자체는 되돌아가지 않는다. 이때 사용자는 화면의 "다시 받기"로 복구하므로, 운영 측은 가입 건수 대비 첫 발송 실패율을 별도로 봐야 한다.
  • 인증하지 않고 방치된 계정의 처리 방침이 아직 없다. 제한 상태는 현재 기한 없이 유지된다. 보관 기간을 정하고 정리 절차를 붙이는 것이 후속 과제다.
  • 기존 환경에서 새 환경으로 데이터를 옮길 때 주의. 이 경계가 생기기 전에 만들어진 계정 중 인증을 마치지 않은 것들은 이전 직후 일제히 제한 상태가 된다. 이전 절차에 한 번의 정리 작업이 필요하다.
