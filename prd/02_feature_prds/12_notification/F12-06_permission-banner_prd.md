# F12-06. 알림 권한 인라인 안내 배너 PRD

<!-- release-document: reference -->
> **문서 구분: 기능·설계·절차 참고 문서.** 본문의 요구사항·과거 확인은 현재 미구현 목록이 아닙니다. 현재 작업 순서는 [앞으로 할 일](../../../../docs/plan/NEXT_WORK.md)을 따릅니다.

## 1. 결론

알림함에서 OS 알림 권한이 거부된 회원에게 ‘알림이 꺼져 있습니다’ 배너와 ‘허용’ 버튼을 보여 준다. 버튼은 기기 설정으로 이어지고, 앱에 돌아오면 권한을 다시 읽어 배너를 갱신한다. 이 기능 자체의 서버 API는 없다.

아직 권한을 묻지 않은 상태, 허용·임시 허용 상태, 웹이나 Firebase를 사용할 수 없는 환경에서는 이 배너를 표시하지 않는다. 최초 권한 요청은 로그인 세션의 푸시 등록 흐름이 맡는다. 권한 허용과 실제 푸시 전달 성공은 구분한다.

## 2. 코드 위치

계약의 정본은 코드다. 앱: `notification_list_screen.dart`, `fcm_permission_banner.dart`, `fcm_permission_provider.dart`.

## 3. 전체 동작 흐름

1. 알림함에 진입하거나 앱이 다시 활성화되면 OS 권한을 읽는다. 거부 상태에서만 배너가 나타난다.
2. ‘허용’을 누르면 권한을 다시 읽고, 계속 거부 상태이면 기기 설정을 연다. 버튼 처리 함수에는 미요청 상태의 시스템 요청 분기도 있지만 처음부터 미요청인 사용자에게 이 배너가 나타나는 것은 아니다.
3. 기기 설정에서 허용하고 돌아오면 재조회 결과에 따라 배너가 사라진다. 계속 거부 상태이면 배너가 남는다. 별도 닫기 동작은 연결되어 있지 않다.
4. 앱 복귀 시 푸시 서비스도 현재 로그인 세션의 등록을 다시 맞춘다. 토큰 획득·APNs 준비·서버 등록이 성공해야 수신 준비가 되며, 배너가 사라졌다는 사실만으로 실제 수신을 확인한 것은 아니다.

## 4. 제품 규칙

- 배너는 알림함의 인라인 안내다. OS 권한과 서비스의 카테고리 설정·마케팅 동의·방해금지는 서로 다른 조건이다.
- 권한 거부 중에도 수신 정책에 따라 서버 알림함 기록은 생성될 수 있다. OS 권한을 허용해도 꺼진 카테고리를 다시 켜지는 않는다.
- 웹 또는 Firebase 조회가 실패한 개발 환경은 지원하지 않는 상태로 처리해 배너를 숨긴다. 이 상태를 모바일 기기의 허용 상태로 판정하지 않는다.
- 권한을 아직 묻지 않은 상태에서는 배너를 표시하지 않는다. 로그인 세션의 푸시 등록 흐름에서 최초 요청한다.
- 허용 또는 임시 허용을 확인하면 배너를 숨기지만 실제 표시·전달 여부는 기기의 알림 설정과 발송 환경까지 확인해야 한다.

## 6. 상태·권한·시나리오 매트릭스

| ID | 시작 조건 | 행동 | 관찰할 결과 |
|---|---|---|---|
| S1 | 아직 OS 권한을 묻지 않음 | 알림함을 연다 | 배너가 나타나지 않는다. 최초 요청은 로그인 세션의 푸시 등록 흐름과 구분한다 |
| S2 | OS 권한 거부 | 배너에서 설정을 열고 허용한 뒤 복귀 | 권한을 다시 읽고 배너를 숨긴다. 실제 수신은 별도 확인한다 |
| S3 | OS 권한 거부 | 설정에서 허용하지 않고 복귀 | 배너가 계속 보인다 |
| S4 | 웹 또는 Firebase 조회 불가 | 알림함을 연다 | 지원하지 않는 상태로 배너를 숨긴다. 허용으로 판정하지 않는다 |
| S5 | 허용 상태 | OS에서 권한을 끄고 복귀 | 재조회 후 배너가 나타난다 |
| S6 | 반복적인 앱 복귀 | 권한 상태를 바꿔 여러 번 복귀 | 최신 OS 상태와 배너가 일치하는지 확인한다. 소스만으로 기기 실행 통과를 단정하지 않는다 |

## 8. Gap / Risk

| 판정 | 항목 | 근거 | 영향·남은 확인 |
|---|---|---|---|
| 미검증 | 실제 OS 설정 왕복·푸시 수신 | 이번 갱신은 `FcmPermissionNotifier`, 알림 화면의 복귀 처리, 앱 복귀의 푸시 등록 재조정을 대조했다 | iOS·Android의 권한 변경과 실제 수신은 해당 기기·앱 버전의 실행 기록으로 확인한다 |
| Risk | 지원 불가 상태의 배너 숨김 | 웹 또는 SDK 조회 예외는 `unsupported`가 된다 | 배너가 없다는 사실만으로 OS 권한이 허용됐다고 안내하면 안 된다 |

## 9. 수용 기준

- **AC-01. 미요청 상태**: 알림함 자체는 배너를 표시하지 않는다. 로그인 세션의 최초 권한 요청과 혼동하지 않는다.
- **AC-02. 허용 후 복귀**: 거부 상태에서 기기 설정을 열어 허용하고 돌아오면 권한을 다시 읽고 배너를 숨긴다. 서버 토큰 등록·실제 수신 결과는 별도로 기록한다.
- **AC-03. 계속 거부**: 설정을 바꾸지 않고 돌아오면 배너가 남고 다시 설정으로 갈 수 있다.
- **AC-04. 지원 불가**: 웹·SDK 조회 불가에서는 배너를 숨기되 이를 모바일 허용 확인으로 세지 않는다.
- **AC-05. 권한 철회**: 허용 상태에서 기기 설정으로 권한을 끄고 돌아오면 배너가 나타난다.
- **AC-06. 반복 복귀**: 반복 전환 뒤 최종 권한과 배너 표시를 실제 기기에서 확인한다. 폴링 구현의 존재를 무한루프·경합 시험 통과로 대신하지 않는다.
