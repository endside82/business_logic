# F08-04. 블록 순서와 계층 변경 PRD

<!-- release-document: reference -->
> **문서 구분: 기능·설계·절차 참고 문서.** 현재 작업 순서는 [앞으로 할 일](../../../../docs/plan/NEXT_WORK.md)을 따른다.

> 2026-11-22 서버와 앱 소스 대조. 작성자 초안의 순서 변경, 최신 트리에서의 의도 재적용, 요청별 저장과 실패 복구를 설명한다. 실제 기기 조작이나 새 제품 시험의 통과 기록은 아니다.

## 진입과 로컬 변경

작성자는 초안 편집기의 **편집기 메뉴 → 재정렬**에서 `/plan/:planId/reorder`로 들어간다. 이 항목은 `DRAFT`이며 블록이 있을 때 표시되고, 라우터도 작성자 접근을 확인한다. 서버는 모든 이동·정렬 요청에서 작성자와 `DRAFT`를 다시 검사한다. 편집 화면 자체의 평탄 트리 인라인 정렬은 [블록 에디터](F08-03_block-editor_prd.md)의 별도 조작이다.

드래그·들여쓰기·내어쓰기는 화면의 `BlockReorderModel`만 바꾼다. 이동 대상 ID, 목적지 부모 ID, 앞에 놓일 형제 ID를 의도로 기록하며 이때 API를 보내지 않는다. 부모를 옮기면 자손도 함께 이동하고, 내어쓰기는 해당 블록과 그 자손만 원래 부모 다음으로 옮긴다. 루트 깊이는 0, 최대 깊이는 3이다. 들여쓰기는 바로 앞 항목이 같은 깊이이고 전체 자손까지 한도 안에 들어갈 때 가능하다.

잠긴 블록은 내부 자손을 별도 행으로 펼치지 않고 직접 드래그·들여쓰기·내어쓰기를 막는다. 일반 블록을 잠긴 부모 밑으로 보내거나 잠긴 블록의 부모를 간접 변경한 경우에는 로컬 검사를 거쳐 거절하고, 저장 직전에도 다시 검사한다. 같은 부모의 전체 형제 순서를 전송할 때에는 잠긴 형제의 ID도 빠뜨리지 않는다.

최초 조회는 로딩·오류와 재시도를 제공한다. 블록이 없으면 편집 화면에서 먼저 추가하라는 빈 화면을 보여준다. 저장 전 취소는 로컬 변경만 폐기한다. 변경이 없는 상태의 완료는 쓰기 없이 돌아간다.

## 최신 트리와 저장 순서

새 트리를 받으면 과거 목록 전체를 덮어쓰지 않고 사용자가 기록한 이동 의도를 최신 트리에 다시 적용한다. 새로 생긴 블록과 사용자가 건드리지 않은 순서는 최신 트리에 남긴다. 사라진 대상의 변경은 제외하고, 목적지 소실이나 깊이 초과로 적용할 수 없는 변경도 제외하며 화면에 알린다.

완료를 누르면 저장 시작 시점의 의도를 사용하여 다음 순서로 처리한다.

1. 부모가 달라진 블록마다 `moveBlockAnchored`를 순차 호출한다. 실제 전송 직전 최신 트리에 의도를 투영하여 부모·위치·깊이를 다시 계산한다.
2. 기록한 의도에 등장한 **목적지 부모 범위**에만 `reorderSiblingsAnchored`를 순차 호출한다. 손대지 않은 모든 부모 범위를 재전송하지 않는다. 각 요청의 `siblingIds`는 최신 트리에 의도를 반영한 해당 부모의 전체 형제 ID다.
3. 전송 직전 대상·부모가 없어지거나 빈 형제 목록이 되면 임의의 대체 위치로 보내지 않고 오류로 중단한다. 모든 호출 성공 후 성공 안내와 함께 이전 화면으로 돌아간다.

서버의 `move` 응답은 이동한 블록 한 건이다. 앱은 그 응답만으로 전체 자손과 형제 구조를 확정하지 않고 트리를 불완전 상태로 표시하여 다음 쓰기 전에 재조회한다. 이 선행 조회가 실패하면 오래된 트리를 이용한 후속 쓰기를 막는다.

## 서버 요청과 트리 무결성

| 동작 | 요청과 응답 | 서버 검사 |
| --- | --- | --- |
| 형제 순서 변경 | `PUT /api/v1/plans/{planId}/blocks/reorder`; `{parentBlockId?, siblingIds, revision}` → `List<PlanBlockVo>`와 개정 헤더 | 현재 살아 있는 전체 형제와 ID 집합이 같고 중복·누락·외부 ID가 없어야 한다. 형제들의 기존 정렬 슬롯을 요청 순서에 배정한다. |
| 부모·위치 변경 | `PATCH /api/v1/plans/{planId}/blocks/{blockId}/move`; `{parentBlockId?, sortOrder, depth, revision}` → `PlanBlockVo`와 개정 헤더 | 같은 플랜의 부모, 자신·자손으로의 이동 금지, 깊이·위치·읽기 전용 범위를 검사한다. |

`parentBlockId=null`은 루트다. 부모 범위 방식의 `siblingIds`가 제공되면 그 방식을 우선한다. 이전 `blockIds` 방식은 전체 살아 있는 플랜 블록 집합을 정확히 보내야 하며, 읽기 전용 조상 내부가 포함되는 전역 정렬은 거절한다. 현재 화면은 부모 범위 방식을 사용한다.

`sortOrder`의 서버 허용 범위는 **0부터 목적지 형제들의 최대 기존 sortOrder + 1까지**다. 이동하는 블록 자체는 그 최댓값 계산에서 제외한다. 따라서 단순히 형제 수 이하라는 규칙으로 설명하지 않는다. 서버는 요청 `depth`를 신뢰하지 않고 새 부모 기준으로 산출하고 자손 깊이도 다시 계산한다. 한 자손이라도 깊이 3을 넘으면 해당 요청 전체가 롤백된다.

`PlanBlock`의 `deleted_at IS NULL` 조건으로 삭제된 블록은 대상 집합에서 제외한다. 미지 타입·미래 스키마·원형 봉투를 가진 읽기 전용 블록 자체와 그 내부에서는 직접 이동을 허용하지 않는다. 읽기 전용 형제 바깥에서 그 ID를 포함한 형제 순서를 정하는 것과 내부 구조를 바꾸는 것은 구분한다.

## 동시 수정과 개정 번호

서버는 플랜 행의 쓰기 잠금으로 변경을 직렬화한다. `revision`이 현재 값과 다르면 `409 CONCURRENT_MODIFICATION`이며 해당 요청의 변경과 개정 증가를 롤백한다. 성공 응답은 `X-Plan-Block-Tree-Revision`을 반환한다.

현재 `plan.editor.revision-fail-closed`의 **코드 기본값은 true**다. 개정 번호 없는 쓰기는 기본적으로 `428 PLAN_BLOCK_REVISION_REQUIRED`다. 명시적으로 false로 설정한 호환 분기에서는 번호 없는 요청도 개정을 증가시키며 받지만, 번호가 제공되면 설정에 관계없이 일치를 검사한다. 이는 소스 기본값이며 실행 환경의 설정을 관측했다는 뜻은 아니다.

앱은 플랜별 변경을 직렬 큐에 넣고 검증 가능한 개정 번호를 전송한다. 조회 헤더 누락·판독 실패·아직 조회 전인 상태에서는 쓰기를 막는다. 저장 응답의 개정 헤더를 잃어도 성공한 쓰기를 없던 일로 취급하지 않으며 후속 쓰기를 막고 상태 복구를 진행한다.

충돌 처리에서는 트리와 개정 번호를 다시 읽고, 유효한 번호를 확보한 경우 **최대 한 번** 다시 시도한다. 재시도 시 동일한 옛 ID 배열을 고정해 보내는 것이 아니라 최신 트리에서 이동·정렬 인자를 다시 만든다. 대상 소실, 해석할 수 없는 개정 번호, 재조회 실패 등의 경우는 자동 재전송을 보장하지 않는다. 성공한 재시도가 외부 변경을 건너뛴 경우와 자신의 직전 응답 번호를 놓친 경우를 구분하여 안내한다.

## 실패와 돌아오기

| 상황 | 현재 처리 |
| --- | --- |
| 앞선 요청이 성공 반환하기 전에 실패 | 이후 호출을 중단하고 트리를 다시 읽되 로컬 이동 의도를 유지하여 새 트리에 재적용한다. 원인별 미반영·새로고침 안내를 표시하고 화면에 남는다. |
| 하나 이상의 요청이 성공 반환한 뒤 실패 | 이후 호출을 중단하고 로컬 모델을 비운 뒤 서버 트리로 재동기화한다. 일부 반영 안내 후 화면에 남는다. |
| 대상·목적지 소실 또는 깊이 초과 | 가능한 남은 의도만 재적용하고 적용할 수 없는 변경을 제외한다. 사용자는 최신 구조를 확인한다. |
| 개정 번호 때문에 쓰기가 막힘 | 편집 화면에서 새로고침한 뒤 다시 시도하도록 안내한다. |
| 모든 요청 성공 | 성공 안내 후 이전 화면으로 돌아간다. |

여러 `move`와 `reorder`는 하나의 서버 트랜잭션이 아니다. **각 요청 안에서는 롤백되지만 요청 사이의 부분 반영은 가능하다.** 저장 시작 뒤 화면을 떠나는 행동도 이미 보낸 요청의 서버 롤백을 뜻하지 않는다.

## 현재 제한과 확인 범위

| 구분 | 현재 판단 | 문서 처리 |
| --- | --- | --- |
| Risk | 여러 요청 중 앞선 저장만 반영될 수 있다. | 전체 완료를 일괄 원자 저장으로 표현하지 않고 재조회·부분 반영 흐름을 명시한다. |
| Risk | 화면의 성공 횟수는 성공 응답을 받은 호출 수다. 네트워크 실패 시 서버가 실제 반영했는지와 일치한다고 단정할 수 없다. | 첫 요청 실패 안내를 서버 미반영의 증명으로 쓰지 않는다. 재조회 결과를 확인해야 한다. |
| 미검증 | 실제 기기의 빠른 반복 이동·저장 중 이탈, 다른 기기와의 동시 수정, 운영 개정 번호 설정은 이번에 실행하지 않았다. | 소스 대조와 기존 단언을 읽은 기록만 남긴다. |

## 수용 기준과 검증 근거

- **AC-01 접근과 상태:** 초안 작성자만 저장하며 편집기 메뉴의 재정렬 입구, 라우터, 서버의 권한 검사를 구분한다.
- **AC-02 저장 전 로컬 처리:** 드래그·들여쓰기·내어쓰기는 로컬 의도만 기록하고 변경 없는 완료와 저장 전 취소는 쓰기를 보내지 않는다.
- **AC-03 자손과 읽기 전용 범위:** 자손을 동반하여 깊이를 계산하고 잠긴 블록 내부와 간접 부모 변경을 막는다. 잠긴 형제 ID는 형제 정렬에서 누락하지 않는다.
- **AC-04 최신 트리 재적용:** 새 블록과 손대지 않은 순서를 보존하면서 사용자 의도를 다시 적용하고 사라진 대상·목적지·깊이 초과 변경을 제외한다.
- **AC-05 저장 대상과 순서:** 부모 이동을 먼저 처리하고 의도에 등장한 목적지 부모 범위만 전체 형제 ID로 정렬한다. 모든 부모 범위를 덮어쓰지 않는다.
- **AC-06 서버 무결성:** 형제 집합의 중복·누락·외부 ID, 자신·자손 부모, 잘못된 위치와 깊이를 서버에서 거절하고 한 요청 내 변경을 롤백한다.
- **AC-07 개정 번호 보호:** 번호 없는 쓰기의 기본 거절, 잘못된 번호의 충돌, 성공 헤더 전달과 앱의 번호 누락 시 후속 쓰기 중단을 구분한다.
- **AC-08 제한된 충돌 재시도:** 최신 트리와 유효 번호를 얻은 뒤 인자를 다시 만들어 최대 한 번 재시도하며 대상 소실·조회 실패는 별도 실패로 처리한다.
- **AC-09 실패 복구 분기:** 성공 반환한 앞선 요청이 없으면 로컬 의도를 유지하고, 앞선 성공이 있으면 모델을 초기화하여 서버 상태로 돌아온다. 응답 실패만으로 실제 서버 미반영을 확정하지 않는다.
- **AC-10 완료와 원자성:** 모든 요청 성공 시 돌아가되 전체 저장의 요청 간 부분 반영 가능성과 저장 후 이탈의 한계를 명시한다.

이번에는 Controller·Service·요청 모델·개정 저장소와 앱 API·Repository·Provider·화면·정렬 모델을 대조했다. 기존 `block_reorder_screen_test.dart`의 손대지 않은 부모 범위 제외, 첫 요청 실패 시 의도 보존, 앞선 성공 이후 부분 반영 안내 단언과 `PlanBlockServiceTest`의 기본 개정 번호 거절 단언을 읽었다. 해당 제품 시험은 새로 실행하지 않았다.
