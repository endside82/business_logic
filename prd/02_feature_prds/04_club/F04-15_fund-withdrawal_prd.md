# F04-15. 클럽 기금 출금 신청·예약·지급 상태 PRD

<!-- release-document: reference -->
> 2026-11-22 서버·앱 소스 대조. 현재 작업 순서는 [앞으로 할 일](../../../../docs/plan/NEXT_WORK.md)을 따른다. 신청·승인·지급 완료를 구분한다.

## 현재 범위와 실제 입구

클럽 재정 화면의 출금과 출금 이력은 해당 동작 권한으로 열리며 서버는 현재 회원인 정본 클럽장만 허용한다. 앱에서 금전 기능이 닫혀 있으면 신청 화면 대신 기능 제한 안내를 보여 주고 서버도 실제 출금 명령에서 금전 기능을 확인한다. 조회된 유료 잔액은 출금 신청 가능한 금액의 확정 값이 아니다.

## 가용액과 신청 제한

최소 신청액은 10,000이다. 서버의 신청 가용액은 `max(0, 유료 기금 − 미승인 출금 예약 총액 − 최근 7일 ACTIVE 기부 환불 보호액 − 최근 7일 환불 가능한 가입비 − 미납금)`이다. 이 계산에서 무료 기금은 출금 재원이 아니며, 환불 보호액은 해당 조회의 총액으로 차감한다. 미납금도 유료·무료 합계다.

출금 예약액 조회는 `PENDING`이면서 아직 예약 거래가 없는 행만 합산한다. 이미 승인하면서 기금에서 차감한 예약을 다시 빼지 않는다. 같은 달에 REJECTED 이외의 출금 신청이 있으면 재신청을 거절한다. 반려 후에는 이 월 제한을 통과할 수 있지만 다른 한도·잔액 조건은 다시 적용한다.

공통 출금 서비스의 추가 제한도 적용된다. 클럽 기준 최근 24시간 신청 횟수는 3회 미만이어야 하고, 이번 요청을 포함한 반려 제외 실수령액 합계는 최근 24시간 10,000,000·최근 30일 100,000,000을 넘을 수 없다. 달력상 월 1회 조건과 최근 30일 금액 한도는 같은 계산이 아니다.

## 신청 계좌와 금액 계산

앱은 등록된 정산 계좌를 읽어 기본 계좌 또는 첫 계좌를 선택한다. 계좌가 없으면 등록 입구를 제공하고 제출하지 않는다. 현재 선택 계좌가 조회 목록에 있어야 하며 `{amount, reason, bankAccountId}`를 보낸다. 서버 요청 모델에 남은 `bankCode`, `accountNumber`, `accountHolder`를 앱이 직접 입력해 송금 계좌로 지정하는 흐름이 아니다.

서버는 `bankAccountId`의 소유자를 확인하고, ID가 생략되면 소유자의 기본 계좌를 찾는다. 출금 요청에 계좌 정보를 복사해 두므로 이후 계좌 변경과 신청 시 송금 대상을 구분한다. 사유는 서버에서 공백 제외 필수·최대 500자이며 앱 입력은 최대 200자다.

현재 코드 계산은 신청액의 5%를 수수료로, 수수료 차감 후 금액의 3.3%를 원천징수액으로 계산하며 각각 정수 HALF_UP 반올림한다. 예를 들어 100,000 신청이면 수수료 5,000·원천징수 3,135·실수령 91,865다. 10,000이면 500·314·9,186이다. 이는 코드 계약 설명이며 세무 적용의 별도 검토 결과는 아니다. 현재 계산은 `FeePolicyType.defaultRate()`를 사용한다.

## 신청과 승인과 지급의 상태

`POST /api/v1/clubs/{id}/fund/withdraw`는 출금 응답을 반환한다. 이 회원 신청 경로에는 기부·미납금 상환과 같은 필수 요청 키가 없다. 클럽·기금 잠금과 월 중복 조건으로 판단하며 같은 키를 이용한 결과 재생 보장을 문서에 붙이지 않는다.

신청 시 연결 출금 요청에는 실수령액을, 클럽 출금 행에는 총액·수수료·원천징수·실수령액·계좌 표시·연결 요청 ID를 저장한다. 이 시점의 클럽 기금은 차감하지 않는다. 승인할 때 유료 기금에서 **총액**을 예약 차감하고 원장을 기록한 뒤 연결 출금 요청을 승인하여 지급 outbox로 넘긴다. 승인 가용액은 다른 미승인 예약을 제외해 계산하며 신청 때와 같은 환불 보호액·미납금 공식을 반복하지 않는다.

승인과 outbox 등록은 실제 입금 완료가 아니다. 연결 출금 상태가 지급 진행 중이면 반려를 막는다. 반려 가능한 요청은 연결 출금 서비스를 통해 처리하고, 이미 예약된 경우 총액을 유료 기금으로 복원한다. 사유 원문과 반려 사유를 구별해 저장한다. 이번 문서 확인으로 PG 송금 성공이나 운영 outbox 소진을 주장하지 않는다.

## 이력 권한과 실패와 복귀

출금 이력은 정본 클럽장만 생성 시각·ID 역순으로 읽고 앱은 20개 페이지를 사용한다. 서버 응답의 BigDecimal 금액은 앱의 double 필드로 받는다. 앱은 연결 요청의 `unifiedStatus`를 우선 해석하고 없으면 기존 `status`, 해석할 수 없으면 알 수 없는 상태로 표시한다. 실패 사유도 별도로 보여 준다. 연결 요청 자체가 결손이면 서버는 INDETERMINATE와 운영 경보로 다루며 완료로 추정하지 않는다.

기존 클럽장의 출금 행을 새 클럽장이 읽을 때 금액·상태는 유지하고 예금주·계좌번호는 빈 값으로 내려준다. 본인 신청 행의 계좌 표시도 마스킹한다. 앱은 비어 있는 계좌 정보를 표시하지 않는다.

앱은 신청 전 총액·공제액·실수령액·계좌를 확인한다. 성공하면 입력 초기화·이전 화면 복귀를 하고 기금·거래 자료를 다시 읽는다. 월 중복 오류에서도 해당 자료를 다시 읽는다. 잔액 부족은 환불 보호액·미처리 출금·미납금의 영향과 함께 안내하고 계좌가 없다는 응답은 계좌 관리로 연결한다. 성공 직후 출금 이력 provider를 이 화면에서 직접 무효화하는 코드는 없으며, 이력은 출금 자료 변경 구독과 자체 조회를 사용한다.

## 수용 기준과 검증 근거

- **AC-01 출금 권한:** 현재 회원인 정본 클럽장과 동작 권한·금전 기능 조건을 충족해야 신청한다.
- **AC-02 최소 금액:** 10,000 미만은 거절하고 무료 기금은 출금 재원에서 제외한다.
- **AC-03 신청 가용액:** 미승인 예약·7일 환불 보호액·미납금을 유료 기금에서 빼고 음수는 0으로 본다.
- **AC-04 중복과 공통 한도:** 당월 반려 제외 신청과 최근 24시간·30일 공통 출금 한도를 각각 적용한다.
- **AC-05 계좌 소유:** 선택 계좌 ID의 소유자를 검증하고 신청 시 계좌를 복사하며 계좌 없음은 제출 성공으로 처리하지 않는다.
- **AC-06 사유와 계산:** 사유 필수·길이 조건과 공제별 HALF_UP 계산을 적용한다.
- **AC-07 신청 상태:** 신청은 연결 요청과 클럽 출금 PENDING을 만들며 아직 기금을 차감하거나 지급 완료로 표시하지 않는다.
- **AC-08 승인 예약:** 승인 시 총액을 유료 기금에서 예약 차감하고 연결 출금 outbox로 넘기며 다른 예약을 중복 차감하지 않는다.
- **AC-09 반려 경계:** 지급 진행 중 반려는 거절하고 반려 가능한 예약은 총액을 유료 기금으로 복원한다.
- **AC-10 이력 상태:** 연결 상태를 우선하며 연결 결손은 INDETERMINATE와 운영 경보로 처리한다.
- **AC-11 계좌 비공개:** 새 클럽장에게 이전 신청자의 예금주·계좌를 숨기고 금액·상태는 유지한다.
- **AC-12 결과 복귀:** 성공·월 중복 때 기금 자료를 갱신하고 불명확한 신청 결과를 임의의 지급 성공으로 처리하지 않는다.

`ClubFundPlanTest`의 신청·승인 가용액, `ClubSettlementServiceTest`의 클럽장 변경 후 계좌 비공개, 앱 `withdrawal_fee_test.dart`의 공제·반올림 단언을 읽었다. 제품 시험이나 실제 송금은 새로 실행하지 않았다.
