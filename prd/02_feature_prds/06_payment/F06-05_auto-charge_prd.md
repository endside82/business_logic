# F06-05. 자동충전 설정과 실행 PRD

<!-- release-document: reference -->
> **문서 구분: 기능·설계·절차 참고 문서.** 2026-11-22 서버·앱 소스와 명시한 기존 시험 단언을 대조했다. 새 제품 시험·기기·외부 결제의 통과 기록은 아니다. 현재 작업 순서는 [앞으로 할 일](../../../../docs/plan/NEXT_WORK.md)을 따른다.

## 결론

자동충전은 설정 저장과 결제 시 부족액 보충을 구분한다. 현재 서버는 결제 필요액보다 사용 가능한 잔액이 적을 때 시도한다. 화면에서 입력하는 잔액 임계값은 저장되지만 실행 판정에 사용되지 않는다. ‘잔액이 설정값 아래로 내려가면 자동 충전된다’는 설명을 현재 동작으로 확정하지 않는다.

## 입구·설정 조회·켜기와 끄기

충전 화면의 자동충전 설정 링크와 해당 앱 경로에서 연다. 켜기 전환은 폼만 펼치며 저장을 눌러야 서버에 반영된다. 설정이 없으면 서버는 비활성·임계값 5,000원·충전액 10,000원과 카드·월 한도 없음으로 응답한다. 조회만으로 설정 행을 만들지 않는다.

설정 조회 오류에는 재시도가 있고 카드 목록은 별도로 읽는다. 카드가 없으면 등록 안내와 결제수단 화면 입구를 표시한다. 선택한 카드가 목록에 없으면 기본 카드 또는 첫 카드로 다시 선택한다. 이 목록에서 무효 카드를 제외하는 필터는 없다.

저장은 값 검증 후 활성 상태와 금액·카드·월 한도를 전송한다. 성공하면 토스트를 표시하고 화면에 남는다. 저장 중 폼을 로딩 화면으로 바꾸지 않으며 실패한 변경은 제공자 상태에서 되돌리고 입력 폼과 오류 안내를 유지한다. 제출 중 같은 화면의 중복 저장·해제는 막는다.

끄기는 확인창 뒤 해제 API를 호출한다. 성공해야 토글을 내리며 실패하면 기존 설정과 오류를 유지한다. 서버는 활성 값만 끄고 금액·카드·월 한도를 보존한다. 앱 제공자는 해제 직후 기본 비활성 객체를 사용하므로 즉시 상태와 나중에 서버에서 다시 읽은 저장값은 구분한다. 해제를 이미 진행 중인 외부 청구의 취소라고 보장하지 않는다.

## 저장 검증과 실행 검증의 차이

| 항목 | 앱 설정 화면 | 서버 저장 | 실제 실행 판정 |
|---|---|---|---|
| 임계값 | 1,000~100,000원 | 1,000원 이상 | 저장값을 사용하지 않고 결제 부족액을 판단 |
| 충전액 | 10,000·30,000·50,000원 칩. 검증 상한은 500,000원 | 10,000원 이상, 상한 검증 없음 | 설정 충전액과 부족액 중 큰 금액. 최소 1,000원, 최대 1,000,000원 |
| 월 한도 | 선택값. 10,000원 이상이며 선택 충전액 이상 | 있으면 10,000원 이상 | 이번 달 자동충전 합계에 이번 시도액을 더해 한도 초과면 건너뜀 |
| 카드 | 선택 번호 필수. 목록에서 선택 | 번호가 없어도 저장 가능, 소유·활성 상태 검증 없음 | 본인 카드 존재·활성 상태와 고객 키를 확인 |
| 지갑 한도 | 설정 화면의 저장 검사 아님 | 설정 저장 검사 아님 | 충전 후 잔액이 50,000,000원 초과이면 건너뜀 |

앱의 충전액 칩은 고정 목록이다. 충전 프리셋 API로 자동충전 화면의 값을 채우는 구현은 아니다. 서버 월 누계는 이번 달 생성된 `CHARGE`·`AUTO_CHARGE` 금액의 합이며 취소 금액을 뺀 순액이라는 보장은 없다.

## 결제 부족액 보충과 원 요청 재시도

결제 시 만료될 무료 포인트를 제외한 사용 가능 잔액으로 부족 여부를 판단한다. 이미 수동·자동충전 확인 중인 요청이 있으면 새 청구를 시작하지 않는다. 결제 기능이 열려 있고, 설정이 활성이고, 유효한 본인 카드와 한도를 만족해야 대상이 된다.

원 결제 요청의 조정기는 첫 시도에서 자동충전 필요 신호를 받으면 외부 청구 단계로 넘어간다. 계정·지갑 잠금 아래 영수증·진행 중 충전·실제 부족액·실행 조건을 다시 보고 확인 중 의도 기록을 저장한 다음 청구한다. 요청 내 자동충전은 한 번만 시도한다.

예를 들어 사용 가능 잔액 4,500원, 결제 필요액 8,000원, 설정 충전액 30,000원이면 부족액 3,500원보다 큰 30,000원을 청구 대상으로 삼는다. 성공 적립 뒤 원 요청을 다시 실행하며 그 결제까지 성공했을 때 잔액은 26,500원이다. 자동충전 성공만으로 원 결제의 성공까지 약속하지 않는다.

청구 결과가 확정되면 적립하고 원 요청을 다시 시도한다. 시간 초과·통신·알 수 없는 결과, 승인 금액 불일치, 승인 후 적립 실패는 확인 중을 유지한다. 이때 조정기는 원 결제를 즉시 다시 실행하지 않고 시간 초과 오류로 돌려준다. 확정된 청구 거절은 실패로 정리하며 무효 빌링키는 카드를 사용 불가로 표시한다. 다음 실행은 카드 활성 여부를 다시 확인한다. 비운영 환경의 서버 청구 단계에는 시뮬레이션 분기가 있으므로 이를 실제 결제 완료로 보지 않는다.

## 현재 제한과 확인 범위

| 분류 | 확인한 차이·한계 | 영향·후속 |
|---|---|---|
| Gap | 설정 임계값이 실행 조건에 사용되지 않음 | 화면의 임계값 안내·기존 화면 명세와 실제 부족액 기준을 일치시킬 대상 |
| Gap | 서버 저장은 카드 소유·활성, 상한, 월 한도와 충전액 관계를 실행 수준으로 검사하지 않음 | 저장 성공 후에도 실행되지 않는 설정이 생길 수 있음 |
| Gap | 무효 카드도 앱 선택 목록에 포함되고 삭제된 카드 번호가 서버 설정에 남음 | 사용 가능 카드 선택·삭제 후 재설정 안내 보완 대상 |
| Gap | 결제 기능이 닫히면 앱은 설정 전체를 안내 화면으로 바꾸지만 서버 해제는 결제 기능 검사 없이 허용 | 기존 설정 해제 입구도 앱에서 가려지는 차이 |
| Gap | 기존 화면 명세의 자동충전 이력은 현재 설정 화면에 없음 | 거래내역 조회와 설정 화면 내 이력을 구분 |
| Risk | 월 누계는 취소 차감 순액이 아니며 해제는 진행 중 청구 취소와 다름 | 월 한도·해제 결과를 과도하게 보장하지 않음 |
| 미검증 | 외부 청구·실DB 경합·원 구매 재실행·기기 계정 전환 | 소스 및 기존 제공자 시험 단언 대조를 전체 실행 통과로 확대하지 않음 |

## 수용 기준과 검증 근거

- **AC-01 기본 조회:** 설정 없음은 비활성 기본값으로 반환하고 조회만으로 저장하지 않는다.
- **AC-02 켜기와 저장:** 토글 켜기만으로 활성화하지 않으며 저장 성공을 기다린다.
- **AC-03 해제:** 확인 뒤 해제 성공 시 끄고 저장된 부가 값 보존과 진행 중 청구를 구분한다.
- **AC-04 실패 보존:** 저장 실패에도 폼을 유지하고 실패한 변경만 되돌린다.
- **AC-05 검증 범위:** 앱·서버 저장·실행의 금액·카드 검증 차이를 표시한다.
- **AC-06 실제 조건:** 설정 임계값이 아닌 결제 부족액을 현재 실행 조건으로 기록한다.
- **AC-07 실행 카드:** 삭제·무효·타인 카드와 고객 키 없음은 청구하지 않는다.
- **AC-08 한도:** 설정액과 부족액 중 큰 금액에 월 한도·지갑 한도·1회 상한을 적용한다.
- **AC-09 재실행:** 자동충전은 요청 안에서 한 번 시도하고 확정 뒤 원 요청을 재평가한다.
- **AC-10 불확실 결과:** 확인 중이면 원 요청 즉시 재실행·새 청구를 막고 복구와 구분한다.
- **AC-11 기능 제한:** 저장 제한과 해제 가능 서버 계약, 앱의 해제 입구 제한을 구분한다.

기존 `auto_charge_provider_test.dart`의 저장 실패 복원, 저장 중 폼 유지, 저장과 해제가 겹쳤을 때 실패한 해제만 되돌리는 단언을 확인했다. 화면 명세의 임계값 기준·5,000원 충전 하한·설정 화면 내 이력은 현재 코드와 차이가 있어 위에 기록했다. 이번에는 새 시험·외부 청구·실DB 경합을 실행하지 않았다.
