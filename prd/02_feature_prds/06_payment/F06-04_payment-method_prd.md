# F06-04. 결제수단 관리 PRD

<!-- release-document: reference -->
> **문서 구분: 기능·설계·절차 참고 문서.** 2026-11-22 서버·앱 소스와 명시한 기존 시험 단언을 대조했다. 새 제품 시험·기기·외부 결제의 통과 기록은 아니다. 현재 작업 순서는 [앞으로 할 일](../../../../docs/plan/NEXT_WORK.md)을 따른다.

## 결론

카드를 등록하려면 서버에서 등록 세션을 받고 결제사 인증을 거친다. 서버는 인증 결과로 빌링키와 카드 표시 정보를 얻는다. 사용자가 카드사·뒷자리·빌링키를 직접 입력하는 예전 등록 시트 설명은 현재 구현과 다르다. 목록·기본 지정·삭제와 자동충전에서 실제 사용 가능한지는 각각 확인한다.

## 입구와 목록

지갑 바로가기, 충전 화면의 결제수단 관리, 자동충전 설정에서 카드를 등록해야 하는 흐름으로 진입한다. 목록은 페이지 객체가 아닌 배열이다. 기본 카드 우선, 그다음 등록 시각 내림차순으로 반환하며 무효 카드도 포함한다.

화면은 등록 수와 5개 한도, 카드사·뒷자리·기본 표시·있는 별칭을 보여 준다. 사용 불가 카드는 재등록 필요 표시를 붙인다. 처음 로딩·오류와 다시 시도·빈 목록을 구분한다. 별칭은 응답과 서버 입력 계약에 있지만 현재 등록 화면에는 별칭 입력이 없다.

하단 카드 등록 단추는 등록 세션 요청·인증창 진행 중 비활성화한다. 이미 5개면 눌렀을 때 한도 안내를 한다. 단추 자체를 항상 숨기는 구현이 아니다. 결제 기능이 닫혀 있어도 목록 화면과 등록 입구는 남고, 등록을 누르면 세션 요청 전에 출시 안내로 이동한다.

## 카드 등록 세션과 저장

| 순서 | 현재 처리 |
|---|---|
| 세션 발급 | 본인 요청에 서버가 본인 번호를 포함한 새 `customerKey`와 공개 클라이언트 키를 반환. 결제 기능과 카드 수를 먼저 확인 |
| 인증창 | 임시 결제 설정이면 임시 인증창, 개발 환경이면 시뮬레이션, 그 외에는 Toss 인증창 구현 선택 |
| 앱 제출 | 인증 결과의 `authKey`와 해당 세션의 `customerKey`를 전송. 카드사·뒷자리·빌링키를 앱이 정해 보내지 않음 |
| 서버 입력 | 인증 키 공백, 고객 키 형식·본인 접두사, 별칭 최대 50 UTF-16 단위를 검사 |
| 발급·저장 | 인증 제공자로 빌링키를 발급받은 뒤 본인 계정을 잠그고 닫힌 계정 여부와 5개 한도를 다시 확인하여 저장 |
| 최초 카드 | 첫 카드이면 기본으로 지정. 카드사·뒷자리는 발급 결과에서 얻음 |
| 성공·실패 | 성공하면 목록을 다시 읽고 토스트. 실패하면 오류를 알리며 인증 취소는 조용히 닫음 |

목록 응답에는 번호·카드사·뒷자리·기본 여부·별칭·상태·생성 시각만 노출한다. 빌링키·고객 키는 목록에 포함하지 않는다. 인증 제공자의 외부 발급과 DB 저장은 한 번의 외부 원자 작업이라고 보장하지 않는다. 동시 등록의 최종 한도 판정은 계정 잠금 뒤에 다시 수행한다.

## 기본 지정·삭제·자동충전 연결

기본이 아닌 카드의 점 메뉴에는 기본으로 설정과 삭제, 기본 카드에는 삭제가 있다. 기본 지정은 본인 카드인지 확인한 뒤 이전 기본을 내리고 선택한 카드를 올린다. 새 기본을 정했다고 이미 저장된 자동충전 카드 번호를 함께 바꾸지는 않는다.

삭제는 확인창 뒤 본인 카드만 지운다. 기본 카드를 지웠고 다른 카드가 남았으면 정렬상 첫 카드를 기본으로 승계한다. 마지막 카드까지 지우면 빈 목록이 된다. 승계와 기본 지정은 현재 활성 카드만으로 제한하지 않는다.

저장·기본 변경·삭제 성공은 목록을 무효화하여 다시 읽는다. 서버 삭제 함수는 자동충전 설정의 카드 번호를 함께 비우거나 기능을 끄지 않는다. 설정이 삭제된 카드를 가리키면 실행 시 본인 카드 조회가 실패하여 자동충전을 하지 않는다. 자세한 실행 조건은 [자동충전 설정과 실행](F06-05_auto-charge_prd.md)을 따른다.

## 현재 제한과 확인 범위

| 분류 | 확인한 차이·한계 | 영향·후속 |
|---|---|---|
| Gap | 사용 불가 카드에도 기본 지정 메뉴가 있고 서버 기본 지정·승계도 활성 상태를 검사하지 않음 | 기본 배지만으로 사용 가능하다고 알리지 않도록 보완 |
| Gap | 카드 삭제가 자동충전 설정의 카드 번호·활성 여부를 정리하지 않음 | 실행 시 중단되는 이유와 재설정 입구를 함께 안내할 대상 |
| Gap | 인증 성공 뒤 저장을 기다리는 구간은 등록 단추의 세션 요청·인증창 잠금에 포함되지 않음 | 최종 저장 중 새 등록 진입 방지 여부 보완 대상 |
| Risk | 인증 세션 응답 후 화면 생존은 검사하지만 충전 화면과 같은 시도별 계정 세션 고정은 없음 | 계정 전환·늦은 인증 응답의 영향은 별도 확인 필요 |
| 미검증 | 실제 인증창·중복 발급·외부 발급 후 저장 실패·계정 전환 | 소스 검토와 모의 시험 단언을 실카드 등록 완료로 쓰지 않음 |

## 수용 기준과 검증 근거

- **AC-01 목록:** 본인의 배열을 기본·등록 시각 순으로 읽고 로딩·오류·빈 상태를 구분한다.
- **AC-02 기능 제한:** 결제 기능이 닫혔을 때 카드 등록은 세션 API 전에 안내로 이동한다.
- **AC-03 등록 세션:** 서버가 본인과 연결된 고객 키를 발급하고 앱은 해당 인증 결과를 제출한다.
- **AC-04 카드 정보:** 카드사·뒷자리·빌링키는 발급 결과에서 얻고 목록에 비밀 키를 노출하지 않는다.
- **AC-05 한도:** 최대 5개를 세션 발급과 최종 계정 잠금 뒤에 확인하며 최초 카드만 기본으로 시작한다.
- **AC-06 기본 지정:** 본인 카드만 변경하고 자동충전 설정의 카드 번호 변경과 구분한다.
- **AC-07 삭제:** 확인 뒤 본인 카드만 삭제하며 기본 승계·마지막 카드 빈 상태를 구분한다.
- **AC-08 무효와 삭제:** 기본 배지와 사용 가능 상태, 삭제된 카드를 가리키는 자동충전 설정을 구분한다.
- **AC-09 실패와 갱신:** 등록 실패를 성공으로 알리지 않고 변경 성공 뒤 목록을 다시 읽는다.

기존 `PaymentMethodServiceTest`의 세션 형식·본인 고객 키·입력 차단·제공자 결과 저장·최초 기본 지정·발급 실패 시 미저장 단언과 `payment_method_money_gate_test.dart`의 기능 제한 전 세션 요청 차단 단언을 확인했다. 이번에는 시험을 새로 실행하거나 실제 카드 인증·등록·경합을 검증하지 않았다.
