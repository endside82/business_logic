# F03-15. 이벤트 카풀 PRD

<!-- source-measured: 2026-08-30; authority: community_api/community_app current source -->

> 현재 상태: **핵심 코드와 서버 통합 검증 완료, 첫 출시에서는 신규 사용 봉인**. 안전 신고, 운전자 철회,
> 탑승 이탈처럼 위험을 줄이는 출구는 유지한다.

## 1. 제품 목적과 현재 결론

참석자가 운전자로 지원하거나 카풀 탑승을 요청하고, 호스트가 운행을 승인한 뒤 탑승자를 배정하는 기능이다.
현재 서버에는 조회·지원·결정·철회·신고·탑승 등록·이탈·배정 9개 API가 있고, 앱에는 참가자·운전자·호스트가
역할에 맞게 사용하는 카풀 화면과 안전 신고 화면이 연결돼 있다.

과거 PRD의 “신고 화면만 있고 진입 버튼이 없다”, “운영 화면·알림·배정 이력이 없다”는 설명은 현재 소스와
맞지 않는다. 지금은 배정·재배정·해제 이력을 남기며 승인·반려·배정·해제 알림을 영속 전송 대기열에 같은
처리로 기록한다. 다만 실제 여러 기기에서 역할별 알림 이동과 신고 종결까지 왕복한 기록은 없다.

## 2. 현재 상태기계와 권한

| 흐름 | 현재 규칙 |
|---|---|
| 운전자 지원 | `OPEN + CARPOOL + ATTENDING`만 가능. 이벤트·운전자당 활성 운행 1건 |
| 호스트 결정 | 호스트·공동 호스트가 `OFFERED`만 승인·반려. 화면이 본 버전을 함께 보내 늦은 결정을 차단 |
| 운전자 철회 | 본인의 `OFFERED` 또는 `CONFIRMED` 운행만 철회. 확정 운행이면 탑승자 전원 해제 |
| 탑승 선택 | 참석자 본인이 `카풀 요청` 또는 `개별 이동`만 저장. 배정 완료·운전자 상태는 서버만 생성 |
| 호스트 배정 | 승인된 운행, 양쪽 참석 유지, 차단 관계 없음, 정원 이내일 때만 배정 |
| 카풀 이탈 | 운전자 지원이 없으면 본인 탑승 행 삭제. 운전자는 먼저 운행을 철회해야 함 |
| 안전 신고 | 운전자 본인이 아닌 참석자만 가능. 서버가 경로의 운행에서 신고 대상 운전자를 확정 |

참가 취소·강퇴·탈퇴가 일어나면 상위 참석 흐름이 좌석과 카풀 흔적을 같이 정리한다. 운전자면 운행을
철회하고 탑승자를 해제하며, 탑승자면 배정을 풀고 행을 삭제한다.

## 4. 완성도 판단

| 판단 축 | 현재 상태 | 남은 일 |
|---|---|---|
| 제품 시나리오 | 8개 정의 완료 | 이동 책임 고지 승인 |
| 코드 구현 | 서버 상태기계·앱 역할별 화면·알림·신고·정리 연결 완료 | 개통 범위에 따라 `각자 이동 허용`의 카풀 적용 결정 |
| 자동 검증 | 서버 핵심 상태·권한·경합·정리·신고를 직접 검증 | 카풀 화면의 지원·결정·배정 widget 테스트와 앱-서버 E2E 보강 |
| 사용자 여정 | 서버 통합 E2E는 있음. 실제 앱 다중 역할 왕복은 없음 | 호스트·운전자·탑승자 계정과 두 기기로 C-02~C-07 실행 |
| 출시·운영 | 신규 카풀은 봉인, 안전 출구만 유지 | 책임 고지·실기기 알림·신고 운영 종결 후 `TRANSPORT` 개통 |

## 5. 남은 위험

- 신고 상세가 운행의 현재 픽업 경로를 참조하므로, 같은 운전자가 종료된 지원 행을 재사용하면 신고 시점의
  과거 경로가 보존되지 않는다. 사건 조사에 경로가 필수라면 별도 스냅샷이 필요하다.
- 서버 핵심 흐름은 강하게 검증됐지만 앱 화면의 정상·실패 분기 테스트가 상대적으로 적다. 실기기 검증 전
  카풀을 열면 서버는 맞아도 역할별 버튼·알림 이동에서 막힐 수 있다.
