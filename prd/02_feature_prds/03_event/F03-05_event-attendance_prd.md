# F03-05. 이벤트 신청·참석·본인 취소 PRD

<!-- release-document: reference -->
> **문서 구분: 기능·설계·절차 참고 문서.** 2026-11-22 해당 서버·앱 함수와 명시한 기존 시험 단언을 대조했다. 새 제품 시험·실DB·기기·알림 수신의 통과 기록은 아니다. 현재 작업 순서는 [앞으로 할 일](../../../../docs/plan/NEXT_WORK.md)을 따른다.

## 결론

무료이며 승인이 필요 없는 모임의 직접 참석과, 심사 또는 참가비 결제가 필요한 모임의 신청을 구분한다. 신청 승인·결제 대기·실제 참석·참석 대기는 서로 다른 결과다. 유료 모임은 신청할 때 바로 지갑을 차감하지 않고, 결제 대기와 별도 결제 확정을 거친다.

호스트의 심사는 [신청서 승인·거절](F03-06_application-review_prd.md), 대기열 운영은 [정원과 대기열](F03-07_capacity-and-waitlist_prd.md), 금액 계산·환불은 [참가비 결제와 신청 취소](../06_payment/F06-06_point-pay-refund_prd.md)에서 이어진다. 비공개 모임의 선정·보관금, 정기모임 고정 회차의 등록은 별도 업무다.

## 실제 입구와 신청 확인

모임 상세 하단의 참석 신청에서 확인 시트를 연다. 로그인이 필요하면 해당 모임으로 돌아올 주소를 붙여 로그인으로 이동한다. 호스트 본인, 가입이 필요한 클럽 비회원, 종료·취소 모임, 이미 참석·대기·심사 중인 상태는 안내하거나 현재 행동을 차단한다. 버튼의 노출 판단과 별개로 서버가 접근·상태·권한을 다시 검사한다.

확인 시트는 본인과 허용된 게스트의 인원을 조립한다. 빈 게스트 이름은 순서별 기본 이름으로 바뀐다. 승인 설정·승인 공개·비공개 모임이면 선택 신청 메시지 칸이 있고, 바로 참석하는 모임에는 없다. 메시지는 앞뒤 공백을 제거하고 빈 값은 보내지 않으며 서버의 최대 길이는 500자다. 비공개 모임은 호스트 선정 안내를 사용하고 게스트 신청을 허용하지 않는다.

안내 확인 체크를 해야 제출할 수 있다. 확인 시트는 입력 결과를 넘기고 닫힌 뒤 실제 신청 요청이 시작된다. 일정 변경 제안이 열려 있으면 변경 내용을 확인받아 해당 제안 번호를 함께 보낸다. 요청 사이에 제안이 바뀌어 재확인이 필요하면 상세를 새로 읽고 한 번 더 동의를 구한다. 동의를 닫으면 그 신청을 보내지 않는다.

## 신청 조건과 서버 결과

서버는 접근 가능 여부, 제재, 일정·장소 결정 대기, 모집 상태, 클럽 회원 여부, 정기모임 전용 등록 여부, 환불 대기, 정원과 호스트 본인 여부를 검사한다. 신청 경로에서는 규칙 묶음으로, 직접 참석 경로에서는 관련 조건을 순서대로 판정한다. 유료인데 선입금 설정이 없으면 결제 없는 참석을 만들지 않는다. 선입금 수단의 공개 준비 조건도 신청·승인 시 검사한다.

| 신청 조건 | 서버가 만드는 결과 | 참가자가 이어서 할 일 |
|---|---|---|
| 무료·승인 불필요, 자리 있음 | 직접 참석 ATTENDING | 상세의 참석 상태 확인 |
| 무료·승인 불필요, 자리 없음·대기 허용 | 직접 참석 WAITING과 순번 | 대기 안내 확인 |
| 승인 필요 | 신청 PENDING | 호스트 심사 기다림 |
| 자동 승인·선입금 필요 | 신청 APPROVED_PENDING_PAYMENT, 결제액·기한 | 별도 참가비 결제로 참석 확정 |
| 심사 뒤 선입금 승인 | 신청 APPROVED_PENDING_PAYMENT | 승인 자체를 참석 완료로 보지 않음 |
| 심사 뒤 무료 승인 | 신청 APPROVED와 참석 ATTENDING 또는 WAITING | 실제 참석·대기 상태를 함께 확인 |
| 정원·대기 상한 초과, 금지된 게스트, 신청 제한 | 해당 조건의 거절 | 상태를 갱신하거나 조건을 해소한 뒤 재시도 |

직접 참석과 무료 승인에서 본인·게스트를 각각 배치한다. 자리가 부족하고 대기가 허용되면 같은 일행 안에서도 참석과 대기로 나뉠 수 있다. 대기열 상한은 설정된 양수 값, 미설정이면 기본 정원의 두 배다. 결제 확정 경로는 대기로 돌리지 않고 자리가 없으면 결제 확정 불가로 처리한다. 실제 승격의 후보·순서·제재 처리는 정원과 대기열 문서의 범위다.

## 일행 금액·결제 대기·만료

선입금 신청은 모임에 저장된 선입금 단가와 본인을 포함한 일행 수로 결제액을 정한다. 자동 승인 때 또는 호스트 승인 때 결제 기한을 설정한다. 결제 대기 일행은 유료 모임의 잔여석 계산에서 자리를 잡지만 아직 참석 행과 실제 참석 수를 늘리지 않는다. 결제가 확정될 때 신청을 APPROVED로 바꾸고 본인·게스트 참석을 연결한다.

결제 기한 만료 작업은 기본적으로 직전 작업 종료 뒤 5분 간격으로 실행한다. 기한이 엄격히 지난 결제 대기를 찾고, 최종 상태 변경에서도 같은 조건을 다시 검사한다. 호스트 확인 대기인 계좌이체 신고가 있으면 제외한다. 실제로 바뀐 건에만 PAYMENT_EXPIRED, 자동 거절 결정 이력, 만료 알림 저장을 남긴다. 한 후보의 실패로 나머지 후보 처리를 중단하지 않는다. 배치 실행과 실제 알림 수신은 이번 문서 대조에서 수행하지 않았다.

앱은 신청 성공 후 반환 상태에 맞춰 심사 대기·결제 대기 등을 표시하고 모임 상세·카드·예정 모임을 다시 읽도록 알린다. 직접 참석의 대기 응답이면 순번 안내를 사용한다. 결제 단추·잔액 부족·자동충전·계좌이체 입구는 참가비 결제 문서의 범위이며, 신청 성공 안내만으로 결제 완료를 선언하지 않는다.

## 재신청과 결과 불명 재시도

PENDING·APPROVED·APPROVED_PENDING_PAYMENT 신청이 있으면 중복 신청을 거절한다. 환불 대기 신청·은행 반환 대기가 있으면 새 신청을 막는다. 취소·거절·결제 기한 만료 후에는 활성 결제가 남아 있지 않아야 재신청할 수 있다. 기존 신청 행을 재사용하되 메시지·일행·결제액·기한을 다시 설정하고 이전 결정 표시를 지우며 신청 차수를 올려 이력을 남긴다. 직접 참석과 신청서 경로가 동시에 살아 있는 것도 막는다.

앱은 신청 내용과 현재 신청 차수·수정 번호를 구분해 같은 불확실한 요청의 번호를 재사용한다. 서버는 요청 번호가 있는 신청·참석·심사에서 저장된 대상 번호로 현재 결과를 다시 읽는다. 앱의 신청·승인·거절 번호는 로그인 세션에 묶인 메모리 보관이다. 앱 재시작 뒤까지 같은 번호가 유지된다고 쓰지 않는다. 결제·신청 취소의 별도 보관 명령과도 구분한다.

반영됐을 수 있는 오류는 상세 등을 다시 읽고 오류를 알린다. 요청 실패 후 참가자의 확인 시트 입력을 자동 복원하는 흐름은 현재 없다. 새로 연 시트에서 다시 입력하는 것과 같은 요청의 결과 확인을 구분해야 한다.

## 시작·종료 상태와 본인 취소

일반 모임은 종료되면 본인 취소를 거절하고, OPEN 상태여도 시작 시각 이상이면 거절한다. 선정된 비공개 모임은 CLOSED 상태를 곧바로 종료로 취급하지 않지만 시작 시각 이후에는 제한하며, 열린 보관금에 묶인 선정자는 별도 취소 조건을 따른다. 취소된 모임의 정리와 일정 변경 거절의 자동 취소는 일반 본인 취소와 구분한다.

앱은 승인 필요·활성 신청·결제 필요 여부를 보고 신청 취소 경로를 고르고, 나머지는 직접 참석 취소로 보낸다. 이미 취소·거절·환불 대기인 신청은 다시 취소하지 않는다. 유료 신청은 직접 참석 취소로 결제 정리를 건너뛸 수 없다. 취소 시트의 예상액·동의와 지갑 반환·주최자 은행 반환 대기는 [참가비 결제와 신청 취소](../06_payment/F06-06_point-pay-refund_prd.md)를 따른다. 성공 안내가 실제 은행 송금 완료를 뜻하지 않는다.

## 취소 뒤 좌석·대기열·화면

직접 참석 취소는 본인과 소유 게스트의 참석을 정리하고 실제로 빠진 참석 수만큼 정원을 낮춘다. 체크인·이동수단 등 참가 종료 후속도 연결한다. 모임이 종료·취소 상태면 대기자를 승격하지 않는다. 그 밖에는 해제된 자리 수만큼 승격 처리를 호출하고 대기 순서를 다시 정리한다. 참가자가 이미 WAITING이었다면 본인에게서 참석 자리 하나가 생긴다고 계산하지 않는다.

앱은 취소 후 상세에 남아 결과를 알리고, 상세·카드·예정/참석 목록을 갱신한다. 신청 취소는 지갑 갱신도 연결한다. 재조회 전에 남아 있는 화면 표시를 최종 서버 상태로 취급하지 않는다.

## 현재 제한과 확인 범위

| 분류 | 확인한 차이·한계 | 영향·후속 |
|---|---|---|
| Gap | 참가자 확인 시트는 요청 전에 닫히며 실패 후 입력을 복원하지 않음 | 메시지·게스트를 다시 입력해야 할 수 있음 |
| Gap | 앱 게스트 이름 입력은 20자, 서버 정규화는 40자 한도 | 서로 같은 입력 한도로 설명하지 않음 |
| Risk | 신청 응답 APPROVED를 앱이 잠정 참석으로 매핑하지만 무료 승인에는 WAITING 배치도 있음 | 상세 재조회 결과까지 대조하며 승인과 실제 참석을 구분 |
| Risk | 시트의 가격 표시는 모임 가격, 서버 신청 결제액은 선입금 단가와 일행 수를 기준으로 함 | 표시액과 최종 결제액의 일치를 별도 확인 |
| Risk | 신청 명령 번호는 세션 메모리이고 참가자 입력 시트는 실패 시 이미 닫힘 | 재시작·재입력 후 재시도와 동일 요청 재생의 범위 구분 |
| 미검증 | 이번 근거는 소스와 기존 시험 단언 대조 | 실DB 동시 신청·배치 실행·자동 승격·실제 결제·알림 수신 통과로 확대하지 않음 |

2026-05-22 선입금 통합, 2026-07-29 일행 신청, 2026-10-24 시작 후 취소 제한, 2026-11-08 신청 메시지·유료 대기 정책의 기록은 당시 변경 이력이다. 옛 문서의 “호스트 알림 없음”, “취소하면 항상 한 자리 감소”, “승인하면 모두 참석”을 현재의 일률적인 결과로 사용하지 않는다.

## 수용 기준과 검증 근거

- **AC-01 로그인과 모임 복귀:** 비로그인 사용자가 신청하면 해당 모임의 복귀 주소를 가진 로그인으로 이동하며 요청을 먼저 보내지 않는다.
- **AC-02 신청 메시지:** 승인 필요 모임에서 공백을 다듬은 선택 메시지를 보내고 빈 입력은 생략한다. 바로 참석하는 모임에는 메시지 칸이 없다.
- **AC-03 일정 변경 동의:** 열린 제안에 동의하지 않으면 신청하지 않는다. 요청 사이 제안이 바뀌면 최신 내용을 다시 보여 주고 동의한 번호로 재시도한다.
- **AC-04 무료 직접 참석:** 자리가 있으면 ATTENDING, 대기 허용 한도 안이면 WAITING과 순번을 반환하고 앱이 상세를 갱신한다.
- **AC-05 심사와 결제 분리:** 승인 필요 신청은 PENDING, 자동 승인 선입금은 APPROVED_PENDING_PAYMENT다. 신청 단계에서 참가비 차감 완료로 안내하지 않는다.
- **AC-06 일행 배치:** 본인·게스트 각각의 자리와 대기 한도를 검사한다. 결제 확정에서는 일행을 대기로 돌리지 않는다.
- **AC-07 금지 조건:** 호스트 본인·제재·클럽 비회원·고정 회차 전용 등록·금지된 게스트·모집 불가 조건은 해당 서버 판정으로 거절한다.
- **AC-08 유료 좌석 예약:** 결제 대기 일행은 유료 잔여석 계산에 포함하고 실제 참석 행 생성은 결제 확정 뒤로 둔다.
- **AC-09 기한 만료:** 기한이 지난 대상도 계좌이체 신고 대기이면 제외한다. 상태 변경에 성공한 대상에만 자동 거절 이력·만료 알림을 남긴다.
