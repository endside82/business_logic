# F05-05. 저장된 검색과 새 결과 알림 PRD

<!-- release-document: reference -->
> **문서 구분: 기능·설계·절차 참고 문서.** 2026-11-22 서버·앱 소스와 기존 시험 목적을 대조했다. 새 제품 시험·실기기·외부 알림 검증 기록이 아니다. 실행 순서는 [앞으로 할 일](../../../../docs/plan/NEXT_WORK.md)을 따른다.

## 결론

저장된 검색은 로그인한 본인의 이벤트 검색어·필터를 서버에 최대 10개 보관하는 기능이다. 최근 검색어의 기기 저장과 다르다. 저장 목록의 실행은 사용 횟수·최근 사용 시각 갱신 후 앱이 이벤트 검색을 따로 요청하는 두 단계다. 실행 기록만으로 검색 결과 조회가 성공했다고 판정하지 않는다.

## 저장·목록·수정·삭제

| 입구·행동 | 현재 결과·실패 |
|---|---|
| 검색 실행 뒤 검색 저장 | 비로그인은 로그인으로 연결. 이름과 새 결과 알림 여부를 입력하고 검색어·현재 필터를 저장 |
| 저장 확인창 | 이름은 공백 제거 후 필수, 최대 50자. 요청 중 중복 저장을 막고 성공하면 닫음. 실패하면 오류를 알리고 입력을 유지 |
| 검색 화면의 저장된 검색 보기 | 기존 검색 화면 위에 목록을 열고 포커스를 해제. 목록 로딩·빈 목록·조회 실패 재시도를 구분 |
| 최신순·이름순 | 최신순은 최근 사용 시각, 없으면 생성 시각. 이름순은 한글·영문·그 밖의 이름 순서를 적용하고 같은 이름에는 번호 순서를 적용 |
| 조건 수정 | 필터 시트를 열어 조건만 바꾸며 이름·검색어·알림 값은 보존. 적용은 요청 완료를 기다리지 않고 시트를 닫고, 실패는 안내 |
| 알림 토글 | 이름·조건과 새 알림 값을 함께 저장. 실패 안내가 있으며 변경 성공 응답을 목록에 반영 |
| 삭제 | 확인 후 목록에서 먼저 빼고 서버에 요청. 실패하면 해당 삭제를 되돌리고 오류 안내 |

서버는 생성 시 소유자 잠금을 잡고 10개 한도를 다시 검사한다. 조회는 본인 목록이며 수정·삭제·실행도 소유자를 확인한다. 존재하지 않는 항목과 다른 사람의 항목을 성공으로 처리하지 않는다. 서버의 이름 변경 지원과 현재 앱의 필터 수정 입구를 구분하며, 앱에서 이름을 다시 편집하는 입구는 없다.

## 조건 저장과 다시 실행

저장 대상은 검색어·카테고리·날짜·요일·반경·좌표·가격·무료 여부·최소 정원·지역이다. 정렬과 결과 탭은 현재 저장 조건에 들어 있지 않다. 서버는 허용한 조건·타입·날짜 및 가격 순서·값 범위를 검사하고 JSON을 정규화한다. 중복 키·알 수 없는 조건·잘못된 형식·16KiB 초과는 거절한다. 과거 단일 카테고리·구역 이름은 현재 형식으로 받아 정규화한다.

실행은 서버에서 사용 횟수와 최근 사용 시각을 갱신하고 저장 항목을 돌려준다. 앱은 조건을 읽어 이벤트 검색 공급자에 적용하고 검색을 시작한 뒤 목록을 닫는다. 돌아갈 화면이 없으면 검색 화면으로 이동한다. 최근 검색어 기록은 별도로 시도한다.

이 실행 경로는 클럽·플랜·사람 검색을 함께 다시 시작하거나 검색 화면의 선택 탭을 이벤트로 강제하지 않는다. 이전에 다른 결과 탭을 보고 있었다면 실행한 이벤트 결과와 화면에 보이는 유형이 다를 수 있다. 기존 검색어가 있는 상태에서 필터를 먼저 바꾸면 이전 검색어의 재조회도 시작될 수 있으므로 최종 요청과 화면 조건을 구분한다.

## 새 결과 알림

알림을 켠 저장 항목은 30분 주기의 검사 대상이다. 매 검사에서 현재 시각보다 2분 앞선 시각을 끝점으로 삼고, 이전 검사 시각 이후부터 그 끝점까지 새로 발행된 이벤트 중 조건에 맞는 건수를 센다. 처음에는 저장 생성 시각을 시작점으로 삼는다. 즉시 알림이나 발행 후 정확히 30분 내 수신 보장은 아니다.

항목별 잠금과 독립 트랜잭션으로 검사 시각·건수·알림 생성 처리를 묶는다. 한 항목 실패가 다른 항목의 검사를 중단시키지는 않는다. 새 결과 건수는 마지막 검사 구간의 건수이며 누적 미확인 건수가 아니다. 실행은 이 건수를 지우지 않는다.

현재 작업자의 검색 호출에는 소유자의 차단 호스트 집합을 전달하지 않는다. 따라서 로그인해 직접 보는 이벤트 결과와 알림 집계가 달라질 수 있다. 저장 조건에 좌표가 없고 반경만 있으면 작업자는 기기 위치를 얻지 않으므로 거리 조건도 적용하지 못한다. 알림 생성·개인 알림 설정·외부 전송·수신·탭 후 결과 조회는 각각 별도 확인 범위다.

## 현재 제한과 확인 범위

| 판정 | 항목 | 영향·다음 확인 |
|---|---|---|
| Gap | 실행 후 유형별 결과 | 이벤트만 재조회하고 선택 탭을 고정하지 않아 다른 탭의 이전 결과가 남을 수 있음 |
| Gap | 저장되지 않는 조건·수정 입구 | 정렬·결과 탭은 보관하지 않으며 앱 이름 수정 입구가 없음 |
| Gap | 알림 집계와 로그인 검색 | 작업자에는 차단 대상이 전달되지 않고 기기 위치도 얻지 않아 표시 결과와 건수가 달라질 수 있음 |
| Risk | 전체 조건을 함께 덮어쓰는 수정 | 필터 수정과 알림 토글의 동시 요청에서 이전 이름·조건·알림 값으로 덮어쓸 수 있어 경합 확인 필요 |
| Risk | 조건 변경·알림 재활성화 | 수정은 이전 검사 시각을 초기화하지 않음. 다시 켠 뒤 어떤 구간을 새 조건으로 셀지 제품 안내와 대조 필요 |
| 미검증 | 실제 알림과 왕복 | 실행 횟수 증가·알림 생성 코드가 실제 검색 성공·기기 수신을 증명하지 않음 |

## 수용 기준과 검증 근거

- **AC-01 저장 입구:** 검색 후 저장·로그인 복귀·저장 목록 진입을 구분한다.
- **AC-02 저장 결과:** 이름 필수·50자·중복 제출 방지·성공 시 닫기·실패 시 입력 유지가 일치한다.
- **AC-03 소유권·한도:** 본인만 조회·수정·삭제·실행하며 동시 생성에서도 10개 상한을 적용한다.
- **AC-04 조건 계약:** 허용 필터·값 범위·잘못된 JSON을 검사하고 정렬·결과 탭이 저장되지 않음을 명시한다.
- **AC-05 목록 순서:** 최근 사용·생성 시각과 이름순·동률 순서가 표시와 일치한다.
- **AC-06 수정·삭제:** 필터 변경 실패·알림 변경 실패·삭제 취소·실패 시 목록 복구를 구분한다.
- **AC-07 실행 단계:** 실행 기록 갱신 뒤 이벤트 조회를 별도로 확인하고 결과 실패를 실행 성공으로 덮지 않는다.
- **AC-08 복귀:** 이전 선택 탭·검색어·필터와 최종 이벤트 결과가 맞는지 확인한다.
- **AC-09 알림 구간:** 30분 검사·2분 지연 끝점·발행 시각·마지막 구간 건수와 실행 뒤 건수 유지를 구분한다.
- **AC-10 알림 차이:** 차단·좌표 누락·알림 재활성화·외부 수신의 현재 제한을 확인한다.

기존 저장 정렬·목록 화면·저장 확인창 대기 시험과 서버 `SavedSearchNotificationSchedulerTest`가 있다. 이번 대조는 현재 동작과 시험 목적 확인이며 동시 수정·실제 전송·기기 수신 시험을 새로 통과한 기록은 아니다.
