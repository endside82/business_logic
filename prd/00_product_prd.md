# 사이숲 전체 제품 요구사항 문서

<!-- release-document: reference -->
> 2026-11-22 제품·기능·정책 정본을 대조한 전체 안내다. 현재 작업은 [앞으로 할 일](../../docs/plan/NEXT_WORK.md)을 따른다. 이 문서의 갱신을 실행 검증·정식 공개·새 정책 승인으로 해석하지 않는다.

## 제품이 해결하는 문제

관심사에 맞는 오프라인 활동을 찾고 참여하며, 관계 유지와 후속 운영·정산·안전 절차를 이어 가는 서비스다. 발견·신청·회차 운영·금전 책임·문제 해결이 이어져야 하며, 사용자는 어느 단계가 끝났고 무엇이 남았는지 알 수 있어야 한다. [서비스 개요](00_prd_items/01_service_overview.md)에 문제별 제품 책임을 정리한다.

## 사용자와 현재 범위

비로그인 방문자와 동반 게스트를 구분한다. 신청자·참석자·책임 회원·호스트·위임자·클럽 소유자·판매자·구매자·제공자·수취자·신고/문의/분쟁 당사자·플랫폼 운영자는 대상과 현재 관계에 따라 다른 권한을 가진다. [사용자 유형과 기대 경험](00_prd_items/02_user_personas.md)을 역할 관점으로 읽고 세부 허용은 권한 정책을 따른다.

첫 출시는 무료 모임·클럽·정기모임, 주최자 계좌 직접 송금과 교통편·투표·마일리지·스탬프·프로필·공유 등 승인된 범위를 따른다. 플랫폼 결제·마켓·데이트·제공자 거래와 외부 연동의 후속 공개 조건은 [현재 범위 검토표](05_planning_artifacts/mvp_scope_matrix.md)에서 구분한다. 모든 기능을 다시 MVP 후보로 돌리거나 구현됐다는 이유로 공개하지 않는다.

## 21개 영역과 175개 기능

[전체 정보구조](00_prd_items/03_information_architecture.md)는 일곱 문서 묶음과 실제 앱 메뉴를 분리한다. [영역별 목적](00_prd_items/04_domain_purposes.md)은 책임 경계를, [175개 기능 목록](00_prd_items/05_feature_definitions.md)은 각 정본을 연결한다. 기능 ID와 도메인 번호는 안정 식별자로 유지한다.

현재 등록 확인 항목 합은 1,654개다. 별도 상세 문서 117개에서 식별한 제목은 1,276개이고 원천 문서가 없는 58개 기능도 해당 PRD의 수용 조건을 가진다. 도식과 등록·상세 집계의 원천은 [시나리오 커버리지](04_qa_acceptance/scenario_coverage_matrix.md)를 따른다. 문서 수·도식 수·등록 수를 실행 통과 수나 품질 점수로 바꾸지 않는다.

## 대표 여정과 완료 경계

| 사용자 업무 | 요구하는 결과와 구분 |
|---|---|
| 가입·로그인·원래 목적지 | 유효한 세션으로 허용된 목적을 이어감. 번호 확인·첫 이용 설정·프로필 완성을 구분 |
| 모임 신청·참석·후기 | 승인·납부·대기·실제 참석·체크인·후기 자격을 구분하고 현재 결과를 확인 |
| 호스트·클럽 운영 | 현재 위임·회원 상태에서 모집·공지·회차·교통편·활동 제도·재정을 처리 |
| 정기모임 등록·출석·종료 | 코스와 회차, 종료 판정과 환불·정산 생성·지급을 분리 |
| 모임 정산과 반환 | 원 납부자·실제 수취자와 지출/수입에 맞는 책임. 부모 취소 뒤 반환 의무 확인 |
| 플랜 작성·판매·구매 | 콘텐츠 공개·후보 심사·판매·구매 당시 권리·부분 환불을 구분 |
| 데이팅 | 본인확인·프로필·현재 매칭·대화·만남·차단과 공개 조건을 각각 확인 |
| 알림·일정·관심인 | 기록·기기 전달·현재 열람 권한, 본인 가능 시간과 공개 모임을 구분 |
| 개인정보·계정 종료 | 동의·노출 중지·좌표 제거·내보내기·삭제 예약·즉시 탈퇴·후속 파기를 구분 |
| 신고·지원·분쟁 | 원천별 접수·관할·자료·판정·이의·보상·종결을 구분 |
| 제공자 거래 | 계약·분담·이행·수금·정산 확정·실제 지급·사후 회수를 구분 |

구체적인 입구·행동·실패 복구는 [사용자 여정](00_prd_items/06_user_journeys.md)과 해당 기능 PRD를 따른다. 모든 여정을 가입부터 결제·후기까지 이어지는 하나의 필수 경로로 만들지 않는다.

## 공통 요구사항과 수용 조건

1. 실제 메뉴·목록·공유·알림의 입구와 원래 화면으로 돌아왔을 때의 갱신을 설명한다. 같은 행동의 중복 입구도 현재 상태·역할별로 구분한다.
2. 계정·관계·위임·대상 상태·기한·공개 조건을 실행 때 확인한다. 버튼 표시와 최종 허용을 합치지 않는다.
3. 요청 접수·승인·돈의 예약·입금·반환·권리 회수를 구분하고 원천별 의무를 남긴다. 결과 불명에서 새 명령을 임의로 만들지 않는다.
4. 실패·부분 처리·만료·권한 상실·계정 전환에서 현재 상태와 복구·재조회 경로를 제공한다.
5. 알림 의도·기록·공급자 수락·기기 표시와 원래 업무 결과를 따로 확인한다.
6. 동의·차단·공개 범위·열람·보존·파기를 대상별로 적용하고 한 단계의 성공으로 다른 단계를 완료 처리하지 않는다.
7. 수용 기준은 시작 조건 → 조작 → 관찰할 결과로 쓰고 소스 대조·기존 실행·새 실행·외부 확인의 범위를 구분한다.

정본은 [상태](03_policy_prds/state_policy_prd.md), [권한](03_policy_prds/permission_policy_prd.md), [결제·정산](03_policy_prds/payment_settlement_policy_prd.md), [알림](03_policy_prds/notification_policy_prd.md), [개인정보·안전](03_policy_prds/privacy_safety_policy_prd.md), [기획 QA](03_policy_prds/planning_qa_policy.md)다. 각 기능의 구체적 조건은 [기능별 수용 기준 표](04_qa_acceptance/acceptance_criteria_matrix.md)로 연결한다. 이 공통 요구사항이 모든 기능의 구현·실행 완료를 증명하지 않는다.

## 문서 운영과 미결정

[PRD 문서 입구](README.md)에서 전체 구성과 정본 관계를, [작성·검수 기준](FEATURE_PRD_STANDARD.md)에서 근거와 완료 판정을 확인한다. 현재 대조 상태는 [문서 전환 현황](PRD_MIGRATION_STATUS.md)과 [전체 대조 기록](../verification/document-refresh-2026-11-22.json)을 따른다.

KPI·운영 응답 기한·외부 계약·고지 문구 등은 [결정 등록부](05_planning_artifacts/decision_register.md)에서 승인 근거와 남은 질문을 구분한다. 제품 정책과 구현이 다르면 차이를 적고 승인 없이 정책을 바꾸지 않는다. 새로운 결정이나 실행 결과가 없는데 날짜·표 개수만 바꿔 완료 처리하지 않는다.
