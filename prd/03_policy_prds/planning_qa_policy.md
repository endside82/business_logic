> 문서 상태: **보조 문서**. 기능별 현재 계약, source trace, Gap/Risk 판단은 [기능 PRD 전환 현황](../PRD_MIGRATION_STATUS.md)와 각 기능 PRD를 우선한다. 이 문서는 인벤토리, 정책, QA, 기획 운영 기준을 보조하며, 기능 세부 판단은 [기능 PRD 작성·검수 기준](../FEATURE_PRD_STANDARD.md) 기준으로 재확인한다.

이 문서는 새 화면, 새 정책, 기존 기능 변경을 검토할 때 사용하는 마지막 점검표다. 기능이 많을수록 "주 흐름"은 기억하지만 상태, 돈, 알림, 권한, 개인정보, 외부 실패를 놓치기 쉽다.

## 검증할 질문과 증거 선택

변경한 내용과 아직 해결되지 않은 의문을 먼저 적고, 그 질문을 판정할 수 있는 증거를 고른다. 적용하지 않는 범주는 이유를 적고 제외한다. 모든 기능에 같은 수의 새 시험·이미지·기기 조합을 만들지 않는다. 문서만 고친 경우에는 내용 대조·링크·파생 문서 동기화를 검사하며 제품 실행을 했다고 기록하지 않는다.

| 판정할 질문 | 사용할 증거 | 그 증거만으로 말할 수 없는 것 |
|---|---|---|
| 요청 값·역할·상태·중복·복귀 | 해당 소스와 실제 조건을 단언하는 시험·로그 | 파일 존재만으로 시험 통과, 로컬 통과만으로 운영 통과 |
| 버튼 위치·잘림·대비·이미지 표시 | 문제가 있는 대표 화면의 실제 이미지 | 화면 한 장으로 요청 성공·정산 완료·알림 도착 |
| 실제 메뉴 입구·업무 결과·복귀 | 해당 버전의 앱에서 구체적인 경로를 실행한 결과 | 탐색 맵·문서 HTML·목업으로 실제 앱 동작 |
| 메일·푸시·PG·은행·서명 앱 | 대상 환경에서 해당 외부 결과를 확인한 기록 | 발송 의도·큐 등록·요청 접수만으로 수신·지급 완료 |
| 문서 통계·연결 | 현재 입력 파일과 집계 규칙·링크 검사 | 시나리오 등록 수·소스 주소 존재로 전체 내용·실행 검증 |

UI 확인이 필요한 변경은 기본 390×844·글자 1배의 실제 입구 → 정상 업무 → 결과 → 원래 상태 복귀를 따른다. 큰 글자·작은 폭 조합은 기본 범위에 넣지 않고 해당 환경의 보고된 결함 또는 사용자 요청에 따라 선택한다. 이미지 없이 판정할 수 있는 상태·권한·키·횟수는 시험과 로그로 확인한다. 테마·분기별 전수 캡처를 기본 절차로 만들지 않는다.

버전과 확인 범위가 맞는 기존 근거는 재사용한다. 변경·새 실패·미해결 의문이 없으면 같은 소스·로그·이미지·회귀 실행을 반복하지 않는다. 근거가 바뀌었을 때 해당 판단만 다시 확인한다. [기능 PRD 작성·검수 기준](../FEATURE_PRD_STANDARD.md#수용-기준과-검증-근거)과 저장소의 검수 운영 규칙을 함께 적용한다.

## 실제 접근 경로와 중복 행동 확인

화면 주소만 직접 열어 확인을 끝내지 않는다. 해당 기능으로 이어지는 실제 메뉴·카드·목록·알림·공유 링크와 로그인 후 복귀 경로를 적는다. 같은 행동이 햄버거 메뉴·상단 독립 버튼·더보기 메뉴·하단에 동시에 나타나는지 비교하고, 상태·역할 때문에 입구가 달라지는 경우에는 그 조건을 명시한다.

입구마다 먼저 확인할 것은 접근 가능 여부·실행 대상·변경 결과·돌아왔을 때 갱신되는 상태다. 공통 동작은 검증한 근거를 재사용하고 차이가 있는 입구만 추가 확인한다. 업무에 필요한 서로 다른 입구와 불필요한 중복 행동은 승인된 제품 기준으로 구분한다. 이 검토표가 기존 입구를 임의로 제거할 권한을 새로 만들지는 않는다.

## 전체 점검 흐름

```mermaid
flowchart TD
    A["기능/화면 변경안"] --> B["사용자와 역할 확인"]
    B --> C["시작 상태와 종료 상태 확인"]
    C --> D["주요 성공 흐름 확인"]
    D --> E["예외/빈 상태/실패 확인"]
    E --> F["돈/알림/위치/리뷰 부수효과 확인"]
    F --> G["개인정보/안전/운영 리스크 확인"]
    G --> H["QA 케이스와 로그/추적 포인트 확인"]
```

## 1. 사용자와 역할

| 체크 | 질문 |
|---|---|
| 주 사용자 | 이 기능을 가장 자주 쓰는 사람은 누구인가 |
| 보조 사용자 | 같은 기능의 결과를 받는 사람은 누구인가 |
| 금지 사용자 | 버튼을 보거나 실행하면 안 되는 사람은 누구인가 |
| 복합 역할 | 호스트이면서 참가자, 클럽 관리자이면서 일반 멤버 같은 경우가 있는가 |
| 비정상 계정 | 제재·탈퇴 예약·탈퇴 상태와 가입 전 번호 확인은 각각 어떻게 되는가 |

## 2. 시작 상태와 종료 상태

| 체크 | 질문 |
|---|---|
| 시작 상태 | 사용자가 이 화면에 들어오기 전에 반드시 만족해야 하는 조건은 무엇인가 |
| 성공 종료 | 성공 후 어떤 상태/화면/데이터가 바뀌는가 |
| 실패 종료 | 실패 후 사용자가 다시 시도할 수 있는가 |
| 중간 이탈 | 입력 중 뒤로가기, 앱 종료, 네트워크 끊김 후 재진입은 어떻게 되는가 |
| 상태 갱신 | 다른 기기나 다른 사용자의 액션으로 상태가 바뀌면 어떻게 반영하는가 |

## 3. 빈 상태와 에러 상태

| 화면 상태 | 반드시 정해야 할 것 |
|---|---|
| 최초 로딩 | 스켈레톤, 스피너, 빈 화면 중 무엇을 쓰는가 |
| 데이터 없음 | 사용자가 다음에 할 수 있는 액션이 있는가 |
| 일부 실패 | 다른 섹션은 보여줄 수 있는가 |
| 전체 실패 | 재시도 버튼이 있는가 |
| 권한 없음 | 로그인 유도, 접근 불가, 이전 화면 복귀 중 무엇인가 |
| 만료/삭제 | 대상이 사라졌거나 만료되었을 때 문구는 무엇인가 |

## 4. 돈이 움직이는 기능

| 체크 | 질문 |
|---|---|
| 잔액 부족 | 충전으로 보낼 것인가, 자동충전을 시도할 것인가 |
| 결제수단 없음 | 결제수단 등록 화면으로 보낼 것인가 |
| 결제 성공 | 거래내역, 잔액, 원래 기능 상태가 모두 갱신되는가 |
| 결제 실패 | 사용자에게 PG 실패인지 잔액 부족인지 구분해서 보이는가 |
| 환불 | 환불 조건, 환불 시점, 환불 금액, 원거래 연결이 명확한가 |
| 중복 결제 | 같은 버튼을 여러 번 누르거나 콜백이 중복 도착해도 안전한가 |
| 정산 | 호스트 돈과 참가자 돈, 클럽 기금이 섞이지 않는가 |

## 12. Notion 운영 권장 구조

```mermaid
flowchart TD
    A["서비스 온보딩 홈"] --> B["전체 서비스 지도"]
    A --> C["175개 기능 인벤토리"]
    A --> D["대표 사용자 여정"]
    A --> E["상태와 정책 가이드"]
    C --> F["업무 영역별 플레이북"]
    F --> G["핵심 기능 카드"]
    G --> H["시나리오/QA 체크"]
    E --> H
    D --> H
```

175개 기능 PRD를 현재 제품 내용의 정본으로 사용한다. Notion 카드는 정본을 연결한 목적별 요약이며 독립적인 구현 상태나 미완료 총계를 만들지 않는다. 카드가 없다는 이유로 해당 기능 PRD도 없다고 판단하지 않는다.

## 시나리오 커버리지 기준

2026-11-22 집계의 대상은 175개 기능·21개 업무 영역이다. 기능 목록의 시나리오 등록 수 합계는 1,654개이고, 상세 시나리오 문서 117개에서 식별한 제목은 1,276개다. 두 값은 집계 대상이 다르다. 상세 문서가 없는 58개 기능도 기능 PRD의 수용 기준을 가질 수 있으며, 제목 집계에서 0이라고 시험·정의가 없다는 뜻은 아니다.

[시나리오 집계 자료](../../docs/assets/scenario-audit.js)는 상세 문서의 지정된 제목 패턴만 세고, [기능 목록 자료](../../docs/assets/features.js)는 기능별 등록 수를 제공한다. 시험 파일 참조·기능 번호 발견·기존 출시 근거 표시는 각각 별도 값이다. 어느 수도 이번 최신화에서 새로 통과한 시험 수나 전체 시나리오 통과율이 아니다. 자동 집계의 근거 연결 단계 역시 모든 수용 기준을 검증했다는 판정으로 확대하지 않는다.

다음 8개 범주의 관련성을 검토한다. 해당 기능·변경에 필요한 조건을 골라 시작 상태·조작·관찰 결과를 적고, 적용하지 않는 조건은 이유를 남긴다. 범주 수를 필수 시험 실행 횟수로 바꾸지 않는다.

## 완료 근거 기록

결과에는 기능·입구·역할·시작 상태, 확인한 저장소 버전과 변경 범위, 관찰 결과, 사용한 근거의 위치·확인 범위, 남은 제한을 함께 적는다. 기존 시험을 읽은 경우와 새로 실행해 통과한 경우를 구분한다. 문서·소스 대조 완료를 배포·공개·실사용 확인으로 바꾸지 않는다.

실행 중인 작업은 확인한 프로세스·세션을 이어 확인한다. 단순 응답 대기나 출력 관찰 시간 만료만으로 같은 작업을 다시 시작하지 않는다. 필요한 검사가 통과하면 추가 검증은 새 변경·실패·의문이 있을 때만 수행한다. 현재 작업과 남은 결정은 정본 작업 목록으로 연결한다.
