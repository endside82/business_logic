# 개인정보·안전 정책 PRD

> 2026-11-22 현재 소스와 아래 기능 정본을 대조했다. 동의·열람 권한·노출 중지·보존·파기를 구분하며, 이 문서 대조를 실제 운영 파기·기기 전달·법적 적합성의 통과 기록으로 사용하지 않는다.

## 적용 범위와 확인 순서

위치, 데이팅, 신고·분쟁, 차단, 본인 자료 내보내기와 계정 종료에 적용한다. 각 기능은 입구 → 현재 계정·관계·상태 확인 → 동의 또는 확인 → 요청 결과 → 재조회·복귀 순서로 판정한다. 요청 접수, 화면 반영, 다른 기기의 재조회, 보존 종료와 저장소 소거는 서로 다른 완료 단계다.

민감 기능을 켜는 입구와 끄는 입구를 함께 문서화한다. 남에게 제공되는 정보와 본인만 보는 정보를 구분하며, 실패·결과 불명·처리 대기를 숨겨 성공처럼 표시하지 않는다. 실제 소스의 제한은 각 기능 정본에 남긴다.

## 신고 유형과 증빙의 유효성

현재 신고 유형은 15종이다. 사용자·이벤트·리뷰·이벤트 메시지·데이팅 사용자·클럽, 이벤트 사진·카풀·버스, 커뮤니티 메시지·게시글·댓글, 데이팅 프로필 사진·클럽 사진첩·클럽 채팅 메시지를 포함한다. 일반 신고 창의 사유 선택은 7종, 서버의 사유 값은 12종이므로 두 목록을 동일하다고 간주하지 않는다. 전용 신고 입구와 대상 문맥은 [신고](../02_feature_prds/11_review_report/F11-04_report_prd.md)를 따른다.

본문은 최대 500자, 증빙은 최대 5개다. 파일 번호는 양수이고 중복이 없어야 하며, 본인 소유·업로드 완료(`COMPLETED`)·허용 목적(`EVIDENCE` 또는 `REVIEW`)을 검사한다. 업로드 완료를 바이러스 검사 통과나 신고 채택과 혼동하지 않는다. 기타 사유의 최소 10자 안내는 앱 조건이며 서버가 같은 최소 길이를 보장한다는 뜻은 아니다.

서버는 대상에서 이벤트·클럽 문맥을 확인하고 자기 신고를 막는다. 같은 신고자·유형·대상·문맥의 중복 제한은 과거 신고가 종결됐다고 자동 해제되지 않으며, 요청 키에 의한 정확히 한 번 실행 보장과 구분한다. 접수는 검토·제재·보상 완료가 아니다. 누적 신고량 표시만으로 자동 제재를 확정하지 않는다.

## 분쟁 자료의 열람과 처리자 노출

분쟁에 접근할 권한을 먼저 확인한 뒤 증빙 가시성을 적용한다. `PARTIES`와 `PUBLIC_SUMMARY`는 사건 열람 권한이 있는 대상에게 제공하며, `PUBLIC_SUMMARY`를 비회원 공개 주소로 해석하지 않는다. `HOST_ONLY`는 기본 해결 권한의 호스트 또는 해당 자료 제출자, `CS_ONLY`는 공개 상세 경로에서 해당 자료 제출자가 볼 수 있다. 타임라인은 별도 필터를 적용하고 이 제출자 예외를 그대로 확장하지 않는다. 자세한 경계는 [증거 가시성](../02_feature_prds/18_dispute_resolution/F18-04_evidence-visibility_prd.md)을 따른다.

호스트 신고 인박스는 현재 처리 가능한 이벤트의 신고를 조회하며 신고 카드에 신고자 번호·닉네임을 싣지 않는다. 비밀 미리보기의 일반 문구를 모든 사건·모든 작성자 식별자가 제거됐다는 보장으로 확대하지 않는다. [호스트 인박스](../02_feature_prds/18_dispute_resolution/F18-05_host-inbox_prd.md)를 따른다.

본인 마일리지 응답의 처리자 번호와 스탬프 부여·취소 처리자 정보는 은닉하며 관리자 응답까지 같은 규칙이라고 추정하지 않는다. 임시 숨김 리뷰의 본문은 작성자·현재 호스트에게, 숨김 사유는 호스트에게 제공하는 서버 규칙과 앱의 일반 숨김 표시를 구분한다. 리뷰 행·별점·답글 전체 삭제를 뜻하지 않는다. [내 마일리지](../02_feature_prds/16_mileage/F16-01_my-mileage-main_prd.md), [리뷰 목록](../02_feature_prds/11_review_report/F11-02_review-list_prd.md)을 따른다.

정산은 문서 작성자·현재 호스트·정산 참여자의 권한과 초안·확정 상태를 나눠 판단한다. 이전의 전체 투명성 설명을 모든 초안·모든 회원에게 금전 정보를 공개하는 근거로 삼지 않는다. [모임 정산](../01_domain_prds/07_모임_정산_prd.md)을 따른다.

## 법적 보존과 파일 파기의 단계

보존 중인 사건은 해당 근거와 연결 자료에 따라 파기를 제한한다. 활성 보존이 있다는 이유만으로 계정 익명화 전체가 항상 중지되는 것은 아니다. 계정 종료의 미결 의무와 자료별 보존을 따로 검사하고, 보존 대상 외 자료를 정리한 뒤 보존 해제 시 다시 현재 상태를 확인한다.

사건별 종결 상태와 처리·해결 시각을 기준으로 보존 만료를 계산한다. 예를 들어 데이팅 차단의 연결 신고는 `RESOLVED` 또는 `DISMISSED`와 처리 시각을 사용한다. 서로 다른 사건 유형의 종결 값·기간을 한 규칙으로 합치지 않는다. 정산 이의 증빙에 별도 파기 분기가 확인되지 않은 경우 다른 사건의 작업을 그대로 적용했다고 쓰지 않는다.

첫 단계는 잠금과 보존 재확인 후 사건의 증빙 JSON·참조를 떼고 파일에 파기 예정 시각을 기록한다. 다음 파일 작업이 남은 참조·채팅·본인확인 보존을 다시 확인하고 저장소 소거를 처리한다. 따라서 사건 참조가 비었다고 이미 S3에서 삭제된 것은 아니며, S3 성공 뒤에만 사건 JSON을 비운다는 설명도 맞지 않는다. 일반 파일 작업의 DB 처리와 저장소 호출 사이 예외·재시도는 전역 원자적 삭제를 보장하지 않는다.

채팅 첨부는 별도 작업이 마지막 관련 종료·재개 상태를 확인한다. 오래된 방이라는 이유만으로 최근 다시 열린 구간의 파일까지 지우지 않으며, 첨부 참조 정리를 메시지 본문 삭제라고 표시하지 않는다. 증빙 개별 삭제 API가 없으면 화면에서 삭제 가능하다고 안내하지 않는다. 위 단계와 사건별 기준은 [증거 가시성](../02_feature_prds/18_dispute_resolution/F18-04_evidence-visibility_prd.md)에 정리한다.

## 데이팅 본인확인과 프로필의 동의

본인확인 상태 응답은 평문 이름·생년월일·CI·DI를 노출하지 않는다. 자동 확인과 수동 확인은 별도 경로이며 외부 공급자 지원 상태를 구분한다. 수동 제출은 본인 소유·업로드 완료·본인확인 목적의 파일을 요구한다. 제출 시 격리 또는 검사 통과 파일을 받을 수 있지만 승인 시에는 `CLEAN`이어야 한다. 관리자는 현재 제출 파일과 일치하는 유효한 열람 토큰을 사용해 승인한다. 열람 토큰 기록은 사람이 실제 내용을 읽었다는 증거와 구분한다.

재제출·철회는 기존 검토와 파일 연결에 영향을 준다. 철회는 검토 정보·참조 정리와 파기 예약이며 저장소 즉시 소거 완료가 아니다. 자동 확인의 기본 보관 설정과 수동 검토 종료·교체 파일의 기본 보관 설정도 구분한다. 정확한 조건은 [본인확인](../02_feature_prds/09_private_date/F09-01_verification_prd.md)을 따른다.

데이팅 프로필 활성 여부와 공개 범위(`PUBLIC`, `MATCHED_ONLY`, `HIDDEN`)는 별개다. 본인은 삭제되지 않은 사진 상태를 확인하고, 타인에게는 승인된 사진만 제공한다. 최초 사진의 서버 승인 상태 부여를 모든 사진의 사람 심사 통과로 표현하지 않는다. 사진 연결 해제는 물리 삭제와 다르며 보존·최소 사진 수 조건이 남는다.

종교를 저장하려면 해당 요청에서 명시적 동의가 필요하다. 관심사·신뢰점수의 커뮤니티 데이터는 양쪽 프로필이 모두 선택한 경우에만 후보 점수에 사용하고, 그렇지 않으면 나머지 데이팅 성분의 비중을 재계산한다. 후보 목록의 조건과 개별 행동 API의 조건을 별도 확인한다. [데이팅 프로필](../02_feature_prds/09_private_date/F09-02_profile_prd.md), [후보 탐색](../02_feature_prds/09_private_date/F09-03_candidate_swipe_prd.md)을 따른다.

## 차단과 발견·프로필 숨김의 경계

데이팅 차단은 만남 기능이 닫혀도 안전을 위한 종료 경로로 사용할 수 있다. 자기 차단은 불가하며 이미 차단 중인 경우를 구분한다. 해제된 행의 재사용은 최초 생성 시각을 새 차단 시각으로 바꾸지 않는다. 차단 시 대상 매치와 해당 활성 방을 닫는 DB 변경과 이후 실시간 통지는 별도 단계다. 모든 접속 기기의 즉시 반영을 단정하지 않는다.

안전 신고 선택 시 데이팅 사용자 신고와 증빙 참조를 연결한다. 신고하지 않는 경우에도 입력 파일의 유효성을 검사하며, 선택 해제로 기존 신고·사건을 취소했다고 간주하지 않는다. 해제는 매치·방을 다시 열지 않고 상대의 차단·다른 자격 조건도 해제하지 않는다. [데이팅 차단](../02_feature_prds/09_private_date/F09-07_block_prd.md)을 따른다.

차단은 건 곳에서 푼다. DATING은 데이트에서 명시적으로 건 차단, COMMUNITY는 커뮤니티 차단이 데이트 쪽에 함께 만든 차단이다. 데이트 목록에는 DATING만 나오며 커뮤니티 통합 목록은 두 출처를 사람마다 한 줄로 제공한다. 데이트에서만 건 줄에는 커뮤니티 프로필 사진을 노출하지 않는다. 커뮤니티 해제는 DATING을 풀지 않고, 데이트 해제 뒤 같은 방향의 커뮤니티 차단이 남으면 BLOCKED·COMMUNITY로 유지한다.

이미 살아 있는 데이트 차단을 신고 없이 다시 요청하면 CONFLICT다. 안전 신고와 함께 요청하면 기존 차단에 신고·증빙을 연결하고 사유를 갱신하되 최초 차단 시각은 유지한다. 같은 상대를 이미 신고한 경우 REPORT_ALREADY_EXISTS로 요청 전체를 되돌리며 차단은 유지된다. 앱은 일반 CONFLICT를 차단된 상태로 다루고, 신고 중복은 입력을 유지해 별도로 안내한다.

어느 쪽에서 해제하든 두 목록을 다시 읽고 남은 출처의 차단을 안내한다. 재조회 실패에는 평소의 해제 안내를 사용하며 이를 모든 차단의 해제로 보장하지 않는다. 모임·받은 후기 목록에서는 두 출처의 양방향 차단 작성자를 제외하고, 차단 호스트의 답변도 붙이지 않는다. 서버 후기 수·평균은 조회자마다 다시 세지 않는다.

매칭 목록의 상대 이름·사진은 데이트 프로필을 사용하고 현재 차단 관계면 비운다. MATCHED 이외의 상태에는 활성·PUBLIC·현재 유효한 본인확인을 추가로 요구한다. 이름이 없으면 회원 번호 대신 상대방으로 표시한다.

만난 사람·추천의 후보와 표시용 함께 만난 횟수는 실제 양쪽 체크인을 우선한다. 체크인이 없는 모임은 양쪽 참석·노쇼 제외에 더해 CLOSED이고 시작 시각이 현재 이하여야 한다. 프로필·사람 검색·추천의 횟수도 같으며, 함께 참석 칩은 1 이상일 때 붙는다. 사람 검색의 후보 관계·상세 프로필 접근·메시지 자격은 각자의 규칙으로 판정하므로 이 표시 집계로 대체하지 않는다.

모르는 사람에게 프로필을 숨기는 설정, 사람 발견에서 제외하는 설정, 캘린더·클럽 표시를 숨기는 설정은 별개다. 캘린더·클럽 숨김을 켜는 유료 자격과 이미 설정한 값의 유지·끄기 조건을 구분한다. 클럽 숨김은 다른 사람에게 제공하는 목록·프로필 집계를 제한하며 원본 게시물을 지우는 기능이 아니다. 검색 숨김은 모든 회원 목록·직접 접근을 차단하는 전역 잠금이 아니다.

상세 프로필은 본인·같은 클럽·확인된 공동 참석 관계에 따라 제공 범위가 다르며 데이팅 매치만으로 커뮤니티 상세 권한을 추정하지 않는다. 같은 앱에서 성공한 설정·차단의 목록 정리와 재조회, 다른 기기의 동기화를 구분한다. [개인정보 노출 설정](../02_feature_prds/19_favorite/F19-03_privacy-visibility-settings_prd.md)을 따른다.

## 위치 동의·좌표·열람 기록

위치 공유는 모임 상태·공유 시간·모임 설정·본인 동의를 함께 검사한다. 동의를 켤 수 있는 역할, GPS를 쓸 수 있는 역할, 좌표를 조회할 수 있는 역할은 같지 않다. 공동 호스트라는 이유만으로 참석 상태 없이 GPS 쓰기까지 허용된다고 해석하지 않는다. 일반 참석자의 조회에는 본인 동의가 필요하며 양방향 차단 등 조건에 따라 응답을 걸러낸다.

위치 권한 허용, 공유 동의 저장, 최초 좌표 전송은 별도 요청이다. GPS 실패·좌표 만료·목록 조회 실패를 구분하고, 조회 실패 때 이전 좌표를 계속 최신처럼 표시하지 않는다. 동의 끄기는 좌표를 제거하지만 기존 열람 로그까지 즉시 지우지는 않는다. 모임의 공유 설정을 실제로 바꾸면 기존 동의·좌표가 초기화되며 다시 켜도 복구되지 않는다.

위치 개인정보 화면과 API·모델·Provider 연결은 현재 존재한다. 본인의 최근 30일 열람 로그와 공유 설정·동의를 조회하며, 반복 열람 로그 행 수를 고유 방문자 수로 표시하지 않는다. 타인의 좌표 목록을 반환하는 기록 범위를 모든 관리자 열람·거리 계산의 감사 기록으로 확대하지 않는다. 본인 공유 끄기의 서버 결과와 화면 오류 알림의 남은 제한도 구분한다. [이벤트 위치 공유](../02_feature_prds/14_location_directions/F14-01_event-location-share_prd.md), [위치 공유 중지](../02_feature_prds/14_location_directions/F14-02_location-opt-out_prd.md), [위치 개인정보 대시보드](../02_feature_prds/14_location_directions/F14-04_location-privacy-dashboard_prd.md)를 따른다.

## 본인 자료 내보내기의 범위와 만료

내보내기는 본인의 프로필·선호, 모임·이동, 클럽·정기모임, 금전 거래·마켓·계약, 문의·제재 처리 사실, 활동·설정 등 현재 지원 자료를 비동기로 만든다. 운영 처리자라는 이유로 다른 회원이 작성한 신고·문의 본문이나 대상 식별자를 제공하지 않는다. 채팅 원문·삭제된 메시지·인증 토큰·계좌 비밀을 복원하는 기능이 아니다. 익명 투표·스탬프의 상세 경계는 아래 절과 [데이터 내보내기](../02_feature_prds/13_profile_settings/F13-05_data-export_prd.md)를 따른다.

신청, 생성 완료, 다운로드 주소 발급, 실제 다운로드, 만료와 파일 소거를 각각 판정한다. 기본 만료는 생성 요청 시각부터 30일이며 주소는 완료 상태·파일 존재·미만료 조건으로 새로 발급한다. 생성 완료를 다운로드 성공으로 세지 않는다. 만료 작업은 자료 연결 정리와 파기 예약을 수행하며 저장소 실패는 후속 재시도 대상이다. 화면의 48시간 안내를 서버의 확정 처리 기한으로 쓰지 않는다.

## 계정 삭제 예약·즉시 탈퇴·후속 정리

삭제 요청은 기본 30일 뒤의 예약이며 즉시 계정 비활성화가 아니다. 대기 중에는 명시적으로 취소하고 로그인 자체가 예약을 취소하지 않는다. 요청 전 미결 의무를 확인하고 필요한 보류금 포기 동의는 현재 고지 버전·대상·금액과 맞아야 한다. 사전 확인을 통과해도 실행 직전 다시 검사하며 새 의무·제한 계정·변경된 동의·실행 실패로 지연될 수 있다. [계정 삭제 요청과 취소](../02_feature_prds/13_profile_settings/F13-06_account-deletion_prd.md)를 따른다.

즉시 탈퇴는 계정 익명화·접속 정리와 후속 자료·지갑·금전 정리를 나눈다. 즉시 탈퇴와 삭제 예약의 입구·동의·취소 가능성을 혼합하지 않는다. 유료 잔액·환불 준비·무료분 정리·보존 중 사건은 각자의 현재 조건을 적용하며 모든 파일이 계정 상태 변경 순간에 사라진다고 안내하지 않는다. [즉시 탈퇴와 후속 파기](../02_feature_prds/13_profile_settings/F13-07_account-deactivation_prd.md)를 따른다.

운영자 금전 작업 원문의 기본 보존 작업은 확인 완료 시각 또는 거절 갱신 시각에서 90일이 지난 종결 행을 대상으로 한다. 계정 파기 시에는 해당 회원의 확인 완료 또는 거절 행을 기간과 무관하게 마스킹한다. 진행 중인 모든 작업의 원문까지 같은 시점에 지운다고 확대하지 않는다. 원문 마스킹·처리 메모 제거와 금전 원장 삭제는 다른 작업이다.

## 클럽 스탬프·투표의 개인정보 경계

스탬프 내보내기는 본인의 카드·도장과 본인 관련 처리 사실을 다루고 메모·다른 스태프 식별자를 그대로 제공하지 않는다. 계정 파기·탈퇴 정리의 메모 제거와 클럽 탈퇴만 한 경우, 업무 기록 전체 삭제를 구분한다. [클럽 스탬프](../../docs/features/club-stamp.html)를 따른다.

익명 투표는 개별 선택의 공개를 제한하며 참여자 목록까지 항상 감춘다는 뜻은 아니다. 익명 투표에서 임의 제외 대상 목록을 사용하는 결정과 기본 참여 자격 조건도 구분한다. 현재 개인정보 내보내기에 투표·선택의 전용 항목이 확인되지 않았으므로 포함됐다고 안내하지 않는다. [클럽 투표](../../docs/features/club-poll.html)를 따른다.

## 클럽 회비 요약과 재식별 가능성

현재 회원에게 제공하는 회비 요약은 최근 월별 수입·환불 등 지정된 집계이며 전체 지출 장부와 같지 않다. 원거래의 기부 월과 환불이 실제 발생한 월이 다를 수 있다. 거래의 회원 번호는 현재 소유자와 해당 조회 권한 조건으로 제한한다. 회원 번호를 감췄더라도 소수 회원의 월별 환불 합계에서 특정인을 추측할 가능성은 남으므로 완전한 익명 통계라고 표시하지 않는다. [회비 현황](../02_feature_prds/04_club/F04-13_fund-overview_prd.md)을 따른다.

## 광고 동의와 처리 결과 안내

실제 동의 값 변경은 동의 원장과 결과 알림 의도를 같은 처리 경계에서 남긴다. 같은 값을 다시 보내거나 해당 값을 생략한 요청은 새 동의 변경과 같지 않으며, 의도 저장은 이메일·푸시의 실제 전달 완료가 아니다. 수신 거부 링크의 GET은 확인 화면이고 서명된 요청의 POST가 변경한다. 보안 검사기의 링크 열람을 동의 철회로 처리하지 않는다.

동의 재확인의 작업 대상 시점·재시도와 법령 문구는 [알림 정책](notification_policy_prd.md)을 기준으로 유지한다. 코드의 재확인 작업 기간을 법적 기한 연장으로 설명하거나 이 개인정보 문서 대조를 별도 법률 검토 완료로 표시하지 않는다.

## 수용 기준과 확인 범위

- **권한:** 사건 접근·자료 가시성·제출자 예외·현재 역할을 각각 적용하고 응답별 마스킹 범위를 확인한다.
- **동의:** 공개 범위·활성 여부·추천 데이터 사용·위치 공유·광고 동의를 같은 스위치로 취급하지 않는다.
- **차단과 중지:** 성공·실패·재조회·실시간 통지를 구분하고 차단 해제로 종료된 관계가 복원된다고 안내하지 않는다.
- **보존과 파기:** 사건 참조 해제·파기 예약·저장소 소거·재시도를 나눠 기록한다. 보존 중인 자료와 계정 정리 범위를 따로 확인한다.
- **계정 종료:** 예약 접수·예약 취소·실행 시 재검사·즉시 탈퇴·후속 금전 정리를 각각 판정한다.
- **검증:** 지정 소스와 기능 정본의 내용 대조를 완료했다. 새 제품 시험·운영 삭제·실기기 결과·법적 적합성 검증을 수행했다는 뜻은 아니다.

> ## 9. 접근권한 감사 교정 (2026-07-02) — 정보노출·차단 정책 변경
>
> > 2026-06-30~07-02 전수 감사(21개 도메인·4개 웨이브)에서 확정·교정한 개인정보·안전 관련 정책 변경. 상세 근거는 `docs/audit/access-control-2026-06-30/` 참조.
>
> ### 9-1. 제재·경고·마일리지 self-view 스태프 신원 은닉
>
> 경고 및 마일리지 도메인의 멤버 대면 조회 응답에서 처리 스태프 신원을 은닉했다.
>
> | 표면 | 은닉 필드 | 운영자(admin) 뷰 |
> |---|---|---|
> | 경고 원장·overview·내 신고·내 이의 | actorId, actorRole, revokedBy, assignedTo, processedBy, resubmitAllowedBy | 신원 유지 |
> | 마일리지 원장·프로필카드·영수증 | actorId(지급/차감 처리자) | 신원 유지 |
> | 배지 부여·회수 (self·타 멤버 프로필카드 포함) | awardedBy, revokedBy | 신원 유지 |
>
> **의도**: 플랫폼 제재 self-view 선례(플랫폼 제재 VO의 처리자 은닉 패턴)와 일관. 제재한 스태프 신원이 피제재 멤버에게 노출되면 보복 벡터가 된다.
>
> ### 9-2. 신고자 익명성 (호스트 인박스)
>
> 이벤트 신고 알림(호스트 인박스)에서 신고자 ID를 제거했다. 교정 전에는 EVENT 유형 신고 카드에 `actorUserId=reporterId`가 포함되어 피신고 이벤트 호스트가 신고자 신원을 파악할 수 있었다.
>
> **교정 후**: 호스트 인박스의 신고 카드에는 신고 내용·상태만 포함되며 신고자 신원은 미탑재. 운영팀 처리 큐에서는 신고자 ID 유지.
>
> **불변식**: 앱 약속("신고 내용은 운영팀 검토에만 사용됩니다")과 정합. 신고자 익명성이 신고 파이프라인(신고→경고검토→제재) 진입 신뢰의 척추.
>
> ### 9-3. 차단 커버리지 확장
>
> 차단 관계가 반영되지 않던 두 표면을 교정했다.
>
> | 표면 | 교정 전 | 교정 후 |
> |---|---|---|
> | 이벤트 실시간 위치 공유 (`getEventLocations`, `getAttendeeDistances`) | opt-in만 필터, 차단·현재 참석 미확인 | 현재 ATTENDING + 양방향 차단 제외 필터 추가 |
> | 친구공개 가용성 (`getFriendsAvailabilities`) | 친구(isFriend) 여부만 확인, 차단 미검사 | 차단(isBlockedEither) 선차단 추가 |
>
> **의도**: 차단한 상대방의 실시간 위치·일정 가용성이 노출되지 않아야 한다. 참석을 취소한 사용자의 마지막 좌표도 위치 read 시 현재 참석 재확인으로 제거된다.
>
> **비변경(의도)**: 홈피드·검색·추천의 공개 이벤트는 차단 상대도 계속 노출(설계 범위 = 프로필·메시지·알림). 공개 콘텐츠 차단 적용 여부는 별도 제품 결정 대상.
>
> ### 9-4. 데이팅 사진 모더레이션 — APPROVED만 외부 노출
>
> 데이팅 사진 read 경로에 `deletedAtIsNull` + `moderationStatus=APPROVED` 필터를 추가했다.
>
> | 경로 | 교정 전 | 교정 후 |
> |---|---|---|
> | 디스커버리 피드 | 삭제 포함 전체 | APPROVED + 미삭제만 |
> | 채팅 아바타 | 동일 | 동일 |
> | 타인 프로필 뷰어 아바타 | 동일 | 동일 |
> | 자기 프로필 | 무필터(본인이 자기 사진 관리용) | 변경 없음 |
>
> 대상 상태: PENDING(검수 대기)·REJECTED(반려)·UNDER_REPORT(신고 접수 중) 사진은 외부에 노출되지 않는다.
>
> ### 9-5. 임시숨김 리뷰 본문·사유 마스킹
>
> 임시 숨김(temporarilyHidden) 처리된 리뷰의 본문과 호스트 사유가 모든 뷰어에게 전송되던 것을 교정했다.
>
> | 필드 | 열람 가능자 |
> |---|---|
> | 리뷰 본문 (`content`) | 작성자·호스트 (임시숨김 시 타 뷰어에게 blank) |
> | 숨김 사유 (`hiddenReasonText`) | 호스트만 (임시숨김 시 작성자 포함 타 뷰어에게 blank) |
> | 상태·사유코드 | 모든 뷰어 (마스킹 없음, 상태 표시용) |
>
> ### 9-6. 신뢰점수 차단 게이트
>
> `getTrustScore` 조회에 차단(isBlockedEither) 게이트를 추가했다. 형제 API인 `getScoreHistory`에는 이미 차단 게이트가 있었으며, 이번 교정으로 두 API가 일관된 정책을 갖게 됐다. 차단 관계에 있는 사용자의 신뢰점수는 USER_NOT_FOUND로 응답한다.
>
> ### 9-7. 타인 프로필 관계유형 티어 노출
>
> 2026-11-22 현재 판정은 본인·같은 클럽·참가가 확정된 같은 이벤트·그 외를 구분한다. 본인 또는 상세 열람 관계에서는 서버가 허용한 소개·MBTI 등을 제공하고, 제3자에게는 사진·닉네임만 제공한다. 데이팅 매칭을 커뮤니티 상세 공개의 근거로 사용하지 않는다. 차단·대상 계정 상태는 별도 열람 관문이다.
>
> 현재 진입·본인/타인 메뉴·후기·작성 글과 복귀는 [마이페이지와 프로필 탐색](../02_feature_prds/13_profile_settings/F13-01_profile-hub_prd.md), 편집과 계정 경계는 [프로필 편집과 사진 변경](../02_feature_prds/13_profile_settings/F13-02_profile-edit_prd.md)을 따른다. 위 과거 감사의 ‘PII 누수·IDOR 0’을 현재 버전의 재검증 결과로 사용하지 않는다.
>
> ### 9-8. 정산 이체 매트릭스 — 전체 투명성(의도)
>
> ACTIVE/COMPLETED 상태의 모임 정산 이체 매트릭스(who-owes-whom, 참가자 전원의 분담 내역)는 **참가자 전원에게 공개**한다. 이는 n빵 정산의 의도적 설계다. 감사에서 검토됐으나 결함이 아님이 확인됐다.
>
> 정산 이의 목록(appeals 목록)은 타인 이의 내용이 포함되므로 **모임 생성자·호스트만** 열람 가능으로 교정됐다(위 정책과 별개).
