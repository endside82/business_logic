# Notion 업로드용 Markdown 가이드

<!-- release-document: reference -->
> **문서 구분: 외부 전달용 작성 기준.** 2026-11-22 저장소 기준으로 정리했다. 실제 Notion 업로드·데이터베이스 생성·가져오기 결과는 이번 작업에서 확인하지 않았다. 현재 작업 순서는 [앞으로 할 일](../../../docs/plan/NEXT_WORK.md)을 따른다.

## 적용 범위와 정본

저장소 Markdown을 다른 문서 공간에 전달할 때 내용과 근거를 보존하는 기준이다. Notion의 특정 가져오기 기능이나 자동 변환을 보장하는 설명은 아니다. 묶음의 준비 순서는 [Notion 업로드 준비 순서](../05_planning_artifacts/notion_import_order.md), 제품 내용의 작성 규칙은 [기능 PRD 작성·검수 기준](../FEATURE_PRD_STANDARD.md)을 따른다.

외부 사본에는 원본 경로와 기준 버전을 남긴다. 외부 사본에서 정책이나 요구사항을 합의했으면 해당 정본과 결정 기록에 반영하고 관련 사본을 갱신한다. 저장소와 외부 페이지를 서로 다른 정책의 정본으로 운영하지 않는다.

## 문서 구조와 연결

- 기능 상세 페이지는 하나의 기능 ID를 기준으로 한다. 여러 기능을 묶는 제품·도메인·정책·목록 문서는 관련 기능 ID를 연결한다.
- 사용자에게 필요한 진입·행동·권한·상태·결과·실패 복구를 본문에 쓴다. 기술 계약을 본문에 복사하지 않고 작성 기준의 코드 위치와 근거로 추적한다.
- 표가 길면 업무 영역별로 나누되 기능 ID와 원본 링크를 유지한다. 내부 문서는 전체 제목으로 실제 대상에 연결한다.
- 저장소의 상대 경로가 외부 공간에서도 작동한다고 가정하지 않는다. 전달 대상 페이지와 연결표를 만든 뒤 실제 이동 여부를 확인한다.
- 과거 기록은 날짜·당시 버전·보존 이유를 유지한다. 과거 결과를 현재 확인 결과로 옮기지 않는다.

## 공통 관리 항목

아래는 저장할 정보의 제안이며, 외부 도구의 속성 타입이나 자동 생성 여부를 규정하지 않는다. 같은 정보를 이중 표로 관리하지 않는다.

| 항목 | 기록할 내용 |
|---|---|
| 문서 유형 | 제품·도메인·기능·정책·QA·기획 자료 구분 |
| 업무 영역·기능 ID | [기능 목록](05_feature_definitions.md)의 ID와 정본에 연결 |
| 주 사용자 | 참가자·호스트·운영자 등 해당 흐름의 역할 |
| 원본·기준 버전 | 원본 경로, Git 커밋 또는 문서 해시, 대조 날짜 |
| 문서 검토 상태 | 초안·검토 중·내용 대조 완료·보류와 검토 범위. 제품 완료와 구분 |
| 구현·검증·공개 근거 | 해당 버전의 소스, 실행 환경·날짜·결과, 배포·공개 근거를 각각 연결. 없는 근거는 미확인 |
| 우선순위 | 합의된 값과 근거. 미합의는 미정으로 유지 |
| 결정 필요 | 미결정 질문, 결정 책임, [결정 등록부](../05_planning_artifacts/decision_register.md)의 해당 기록 |
| 검토 담당·확인일 | 실제 검토자와 확인한 시점. 미배정이면 미배정 |

문서의 ‘내용 대조 완료’는 시험 통과나 출시 승인이 아니다. [문서별 대조 기록](../../verification/document-refresh-2026-11-22.json)의 소스 대조·과거 기록 보존·생성물 일치 판정도 각각의 확인 범위로 해석한다.

## 도식과 상태 표

업무 흐름은 `flowchart`, 상태 변화는 `stateDiagram-v2` 또는 상태 표로 설명한다. 노드는 사용자가 이해하는 업무 용어를 쓰고, 시작 조건·분기·결과가 본문과 일치하게 한다. 코드 블록 언어는 `mermaid`로 보존하되, 외부 공간의 표시 결과는 별도 확인한다. 표시할 수 없으면 원문 코드와 같은 의미의 단계·상태 표를 함께 제공한다.

도식의 연결 검사, 화면 표시 확인, 실제 앱의 업무 성공은 서로 다른 근거다. 문서 변경마다 제품 화면 캡처를 요구하지 않는다.

## 변경과 전달 확인

1. 정책 변경의 승인 근거와 현재 구현의 차이를 확인하고 관련 기능 PRD를 대조한다.
2. 수용 기준이 바뀌면 [기능별 수용 기준 표](../04_qa_acceptance/acceptance_criteria_matrix.md)와 관련 QA 설명을 함께 갱신한다. 등록 수를 시험 통과 수로 바꾸지 않는다.
3. 미합의 KPI·법무 문구·운영 응답 기한은 결정 등록부에 질문과 필요한 근거를 남긴다. 임의로 수치나 책임자를 확정하지 않는다.
4. 전달할 원본 버전, 문서 목록, 링크 연결표를 기록한다. 가져온 뒤에는 누락·표·도식·링크와 검토 상태의 의미가 유지됐는지 확인한다.
5. 실제 전달을 했을 때만 대상 공간·시각·버전·확인 결과를 기록한다. 로컬 문서 정리 완료를 업로드 완료로 표시하지 않는다.
