## 판정할 결과부터 정하기

수용 기준은 기능이 제공해야 할 결과다. 문서 작성, 소스 대조, 시험 파일 존재, 시험 실행, 실제 외부 결과, 출시 승인은 서로 다른 증거다. 기능에 관련된 조건을 고르고 적용하지 않는 조건은 이유를 남긴다. 모든 기능에 동일한 개수의 시험·이미지·기기 조합을 요구하지 않는다.

[기획 QA 정책](../03_policy_prds/planning_qa_policy.md)의 실제 입구 → 업무 → 결과 → 복귀를 따른다. 공통 결과는 확인한 근거를 재사용하고 입구마다 다른 권한·대상·상태만 추가 검토한다. 햄버거 메뉴·상단 버튼·더보기·하단에 같은 행동이 중복되는지 실제 경로에서 확인한다. 탐색 맵이나 문서 HTML은 실제 앱 화면 검수의 증거가 아니다.

## 공통 수용 기준

| 범주 | 판정할 결과 |
|---|---|
| 기능 범위 | 현재 21개 도메인·175개 기능에서 해당 기능과 연관 변경을 식별. 목록 등록과 구현·실행 완료를 구분 |
| 계정·역할 | 실제 입구에서 현재 계정·관계·유효한 위임·공개 범위·제재를 검사. 클럽 운영진과 플랫폼 관리자를 구분 |
| 상태 | 시작 상태·실제 저장 결과·계산한 화면 단계·후속 작업을 구분. 신청 승인·참석·입금 확인·반환을 합치지 않음 |
| 빈 상태·오류 | 로딩·자료 없음·조회 실패·부분 실패·권한 거절·삭제/만료를 나누고 다음 행동 제시 |
| 입력·이탈 | 서버의 필드·타입·범위와 앱 검증을 대조. 초안·첨부·저장 중 이탈의 기능별 보존 범위 명시 |
| 돈 | 원거래·납부자·수취자·유료/무료 몫·예약·실제 지급·반환·수동 수습을 연결. 잔액 부족과 외부 결과 불명 분리 |
| 알림 | 대상·설정·현재 업무 상태·발송 의도·알림함·공급자 수락·기기 수신·이동 목적지를 구분 |
| 개인정보·안전 | 현재 동의·열람 목적·파일 소유권·중지·보존·원천별 분쟁 보류를 확인. 예약·비활성·물리 제거를 구분 |
| 평판·신고 | 작성 자격·자기 대상 제한·중복 정책·수정/삭제·검토·점수 반영 시점을 해당 기능에서 확인 |
| 외부 의존 | 로그인 제공자·메일·PG·은행·푸시·지도·파일 저장소의 접수·실행·실제 결과를 구분 |
| 경합·재시도 | 중복·다른 기기·역할 회수·마지막 정원·늦은 응답을 검토. 확정 거절과 결과 불명에 맞는 키 정책 적용 |
| 복귀 | 저장 성공 뒤 조회 실패와 명령 실패를 구분. 원래 화면에서 현재 상태·허용 행동을 갱신 |

## 증거를 선택하는 기준

| 질문 | 필요한 증거 | 그 증거만으로 확정하지 않는 것 |
|---|---|---|
| 입력·권한·상태·계산·중복 조건 | 해당 코드와 조건을 단언하는 기존 시험·로그 | 시험 파일 존재를 실행 통과로 계산하지 않음 |
| 실제 메뉴·업무 결과·복귀 | 해당 버전 앱에서 구체적인 접근 경로 실행 | 목업·탐색 맵을 앱 사용 결과로 대체하지 않음 |
| 잘림·대비·이미지·배치 | 문제와 관련된 대표 실제 화면 | 화면 한 장을 돈 지급·저장·푸시 수신 증거로 쓰지 않음 |
| PG·메일·푸시·은행·서명 앱 | 대상 환경의 실제 결과 기록 | 로컬·모의 호출 성공을 운영 성공으로 확대하지 않음 |
| 문서 목록·집계·참조 | 입력 파일·집계 규칙·링크·정본 해시 검사 | 문서 개수나 시나리오 개수를 제품 통과율로 쓰지 않음 |

UI 확인이 필요한 변경은 기본 390×844·글자 1배에서 시작한다. 큰 글자·다른 폭·테마는 요청 또는 관련 결함에 따라 선택한다. 문서만 고친 경우 내용 대조·링크·파생 동기화를 검사한다. 새 변경·실패·미해결 의문이 없으면 이미 판정한 이미지·시험·회귀를 반복하지 않는다.

## 결과와 출시 판단 기록

판정마다 대상 버전·계정/역할·입구·시작 조건·행동·예상 결과·관측 결과·후속 미완료·증거 위치를 남긴다. 결과는 확인 완료, 실패, 미실행, 환경 미확인, 적용하지 않음과 사유로 구분한다. ‘O’ 한 칸으로 계획과 통과를 함께 표현하지 않는다.

금전 오집행·권한 우회·민감정보 노출·실제 핵심 업무 단절은 해당 기능의 출시 판단에 반영한다. 모든 기능의 모든 조합을 새로 실행해야만 문서를 고칠 수 있다는 절차로 확대하지 않는다. 구현·자동 검사·실제 사용 흐름·외부 환경·공개 승인은 [출시 완료 기준](../../docs/qa/completion-criteria.html)의 별도 단계로 남긴다. 이번 문서 최신화는 출시 승인 또는 기능 공개 변경이 아니다.

## 기능별 범위와 연결 문서

[전체 수용 기준 매트릭스](../04_qa_acceptance/acceptance_criteria_matrix.md)는 175개 기능의 정본·등록 확인 항목·상세 시나리오를 연결한다. [시나리오 커버리지](../04_qa_acceptance/scenario_coverage_matrix.md)는 도메인별 수와 빠뜨리기 쉬운 범주를 구분한다. 정해진 ‘최소 5개’보다 기능의 실제 분기·실패·복구를 기준으로 작성한다.

Notion으로 옮겨도 기능 ID·정본 링크·동기화 기준·증거 범위는 유지한다. 아직 별도 카드를 만들지 않았다는 사실을 기능 PRD나 서버 계약이 없다는 뜻으로 쓰지 않는다. 기능별 현재 제한은 각 PRD가 우선한다.
