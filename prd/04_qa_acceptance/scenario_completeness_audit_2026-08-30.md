# 기능별 제품 시나리오 완성도 감사

작성일: 2026-08-30
대상: 제품 기능 175개, 다섯 코드 저장소의 테스트와 통합 실행 자산, 제품 PRD와 상세 시나리오 문서

## 핵심 결론

제품 시나리오가 아예 없는 기능은 이번 정리로 없어졌다. 175개 기능 모두 제품 시나리오 또는 수용 조건을
갖는다. 다만 이것은 **제품 정의가 채워졌다는 뜻**이지, 175개 기능의 모든 시나리오가 자동 테스트와 실제
사용자 여정으로 증명됐다는 뜻은 아니다.

이번 감사에서 수치로 확인된 가장 큰 공백은 **각 제품 시나리오와 검증 근거의 연결**이다. 이것만으로 기능
구현 공백보다 더 크다고 단정하지는 않는다. 시나리오 문서가 테스트 파일을 직접 지목한 기능은 자동 테스트
59개, 통합·E2E 54개다. 로컬 신규 계정으로 서버 상태까지 왕복한 기록은 30개 기능에 있다. 세 근거가 모두
연결된 기능은 53개다. 이 숫자는 해당 기능의 모든 분기가 통과했다는 뜻이 아니라, 적어도 어떤 문서가 어떤
검증 파일을 근거로 삼는지 확인할 수 있다는 뜻이다.

테스트 내부에서 기능 번호가 발견된 기능은 자동 테스트 75개, 통합·E2E 46개다. 그러나 F03-17 번호가
차량 레이아웃과 무관한 일정 변경 안내 테스트에 들어 있던 사례처럼 번호만으로는 의미를 확정할 수 없다.
이 값은 기존 테스트를 찾기 위한 후보로만 쓰고 완료 근거에는 포함하지 않았다. 문서 연결이 없는 기능에는
관련 테스트가 이미 존재할 수 있으므로, 먼저 기존 테스트를 찾아 시나리오와 연결한 뒤 실제 공백만 새로
작성해야 한다.

기능 175개 전체 상세는
[기능별 시나리오 완성도](../../docs/qa/scenario-completeness.html)에서 검색·필터할 수 있다.

## 이번에 바로잡은 것

기존 기능 목록에는 시나리오 수가 0으로 표시된 기능이 23개 있었다.

- 클럽 레퓨테이션, 경고·징계 9개, 마일리지 8개, 분쟁 3개 기능은 PRD 안에 이미 수용 시나리오가 있었지만
  기능 목록에 집계되지 않았다. 기존 수용 조건 109개를 목록에 등록했다.
- 플랜 마켓 구매 환불과 크리에이터 매출 귀속·정산은 흐름 설명만 있었고 판정 가능한 정식 시나리오가 없었다.
  현재 서버·앱·운영자 화면과 테스트를 다시 읽고 각각 10개와 9개의 시나리오를 새로 작성했다.
- 이 과정에서 플랜 마켓 문서에 남아 있던 오래된 설명도 고쳤다. 번들 구성품 일부 환불, 환불 분쟁 운영 화면,
  번들 보너스 포인트 원장, 정산 후 미수금 부분 회수는 이미 구현되어 있었다.
- 이동수단 공통 설정, 카풀, 버스, 차량 레이아웃의 정본 PRD는 7월 상태에 머물러 앱·알림·상태기계가 없다고
  잘못 적혀 있었다. 현재 서버·앱·관리자 소스를 다시 확인해 4개 기능을 26개 시나리오로 나누고, 각 시나리오의
  코드·자동 검증·실제 사용자 여정·출시 상태를 따로 적었다.

이 보정 뒤 기능 목록에 등록된 시나리오·수용 조건 숫자의 합은 1,403이다. 상세 시나리오 문서 117개에서
실제로 식별되는 시나리오 제목은 1,086개이고, 49개 기능은 등록 숫자와 제목 수가 다르다. 나머지 58개 기능은
정본 PRD의 수용 조건을 사용한다. 과거 문서마다 집계 방식이 달랐으므로 1,403을 최소 보장 수나 테스트
통과율의 분모로 사용하지 않는다.

각각 100%, 67%, 33%로 표시하지만, 이 숫자는 **검증 근거의 연결 비율**이지 구현률이나 시나리오 통과율이 아니다.

## 출시 상태와 시나리오 완성도는 별개다

현재 첫 출시에서 개통 또는 일부 개통되는 기능은 139개다. 그중 19개는 첫 출시 현황에 남은 문제가 연결되어
있고, 87개는 시나리오 문서가 자동 테스트를 직접 지목하지 않는다. 통합·E2E 문서 연결 또는 로컬 실계정 근거 중
하나라도 있는 첫 출시 기능은 65개다. 이 역시 구현 부재 수가 아니라 검증 근거를 추적할 수 있는 기능 수다.

따라서 아래 표현을 구분한다.

- **구현됨**: 코드 경로와 화면이 존재한다.
- **자동 검증됨**: 해당 시나리오의 기대 결과를 테스트가 직접 단언한다.
- **사용자 여정 검증됨**: 앱 또는 운영 화면에서 서버 상태 변화까지 연결해 실행했다.
- **실환경 검증됨**: 실제 계정·기기·외부 서비스로 같은 결과를 확인했다.
- **출시 가능**: 위 근거에 더해 출시 범위, 운영 복구, 외부 준비, 정책 승인이 모두 끝났다.

앞 단계 하나가 끝났다고 뒤 단계까지 끝난 것으로 표시하지 않는다.

## 우선 실행 순서

### 1. 첫 출시 범위의 알려진 문제 19개 기능

이 기능들은 시나리오 연결 정비보다 실제 남은 문제를 먼저 처리한다. 구체적인 원인과 완료 조건은
[첫 출시 현황의 남은 작업](../../docs/qa/launch-status.html#unresolved)을 따른다. 외부 메일·로그인·푸시·지도·파일
저장·캘린더 실기기 확인과 현재 작업 중인 코드 변경을 구분해 닫는다.

### 2. 돈·권한·개인정보 기능의 기존 테스트 연결

자동 테스트 문서 연결이 특히 부족한 인증·온보딩, 모임 정산, 정기모임, 경고·징계, 분쟁 해결부터 기존 테스트를
제품 시나리오에 연결한다. 각 시나리오에 테스트 파일과 테스트 이름을 붙이고 최근 실행 결과를 기록한다.
연결할 테스트가 없을 때만 새 테스트를 작성한다.

### 3. 이동수단 4개 기능의 개통 공백

현재 코드가 없어서가 아니라 운영과 사용자 왕복이 부족해 봉인된 영역이다.

- 이동수단 공통 설정: 권한·모집 상태·방식 전환 시 하위 데이터 삭제 회귀 테스트
- 카풀: 호스트·운전자·탑승자 실제 앱 왕복, 알림 이동, 신고 시점 경로 보존 결정
- 버스: 차량 레이아웃 관리자 웹, 초기 운영 데이터, 빈 좌석맵 활성화 차단, 실제 기기 좌석 경합
- 차량 레이아웃: 관리자 생성→좌석 등록→활성화→호스트 편성→참가자 좌석 확인 전체 여정

상세 판단은 [기능별 시나리오 완성도](../../docs/qa/scenario-completeness.html)에서 검색하거나 아래 정본을
따른다.

- [이동수단 공통 설정 제품 요구사항](../02_feature_prds/03_event/F03-14_event-transport-mode_prd.md)
- [이벤트 카풀 제품 요구사항](../02_feature_prds/03_event/F03-15_event-carpool_prd.md)
- [이벤트 버스 제품 요구사항](../02_feature_prds/03_event/F03-16_event-bus-charter_prd.md)
- [차량 레이아웃 카탈로그 제품 요구사항](../02_feature_prds/03_event/F03-17_vehicle-layout-catalog_prd.md)

### 4. 플랜 마켓의 확인된 시나리오 공백

새로 작성한 시나리오를 기준으로 다음 검증은 실제로 부족하다.

- 구매 환불: 판매자 거절 전 과정, 자료 보완 요청·응답·만료, 7일 자동 처리, 구매자·판매자 모바일 왕복
- 매출 귀속·정산: 정가 합계 0과 반올림 잔액, 다중 원작자 유료·무료 혼합 배분, 정확한 14일 정산 경계

이 항목들은 소스 구현이 보이지만 해당 경계 전체를 직접 단언하는 테스트가 없거나 부분적이다.
정본은 [플랜 마켓 구매 환불 제품 요구사항](../02_feature_prds/08_plan_market/F08-14_purchase-refund_prd.md)과
[크리에이터 매출 귀속·정산 제품 요구사항](../02_feature_prds/08_plan_market/F08-15_creator-earning-coverage_prd.md)이다.

### 5. 등록 숫자와 시나리오 ID 정규화

상세 문서 117개 중 등록 숫자와 실제 제목 수가 다른 49개 기능을 정리한다. 시나리오 ID, 기대 결과, 테스트
파일과 테스트 이름, 최근 실행 결과를 같은 행에 연결해야 시나리오 단위 통과율을 계산할 수 있다.

### 6. 오래된 소스 줄 링크 정비

기능 동작과 무관한 줄 번호 변경을 실제 결함처럼 보이게 하는 204개 표식을 갱신한다. 가능하면 줄 번호 대신
컨트롤러 클래스, 메서드 이름, HTTP 경로를 함께 저장해 코드가 이동해도 의미가 남게 한다. 삭제된 타 사용자
가용시간 기능의 2개 표식은 철회 기록으로 바꾸고 현행 구현 근거에서 제거한다.

### 7. 봉인 기능의 개통 시나리오

봉인 기능은 코드 테스트만 추가해서 완료하지 않는다. 고객 안내 화면, 운영 조회·처리·복구 화면, 외부 계약과
키, 봉인 해제 설정, 같은 버전의 회귀 실행을 하나의 개통 시나리오로 묶는다. 개통 조건은
[첫 출시 현황](../../docs/qa/launch-status.html)의 봉인 해제 계획을 따른다.

## 앞으로의 완료 판정 규칙

기능별로 다음 다섯 칸을 독립적으로 관리한다.

| 판정 칸 | 완료 조건 |
|---|---|
| 제품 시나리오 | 정상, 권한, 상태 변화, 입력 오류, 실패·복구, 중복·동시성 중 해당 범주가 문서에 있음 |
| 코드 구현 | 서버·앱·운영 화면의 실제 진입점과 상태 변화가 현재 소스에서 확인됨 |
| 자동 검증 | 시나리오 ID와 테스트 이름이 1대1 또는 명시적 다대일로 연결되고 기대 결과를 직접 단언함 |
| 사용자 여정 | 앱·운영 화면에서 서버 상태 변화까지 같은 실행으로 통과함 |
| 실환경·출시 | 실제 외부 서비스·기기·운영 복구와 출시 범위가 같은 버전에서 확인됨 |

완성도 백분율이 필요하면 이 다섯 칸을 섞어 한 숫자로 만들지 않는다. 예를 들어 “코드 100%, 자동 검증
70%, 사용자 여정 40%, 실환경 0%”처럼 축별로 표시해야 어디에 일을 투입할지 판단할 수 있다.

node business_logic/verification/build_scenario_audit_data.mjs --write

계산한다. 테스트 파일 안의 기능 번호는 오탐 가능성이 있어 연결 후보로만 별도 표시한다.
