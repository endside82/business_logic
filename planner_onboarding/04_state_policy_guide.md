## 먼저 나눌 질문

사용자가 ‘완료’를 봤을 때 **무엇이 끝났고 무엇이 남았는지**를 적는다. 신청 승인, 실제 참석, 입금 확인, 정산 종결, 돈 반환, 알림 도착은 각각 다른 사실이다. 저장 enum과 계산된 화면 단계도 구분한다.

1. 실제 입구에서 어떤 계정이 어느 기록을 보았는지 정한다.
2. 현재 상태·권한·기한·보류·공개 조건을 확인한다.
3. 실행 뒤 바뀌는 기록과 후속 돈·알림·정리 작업을 나눈다.
4. 성공·확정 거절·결과 불명·부분 처리에 맞는 안내와 복귀를 정한다.

전체 값과 전이의 정본은 [상태 정책](../prd/03_policy_prds/state_policy_prd.md), 행동 자격은 [권한 정책](../prd/03_policy_prds/permission_policy_prd.md)이다. 이 가이드의 예시를 모든 기능의 동일한 실행 보장으로 확대하지 않는다.

## 업무별로 구분할 상태

| 업무 | 먼저 구분할 기록 | 대표적인 오해와 현재 판단 |
|---|---|---|
| 모임 공개 | DRAFT·OPEN·CLOSED·CANCELED와 숨김 설정 | HIDDEN은 일반 EventStatus가 아님. 모집 마감과 실제 만남 종료도 다름 |
| 신청과 참석 | 신청 7값, 참석 3값, 결제 5값 | 결제 대기 승인은 실제 참석 완료가 아님. 회원·게스트와 논리 예약을 따로 셈 |
| 비공개 만남 | EventStatus·matchedAt·completedAt에서 계산한 단계 | 상대 선정으로 CLOSED가 돼도 만남·양쪽 확인·보관금 조건이 남음 |
| 정산과 송금 | 모임 정산 4값, 송금 9값, 호스트 정산금 6값 | 초안 확정은 송금이 아님. 취소·만료 표시가 반환·채무 해소를 보장하지 않음 |
| 이동 조율 | 지원·운행·현재 배정·물리 좌석·조정 요청 | 지원 대기는 기존 배정을 바꾸지 않음. 조율 종료 LEFT는 모임 참가 취소가 아님 |
| 일정 변경 | 개별 동의·자동 동의·묶음 확정 | 응답 기한 경과와 모임에 새 일정이 실제 반영된 시점을 구분 |
| 노쇼·분쟁 | 판정·소명·통합 사건·이의·보상 | 소명 7일 기한과 기각 뒤 재소명 제한을 적용. 결정·종결·보상 완료를 합치지 않음 |
| 플랜과 구독 | 공개·판매·구매 권리·구독 상태·이용 기간 | 무료 본문 열람은 구매 권리와 다름. 구독 갱신 해제는 즉시 환불이 아님 |
| 개인정보 | 내보내기·삭제 예약·비활성·물리 제거 | 삭제 APPROVED는 본인 취소 불가. 30일 도래만으로 실행 완료가 아님 |
| 위치와 알림 | 동의·권한·좌표·만료, 알림 의도·발송·실수신 | 좌표 갱신이 공유 기한을 늘리지 않음. 알림 의도 저장은 실제 도착과 다름 |

## 신청 완료 안내를 만드는 예

승인제 유료 모임에서 신청을 승인했다고 바로 ‘참석 확정’이라고 쓰지 않는다. 신청의 APPROVED_PENDING_PAYMENT, 선입금의 PENDING, 실제 참석 행 존재를 따로 본다. 은행 이체 신고 뒤에는 호스트 확인이 남을 수 있고 기한 만료 처리도 신고 상태를 구분한다. 기능별 안내와 정원 계산은 [신청·참석·취소 정본](../prd/02_feature_prds/03_event/F03-05_event-attendance_prd.md), [선입금 정본](../prd/02_feature_prds/03_event/F03-13_event-prepayment_prd.md)을 따른다.

## 정산 취소 안내를 만드는 예

모임 정산이 CANCELLED로 바뀌어도 원래 납부자의 지갑 반환, 은행 직접 반환, 수동 수습이 끝났는지 따로 본다. 돈을 실제 받은 사람과 정산 생성자가 다를 수 있다. ‘취소 완료’ 다음에 남은 금액·책임자·확인 행동을 안내하며, 지갑 반환 알림만으로 외부 은행 반환까지 완료로 표시하지 않는다. [정산 확정·취소와 반환](../prd/02_feature_prds/07_meeting_settlement/F07-03_activate-cancel_prd.md), [결제·환불·정산 정책](../prd/03_policy_prds/payment_settlement_policy_prd.md)을 따른다.

## 응답이 없을 때의 복구를 만드는 예

요청 결과를 모르면 현재 대상·거래를 먼저 조회한다. 앱의 시간 제한형 요청 키 보관함, untimed 보관함, 계정별 영속 금전 의도 저장소는 보장이 다르다. 시간 제한형의 23시간 미만 재사용 규칙을 모든 API의 서버 보존 기간이나 모든 화면의 재시작 복구로 설명하지 않는다. 확정 거절과 결과 불명에 따른 키 해제·보존은 각 명령의 계약을 따른다.

조회 실패를 ‘요청 없음’으로 바꾸거나 새 요청을 자동 생성하지 않는다. 다른 계정으로 바뀌었으면 이전 작업의 결과를 현재 계정에 반영해도 되는지 해당 기능의 세션 경계를 확인한다. 기준과 확인 범위는 [결과 불명 명령과 재요청 키](../prd/03_policy_prds/state_policy_prd.md#결과-불명-명령과-재요청-키)를 따른다.

## 기획서에 남길 결과

| 항목 | 기록할 내용 |
|---|---|
| 실제 경로 | 메뉴·목록·알림·공유에서 들어온 위치와 돌아갈 곳 |
| 전이 조건 | 누가, 어느 현재 상태에서, 어떤 기한·동의·보류 조건으로 실행하는지 |
| 사용자 문구 | 무엇이 끝났고 무엇이 남았는지. 같은 완료 문구로 후속 작업을 숨기지 않음 |
| 실패와 재시도 | 확정 거절·결과 불명·부분 처리·조회 실패와 복구 동선 |
| 영향 | 정원·돈·권리·알림·보존에 실제로 연결된 효과 |
| 근거 | 기능 정본·확인한 소스·기존 시험·새 실행 기록을 구분 |

[기획 QA 체크리스트](10_planning_qa_checklist.md)의 필요한 증거를 선택한다. 상태값·권한·저장 결과의 대조만으로 답할 수 있는 질문에 화면 이미지를 추가 요구하지 않는다. 실제 메뉴 중복이나 화면 배치를 확인할 때는 해당 실제 경로의 관측이 필요하며 모형 화면을 제품 실행 증거로 쓰지 않는다.
