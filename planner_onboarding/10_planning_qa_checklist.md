# 기획 QA 체크리스트

<!-- release-document: reference -->
> 2026-11-22 현재 [기획 QA 정책](../prd/03_policy_prds/planning_qa_policy.md)을 업무 시작 전에 빠르게 확인하는 요약이다. 현재 작업 순서는 [앞으로 할 일](../../docs/plan/NEXT_WORK.md)을 따른다. 체크 항목이 존재한다고 구현 미완료 또는 시험 미통과로 세지 않는다.

## 작업 시작 전에 정할 것

- [ ] 해당 기능 PRD와 변경한 내용·저장소 버전을 찾았다.
- [ ] 이미 검증한 근거 중 현재 버전·확인 범위에 맞는 것을 확인했다.
- [ ] 남은 의문을 권한·상태·입구·금전·외부 결과·시각 문제로 구체화했다.
- [ ] 적용할 검토 범주와 제외 이유를 정했다. 고정된 시험 개수나 전수 캡처를 요구하지 않는다.

## 실제 입구에서 결과와 복귀까지

- [ ] 메뉴·카드·목록·알림·공유 링크 등 실제 입구와 로그인 후 복귀를 적었다.
- [ ] 같은 행동이 햄버거·상단·더보기·하단에서 중복 노출되는지 상태·역할별로 비교했다.
- [ ] 사용자가 누르는 행동, 서버의 현재 조건, 성공 뒤 바뀌는 상태를 구분했다.
- [ ] 취소·뒤로 가기·재진입·부분 실패·권한 상실·결과 불명에서 다음 행동을 적었다.
- [ ] 원래 화면으로 돌아왔을 때 목록·배지·선택 상태가 갱신되는지 확인했다.

## 관련 위험을 빠뜨리지 않았는지

| 범주 | 확인할 질문 |
|---|---|
| 사용자·역할 | 주 사용자·금지 사용자·복합 역할·제한 계정의 조건이 다른가 |
| 시작·종료·중간 상태 | 화면을 보는 사이 조건이 바뀌거나 중간에 이탈하면 어떻게 복구하는가 |
| 빈 상태·일부 실패 | 데이터 없음과 오류를 구분하고 가능한 다음 행동이 있는가 |
| 돈 | 요청 접수·결제·정산·반환 완료가 다를 수 있는가, 같은 요청을 어떻게 확인하는가 |
| 알림 | 대상·설정·통지 의도·실제 전달·탭 후 권한과 복귀를 구분했는가 |
| 개인정보 | 동의·노출 중지·열람 권한·보존·파기의 범위가 무엇인가 |
| 리뷰·신고·신뢰 | 작성 자격·자기 대상·중복·처리 결과·공개 범위가 무엇인가 |
| 외부 의존 | 취소·실패·지연·결과 불명에서 외부 결과를 어떻게 확인하는가 |
| 동시 변경 | 클릭·다른 기기·관리자·외부 콜백이 겹칠 때 현재 상태를 누가 판정하는가 |

구체적인 역할·값·전이는 [기획 QA 정책의 영역별 검토 우선순위](../prd/03_policy_prds/planning_qa_policy.md#영역별-검토-우선순위)에서 연결한 기능·정책 정본을 따른다. 체크리스트에 독립적인 권한·상태 계약을 복사하지 않는다.

## 필요한 증거만 선택

- 요청·키·횟수·권한·상태·복귀는 소스와 해당 조건을 확인하는 시험·로그로 판정한다.
- 배치·잘림·대비·이미지 표시처럼 시각 질문이 있는 경우에만 대표 이미지를 확인한다.
- UI 작업의 기본은 390×844·글자 1배다. 큰 글자·작은 폭은 사용자 요청 또는 해당 환경 결함에 따라 추가한다.
- 탐색 맵·문서 HTML·목업을 실제 앱 성공의 증거로 사용하지 않는다.
- 변경·새 실패·미해결 의문이 없으면 같은 근거 열람이나 회귀를 반복하지 않는다.

## 결과를 기록할 때

- [ ] 시나리오 정의·시험 파일 참조·소스 대조·실행 통과·외부 확인·공개 상태를 구분했다.
- [ ] 시작 조건·조작·관찰 결과와 근거의 경로·버전·확인 범위를 남겼다.
- [ ] 남은 차이를 Gap·Risk·결정 필요·미검증 중 맞는 의미로 기록했다.
- [ ] 관련 HTML·도메인 요약·카드에 같은 내용이 있으면 정본과 맞췄다.
- [ ] 필요한 검사가 끝난 뒤 근거 없는 추가 반복을 하지 않는다.

시나리오 수는 [기획 QA 정책의 시나리오 커버리지 기준](../prd/03_policy_prds/planning_qa_policy.md#시나리오-커버리지-기준)을 따른다. 카드 작성은 [기능 카드 템플릿](06_feature_card_template.md)을 사용한다.
